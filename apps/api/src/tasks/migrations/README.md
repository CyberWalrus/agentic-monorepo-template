# Каталог миграций (домен задач)

Форма данных здесь — второй источник правды рядом с `packages/contracts`: контракт
виден клиентам, схема — базе. Гейт `pnpm --filter @repo/api db:check` держит их
согласными (ADR 0018): правка `../schema.ts` без миграции красит гейт, data-only
миграция — предупреждение. Применение миграций с нуля сверяется со схемой кода
integration-тестом `apps/api/test/schema-sync.postgres.test.ts`.

## Как менять схему (правило expand/contract)

1. **Expand (совместимое расширение)** — в том же PR, что и код, который это
   использует: правка `../schema.ts` → `pnpm --filter @repo/api db:generate`.
   Новые колонки — nullable или с дефолтом, чтобы старый код работал до выката.
2. **Наполнение (data-only)** — `pnpm --filter @repo/api db:custom` и SQL
   миграция вручную (backfill и т.п.): снапшот не меняется, `db:check`
   предупреждает — человек смотрит SQL глазами. Данные в Postgres-контейнере
   тестов наливаются миграциями, поэтому backfill виден integration-тестам.
3. **Contract (сжатие)** — отдельным шагом **после** выката кода, который
   перестал использовать удаляемое: правка `../schema.ts` → `db:generate`.
   Сжатие в том же PR, что и расширение, запрещено: между ними обязан быть
   выкат работающего кода (ADR 0018, «Отвергнутые»).

## Правила каталога

- Миграции не редактируются задним числом: ошибка формы данных — новая
  миграция, а не правка старой.
- Ручной SQL меняющий схему, минуя снапшоты, ловит integration-тест
  (`pushSchema` на базе из миграций с нуля).
- Каталог под review-защитой (CODEOWNERS): каждая миграция видна человеку.
  Подключение класса — операторский PR (ADR 0014), чек-лист в журнале задачи
  c1.3 (`backlog/done/c1.3.md`).

Файлы: `NNNN_<тег>.sql` — SQL по тегу из `meta/_journal.json`;
`meta/NNNN_snapshot.json` — снапшот состояния схемы после миграции (имя от
`idx`, не от тега), цепочка `id`/`prevId` — то, что проверяет гейт.
