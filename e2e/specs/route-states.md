# Route states

E2E-план фичи route-states: AC2 задачи C5 («Состояния интерфейса и
доступность как гейты», план из PR #24). Ошибочные и несуществующие
маршруты показывают компоненты состояний из `@repo/ui` (дефолты роутера),
а не пустой экран; гейт дерева маршрутов — `apps/web/src/router-gate.test.ts`.
AC-3 и AC-4 добавлены задачей e61: состояние ошибки маршрута с «Try again».

## Критерии приёмки

- **AC-2**: Неизвестный URL показывает понятную страницу not-found («Page not found») со ссылкой «Back to tasks», ведущей обратно в список задач.
- **AC-3**: Ошибка загрузки данных маршрута (API недоступен) показывает состояние ошибки («Something went wrong») с видимой и доступной по роли кнопкой «Try again», без технических деталей.
- **AC-4**: Нажатие «Try again» перезапускает загрузку данных маршрута: когда данные снова доступны, состояние ошибки уходит и страница задач восстанавливается с ними.

## Сценарии

- `shows a not-found page for an unknown URL and navigates home` — открыть несуществующий URL, увидеть not-found, перейти по «Back to tasks» и оказаться в списке задач (SSR-рендер).
- `recovers from a route error via "Try again"` — запросы браузера к `/rpc` подменяются ответом прокси при недоступном API (502); клиентская навигация с not-found на `/` запускает loader в браузере — появляется состояние ошибки с кнопкой «Try again» (видима и доступна по роли), без технических деталей ошибки; API снова доступен, нажатие повторяет запрос — состояние ошибки уходит, страница задач показывает сидированные данные.

## Воспроизведение ошибки (e61)

Ошибку данных вызывает сам тест на границе сети (`page.route` для `/rpc`), без тестовой ручки в продукте. Loader `/` идёт из браузера, поэтому сценарий не зависит от того, как прод-сборка обрабатывает ошибку loader'а на сервере (SSR ходит в API напрямую, из теста этот запрос не виден).
