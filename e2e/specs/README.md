# Test plans

Markdown-планы тестов фич. Их пишет `playwright-test-planner` (или человек), по ним `playwright-test-generator` генерирует тесты в `e2e/features/<feature>/`.

Один файл на фичу: `<feature>.md`. В плане перечислены критерии приёмки, сценарии (шаги и ожидания) и seed (`e2e/agents/seed.spec.ts`).

## Критерии приёмки и трассировка

Критерий в плане — строка `- **AC-<n>**: <текст>`. Тест ссылается на критерий
тегом `[AC-<n>]` в заголовке, тег ставится перед `@critical`:
`test('does X [AC-1] @critical', …)`.

Гейт `e2e/features/traceability/traceability.spec.ts` проверяет двусторонне и
покомпонентно: у каждого критерия есть тест, каждая ссылка существует в плане
своей фичи (каталог `e2e/features/<f>/` ↔ `e2e/specs/<f>.md`, кросс-фичевые
ссылки — ошибка), планы и каталоги соответствуют 1:1. Гейт не проверяет
смысловую адекватность тега — что тест реально покрывает критерий, остаётся за
`product-logic-reviewer`. Гейт исполняется в `pnpm e2e` и `pnpm verify --full`;
в быстром `pnpm verify` e2e не гоняются, поэтому его там нет.

Таблицу «критерий → тесты» для PR генерирует сам гейт:
`reports/spec-traceability.md` (каталог игнорируется git-ом, файл руками не
заполняется).
