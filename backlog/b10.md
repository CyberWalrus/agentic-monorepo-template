# B10. E2E toggle: ждать сеть перед reload

**Проблема.** `e2e/features/tasks/tasks.spec.ts:28-34`: `checkbox.check()` → `toBeChecked()` проходит на синхронном оптимистичном обновлении кэша (`setQueryData` в обработчике клика, `apps/web/src/features/tasks/use-tasks.ts:56-61`), а `page.reload()` может прервать ещё не долетевший POST `/rpc`; после reload состояние тянет сервер, где toggle может отсутствовать. Окно — миллисекунды на localhost, но `failOnFlakyTests` в CI (`e2e/playwright.config.ts:74`) превращает единичный случай в красный прогон «flaky».

## Что сделать

- Перед reload дождаться серверного подтверждения: `page.waitForResponse` на `/rpc` или проверка через API-request. «Ждать сеть перед навигацией» — обязательный паттерн для сценариев с оптимистикой.

## Решение

- **`waitForResponse`, а не polling через API-запрос.** Почему: дешевле — один сигнал на уже отправленный запрос, без второго клиента API в тесте.

## Критерии приёмки

- Тест зелёный на 20 повторов подряд (`repeat-each`); в сценарии нет ожиданий фиксированной длительности.

## Журнал

- 2026-11-20: заведена по итогам аудита обвязки (линза фронтенда). Флак прогоном не воспроизводился — вывод из чтения кода; повторы в критериях — чтобы убедиться. Номера строк — по состоянию дерева на дату аудита.
