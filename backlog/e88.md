# E88. Шаг `test:hooks` подорожал вдвое за три ночи: разгон сюита

**Проблема.** Шаг `test:hooks` (`vitest run` по `tools/test/**/*.test.ts`, корневой `vitest.config.ts`) идёт в каждом `pnpm verify`, то есть в гейте каждого PR. По артефактам `verify-durations-<run>` ночных прогонов 23–25.11 он вырос: 20,6 → 26,1 → 38,7 → 34,5 → 38,1 → 48,7 → 51,1 с (последние три — 45619705671, 45646832636, 45680346493). Бюджет 50 с превышен в ночь 45680346493; задача e87 пересчитывает порог по правилу — это снимает красный, но не стоимость: лишние ~30 с платит каждый PR и каждая локальная проверка.

Рост дают канарейки храповиков, которые исполняют текст шага `nightly.yml` в подставном репозитории с настоящими процессами (git, node CLI, подставной `gh`): e40 (`tools/test/test-count-ratchet.test.ts`), e82 и e85 (`tools/test/check-mutation-ratchet.test.ts`; в журнале e82 — «10 запусков шага», один репозиторий на группу ночей). Всего в сюите 1275 тестов (`reports/vitest-hooks.json`, базлайн `test-count-baseline.json`).

Это обещанная владельцу часть решения по бюджетам (25.11): порог поднят по правилу, а реальный рост стоимости убирается отдельно.

**Что сделать.**

1. **Замер до.** По файлам сюита: время на файл и число тестов — `reports/vitest-hooks.json` шага (vitest `--reporter=json`) на раннере CI и локально. Таблица в «Журнале»: файл, секунды, тесты; отдельно — топ-5 самых дорогих.
2. **Причина по каждому файлу из топ-5:** сколько запусков процесса на тест (spawn `node`, `git`, `gh`), что повторяется между тестами одной группы (репозиторий, `pnpm install`, `oxfmt --check`), что можно разделить или закэшировать.
3. **Разгон — без потери канареек.** Варианты оценить замером и выбрать минимально достаточный (порядок — от дешёвого к дорогому):
   - общий репозиторий и общие фикстуры на группу сценариев одного файла, если сейчас они пересоздаются;
   - убрать повторные запуски внешних инструментов внутри одного теста, если результат не меняется между запусками (`oxfmt --check` и подобное);
   - параллельное исполнение независимых групп внутри файла (`describe.concurrent` / `it.concurrent`) — только если фикстуры групп не пересекаются;
   - параллелизм воркеров на раннере (настройка корневого `vitest.config.ts`: `maxWorkers`, `fileParallelism`) — по числу vCPU раннера;
   - `isolate: false` — только с доказательством, что тесты не делят состояние (e14 оценивала выигрыш около 4 с).
     Под запретом: удалять или помечать `skip`/`only` тесты; ослаблять проверки канареек; менять смысл сценариев «до/после»; уменьшать число тестов (храповик числа тестов, З7).
4. **Доказательство канареек после разгона.** Для каждой тронутой канарейки — прогоны «до правки шага» и «после» (как в журналах e40, e82, e85): канарейка по-прежнему красная на старом поведении и зелёная на новом.
5. **Замер после** — тем же способом, что пункт 1, на том же раннере (прогон CI этого PR и первый ночной прогон после merge). В «Журнале» — таблица «до/после» и ссылка на прогоны.

**Критерии приёмки.**

- `test:hooks` на раннере CI не дольше 35 с (уровень 23.11 плюс рост без канареек храповиков) — замер в «Журнале» до и после; если 35 с не достигнуто, записано, что именно мешает, и достигнутое число.
- Число тестов сюита не уменьшилось: `reports/vitest-hooks.json` — не меньше 1275, ни одного `skip`, `only`, `fixme`, `test.fail`.
- Каждая тронутая канарейка сохранила доказательство «до/после» — выводы прогонов в «Журнале».
- Пороги `verify-budgets.json` этой задачей не трогаются (значения e87 остаются потолком); `perf-budgets.json` не тронут.
- Два зелёных ночных прогона подряд после merge — ссылки в «Журнале».

**Решение.**

- **Сначала измерить, потом выбирать вариант.** Варианты пункта 3 — кандидаты, а не задание сделать все: выбрать наименьший набор, дающий критерий. Альтернатива «применить всё подряд» отклонена: каждый вариант — риск флака, а цена шага измеряется одним числом.
- **Не выносить канарейки в отдельный шаг.** Альтернатива — новый шаг `test:canaries` со своим бюджетом — отклонена: новый шаг меняет `tools/verify-steps.ts`, бюджеты и время CI, а канарейки должны идти в каждом `pnpm verify` (З6). Условие возврата: если канарейки храповиков остаются дороже 20 с после разгона — завести задачу на отдельный шаг с оценкой.
- **Параллельность внутри файла — последней.** `describe.concurrent` с общими фикстурами даёт флак, который увидит только ночная канарейка. Условие: только для групп с непересекающимися каталогами фикстур.
- Задачу ведёт оператор: `tools/test/**` и корневой `vitest.config.ts` — `deny` (режим обслуживания, ADR 0009). Новый файл сюиты появится — `touches` расширяется мини-PR расширения. Label и merge — поезд по поручению владельца.
