# A7. Remote cache: правила доверия до подключения

**Проблема.** В `.github/workflows/ci.yml:24` `TURBO_TOKEN` объявлен на уровне workflow и доступен всем job, включая те, что исполняют код PR. Код PR может записать в кэш артефакт «e2e пройден» для нужного хеша, а `gate` доверяет попаданию в кэш так же, как настоящему прогону. Подпись артефактов по документации Turborepo проверяет целостность и не является защитой, к тому же ключ лежал бы в том же окружении. Сейчас remote cache не настроен, поэтому это нужно решить до подключения. Отдельно: задача `perf` кэшируется, и замер с одной машины будет принят на другой.

## Что сделать

1. Job в PR читают кэш, но не пишут: `--cache=local:rw,remote:r` (флаг есть в установленной версии Turborepo). Пишет только job на `push` в `main`.
2. Токен с правом записи выдаётся только этому job, через environment с ограничением по ветке.
3. Машины разработчиков и агентов получают токен только на чтение.
4. Для `perf` выключить кэш либо включить класс машины в `env` задачи.
5. Решение человека: доверяет ли merge queue кэшу `main` для тестовых задач или прогоняет их принудительно.

## Подводные камни

- Без записи из PR повторные прогоны того же PR remote-кэшем не ускоряются. Компенсируй это `actions/cache` для каталога `.turbo` с ключом по номеру PR, изолированно от `main`.
- Self-hosted сервер кэша должен уметь выдавать токены только на чтение. Проверь это до выбора реализации.

## Критерии приёмки

- Job из PR не может записать в remote cache (проверено попыткой).
- Правила перенесены в `docs/architecture.md` как действующие.
