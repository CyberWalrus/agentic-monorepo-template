# C3.2. Production-сервер: entry, Dockerfile, readiness

**Проблема.** Web запускается через `vite preview` — это не production-сервер; production-способа запуска нет ни у человека, ни у агентов.

## Что сделать

- Добавить серверный entry в оба приложения (выбор — в разделе «Решение»).
- Dockerfile и readiness-проверка: контейнер стартует, readiness отвечает, сборка минимальна по размеру.
- E2E и перф позже переключаются на тот же способ запуска (отдельная задача C3.4), чтобы тестировалось то, что деплоится.

## Решение (2026-11-15)

Выбор делегирован человеком агенту в сессии 2026-11-15; принимается merge PR с этой правкой (ADR 0009, «Развилки в задачах»).

- **Node без Nitro.** API уже работает на `@hono/node-server`; web получает тонкий собственный entry на Node: раздаёт статику сборки, проксирует `/rpc` на `API_URL` (ADR 0005) и отдаёт остальное обработчику TanStack Start из серверной сборки.
- Почему: одна модель запуска для обоих приложений; прокси `/rpc` и readiness остаются явным кодом под тестами, а не конфигурацией пресета; Nitro добавляет слой сборки и меняет раскладку артефактов, что потянуло бы правку бюджета бандла; меньше зависимостей.
- **Запасной вариант без вопроса человеку.** Перед реализацией сверить по актуальной документации TanStack Start версии из `catalog:`, отдаёт ли серверная сборка fetch-обработчик без Nitro. Если нет — взять Nitro с пресетом `node-server`, записать в «Журнал» версию и ссылку на документацию и продолжить.
- Условие возврата к Nitro как основному варианту: появляется цель деплоя не на Node (serverless, edge).
- Решение оформляется ADR «production-сервер и деплой» тем же PR (architecture.md, раздел 5).

## Критерии приёмки

- Локальный запуск production-entry зелёный; Docker-образ собирается, readiness отвечает; `vite preview` больше не упоминается как способ production-запуска web (в e2e webServer он остаётся до C3.4 — защищённый `e2e/playwright.config.ts`; production-способ описан в README, см. «Журнал» 2026-11-16).

- 2026-11-16: защищённые пути не понадобились: тесты фабрики влезли в существующий node-проект `src/**/*.test.ts`, entry `server.ts` knip подхватил из скрипта `start:prod`. Доказательства: `pnpm deploy --filter @repo/web --prod` + `node <out>/server.ts` — SSR-HTML, POST /rpc/tasks/list через web, статика с content-type, `/healthz` 200, `/health` через web 404, 502 при недоступном API, fail-closed (нет API_URL / нет PORT / `HOST=''` — отказ при старте), `HOST=0.0.0.0` слушает, SIGTERM — graceful; `docker build` обоих образов и readiness из контейнеров — ниже в PR.
- 2026-11-16, находка Docker-деплоя: контейнер api падал на старте — три наложенные причины. (1) Node не стриппит типы внутри `node_modules` (`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`), а `pnpm deploy` пакует TS-workspace-контракт именно туда — контракт вынесен симлинками (раскладка как в pnpm-workspace). (2) В Dockerfile api копировались только манифесты, но не исходники: deploy пакует каталог проекта — без `COPY apps/api apps/api` и `COPY packages packages` в образе не было ни `src` api, ни исходников контракта (локальный deploy против полного workspace это маскировал). (3) Итоговые образы: api 295MB, web 415MB. web не тронула только причина (1)-часть — контракт влинен в серверную сборку vite. Детали и условие возврата — ADR 0012, строка «TS-workspace в api». Дальше: CI-сборка образов (C3.3) столкнётся с медленной supply-chain-проверкой pnpm внутри контейнера (~9 мин на холодном кэше метаданных) — учесть при бюджетах CI.
- 2026-11-16, вечер: инцидент Docker Desktop (не код репо): при 6 GB RAM на VM и нескольких параллельных сессиях виртуалка голодала — в логах бэкенда `failed to call diskusage: DeadlineExceeded`, API отвечал 500; затем Docker Desktop был штатно остановлен в 22:30. После запуска: подняты оба контейнера на портах вне рабочего диапазона (4880/4881) — **оба healthy**, api `/health` 200, web `/healthz` 200, POST `/rpc/tasks/list` через web-контейнер → ответ api-контейнера, SSR-HTML, статика 200 с content-type, `/health` через web 404; `pnpm verify --full` — зелёный (все 21 шаг, bundle 126.7/130). 26 осиротевших stopped-контейнеров `agentic-pg-test-*` от сессий, умерших при клине, удалены (409 «container name already in use» валил testcontainers); их локи test-database восстанавливает сам. Бюджет-гейт поймал мой регресс: схемы `processPort/HostSchema` были на верхнем уровне `env.ts` — zod вернулся в клиентский бандл (149.4/130); перенесены внутрь `loadWebProcessEnv` — 126.7/130, правило c3.0 соблюдено.
