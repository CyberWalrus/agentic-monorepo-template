# E70. Песочница × `pnpm install`: блокировка хранилища не открывается

**Проблема.** ADR 0004 (строка «Запись») и `.claude/settings.json` заявляют `allowWrite: ["~/Library/pnpm/store"]` — хранилище pnpm открыто для записи, чтобы `pnpm install` работал из командного инструмента внутри песочницы Claude Code. Живой прогон 2026-11-24 (владелец запуска, Claude Code 2.1.330, `permissionMode: auto`, этот репозиторий на main 02592926, проба в отдельном worktree) показывает обратное: `pnpm install` из командного инструмента внутри песочницы падает на первом шаге — `ERR_PNPM_STORE_DIR_OPEN_OPERATION_LOCK: Failed to open the store operation lock at "pnpm-store-operation-locks": Operation not permitted (os error 1)`. Воспроизведено трижды: две заглушки проекта без lock-файла (зависимости `cpu-features@0.0.10` и `ms@2.1.3`) и копия проекта с lock-файлом (`git archive HEAD package.json pnpm-lock.yaml pnpm-workspace.yaml apps packages e2e | tar -x -C .probe-copy; pnpm install --frozen-lockfile --ignore-scripts --prefer-offline --offline`). Хранилище pnpm 12.21.0 — `~/Library/pnpm/store/v11`, то есть внутри заявленной в `allowWrite` директории; каталог `pnpm-store-operation-locks` по завершении падения на диске не найден (создаётся по требованию). Попутно из того же прогона: при старте сессии в worktree без `node_modules` Claude Code сам ставит зависимости вне песочницы командного инструмента (появилось `node_modules/.pnpm`, 598 пакетов, инструмент не вызывался); запись в `/tmp` из песочницы запрещена; защищённые пути блокируются по факту (вложенная копия не смогла создать `**/vitest.config.ts`, `packages/ui/src/__screenshots__/**`, `.claude/agents/*.md`).

Почему это осталось незамеченным: гейт `sandbox` (`tools/check-sandbox-paths.ts`) сверяет конфиг с ADR, а не поведение — он не запускает установку. Дефект существовал до задачи b8 (журнал `backlog/done/b8.md`, запись о находке 3).

## Что сделать

1. Установить факт: где pnpm 12.21.0 создаёт `pnpm-store-operation-locks` (относительно `store-dir`; проверить `--store-dir`, `PNPM_HOME`, переменные окружения) и почему `allowWrite: ["~/Library/pnpm/store"]` его не покрывает — путь вне директории, нет развёртки `~`, либо лимитация песочницы. Способ — живой прогон в Claude Code: свежий worktree без `node_modules`, из командного инструмента `pnpm install --frozen-lockfile --ignore-scripts --offline` в копии проекта (как выше). Команды и вывод записать в `docs/research/2026-11-sandbox-pnpm-install.md`.
2. Если исправление — расширить `allowWrite` на фактический каталог блокировок, не открывая `$PNPM_HOME` целиком (ADR 0004: там бинари на `PATH`): внести правку в `.claude/settings.json` и в ту же строку ADR 0004 синхронно — гейт `sandbox` сверяет `allowWrite` с ADR дословно (`tools/test/sandbox-gate.test.ts` — канарейка).
3. Если без открытия `$PNPM_HOME` исправить нельзя — зафиксировать границу: в ADR 0004 и в `docs/architecture.md` (раздел про песочницу) написать, что `pnpm install` из песочечного Bash в этом репозитории не работает и зависимости ставит старт сессии; проверить, что `pnpm preflight` в этом случае не пытается ставить зависимости из песочницы (иначе — понятное сообщение вместо падения).
4. После изменения повторить живую установку из песочницы: если теперь установка доходит до записи файлов пакетов и падает на `**/.gitignore`, `**/.eslintignore`, `**/.prettierignore` (`Operation not permitted` в `node_modules/.pnpm/...`) — **остановиться**, ничего не ослаблять, записать вывод в журнал задачи: это условие возврата к варианту A находки 3 задачи b8 (развести `denyWrite` и `deny` правилом исключений — отдельная задача режима обслуживания с needs_human «человек: …»).
5. Строка в `docs/escaped-defects.md`: расхождение ADR 0004 с фактом прошло все гейты и найдено живым прогоном.

## Критерии приёмки

- В `docs/research/2026-11-sandbox-pnpm-install.md` — путь каталога блокировок, команды живого прогона и вывод до изменения.
- Либо живая установка из песочницы проходит (вывод после изменения в том же файле, `node tools/check-sandbox-paths.ts` → exit 0, строка ADR 0004 и `.claude/settings.json` согласованы), либо граница записана в ADR 0004 и `docs/architecture.md`, а `pnpm preflight` в песочнице объясняет ситуацию, не падая.
- `pnpm verify` зелёный; для правки конфига — `pnpm verify --full`.

## Решение

Выбрано сначала установить факт, потом выбрать между исправлением `allowWrite` и документированием границы: неизвестен каталог блокировок, а открывать `$PNPM_HOME` целиком нельзя по ADR 0004. Альтернатива — открыть `$PNPM_HOME` целиком — отклонена (подложный shim на `PATH`). Условие возврата: если живой прогон после исправления покажет запреты на ignore-файлы пакетов — вернуться к варианту A находки 3 b8 через отдельную задачу.

**Решение 2026-11-24 (исполнитель e70-п1, живые прогоны): грант не расширять, зафиксировать границу.** Факт: каталог блокировок — `/tmp/pnpm-store-operation-locks-<uid>` (на машине прогонов — `/private/tmp/pnpm-store-operation-locks-501`; суффикс `-<uid>` — почему точное имя из ошибки и не находили), он вне `allowWrite`, и pnpm берёт блокировку даже при no-op-установке. С открытым каталогом (проверено без правки конфига — грантом `--settings` вложенной сессии) установка проходит блокировку, но pnpm отказывается от общего хранилища, создаёт проектный `.pnpm-store` (136 МБ) и падает на записи файлов пакетов: `Operation not permitted` на `.vscode/launch.json` пакета `docker-modem` (защищает сам Claude Code) и — прямыми пробами — на вложённых `.gitignore`, `.eslintignore`, `.prettierignore` (собственный `denyWrite`). То есть шаг 4 наступает ровно как описано в задаче, а грант с каталогом блокировок превращал бы быстрый чистый отказ в медленное падение с побочными эффектами. Граница записана в ADR 0004 (раздел «`pnpm install` из песочницы») и architecture.md 3.5; строка — в `docs/escaped-defects.md`. Альтернатива — расширить `allowWrite` каталогом блокировок (шаг 2) — отклонена до варианта A находки 3 b8. Условие возврата: вариант A принят и песочница Claude Code не запрещает файлов пакетов — тогда расширить `allowWrite` синхронно со строкой «Запись» ADR 0004 и повторить живую установку по методике research-документа. Конфиг песочницы, гейт `sandbox` и его канарейка не менялись, режим обслуживания не включался.

Задача ведёт оператор (режим обслуживания): touches — `.claude/settings.json`, `tools/check-sandbox-paths.ts`, `tools/test/sandbox-gate.test.ts` (deny). Локальные `pnpm canaries` из параллельных worktree не запускать — проверка в CI, job `canaries`.
