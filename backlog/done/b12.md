# B12. Состояния UI: SSR-индикация, a11y AC, баннер ошибки под визуальным тестом

**Проблема.** Три продукт-полировки из аудита 2026-11-20 (линза фронтенда):

1. SSR отдаёт disabled-форму и чекбоксы (`TasksPage.tsx:19,34,45`, `interactive = useHydrated()`) без индикации «почему не работает»: пользователь без JS и на медленной сети видит нерабочую форму, неотличимую от рабочей. Tradeoff осознанный (комментарий на :18 — «клик по SSR-разметке теряется»), но нигде не записан.
2. AC-6 в `e2e/specs/a11y.md:10` говорит «нарушений axe (critical и serious)», тест валится на все нарушения (`AxeBuilder` без `.withTags`) — реализация строже плана, а план — источник трассировки и дрейфовал.
3. Баннер ошибки после неудачного toggle (`TasksPage.tsx:35-39`) — единственный экран, меняющийся по рантайм-данным, — не закреплён визуальным тестом.

## Что сделать

- Индикация не-интерактивности до гидратации (минимум — `aria-disabled` и подсказка) + запись ограничения в `e2e/specs/tasks.md`.
- Формулировку AC привести к гейту: «любых нарушений».
- Визуальный сценарий страницы с активным баннером ошибки.

## Решение

- **AC приводится к гейту, не наоборот.** Почему: сужение `.withTags` снижает гарантию ради соответствия старой формулировке.
- Альтернатива (сузить гейт до critical/serious) — условие возврата: axe начнёт шуметь moderate/minor на коде новых фич — тогда сужать осознанно, со списком исключений.

## Критерии приёмки

- Визуальный сценарий баннера зелёный (базлайн пишет CI, человек одобряет `/approve-visual` по ADR 0015); формулировка AC совпадает с гейтом; ограничение SSR записано в плане фичи.

## Журнал

- 2026-11-20: заведена по итогам аудита обвязки. Ожидаемые визуальные изменения перечислить в PR по шаблону. Номера строк — по состоянию дерева на дату аудита.

JavaScript is required.» и помечает `<main>` `aria-disabled` (после гидратации атрибут уходит — `undefined` не рендерит его вовсе; у `aria-disabled={false}` React рендерит строку «false»). Ограничение записано в `e2e/specs/tasks.md` (новый AC-5 + раздел «Ограничения»). Тесты: SSR-разметка через `renderToString` (browser-проект vitest), отсутствие индикации после гидратации, E2E без JavaScript `[AC-5]`.
  2. AC-6 в `e2e/specs/a11y.md` приведён к гейту («любых нарушений», `AxeBuilder` без `.withTags`), решение из раздела «Решение» задачи применено как записано.
  3. Визуальный сценарий «error banner after a failed toggle»: `page.route('**/rpc/tasks/toggle')` → `abort()`, клик по неотмеченной задаче, скриншот `tasks-page-error.webp` (fullPage).
- 2026-11-21, решения по ходу:
  - `aria-disabled` выбран на `<main>`, а не на форме/списке по отдельности: одна явная метка неинтерактивной области, тестируется `getByRole('main')`; контролы и так несут реальный `disabled`, который скринридер объявляет сам. `CreateTaskForm` не менялся.
  - Подсказка рендерится только до гидратации — существующие визуальные базлайны не изменились (снимки делаются после гидратации; проверено прогоном `pnpm visual`: 3 существующих сценария зелёные, 0 пиксельных диффов).
  - Грабли визуального сценария: `makeTasks` отмечает каждую третью задачу (`index % 3 === 0`), `.check()` по уже отмеченному чекбоксу — no-op без мутации и без ошибки; сценарий кликает «Seeded task #2».
  - Альтернатива индикации через перевод контролов с `disabled` на `aria-disabled` (интерактивная, но фокусируемая разметка) отклонена: клики до гидратации теряются, `disabled` честнее.
- 2026-11-21, состояние и что дальше:
