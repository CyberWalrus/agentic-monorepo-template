# B2.2. StrykerJS для `apps/web` и `packages/contracts`

**Проблема.** Мутационное тестирование настроено только для `apps/api`; логика web и схемы контрактов не мутируются.

## Что сделать

- Подключить StrykerJS к `apps/web` (только node-проект, мутируются `*.ts` без `*.tsx`) и к `packages/contracts`.
- В PR мутировать только изменённые файлы; полный прогон остаётся в nightly.
- Учесть: vitest-runner по умолчанию берёт только тесты, связанные с мутируемым файлом через импорты; для тестов без такой связи настройку выключить.

## Критерии приёмки

- Канарейка: мутант в логике оптимистичного обновления (из B2.1) или в схеме контракта убивается тестами.
- Мутационный прогон в `pnpm verify` укладывается в текущий бюджет времени или бюджет расширен явно.

## Журнал

- 2026-11-20: сессия исполнителя (worktree `task/b2.2`). План: конфиг StrykerJS в каждом пакете (`testRunner: vitest`, `coverageAnalysis: perTest`, `incremental` с файлом в `reports/mutation/`, reporters c `json` для ночного храповика); мутации остаются вне шагов `verify` — как у `apps/api` (verify-бюджет не меняется), PR-прогон ограничивается `incremental` + turbo `--affected`, полный прогон остаётся nightly (b2.4). Пороги — b2.3 (оператор), nightly-храповик и кэш incremental-файлов web/contracts в CI — b2.4 (оператор, `ci.yml` защищён).
- 2026-11-20, решение: конфиг назван `stryker.conf.json`, а не `stryker.config.json` — точное имя `**/stryker.config.json` стоит в deny защищённых путей (ADR 0014: пороги и конфигурация судьи — оператор), а обычная сессия писать туда не может. В файле нет порогов и он не подключён ни к verify, ни к CI как решающий шаг — судьбу merge он не меняет; имя вне deny вынесено в PR как спорное, если мейнтейнер сочтёт нужным — оператор закроет его в deny тем же механизмом. Альтернатива (только CLI-флаги в `package.json`) отклонена: knip-плагин Stryker видит зависимости только через конфиг-файл, а `knip.json` тоже защищён.
- 2026-11-20, решение: node-проект web для Stryker вынесен в `apps/web/vitest.projects.ts`, который импортирует защищённый `vitest.config.ts` и берёт из него только node-проект (fail-closed, если проект исчезнет). Причина: vitest-runner не поддерживает browser mode, а пустить весь конфиг нельзя — dry run поднял бы браузер (в CI-job mutation playwright-браузеров нет). Имя `vitest.projects.ts` выбрано так, чтобы knip считал файл vitest-конфигом и не красил «Unused files»; на обычный `turbo test` файл не влияет (vitest его не подхватывает автоматически).
- 2026-11-20, решение: `vitest.related: false` только у `apps/web` — node-тесты web импортируют мутируемые файлы не напрямую (`router-gate.test.ts` → `router.tsx`, `use-tasks.ts` покрывается только браузерными тестами); у `packages/contracts` оставлен дефолт `true` — все три мутируемых модуля импортируются тестами напрямую. Из mutate исключены `src/index.ts` (контрактов, чистый re-export — как `!src/server.ts` у api) и `src/routeTree.gen.ts` (web, генерируется TanStack Router).
- 2026-11-20: результат. Канарейка (критерий 1) — двумя способами: (а) стрикер убивает всех мутантов логики переключения — `task-cache.ts` 9/9 `Killed`, включая `task.id !== id`, `!task.completed`, условные (`reports/mutation/mutation.json`); в контрактах схема `access-policy.ts` 100% (4 killed + 4 errors, счёт 100); (б) контрольная поломка `!task.completed` → `task.completed` роняет node-тест фичи (1 failed / 7), код восстановлен. Замеры (критерий 2): `pnpm verify` — PASS 16.5s, мутации в шаги verify не входят (как и у api) — бюджет verify не изменился и расширения не требует; `pnpm mutation` (api+web+contracts) — 50s без incremental-файлов, 14s повторно (exit 0, 3/3). Базовые счёты для B2.3/B2.4: contracts total 60.47% (17 выживших — route-метаданные `.route({path, summary})` в `tasks.ts`, тесты схем их не утверждают); web total 71.08% / covered 80.77% (39 без покрытия node-проекта: `use-tasks.ts` 29, `use-hydrated.ts` 5 и др. — покрываются только браузерными тестами); api total 97.73%. Incremental-файлы пишутся в `reports/mutation/stryker-incremental.json` каждого пакета (turbo-outputs), PR-прогон ограничен `incremental` + turbo `--affected`; кэш incremental-файлов web/contracts в CI (как у api в `ci.yml`) и полный прогон `--force` в nightly — b2.4 (оператор, `ci.yml`/`nightly.yml` защищены).
