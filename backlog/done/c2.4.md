# C2.4. Канарейка табличного теста «чужой ресурс — отказ»

**Проблема.** Табличные тесты «чужой ресурс — отказ» (C2.3) — вторая половина покрытия З6 для политик доступа. Без канарейки их можно обезвредить сужением генерации таблицы, и покрытие З6 молча закончится на тесте перебора (C2.0): канарейка из C2.1 держит живым только перебор.

## Что сделать

- Канарейка в `tools/gate-canaries.ts`: обезвреживание табличного теста C2.3 сужением генерации таблицы красит свой шаг verify.
- Шаг, якорь и способ сужения определить по фактической реализации C2.3.

## Критерии приёмки

- Канарейка направления: суженная генерация таблицы красит гейт; `pnpm canaries` зелёный.

C2.1 отдала канарейку перебора (направление уже опоздало на один PR по компромиссу из C2.0), эта задача догоняет табличную после C2.3. Bad change: owner-процедура `evilOwnerProbe` с валидной meta `{ access: { type: 'owner' } }`, добавляемая apply() в копии ДВУХ файлов — `packages/contracts/src/tasks.ts` (через `ocAccess…meta`, якорь — закрывающая скобка contract-объекта с guard «canary anchor not found», образец — канарейка C2.1 «процедура контракта без политики доступа») и `apps/api/src/router.ts` (`evilOwnerProbe: os.tasks.evilOwnerProbe.handler(…)`). Вторая правка обязательна: роутер строится `implement(contract).router({…})` и содержит только объявленные обработчики — контрактный зонд без handler'а до `collectProcedures(router)` не доходит, генерация таблицы его не видит и шаг остаётся зелёным. Зонд без строки сценария красит шаг `test` собственными проверками целостности генерации таблицы C2.3: «every owner procedure has a scenario row — no empty rows» (`owner-access-table.test.ts:158`) и ячейки `it.each` («access scenario row for tasks.evilOwnerProbe is missing»). При этом перебор C2.0 остаётся зелёным (политика объявлена) и router-divergence зелёным (контракт ≡ роутер) — ровно сценарий из «Проблемы»: без таблицы покрытие молча закончилось бы на переборе. Expect матчится в хвосте вывода шага (VERIFY_TAIL_LINES=400 в run-gate-canaries.ts); точный RegExp (кандидаты `/access scenario row for tasks\.evilOwnerProbe/`, `/add an access scenario for/`) закрепить по фактическому прогону `pnpm canaries`. Негатив-контроль раннера не меняется: `test` уже в union покрытых шагов. Смысловая формулировка AC «суженная генерация красит гейт» выполняется так: канарейка доказывает, что bad change, который суженная генерация пропустила бы, красит гейт; будущее сужение перебора (`ownerProcedurePaths`) делает канарейку зелёной → `pnpm canaries` красный → обезвреживание громкое.
  - **Альтернатива (отклонена)**: bad change = само сужение генерации в копии теста. Сужение до пустого перебора красит шаг через «the table is not vacuous», но держит живым только громкое сужение; тихое (фильтр по `accessScenarios`, хардкод списка) по построению оставляет набор зелёным — угрозу из «Проблемы» не закрывает. Вариант «сузить + посадить зонд» не применим: канарейка требует красного failedStep, а такой комбинированный bad change даёт зелёный шаг.
  - **Условие возврата**: вторая точка исполнения политик или переезд перебора с роутера (условия возврата C2.3) — якорь зонда пересматривается; expect не матчится в хвосте первого прогона — закрепить RegExp по реальному выводу; появление второй owner-процедуры в продукте — зонду нужно уникальное имя, коллизии нет (`evilOwnerProbe`).
  - **Слои и границы**: единственная продуктовая правка — `tools/gate-canaries.ts` (deny, protected-paths.json:59) + этот файл в PR; contracts/api/ui/e2e не меняются — apply() правит только копии во временном worktree канарейки (run-gate-canaries.ts:189–229, откат checkout+clean после каждой). Правка защищённого пути — в режиме обслуживания оператора: перед реализацией включить `.claude/settings.local.json` в worktree задачи, время включения/выключения записать сюда, файл удалить до открытия PR. Проверки реализации: `pnpm verify`, затем `pnpm canaries` (критерий AC), перед PR `pnpm verify --full`. План отдать `architecture-reviewer`/`sanity-reviewer` до кода.
