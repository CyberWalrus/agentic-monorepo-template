# C2.2. Middleware авторизации oRPC и актор в контексте

**Проблема.** Проверка политики исполняется там, где её забыли написать; нужна единая точка исполнения, читающая метаданные из C2.0.

## Что сделать

- Авторизация выполняется в middleware oRPC: актор приходит через контекст, middleware читает политику процедуры и решает.
- Нет пути вызвать процедуру в обход middleware: middleware ставится на уровне обработчиков, а не отдельных процедур.
- Отказ доступа — типизированная ошибка домена, различимая клиентом.

## Критерии приёмки

- Тест направления (поведенческий тест в `apps/api/test`, не канарейка гейта): процедура с политикой «владелец», вызванная без актора или чужим актором, получает отказ до входа в доменную логику.

## Журнал

- 2026-11-15: зависимость перенесена с C2.1 на C2.0 (метаданные и тест перебора без правки `tools/`); канарейка C2.1 этой задаче не нужна.
- 2026-11-16, план: план прошёл ревью `architecture-reviewer` и `sanity-reviewer` (approve) до кода; major-находка архитектурного ревьюера — та же правка `docs/architecture.md` §2.2 в этом PR, поэтому `touches` расширен фактической правкой docs (объявление задачи не менялось: доска считает пересечения, а не запрет). Механику oRPC подтвердили пробой на установленной 1.16.1: builder-ошибки `oc.$meta({}).errors({FORBIDDEN})` наследуются всеми процедурами; `implement().use(mw)` вешает mw на каждую процедуру роутера; опции mw дают `procedure` (`~orpc.meta` читается нативно) — реестр путей, отвергнутый ADR 0011, не понадобился.
- 2026-11-16, решения (развилки закрыты по правилам AGENTS, условия возврата):
  - Исполнение — `apps/api/src/authorization.ts`: middleware на строителе реализаций, политика из `procedure['~orpc'].meta` через `accessPolicyFromMeta` (Zod-обёртка meta); процедура без политики или с битой — отказ (deny-by-default, свойство из журнала C2.0). Диагностику расхождения «контракт — роутер» даёт `router-divergence.test.ts` (перебор реального роутера: политика валидна + mw в цепочке каждой процедуры).
  - Актор: `Actor { id }` и `AppContext { tasks, actor, ownerOf }` — в authorization.ts (не в router.ts, иначе цикл импортов и красный `no-circular`). Аутентификации в шаблоне нет: `createApp` получает `resolveActor?` (дефолт — null), контекст строится на каждый запрос в Hono-middleware. Возврат: с появлением настоящей аутентификации резолвер становится её точкой подключения.
  - Владелец ресурса — порт `ownerOf(input) → string | null` в контексте, fail-closed: null (не найден / неизвестен / незнакомая форма input) — отказ. В `createApp` адаптер захардкожен `async () => null`: владельцев у задач пока нет (ownerId — не в этой задаче), owner-процедур в контракте тоже. Возврат: вторая owner-область — пересмотреть порт (параметры политик, отложенные ADR 0011).
  - `admin` — отказ всегда: ролей и источника админ-акторов нет, случайный allow при расширении union хуже явного отказа. Возврат: появились роли.
  - Один код отказа `FORBIDDEN` (без пары с `UNAUTHORIZED`): 401-семантика до появления аутентификации вводила бы клиентов в пустоту и давала оракул «сессия есть/нет». Разделение позже — аддитивное изменение контракта. Возврат: появилась реальная аутентификация.
  - `createApp` получил опции `router?` (дефолт — реальный роутер; подмена только в тестах транспортов, прецедент — `enableTestApi`; перебор реального роутера pin-ит дефолт) и `resolveActor?`. FORBIDDEN → 403 проверен по REST, типизированный код — по RPC.
- 2026-11-16, контракт: `ocAccess` += `.errors({ FORBIDDEN: { message: 'Access denied' } })` — отказ объявлен контрактом для всех процедур; `openapi.json` перегенерирован: во всех операциях задокументирован 403 (ожидаемое документирующее изменение, не дрейф). Комментарий AccessPolicySchema больше не называет декларацию неисполняемой; ADR 0011 — статус «принято» (C2.0 смержена).
- 2026-11-16, тесты: AC говорит «apps/api/test», скил `writing-tests` кладёт in-process API-тесты в `apps/api/src/*.test.ts` (apps/api/test — только Postgres) — исполнено по конвенции скила, смысл AC («поведенческий тест, не канарейка гейта») соблюдён: `authorization.test.ts` — матрица политик (owner без актора / чужой / без владельца / свой — успех; admin — отказ; без политики — отказ; public без актора — успех), отказ до домена проверен счётчиком вызова обработчика; транспортный блок в `app.test.ts` — RPC (типизированный FORBIDDEN, прокидка актора через `resolveActor`-хедер) и REST (403 с актором и без).
- 2026-11-16, мутации: `pnpm mutation` — 94.65%, гейт зелёный (break 75); в изменённой логике выживших нет, кроме трёх эквивалентных: `next({ context }) → next({})` ×2 — oRPC мержит контекст downstream, в одно-мидлварной цепочке формы неразличимы (прокидка нужна будущим цепочкам; тесты whoAmI с прокидкой актора мутанта покрывают и проходят); `ownerOf`-адаптер `() => null → () => undefined` — оба значения отказывают (fail-closed), тип порта `string | null` защищает имплементаторов. Подавления (stryker-директивы) не вводились.
- 2026-11-16, ревью PR: `test-quality-reviewer`, `security-reviewer`, `product-logic-reviewer` — approve. Minor-находки внедрены: (1) unit-ассерты `accessPolicyFromMeta` — битая политика (незнакомый тип, лишний ключ, не-объект) даёт undefined → отказ, ветка больше не без рантайм-теста; (2) runtime-guard в `createApp`: подменённый роутер без authorizationMiddleware падает на старте (`proceduresWithoutAuthorization`, обходилка общая с тестом перебора), эксплуатируемого пути сегодня не было — закрыли на вырост. От product-логики для C2.3: с первой owner-процедурой веб получит достижимый 403 — вспомнить пользовательское сообщение и тест UI-состояния (сейчас generic catch, диффа веб не требует).
- 2026-11-16, дальше: C2.3 (табличные тесты «чужой ресурс — отказ») потребует владельцев в домене: у задач появится `ownerId`, `ownerOf`-адаптер в `createApp` начнёт читать репозиторий, первая процедура перейдёт на политику `owner` — все три правки в границах `touches` C2.3.
