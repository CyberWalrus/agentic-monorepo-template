# B11. Тесты хуков use-tasks: конкаренси оптимистики

**Проблема.** `apps/web/src/features/tasks/use-tasks.ts` — единственное место с нетривиальной логикой конкурентности на клиенте (guard `isMutating(...) === 1` в `refetchAfterLastMutation`, порядок `setQueryData` → `cancelQueries({ revert: false })` → `mutateAsync` → rollback), и для него нет ни одного теста: в фиче покрыты `task-cache`, `summarize`, `CreateTaskForm`, `TasksPage`, а сами хуки — нет. E2E покрывает happy-path: регрессия в guard'е (например, инвалидация на каждую мутацию, затирающая оптимистичное состояние) не поймается ничем до прод-гонки. Задача также готовит почву B2.2: без базовых тестов мутанты `use-tasks.ts` неубиваемы.

## Что сделать

- Браузерные тесты на deferred-промисах (паттерн уже есть в `TasksPage.test.tsx:22-30`): refetch между двумя мутациями не затирает оптимистичное состояние; ошибка мутации откатывает значение; после последней мутации выполняется ровно один refetch.

## Критерии приёмки

- Три сценария зелёные; инверсией guard'а в `use-tasks.ts` красится хотя бы один из них (проверить руками перед PR).

## Журнал

- 2026-11-20: заведена по итогам аудита обвязки (линза фронтенда). Номера строк — по состоянию дерева на дату аудита.
- 2026-11-20 (выполнение): добавлен `apps/web/src/features/tasks/use-tasks.test.tsx` — 4 браузерных теста (Vitest browser mode, Chromium). Транспорт `api-client.ts` подменён через `vi.mock`, но ключи и mutation/query options строит настоящий `@orpc/tanstack-query` над фейковым клиентом: проверяется реальная логика хуков над query-кэшем, а не имитация. Deferred-паттерн из `TasksPage.test.tsx` расширен до deferred-транспорта: тест сам решает, когда сервер коммитит мутацию и что возвращает list.
- Сценарии: (1) refetch между двумя мутациями не затирает оптимистичное состояние — дополнительно инвариант «каждая запись в кэш после оптимистичного тоггла сохраняет его значение», ловит затирание даже между кадрами рендера; (2) ошибка мутации откатывает значение и показывает alert; (3) после последней мутации ровно один refetch, порядок проверен по журналу событий кэша и мутаций (в TanStack v5 dispatch success идёт после `onSettled`, поэтому маркер settled надёжно отделяет «мутация завершена» от «refetch запущен»); (4) create и toggle считаются одним семейством по базовому ключу `orpc.tasks.key()` — сужение ключа в guard'е красится. Тест (4) добавлен сверх трёх из «Что сделать»: он убивает мутанта «суженный mutationKey» и готовит почву B2.2.
- Критерий приёмки проверен руками, двумя инверсиями: guard `=== 1` → `=== 0` красит тесты 1, 3, 4 (refetch не выполняется вовсе); снятие guard'а (invalidate на каждую мутацию — регрессия из постановки) красит тесты 1, 3, 4 (затирание оптимистики). Код `use-tasks.ts` восстановлен (`git checkout --`), прод-логика в PR не меняется.
- Проверка: `pnpm --filter @repo/web exec vitest run src/features/tasks/use-tasks.test.tsx` — 4 passed, три последовательных прогона подряд стабильно; `pnpm verify` зелёный (18 шагов). `pnpm mutation` не прогонялся: мутационный контур (`apps/api/stryker.config.json`) покрывает только `apps/api`, `apps/web` войдёт в него в B2.2.
- Наблюдение для B2.2: наблюдаемость теста построена на кэш-событиях (`action.type === 'fetch'`/`'success'` в `updated`-событии QueryCache, `updated` в MutationCache) — при обновлении TanStack Query их контракты стоит перепроверить первыми.
