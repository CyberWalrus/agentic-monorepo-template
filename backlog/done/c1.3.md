# C1.3. Миграции: гейт «схема совпадает с миграциями» и expand/contract

**Проблема.** С постоянным хранилищем появляется второй источник правды о форме данных — схема базы; без гейта она разъезжается с миграциями и контрактом.

## Что сделать

- Каталог миграций с правилом expand/contract: сначала совместимое расширение, сжатие — отдельным шагом после выката кода.
- Гейт: схема, полученная применением всех миграций с нуля, совпадает со схемой, выведенной из кода/конфигурации Drizzle.
- Каталог миграций в классе `review` (CODEOWNERS): человек видит каждую миграцию.

## Критерии приёмки

- Канарейка: правка схемы без миграции красит гейт; миграция без правки схемы — предупреждение.

## Журнал

- 2026-11-20, аудит обвязки (линза бэкенда): отсутствие гейта подтверждено — расхождение схема/миграции сегодня ловится только typecheck и интеграционными тестами (те требуют Docker), а колонка, удалённая из схемы, но живая в базе, не ловится ничем (drizzle читает только объявленные колонки). Уточнение к плану: шаг `drizzle-kit check`/`generate --verify` — в быструю волну verify по образцу `openapi:check`. Гонка миграций при параллельном старте реплик выделена в отдельную задачу C1.6 (это рантайм-блокировка, не гейт дрейфа).
- 2026-11-20, план до кода (по `feature-workflow`). Гейт двухволновый: (1) файловая волна без базы — журнал миграций валиден (цепочка `id`/`prevId` снапшотов, SQL-файлы на месте), а дифф последнего снапшота против схемы кода (`drizzle-kit/api`: `generateDrizzleJson` + `generateMigration`) пуст — по образцу `openapi:check`, механика выверена экспериментами в песочнице (`/tmp`, не в репо); (2) волна на Postgres — схема после применения всех миграций с нуля сверяется через `pushSchema` (integration-тест на хелпере c1.4). Критерии → тесты: правка схемы без миграции → errors (unit-фикстура + интеграционный `ALTER TABLE`); data-only миграция (`drizzle-kit generate --custom` пишет снапшот с новым id и тем же содержимым — канонический признак) → warnings, гейт зелёный (unit + интеграционный `INSERT`); битая цепочка журнала → errors. Слои: `apps/api/src/tasks/**`, `apps/api/test/**`, `docs/adr/0017`, README каталога. **Не в этом PR** (защищённые пути, ADR 0014 «правило декомпозиции» — операторский маленький PR): шаг в `tools/verify-steps.ts` (deny), review-класс каталога миграций в `tools/protected-paths.json` + `CODEOWNERS` (deny), канарейки в `tools/gate-canaries.ts` (deny). До проводки enforcement держит существующий шаг `test` fast-волны (vitest). Гонка миграций — не здесь (c1.6).
- 2026-11-20, развилка «drizzle-kit check против собственного расчёта» (ADR 0009, «Развилки»): выбран собственный расчёт на `drizzle-kit/api` (валидация цепочки `id`/`prevId` + дифф `generateMigration`). Почему: `drizzle-kit check` в 0.31 проверяет только историю журнала и не отвечает на главный вопрос задачи — «схема кода == схема миграций»; отдельный шаг verify защищён (`tools/verify-steps.ts` — deny), поэтому логика гейта живёт в `apps/api` по прецеденту `openapi:check` (логика в пакете, шаг подключает оператор). Альтернатива: ждать операторский PR с шагом `drizzle-kit check` — отклонена: дрейф схемы остаётся неуловимым, а шаг всё равно пришлось бы расширять. Условие возврата: если `drizzle-kit` выпустит «verify»-режим generate, шаг можно сузить до него.
