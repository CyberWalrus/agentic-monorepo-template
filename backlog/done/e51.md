**Проблема.**

- `tools/snapshot.ts:328`: перебазировка снимка считает «совпадение содержимого с blob текущего HEAD» легитимным движением ветки (pull/merge принёс изменения гейтов). Команда вида `perl -pi -e '…' tools/protected-paths.json && git commit -am x` (также `python`, `node -e`, редирект `1>`) меняет защищённый файл и коммитит его одним вызовом: к проверке по результату файл уже равен blob HEAD — чекер принимает это за pull, перебазирует снимок и не восстанавливает файл. Запись через `perl -pi`, `python`, `node -e`, `1>` в `writeTargets` не распознаётся. В шаблоне запись в защищённые пути держит песочница ОС (ADR 0004); у потребителей плагина `agent-harness` песочницы нет — там это дыра.
- `tools/snapshot.ts:185`: `copy = join(dir, path.replaceAll('/', '__'))` — имена копий с потерями: `a/b__c` и `a__b/c` дают одно имя.

Аудит владельца, 2026-11-23, «Средние → Гейты и защита» и «Низкие → Безопасность и стабильность». Дыры прошли все гейты — строк в `docs/escaped-defects.md` нет.

## Что сделать

## Решение

Признак «pull» — движение `HEAD`, а не совпадение содержимого: совпадение можно создать командой, движение ссылки — нет. Альтернатива — только расширить список распознаваемых записей — отклонена: список форм всегда неполон. Обе правки делаются вместе. Условие возврата: если определение движения `HEAD` ломает легитимные сценарии (rebase, switch веток в сессии) — вернуться к равенству blob плюс требование «ссылка менялась после старта команды», записать в «Журнале».

Задача ведёт оператор (задача будет в режиме обслуживания): touches — `tools/snapshot.ts`, `tools/analyze-command.ts`, `tools/test/**` (deny); условное замыкание в touches не объявлено (2026-11-24, волна seed-D7; понадобится — мини-PR расширения touches). Пересекается с e45 и e50 по `tools/analyze-command.ts`: кто мержит вторым — ребейз.

- **Решение по признаку pull (развилка закрыта).** Выбрано: снимок перебазируется, только если одновременно (1) HEAD двигался с прошлой проверки — `manifest.head` теперь обновляется на каждой проверке, а не только при перебазировке; (2) движение объяснено reflog HEAD: среди записей до прежнего HEAD нет действия `commit` (включая amend) и нет пустого действия (`git update-ref` без сообщения); (3) файл равен blob HEAD; (4) этот blob не отвергался раньше — отвергнутые blob'ы запоминаются в записи снимка (`rejected`). То же условие — у «файл исчез вместе с HEAD». Почему не «только движение HEAD», как намечено в «Решении»: `git commit` двигает HEAD ровно так же, как pull, и с одним этим условием тест (а) остаётся красным. Отличить их может только источник движения, а его показывает reflog. Память blob'ов закрывает «промывание»: commit с подменой после отката остаётся в истории, и merge или `reset --hard` над ним переносят то же содержимое движением, которое reflog объяснит. Альтернативы: расширять только `writeTargets` — список неполон, отклонён в задаче; разбирать текст команды на `git commit` — зависит от написания (`git -C … commit`, путь к бинарнику). Условие возврата: если в легитимном окружении reflog недоступен (`core.logAllRefUpdates=false`, `git reflog expire`) и честный pull начинает откатываться в рабочем дереве — вынести запись HEAD до команды в PreToolUse-хук и решать по ней.
- **Изменение поведения, важное для ревью.** (1) Локальный commit, меняющий защищённый файл, больше не доказательство: правка откатывается в рабочем дереве, commit остаётся в истории — это и есть закрытая дыра. (2) Поэтому поменялся порядок оператора в локальном режиме: закоммиченное при включённом режиме принимается в снимок сразу; коммитить надо до удаления `.claude/maintenance.json` — commit после выключения режима откатится. - **Находка при сверке п. 2 — не исправлена, вынесена решению владельца.** Правило «HEAD сдвинулся, между прежним HEAD и текущим в reflog нет `commit`» обходится одними обычными командами: `git checkout -q -b x && <запись> && git commit -qam x && git checkout -q main && git merge -q --ff-only x` одной командой. Возврат HEAD на прежнее значение закрывает окно: `isLegitMovement` идёт от самой новой записи до первой с sha прежнего HEAD, а это запись возврата — commit остаётся старее её. Проверка видит один `merge`, файл равен blob HEAD, `rejected` пуст — снимок перебазируется. Запускал настоящую `isLegitMovement` из `tools/snapshot.ts` на чистых репозиториях в `/tmp`: `commit`, `commit --amend`, `update-ref HEAD` без сообщения — `false`; `merge --ff-only side`, `cherry-pick side`, `reset --hard side`, `checkout side` после commit-а на `side` в том же worktree — `true`. Сквозной прогон через хук не делал, вывод по чтению `reconcile`. Тот же класс, по чтению кода (не запускал): pull или merge из источника, который агент подготовил сам (локальный клон, другой worktree), reflog объясняет как pull; «Остаток, честно» выше называет только plumbing. Почему не исправил: поручение — начатое не переделывать, а само правило — записанное в «Решении» решение задачи (доверять любому движению HEAD кроме commit-а); его расширение — не локальная правка, и план такого изменения по AGENTS.md идёт через ревьюеров до кода. Выбрано: задокументировать здесь и в теле PR, не менять правило. Альтернатива: окно reflog — вся сессия (число записей на старте в manifest), а blob, который commit сессии записал на защищённый путь или которым удалил путь, не считается движением ветки, каким бы оно ни казалось; регрессии — вариант с побочной веткой (изменение и удаление) и «commit открытых путей, затем честный pull — перебазирует». Такой вариант всё равно не видит commit, сделанный вне этого worktree. Условие пересмотра: поручение владельца или оркестратора — тогда альтернатива; если решено мержить как есть — завести задачу на остаток и дописать его в строку реестра.
- **Документация вне touches — не правил.** `AGENTS.md` (пункт «Проверка по результату») и ADR 0003 (строка «Сверка») описывают прежний признак — совпадение содержимого с blob HEAD.
