**Проблема.**

- `tools/snapshot.ts:328`: перебазировка снимка считает «совпадение содержимого с blob текущего HEAD» легитимным движением ветки (pull/merge принёс изменения гейтов). Команда вида `perl -pi -e '…' tools/protected-paths.json && git commit -am x` (также `python`, `node -e`, редирект `1>`) меняет защищённый файл и коммитит его одним вызовом: к проверке по результату файл уже равен blob HEAD — чекер принимает это за pull, перебазирует снимок и не восстанавливает файл. Запись через `perl -pi`, `python`, `node -e`, `1>` в `writeTargets` не распознаётся. В шаблоне запись в защищённые пути держит песочница ОС (ADR 0004); у потребителей плагина `agent-harness` песочницы нет — там это дыра.
- `tools/snapshot.ts:185`: `copy = join(dir, path.replaceAll('/', '__'))` — имена копий с потерями: `a/b__c` и `a__b/c` дают одно имя.

## Решение

Признак «pull» — движение `HEAD`, а не совпадение содержимого: совпадение можно создать командой, движение ссылки — нет. Альтернатива — только расширить список распознаваемых записей — отклонена: список форм всегда неполон. Обе правки делаются вместе. Условие возврата: если определение движения `HEAD` ломает легитимные сценарии (rebase, switch веток в сессии) — вернуться к равенству blob плюс требование «ссылка менялась после старта команды», записать в «Журнале».

**Дополнение 2026-11-24 — решение оркестратора по обходу правила.** Принято по поручению владельца от 24.11 («запускать операторов для задач режима обслуживания»). Выбрано: чинить в этом же PR. Почему: строка реестра `docs/escaped-defects.md` заявляет, что дыра «правка и commit одной командой приняты за pull» закрыта; мержить исправление, которое обходится пятью обычными командами в одной строке (`git checkout -q -b x && <запись в защищённый файл> && git commit -qam x && git checkout -q main && git merge -q --ff-only x`), под такой строкой нельзя — это не закрытие, а видимость. Альтернатива — смержить как частичное улучшение и завести задачу на остаток — отклонена. Условие возврата: если новое правило ломает легитимные сценарии (честный pull с изменением гейтов, смена веток в сессии, rebase или merge ветки задачи перед PR без правки защищённых файлов) — сузить правило, а не снимать его. Какое правило выбрано и почему не «окно reflog за всю сессию» — запись «Решение по происхождению содержимого» в «Журнале».

**Дополнение 2026-11-24 — решения оркестратора по границе правила и условию reflog (поручение владельца от 24.11; числа прогонов — в «Журнале», запись пятой сессии).**

(1) _Граница правила — публикация._ Выбрано: коммит, попавший хотя бы в одну remote-tracking ссылку, считается удалённой историей — записанное им состояние защищённого пути перебазирует снимок. Почему: запись в удалённый репозиторий — отдельное видимое действие (CI и ревью видят коммит), а модель угроз модуля — агент в рабочей копии. Альтернатива — считать легитимной только историю upstream текущей ветки — отклонена: даёт ложный отказ честному локальному слиянию запушенной ветки с изменением гейтов. Условие возврата: инцидент отмывания подмены через побочную ветку — сузить правило до истории upstream.

(2) _Условие «в окне reflog с прошлой проверки нет `commit`» снято — решено тестом._ Выбрано: движение HEAD с прошлой проверки остаётся необходимым условием, а единственное доказательство происхождения — `writtenLocally`; reflog больше не читается. Почему: охранный тест «честный pull с изменением защищённого файла в одной команде с commit-ом открытых путей» на коде с условием красный (ложный отказ), без условия зелёный; все пять регрессий обхода остаются красными-до и зелёными-после — их держит `writtenLocally`, а не условие. Альтернатива — вернуть условие, сузив до действия новейшей записи reflog, — отклонена: закрывает лишь commit на текущей ветке с подделанной remote-tracking ссылкой (побочное написание той же подделки не закрывает и оно) и даёт свой ложный отказ — commit открытых путей после pull-а в той же команде. Условие возврата: если подделка remote-tracking ссылки на текущей ветке (`git update-ref refs/remotes/origin/<ветка> HEAD` после commit-а) признана угрозой модели — вернуть условие и принять ложный отказ охранного теста.

Задача ведёт оператор (задача будет в режиме обслуживания): touches — `tools/snapshot.ts`, `tools/analyze-command.ts`, `tools/test/**` (deny); условное замыкание в touches не объявлено (2026-11-24, волна seed-D7; понадобится — мини-PR расширения touches). Пересекается с e45 и e50 по `tools/analyze-command.ts`: кто мержит вторым — ребейз. Документы правила — `AGENTS.md`, `docs/adr/0003-result-based-protection.md`, `docs/adr/0009-operator-delegation.md` (класс `review`): добавлены в `touches` мини-PR #225, правятся в ветке задачи после его мержа.

- **Решение по признаку pull (развилка закрыта).** Выбрано: снимок перебазируется, только если одновременно (1) HEAD двигался с прошлой проверки — `manifest.head` теперь обновляется на каждой проверке, а не только при перебазировке; (2) движение объяснено reflog HEAD: среди записей до прежнего HEAD нет действия `commit` (включая amend) и нет пустого действия (`git update-ref` без сообщения); (3) файл равен blob HEAD; (4) этот blob не отвергался раньше — отвергнутые blob'ы запоминаются в записи снимка (`rejected`). То же условие — у «файл исчез вместе с HEAD». Почему не «только движение HEAD», как намечено в «Решении»: `git commit` двигает HEAD ровно так же, как pull, и с одним этим условием тест (а) остаётся красным. Отличить их может только источник движения, а его показывает reflog. Память blob'ов закрывает «промывание»: commit с подменой после отката остаётся в истории, и merge или `reset --hard` над ним переносят то же содержимое движением, которое reflog объяснит. Альтернативы: расширять только `writeTargets` — список неполон, отклонён в задаче; разбирать текст команды на `git commit` — зависит от написания (`git -C … commit`, путь к бинарнику). Условие возврата: если в легитимном окружении reflog недоступен (`core.logAllRefUpdates=false`, `git reflog expire`) и честный pull начинает откатываться в рабочем дереве — вынести запись HEAD до команды в PreToolUse-хук и решать по ней.

- **Решение по происхождению содержимого (развилка «окно reflog за всю сессию» против «происхождение коммита» закрыта по фактам таблицы).** Выбрано: состояние защищённого пути в HEAD (blob или «пути нет») — не pull, если вслед за HEAD по истории, пока путь не менялся, первым встречается коммит, которого нет ни в одной remote-tracking ссылке (`refs/remotes`) и который записал это состояние относительно всех родителей. Прежние механизмы сохранены: память отвергнутых blob, отказ по пустому действию `update-ref`, «файл исчез вместе с HEAD», движение HEAD с прошлой проверки. Почему не окно reflog за всю сессию: (1) действие в записи задаёт та же команда — `GIT_REFLOG_ACTION=pull git commit -m "Fast-forward"` пишет `pull: Fast-forward`, неотличимую от настоящего pull (две строки таблицы выше); значит, и правило первого исполнителя «в окне нет `commit`», и любое правило «какие записи считать локальным commit-ом» обходятся одной командой с переменной окружения — закреплено регрессией; (2) окно по числу записей на старте сессии сжимается, если во время сессии `git gc` или `git reflog expire` срежет старые записи; (3) такое окно не видит commit, сделанный в другом worktree этого репозитория и влитый локальной веткой, — по происхождению он виден, пока не отправлен на удалённый. Альтернативы: классифицировать записи по «известным действиям commit» — отвергнута по (1); различать «remote-tracking ссылка обновлена fetch» и «обновлена push» по её reflog — отклонена: закрывает лишь вариант с `git push` и не закрывает `git branch -dr` с последующим `git fetch`, зато добавляет зависимость от формата чужих сообщений и ложные отказы для не-CLI клиентов. - **Остаток, честно (обновлено третьей сессией — заменяет запись первого исполнителя).** Вне модели угроз модуля по-прежнему: подмена источника движения через plumbing (`commit-tree` + `update-ref -m "pull: Fast-forward"`) и подделка state; стирание или сжатие reflog (`git reflog delete`, `git reflog expire`) — новое правило reflog не читает, но от них зависят прежние условия «движение с прошлой проверки» и «в окне нет `commit`». Прежнее условие «в окне с прошлой проверки нет `commit`» осталось как есть и, по чтению кода (не запускал), отклоняет и честный pull с merge-коммитом после локального commit-а без проверки между ними; с новым правилом оно избыточно для незапушенных коммитов, но его снятие — ослабление существующего отказа: решение за человеком.
