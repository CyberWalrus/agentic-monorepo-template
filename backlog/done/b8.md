# B8. Замыкание protected-paths: конфиги гейтов вне deny/review

**Проблема.** Замыкание гейт-контура (ADR 0014) неполное: protectionOf возвращает null для файлов, меняющих поведение гейтов, — хук, CI-гейт и песочница молчат (перепроверено прогоном реального модуля tools/protected-paths.ts:45-57). Незащищены: .secretlintignore (существует; lefthook.yml:13-14 называет его «защищённым» — не соответствует списку; прогон: secretlint пропускает файл из ignore с синтетическим секретом, exit 0; дописывание apps/** скрывает дифф и от pre-commit, и от ci.yml:107 secrets:check; канарейка b6 не ловит — проверка toContain) и .secretlintrc.json; .gitignore (живой вход oxlint/oxfmt/secretlint — строка в нём + git add -f скрывает закоммиченный файл от всех трёх static-гейтов CI, secretlint пропускает даже явно; для агентных коммитов без lefthook CI — единственный барьер); .nvmrc (единственный незащищённый из globalDependencies turbo — perf-budgets.json, tsconfig.base.json, tools/ports.ts уже deny); вложенные oxlint-конфиги (oxlint 1.94.0 грузит .oxlintrc.json/oxlint.config.ts автоматически — живое воспроизведение: вложенный конфиг гасит ошибку линта, exit 0; --disable-nested-config в скриптах не передаётся); пакетные package.json (apps/*, packages/ui, packages/preflight, e2e — точечное удаление скрипта mutation/test проходит required-tasks: красит только при нуле носителей, tools/check-required-tasks.ts:24,102-103); пакетные tsconfig.json и корневой tsconfig.json (перекрытие strict-флагов защищённой базы — живой пример apps/web/tsconfig.json:10 verbatimModuleSyntax:false; корневой tsconfig — опора typecheck:tools, tsc -p tsconfig.json); apps/web/vite.config.ts (вход build/bundle-гейтов); apps/web/vitest.projects.ts (раннер мутационного гейта web, вне tsconfig-include — tsc --listFilesOnly его не видит); .editorconfig (шесть дефолтов format-гейта). test-count-baseline.json — осознанное warning-only окно, задокументированное в заголовке чекера, но не в $comment списка.

## Что сделать

- В deny: .secretlintrc.json, .secretlintignore, .gitignore, .nvmrc, apps/web/vitest.projects.ts, **/.oxlintrc.json, **/.oxlintrc.jsonc, **/oxlint.config.ts, **/oxlint.config.mts; дешёвым хардненингом — **/.eslintignore, **/.prettierignore, **/.oxlintignore.
- В review: **/tsconfig.json, **/package.json (корневые уже защищены точными паттернами, deny-приоритет сохранится), apps/web/vite.config.ts, .editorconfig.
- test-count-baseline.json: deny либо осознанный NULL в $comment; в $comment записать и опровергнутые векторы (knip.config.ts инертен — knip.json первый в KNIP_CONFIG_LOCATIONS; sherif без RC-файла; depcruise получает --config явно), чтобы список не «дополняли» без нужды.
- Поправить комментарий lefthook.yml:13-14 под реальность; добавить строки по secretlint/gitignore/tsconfig/package.json в docs/CODEOWNERS и .github/CODEOWNERS.jinja (parity).
- Проверить равенство denyWrite песочницы (tools/check-sandbox-paths.ts) — расхождение красит шаг sandbox.

## Критерии приёмки

- Прогон protectionOf (node --experimental-strip-types с реальным модулем) возвращает заданные классы для каждого добавленного пути; все null-пути из аудита закрыты или осознанно задокументированы в $comment.
- node tools/check-tool-class.ts — «замыкание … покрыто deny», exit 0; равенство denyWrite песочницы не нарушено; pnpm verify и pnpm canaries зелёные.
- Edit/Write apps/web/.oxlintrc.json и .gitignore в тестовой ветке красит protect-paths хук.
- Правка пакетного package.json/tsconfig.json требует ревью по правилам review-класса в CI-гейте.
- Комментарий lefthook.yml:13-14 соответствует списку; строки по secretlint/gitignore/tsconfig/package.json есть в docs/CODEOWNERS и .github/CODEOWNERS.jinja.

## Решение

Выбрано: deny для конфигов сканеров/ignore/тулчейна (в нормальной работе фич не меняются — как их соседи .oxlintrc.json/.oxfmtrc.json/knip.json), review для **/tsconfig.json и **/package.json (меняются в каждой второй фиче — граница по ADR 0014: обязательное ревью). Альтернатива «всё в deny» отклонена: превратит каждую фичу, трогающую package.json, в режим обслуживания. Условие возврата: если review-класс окажется проходим мимо ревью (в репозитории-потребителе CODEOWNERS пуст) — ужесточить до deny; канарейка strict-флагов (B13) остаётся защитой в глубину независимо от класса.

Задача ведёт оператор (задача будет в режиме обслуживания): touches — tools/protected-paths.json и lefthook.yml (deny).
