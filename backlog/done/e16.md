# E16. CI-гигиена: пагинация check-runs, кэш Stryker, permissions, алерт токенов evals

**Проблема.** Четыре точечные находки аудита 2026-11-20 (линза гейтов/CI):

1. Запросы check-runs без `--paginate` там, где комментарий рядом признаёт «может быть больше 100» (`gate-integrity.yml:96,173`, `visual-approve.yml:70`; соседняя команда в том же файле использует `--paginate`). Обрезка на 100 записях сдвигает `pushedAt` (min started_at) — fail-open для второй линии freshness-метки.
2. Мёртвый restore-key кэша Stryker (`ci.yml:113-119`): mutation-job не запускается на push в main, ключ от `ref_name` merge queue никогда не совпадает — межветочное переиспользование невозможно.
3. `issues: write` в `nightly.yml` выдан уровнем workflow: `gate-canaries` и `verify-budgets` сужают, `flake-hunt`, `mutation-full`, `perf-trend` наследуют без нужды.
4. Отчёты evals собирают токены (ADR 0016), но на их дрейф нет алерта — тренд 2026: жёсткие token/cost-бюджеты агентных прогонов.

## Что сделать

- `--paginate` во всех запросах check-runs, обещающих полный список.
- Мёртвый restore-key убрать; межветочный кэш заводить отдельной задачей, когда появится потребность.
- `issues: write` срезать до job-уровня только там, где он нужен.
- Порог на суммарные токены прогона evals в report-job: превышение красит job; значение порога — по правилам «Порогов» ADR 0009 (факт раннера, не желание).

## Критерии приёмки

- Grep по workflow не находит запросов check-runs без `--paginate`; mutation-job не читает несуществующий ключ; permissions nightly минимальны по job'ам; evals с заведомо заниженным тестовым порогом токенов красится.

## Решение

- **Развилка «шаг в job evals против report-job»** (задача говорит «в report-job», но report-job бежит `if: failure()` — на зелёном прогоне дрейф не поймал бы). Выбрано: inline-шаг в job `evals` после upload-artifact (`success()`, дефолт); превышение красит job `evals`, алерт идёт существующим путём `report` (issue). Почему: дрейф ловится на зелёном прогоне, механика отчёта не усложняется (артефакт уже заливается до шага и переживёт красный шаг). Альтернатива: отдельный always-job со скачиванием артефакта — отклонена как лишняя механика. Условие возврата: если проверке понадобится сравнение между прогонами (тренд, а не абсолют), — отдельная задача c9.4 «единый тренд-отчёт».
- **if: success(), а не always()** у шага бюджета: на красном прогоне отчёта может не быть (агент умер до записи), факт бюджета осмыслен для завершённого прогона; issue на красный всё равно заводит report-job.
- **Порог**: cap 70 000 000 токенов/сценарий, предел прогона = cap × totals.scenarios (сейчас 2 сценария → 140M). Арифметика: медиана(23 181 313; 20 882 265) = 22 031 789 (два сопоставимых прогона полного сценария 2026-11-19, отчёты в backlog/done/c9.1.md; прогонки FAIL по AC, локальная машина, не CI) × 3 (запас, прецедент абсолютных потолков ADR 0006) = 66 095 367, округление вверх до 10M → 70M. Единица округления названа явно (прецедент ADR 0006 «округлить вверх до 10 мс»). Формула cap × scenarios в jq — добавление сценария в --all не ужимает бюджет молча. Пересчёт: по первому зелёному CI-прогону (сейчас evals job в CI ещё не исполнялся — все прогоны 5–7 с, скип без секрета ANTHROPIC_API_KEY, `gh run list --workflow evals.yml`) и при любом изменении набора сценариев --all; происхождение фактов (два локальных FAIL-прогона) зафиксировано. Подъём порога выше того, что даёт правило, — только человеком (З7).
