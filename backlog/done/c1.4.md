# C1.4. Изоляция unit/integration тестов на Postgres

**Проблема.** С настоящей базой каждый тест должен получать чистое состояние без общего сброса данных между параллельными воркерами.

## Что сделать

- Схема изоляции unit/integration — **база на воркер из шаблона** (решение 2026-11-15, ADR 0009 «Развилки в задачах»): миграции применяются один раз к базе-шаблону, каждый воркер получает свою базу через `CREATE DATABASE … TEMPLATE` в том же контейнере, что и в C1.2.
- PGlite отклонён: он неполный (расширения, блокировки, параллелизм), и с ним тесты шли бы против одного движка, а production работал бы на другом. Условие возврата — то же, что в C1.2: требование Docker стало узким местом локального цикла.
- Схема изоляции описывается в `docs/`, чтобы фичи копировали её, а не придумывали свою.

## Критерии приёмки

- Два воркера гоняют integration-тесты параллельно без взаимного влияния; `SHARED_DATA_LOCK` для unit/integration больше не нужен.

### План

**Что и зачем.** Integration-тесты на Postgres сейчас в одном файле с одним контейнером: чистка таблицы перед каждым чеком безопасна, потому что воркер один. Второй integration-файл — и файлы либо тянут по контейнеру (≈5 с и RAM каждый), либо дерутся за одну базу. Схема задачи: один контейнер на прогон, миграции один раз в базу-шаблон, каждый воркер получает свою базу через `CREATE DATABASE … TEMPLATE`.

**Критерии приёмки → чем покрыты.**

1. «Два воркера параллельно без взаимного влияния»: integration-набор делится на два файла (контрактный набор — `postgres.test.ts`, специфичные тесты — `postgres-specific.test.ts`); vitest гоняет файлы в разных fork-воркерах, каждый со своей базой из шаблона — чистка таблицы не задевает соседа. Доказательство: структурное — тест хелпера проверяет, что две базы из одного шаблона не видят данных друг друга; наблюдение — замеры прогона в журнале (без теста на scheduling vitest).
2. «`SHARED_DATA_LOCK` для unit/integration больше не нужен»: в apps/api-тестах ни одного лока; правило «изоляцию на этом уровне даёт база, лок — механика E2E (снимается в c1.5)» — в docs/ и строкой в скиле `writing-tests`.

**Затронутые слои.** api-тесты (`apps/api/test/**`), одна константа в `apps/api/src/tasks/database.ts` (экспорт пути миграций), docs, скил `writing-tests` (одна строка, review-зона). Contracts / ui / web / e2e не меняются (e2e-изоляция — c1.5, миграции-гейт — c1.3, `server-config.ts` не трогаем).

**Дизайн.**

- `apps/api/test/test-database.ts` — новый хелпер, без новых зависимостей:
  - `process.env.TESTCONTAINERS_RYUK_DISABLED = 'true'` в хелпере (проверено по reaper.js testcontainers 12.2.1 → `DisabledReaper`): контейнером распоряжается только хелпер;
  - API: `createPostgresTestDatabase({ image, migrationsFolder, migrate, coordinationDir? })` → `{ db, databaseName, close() }`; каталог координации по умолчанию `os.tmpdir()/agentic-pg-<hash пути репо>` (hash → два worktree не пересекаются, З9);
  - ключ экземпляра = hash(образ + путь migrationsFolder): файл `instance-<key>.json` {uri, containerId, fingerprint, refcount} + детерминированное имя контейнера `agentic-pg-test-<hash(каталог координации + key)>`;
  - fingerprint = hash(образ + содержимое migrations/**): смена миграций → контейнер пересоздаётся, шаблон не протухает;
  - все переходы состояния — под mkdir-мьютексом (атомарный `mkdir`, без зависимостей): владелец стартует контейнер, мигрирует базу-шаблон, закрывает пул мигратора (TEMPLATE требует 0 подключений к шаблону); последователь — читает `instance.json`, пингует `SELECT 1`, подключается; stale-лок (PID-файл, мёртвый процесс) — ломается;
  - воркер: `CREATE DATABASE w_<pid>_<rand> TEMPLATE <шаблон>` через системную базу `postgres` (без лока — параллельные клоны безопасны); `close()`: `DROP DATABASE … WITH (FORCE)` + refcount-- под локом; ноль → контейнер stop+remove через `getContainerRuntimeClient().container.getById()` (работает и для прикрепившегося процесса без собственного хендла);
  - контейнер-мусор без instance.json (снёсся tmpdir, container жив): пересоздание под локом — найденный по имени контейнер убирается тем же getById-механизмом, затем стартуется свежий;
  - Docker недоступен → падение с объяснением (З11), таймауты 120 с на уровне файла, как в C1.2 (`vitest.config.ts` защищён); краш воркера (SIGKILL): контейнер переживает прогон — следующий прогон реиспользует по ping+fingerprint или заменяет; ручная чистка `docker rm -f agentic-pg-test-…` — в docs.
- `src/tasks/database.ts`: константа пути миграций экспортируется (один источник, З10 по духу), `migrateTaskDatabase` без изменений.
- Существующий `test/task-repository-contract/postgres.test.ts` переведён на хелпер; реализационно-специфичные тесты выносятся в `postgres-specific.test.ts` → два integration-файла = два fork-воркера.
- Новый `apps/api/test/test-database.test.ts` на инъектированном каталоге координации: изоляция двух баз из одного шаблона (детерминированное доказательство критерия 1), lifecycle (drop своей базы, refcount-очистка контейнера).
- `docs/test-database-isolation.md` — схема для фич (как скопировать хелпер с параметрами своего модуля, PGlite отклонён + условие возврата C1.2, правило «локи на unit/integration не нужны», чистка мусорного контейнера); ссылка из `docs/architecture.md` §2.6; строка в скиле `writing-tests`.

**Замеры.** Бюджет шага test (90 с) не поднимается: холодный прогон ≈ как C1.2 (9.5 с на pull+старт), тёплый — старт контейнера + миграции шаблона ≈2–3 с + клон базы ≈0.1 с на воркер. Замеры фактического прогона — в журнал.

**Вне scope.** `pnpm mutation` не запускается: доменная логика (`postgres-repository.ts`, `repository.ts`) не меняется; `database.ts` получает только экспорт константы. Условие возврата схемы — в журнале выше.

### Реализация

- 2026-11-15: реализация по плану. Замечание к плану: специфичные тесты вынесены не в `postgres-specific.test.ts`, а в `postgres-repository.test.ts` — имя честнее (файл про `PostgresTaskRepository`), шов тот же. Хелпер получил детерминированный тест recovery мёртвого лока (PID завершившегося `spawnSync('true')` процесса) — при его подготовке найдено и исправлено: кривой/нечитаемый `holder.json` вешал ожидание до таймаута, теперь такой лок считается мёртвым сразу. `no-await-in-loop` не отключался (конфиг защищён): закрытия и удаления — `Promise.all`, поллинг лока — setTimeout-рекурсия. Валидация файлов состояния — type-guard'ами вместо `as` (lint-требование, попутно делает битый state-файл определяемым, а не падающим).
- 2026-11-15: замеры прогона (macOS, Docker тёплый, образ в кэше): `pnpm --filter @repo/api test` — 46 тестов, 8 файлов, wall 6.3 с; файлы `postgres.test.ts` 4.4 с + `postgres-repository.test.ts` 1.3 с + `test-database.test.ts` 5.8 с (свой контейнер lifecycle) — сумма 11.5 с при wall 6.3 с: три fork-воркера шли параллельно, взаимного влияния нет. Шаг `test` verify — 7.9 с (было 5.8–7.2 с в c1.2, бюджет 90 с не поднимается). Контейнеры после прогона убраны (`docker ps -a` по имени пуст), каталог координации без instance-файлов. Холодный старт — как в c1.2 (pull+старт ≈9.5 с), сверх того миграция шаблона ≈0.5 с и клон базы ≈0.1 с на воркер.
