# E74. API: запрос TRACE с телом проходит мимо лимита тела; таймаут не накрывает чтение тела

**Проблема.** Слитый код, прошёл все гейты; строки в `docs/escaped-defects.md` нет. Ограждения маршрутов API построены на `bodyLimit` из `hono/body-limit` (`apps/api/src/app.ts:234`) и зарегистрированы парой «потолок, затем срок»: `app.use('/rpc/*', bodyLimitGuard, timeoutGuard)`, `app.use('/api/*', bodyLimitGuard, timeoutGuard)` (`app.ts:242-243`) и так же для тестового API `/__test__/*` (`app.ts:280`). Отсюда два класса запросов мимо контура. Найдено ревью безопасности задачи e55 (2026-11-24); в веб-сервере оба класса закрыты задачей e55 (PR #226), API остался с прежним контуром.

- **TRACE с телом — мимо лимита тела.** `bodyLimit` начинается с `if (!c.req.raw.body) return next();` (`hono@4.13.19`, `dist/middleware/body-limit/index.js:43`), а `@hono/node-server@2.1.11` собирает Request для TRACE как GET с подменённым геттером `method` (`dist/index.mjs:514`, `:525-526`): `request.body === null`, но `text()` и `arrayBuffer()` тело читают. Лимит для TRACE не действует ни по `content-length`, ни по фактическим байтам — обработчик получает тело целиком.
- **Медленное тело без `content-length` — мимо таймаута.** Без `content-length` (или с `transfer-encoding`) `bodyLimit` уходит в стримящую ветвь и дочитывает тело до конца (`rawReader.read()` в цикле, `index.js:46-61`), прежде чем вызвать `next()` (`index.js:63`). Таймер `timeoutGuard` заводится только внутри `next()`, то есть после чтения: chunked-клиент, который прислал часть тела ниже потолка и замолчал, не получает ответа вовсе и держит соединение до `requestTimeout` Node (по умолчанию 300 000 мс). С `content-length` ниже потолка такой запрос `bodyLimit` пропускает не читая (`index.js:45`) — там срок действует и сейчас.

Оба пункта воспроизведены при заведении задачи на библиотеках `apps/api` — «Журнал», 2026-11-24.

## Что сделать

1. Проверка формы запроса — fail-closed, по методу и заголовкам, а не по `request.body`: `TRACE` → 405 (`Method not allowed`); тело объявлено (`content-length` больше 0 или есть `transfer-encoding`), а `request.body === null` → 400 (`Request body is not readable`). Запрос без объявления тела (POST с `content-length: 0`) проходит как прежде. Форма тела ответа — как у 413 и 504 API (`{ error: … }`, `app.ts:236`, `:56`; без данных запроса, C4.1). Определение — своё в `apps/api`: импорт из `apps/web` запрещён границей приложений (e55, «Решение 3»: API оставляет свою копию).
2. Поставить проверку формы перед `bodyLimit` и заменить пару на порядок «форма → срок → потолок» на обоих местах регистрации: публичные `/rpc/*` и `/api/*` (`app.ts:242-243`) и тестовый API `/__test__/*` (`app.ts:280`). Таймер заводится до чтения тела — медленное тело получает 504 за `requestTimeoutMs`, а не ждёт `requestTimeout` Node.
3. Регрессии в `apps/api/src/app.test.ts`, красные до правки и зелёные после. TRACE через `app.request()` не собрать (`new Request` с методом TRACE бросает `TypeError`) — тест на TRACE идёт через настоящий адаптер и сырой запрос по сокету, как `on a real HTTP server` в e55 (`apps/web/src/server-app.test.ts:929` на ветке `task/e55`).
4. Строка в `docs/escaped-defects.md` — дефект слитого кода, прошёл все гейты.

## Критерии приёмки

- Тест «TRACE с телом сверх потолка → 405, процедура не вызвана» красный на коде до правки и зелёный после — для `/rpc/*`, `/api/*` и тестового API `/__test__/*`.
- Тесты «`content-length` больше 0, потока нет → 400» и «`transfer-encoding`, потока нет → 400» зелёные; «POST с `content-length: 0` проходит как прежде» зелёный.
- Тест «chunked-тело ниже потолка зависло → 504 за время порядка `requestTimeoutMs`» красный на коде до правки (сейчас ответа нет) и зелёный после.
- Существующие тесты ограждений зелёные: 413 (`apps/api/src/app.test.ts:287-325`), 504 (`app.test.ts:328`).
- Тела 405 и 400 — `{ error: … }` той же формы, что 413 и 504 API (тест на форме).
- `pnpm verify` зелёный; строка добавлена в `docs/escaped-defects.md`.
