# C3.0. Схема окружения на Zod: один модуль чтения в каждом приложении

**Проблема.** Схемы окружения нет: переменные читаются напрямую — `process.env` в `apps/api/src/server.ts`, окружение в `apps/web/src/lib/api-client.ts`. Неверное или пропущенное значение обнаруживается в момент использования, а не при старте.

Продуктовая часть бывшей C3.1: защищённых путей не трогает, её берёт обычный агент. Правило линтера и проверку примера окружения подключает оператор задачей C3.1.

## Что сделать

- В каждом приложении — один модуль окружения: читает переменные, проверяет схемой Zod и отдаёт типизированный объект. В API опереться на существующий `apps/api/src/server-config.ts`: расширить его, а не заводить второй.
- Остальной код `src/` получает значения из модуля; прямых обращений к `process.env` и `import.meta.env` вне модуля не остаётся.
- Невалидное окружение — отказ при старте с перечнем переменных и причин, без значений секретов в сообщении.
- Тесты модуля: пропущенная обязательная переменная, неверный формат, значения по умолчанию.

## Что учесть

- Конфиги сборки и тестов (`vite.config.ts`, `vitest.config.ts`, `e2e/playwright.config.ts`) читают окружение сами — это не код приложения, и часть из них защищена. Их задача не трогает; исключения для них оформит C3.1 в правиле линтера.
- Файл примера окружения здесь не создавать: его имя и проверка — решение C3.1.

## Критерии приёмки

- В `apps/api/src` и `apps/web/src` окружение читает ровно один модуль на приложение (в PR — вывод поиска по `process.env` и `import.meta.env`).
- Тесты модуля зелёные; старт с невалидным окружением завершается ошибкой с перечнем переменных.

## Журнал

- 2026-11-15: выделена из C3.1 по итогам аудита, чтобы C3.2 (production-сервер) не ждал оператора. Осознанный компромисс: до C3.1 правило «только один модуль» держится тестом и ревью, а не линтером.
- 2026-11-16: план отрепьюерен до кода (architecture-reviewer: блокеров нет; sanity-reviewer: changes-requested в лёгкой форме — учтено).
  - API: `server-config.ts` расширяется — Zod-схема (PORT обязательный положительный integer с подсказкой про `pnpm dev`; `ENABLE_TEST_API*` через `z.stringbool()`, дефолт false, чужие значения — отказ; `INSTANCE_ID`/`DATABASE_URL` — опциональные строки, `''` → undefined; `NODE_ENV` — опциональный enum development/production/test) + `loadServerEnv(source = process.env)`, отказ со списком «переменная: причина» через `superRefine`, без значений секретов. Прод-гвард «ENABLE_TEST_API в production» переезжает из `server.ts` в валидацию схемы. `resolveServerStorage` — логика не меняется, сигнатура `Pick<ServerEnv, …>`.
  - Web: новый `apps/web/src/lib/env.ts` — единственный читатель `process.env`/`import.meta.env` в `apps/web/src`; `API_URL` — обязательный абсолютный URL (`z.url()`) с текущей подсказкой; `api-client.ts` вызывает лениво на запрос.
  - Docs: закон §2.3 обновляется (server-config.ts — модуль env API; src/lib/env.ts — web; SSR-чтение ленивое, прокси — при старте).
- 2026-11-16: решения по находкам ревью и развилкам.
  - [sanity, major] zod не должен попасть в клиентский бандл web: SSR-ветка выбрасывается минификатором (ADR 0005), но гейт `bundle` проверяем после wiring; при провале — реструктуризация env.ts, порог не трогаем (он защищён).
  - [architecture, minor] Гвард production — `superRefine` на объектной схеме: одна ошибка с полным перечнем, не отдельный throw.
  - [оба, minor] Развилка «отказ при старте» для web: валидация `API_URL` срабатывает на первом SSR-запросе, а не при старте web-процесса (непустоту при старте ловит `requireApiUrlForServe` в vite.config.ts). Принято как продолжение существующего дизайна (ленивое чтение — инвариант node-тестов, api-client.ts). Отказ при старте с полной валидацией — предмет C3.2 (условие возврата).
  - [architecture, nit] `''`-ветка в `resolveServerStorage` сохранена как защитная для прямых вызовов мимо схемы; существующий тест с `''` мутанта убивает.
  - [sanity, nit] `NODE_ENV` — строгий enum без нормализации `''`: никто в репо NODE_ENV не ставит, строгость ловит опечатки вида `NODE_ENV=prod`, которые молча отключали бы прод-гвард.
  - `DATABASE_URL` формат не валидируем: libpq принимает keyword-строки без URL-схемы; заодно значения не попадают в сообщения об ошибках.
