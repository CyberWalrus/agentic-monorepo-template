# C4.1. Структурные логи, идентификатор запроса и таксономия ошибок

**Проблема.** Логи API неструктурированы, запрос нельзя проследить от web до домена, ошибки домена не отличимы по таксономии. Без этого нечего прикладывать к отчёту E2E (задача C4) и нечем разбирать дефект после деплоя (C3.2).

Продуктовая часть бывшей C4: защищённых путей не трогает, её берёт обычный агент.

## Что сделать

- Структурные логи API (JSON, одна запись — одно событие) с идентификатором запроса. Идентификатор принимается из заголовка или создаётся на входе, возвращается в ответе и проходит через прокси `/rpc` из web (ADR 0005).
- Единая таксономия ошибок на основе типизированных ошибок oRPC в `packages/contracts`: клиент различает ошибки по коду, а не по тексту. Contract-first: сначала контракт, затем `openapi.json` (скил `api-contract-change`).
- В лог не попадают тела запросов и значения секретов; тест на это обязателен.
- Трейсы OpenTelemetry — только если обходится без новой инфраструктуры в тестах; иначе записать в «Журнал» как отложенное с условием.

## Решение (2026-11-15)

- **Логгер без новой зависимости, если хватает `console` с JSON-сериализацией и middleware Hono.** Почему: правило репозитория — зависимости только при реальной необходимости; формат записи важнее библиотеки.
- Альтернатива: `pino`. Взять, если понадобятся уровни по окружению, редактирование полей или производительность под нагрузкой перфа; версия — в `catalog:`, обоснование — в PR.
- Условие возврата: перф-бюджет p95 API краснеет из-за логирования.

## Критерии приёмки

- Каждое событие лога несёт идентификатор запроса; идентификатор из ответа находит записи этого запроса в логе (тест).
- Ошибки домена типизированы и различимы клиентом по коду; тесты обоих транспортов.
- Тест: тело запроса и значения секретов в лог не попадают.

## Журнал

- 2026-11-15: выделена из C4 по итогам аудита; C4 сужена до доставки логов в отчёт Playwright и зависит от этой задачи.
- 2026-11-17, план (до кода, на ревью architecture-reviewer и sanity-reviewer):
  - **Логгер — свой, на console** (по разделу «Решение» задачи): `apps/api/src/observability.ts` — `logEvent(level, event, fields)`: одна запись = один JSON-объект на stdout (`{ ts, level, event, ...fields }`). pino не берётся: уровней по окружению и редактирования полей не нужно (условие возврата из задачи остаётся — перф-бюджет p95 API краснеет из-за логирования). pnpm-workspace.yaml не меняется (pino не берём).
  - **Request id**: Hono-middleware в `createApp`: читает `x-request-id`, принимает только безопасную форму (`^[A-Za-z0-9._~-]{8,128}$` — защита от log-injection и мусора в ответе), иначе генерирует `randomUUID`; ставит `x-request-id` в ответ. Заголовок — тот же канал для будущего trace-id (OTel отложено, см. ниже).
  - **События запроса**: middleware вокруг `next()`: одна запись `event: 'request'` с `{ requestId, method, path, status, durationMs }`; статус ≥400 — `level: 'warn'`. Тела запросов не читаются и не логируются вообще; в поля попадают только метод/путь/статус/длительность — тест AC3 постит тело с маркером-«секретом» и проверяет, что маркера нет ни в одной записи.
  - **Ошибки**: коды oRPC-ошибок в лог — через перехват в `createApp` (Hono onError / oRPC-интерцептор — решить по факту API 1.16.1 при реализации; fallback: только status в request-событии). Непойманное — INTERNAL: в контракт добавляется код INTERNAL, unexpected пишется level error без стека наружу (стек — в лог, не в ответ).
  - **Таксономия (contract-first)**: `packages/contracts/src/errors.ts` — каталог ошибок: единые `{ message }` на код: FORBIDDEN 'Access denied', NOT_FOUND 'Resource not found', INTERNAL 'Internal error'. `ocAccess` продолжает нести FORBIDDEN (все процедуры); `tasks.toggle` переключается на каталог (сообщение NOT_FOUND становится 'Resource not found' — унификация: клиент различает по коду, текст одинаков на код); INTERNAL декларируется, но выбрасывается только catch-all. openapi.json перегенерируется (404 на toggle остаётся, сообщение меняется). Тест обоих транспортов: одна и та же ситуация (toggle неизвестного id → NOT_FOUND; remove неизвестного id → FORBIDDEN) даёт различные коды, клиент ветвится по `error.code`.
  - **Прокси web**: `forwardHeaders`/`filterResponseHeaders` уже переносят x-request-id в обе стороны — добавляются два теста в server-app.test.ts (проход запросного заголовка в API и ответного — браузеру). Генерация id в браузере не нужна: создаётся «на входе» API.
  - **server.ts**: стартовые console.warn переводятся на структурный логгер (event: 'startup' / 'listen' / 'shutdown').
  - **OTel — отложено с условием**: для трейсов в тестах нужен коллектор/экспортёр — новая инфраструктура, которой в песочнице нет. Записывается в журнал как отложенное: «отложено: появился коллектор трейсов в тестовом контуре (или задача о его заведении) — трейс-id ложится в тот же заголовок x-request-id».
  - **Слои**: contracts (errors.ts + openapi) → api (observability.ts, app.ts middleware, server.ts, тесты) → web (2 теста прокси). E2E/UI не затрагиваются. pnpm-workspace.yaml не меняется.
  - **Тесты**: api — sink-логгер как опция createApp (`log?: (record) => void`, дефолт — console): AC1 (id из ответа находит записи), AC3 (маркер тела и «секрета» нет в записях), re-use валидного id, регенерация невалидного, запрос-событие на каждый запрос; web — прокси-проход заголовка; contracts — сообщения каталога статичны (нет интерполяции) — тест.
- 2026-11-17, правки плана от ревью (architecture: changes-requested по тексту; sanity: approve) — внесены до кода:
  - **[major] errors.ts — единственный источник**: `ocAccess` строится с импортом из каталога (`.errors({ FORBIDDEN: { message: ERROR_MESSAGES.FORBIDDEN }, INTERNAL: … })`), инлайн-литерала FORBIDDEN больше нет; contracts-тест сверяет декларацию ocAccess с каталогом.
  - INTERNAL прикрепляется к `ocAccess` (все процедуры наследуют — клиент типизированно ловит от любой; openapi получит 500 у всех операций осознанно), выбрасывается только catch-all. NOT_FOUND остаётся на toggle — 404 не документируется там, где кода нет (без оракула на remove).
  - З13: `generateRequestId?: () => string` и источник времени — через опции createApp/логгера (дефолты randomUUID/new Date), тесты детерминированы.
  - Логируется pathname без query (токен из `?token=` не попадает); AC3-тест добавляет маркер-секрет и в query; обработанные (задекларированные) ошибки пишутся только кодом (+name/message/stack явно сериализованные — только для unexpected); тест сериализации ошибки.
  - Обновление ассертов текста в app.test.ts ('Task not found' → 'Resource not found') — осознанная контракт-first правка, не ослабление.
  - touches не меняются (объявление задачи не трогаем): pnpm-workspace.yaml в touches не использован — записано здесь.
  - Интерпретация AC1: request-scoped события несут requestId; события жизненного цикла процесса (startup/listen/shutdown) — по определению без него. Условие: web-логгер при следующей потребности потребует общего пакета (no-app-to-app запрещает импорт между приложениями).
