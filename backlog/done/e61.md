# E61. Состояние ошибки маршрута: e2e-проверки нет

**Проблема.** `e2e/features/route-states/route-states.spec.ts:4`: единственный тест фичи — not-found для неизвестного URL. Состояние ошибки маршрута с кнопкой «Try again» end-to-end не проверено: ни появление состояния, ни действие кнопки. Аудит владельца, 2026-11-23, «Средние → Тесты и перф».

## Что сделать

1. Решить, как воспроизвести ошибку маршрута без продуктовых изменений, — по решению в «Решении»; способ записать в «Журнале».
2. Тест в `e2e/features/route-states/route-states.spec.ts`: состояние ошибки появляется, «Try again» видима и доступна по роли; нажатие восстанавливает страницу или повторяет попытку.
3. Пункт в плане тестов (`e2e/specs/`) с идентификатором AC — тест ссылается на него (трассировка AC).
4. Если тест вскрывает дефект состояния ошибки — исправить и добавить строку в `docs/escaped-defects.md` (этот путь не входит в touches: до такой правки расширить touches отдельным PR в main).

## Критерии приёмки

- Тест зелёный; способ воспроизведения и его независимость от прод-сборки записаны в «Журнале».
- AC в плане тестов есть, трассировка (`e2e/features/traceability`) зелёная.
- pnpm e2e зелёный; файл помечен `@critical` по решению b18 (или наследует метку после PR b18).

## Решение

По умолчанию — ошибка загрузки данных на странице (API недоступен), без тестовой ручки в продукте: состояние ошибки пользователь видит именно так. Условие возврата: если ошибка загрузки данных в шаблоне рендерит не маршрутное состояние, а состояние внутри страницы, — добавить тестовую ручку только для e2e-режима и записать в «Журнале», почему без неё нельзя.

Пересекается с b18 по файлу: кто мержит вторым — ребейз.

Реализация: тест подменяет на границе сети браузерные запросы к `/rpc` (`page.route`, ответ 502 `{"error":"API is unreachable"}` — тот же, что отдаёт прокси web при недоступном API, `apps/web/src/server-app.ts:288-291`) и делает клиентскую навигацию с not-found на `/` (`history.pushState` + `popstate`: роутер слушает историю; `<Link>` в шаблоне нет, «Back to tasks» — обычный `<a>`). Условие возврата из «Решения» не наступило: ошибка загрузки рендерит именно маршрутное состояние (`defaultErrorComponent: RouteError`, `apps/web/src/router.tsx:32`). Условие возврата к тестовой ручке: loader перестанет идти через браузерный `/rpc`.
- 2026-11-24 — **Тест вскрыл дефект состояния ошибки (пункт 4 задачи): «Try again» не повторяет загрузку.** Полная версия теста (нажатие кнопки при снова доступном API → ожидание страницы задач с сидированными данными) красная. Прогон с диагностикой (`page.on('request')`, счётчик в обработчике `/rpc`): до клика один запрос `POST /rpc/tasks/list → 502`, состояние ошибки появляется сразу (повтора с паузой нет — `fetchQuery` не ретраит); после клика за 3 с запросов ноль, `role="alert"` остаётся, в консоли повторно та же ошибка (`Bad Gateway`). Причина: `RouteError` передаёт кнопке пропс `reset` роутера (`apps/web/src/lib/route-states.tsx:16`), а `reset` только сбрасывает React-границу ошибок (`this.setState({ error: 0 })`, `@tanstack/react-router` 1.170.46, `dist/esm/CatchBoundary.js:10-12`); совпадение маршрута снова бросает сохранённую ошибку (`dist/esm/Match.js:113-123`), loader не перезапускается. Комментарий `route-states.tsx:8` («reset инвалидирует роутер и заново прогоняет loader'ы») поведению установленной версии не соответствует. Юнит-тест проверяет только, что кнопка вызывает мок `reset` (`apps/web/src/lib/route-states.test.tsx:7-15`), поэтому дефект прошёл все гейты. Независимость от теста подтверждается исходником пакета, а не только прогоном.

- 2026-11-24 — **Решение по исправлению (развилка закрыта).** `RouteError` больше не принимает пропс `reset`: обработчик повтора — `router.invalidate()`. Почему: invalidate заново прогоняет loader'ы упавшего маршрута (`@tanstack/router-core` 1.171.39, `dist/esm/router.js:527-539` — ошибочный match получает `status: 'pending'` и очищенную ошибку), а сменившийся объект match сбрасывает границу ошибок: её ключ сброса — сам match (`@tanstack/react-router` 1.170.46, `dist/esm/Match.js:53`, `CatchBoundary.js:14-20`). Подтверждено прогонами (следующая запись). Альтернатива — вызывать `reset()` и `router.invalidate()` вместе; отклонена: `reset` даёт повторный бросок сохранённой ошибки и ничего не добавляет. Условие возврата — если при обновлении роутера граница перестанет сбрасываться сменой match: покраснеют юнит-тест на настоящем роутере и e2e.
