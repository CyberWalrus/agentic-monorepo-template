# C12. Генератор openapi: корректные схемы ответов и кодов ошибок

**Проблема.** Два дефекта сгенерированного `packages/contracts/openapi.json` (аудит 2026-11-20, линза бэкенда):

1. `z.void()` у `tasks.remove` рендерится в всегда-ложную схему `anyOf: [{ not: {} }, { not: {} }]` — ей не удовлетворяет ничего, кодогенерация клиента даст мусорный тип.
2. 400 не документируется для публичных процедур: oRPC возвращает `BAD_REQUEST` при провале `CreateTaskInputSchema` (тест `app.test.ts:50-56`), но в спеке у POST /tasks только 200/403/500 — потребитель кодогенерацией получит неполный контракт.

## Что сделать

- Проверить опции генератора (`packages/contracts/scripts/openapi.ts`) для обеих проблем; если опции нет — минимальное обогащение спеки после генерации так, чтобы `openapi:check` оставался детерминированным.
- Рантайм не меняется: контракт в коде остаётся тем же.

## Решение

- **Сначала опции генератора, потом обогащение.** Почему: ручное обогащение — второй источник правды, который надо удерживать гейтом; опция держит один источник.

## Критерии приёмки

- Схема 200 DELETE — корректная; у POST /tasks и toggle документирован 400; перегенерация стабильна, `openapi:check` зелёный.

## Журнал

- 2026-11-20: заведена по итогам аудита обвязки. Связана с C6: C6 — гейт совместимости между версиями контракта, эта — корректность содержимого спеки на текущей версии.
- 2026-11-20: реализовано в ветке `task/c12`.
  - **Void-вывод — опцией генератора** (как предписывает «Решение»): у `OpenAPIGenerator` есть штатный крюк `schemaConverters`. Добавлен `voidSchemaConverter` (`scripts/openapi-spec.ts`): для `z.void()`/`z.undefined()` возвращает `[required=true, { not: {} }]` вместо штатного `[false, { not: {} }]` из `@orpc/zod` (zod4-конвертер, ветка `undefined|void`). Обязательная never-схема не заворачивается в `applySchemaOptionality` в ложную `anyOf`, а `toOpenAPIContent` опускает content у never — 200 остаётся без тела, как и отдаёт рантайм (OpenAPI-транспорт отвечает void-процедуры «200 с пустым телом», app.test.ts).
  - **400 — обогащением: опции у генератора нет.** `OpenAPIGeneratorGenerateOptions` (`filter`, `commonSchemas`, `customErrorResponseBodySchema`, route-level `spec`) документирует только объявленные в `errorMap` коды; неявный 400 от валидации входа не выражается. Добавлен детерминированный проход `documentValidationErrors`: операции из явного списка `OPERATIONS_WITH_INPUT_VALIDATION` получают 400 в форме рантайма (`defined:false`, `code:"BAD_REQUEST"`, `data.issues` с `path`+`message` — снято с живых ответов API: POST /tasks с `title:"   "` и POST /tasks/<не-uuid>/toggle дают ровно такое тело).
  - **Список явный, а не «все операции с input»**: рантайм-зонд показал, что DELETE /tasks/<не-uuid> отвечает 403 (owner-проверка fail-closed, C2.3 — раньше валидации), поэтому 400 у DELETE недостижим и не документируется. Критерий «у POST /tasks и toggle документирован 400» выполняется точно. Новая процедура с достижимым 400 добавляется в список явно вместе с тестом.
  - **Побочный чисткой**: генератор ставит `content: {}` у void-ответа даже после корректора — пустая мапа утверждает тело, которого нет; `documentValidationErrors` такие content убирает.
  - **Контракт в коде не тронут** (tasks.ts, errors.ts без изменений), рантайм не менялся — только спека и генерирующий скрипт.
  - Тесты: `scripts/openapi-spec.test.ts`, 10 тестов — unit конвертера и обогащения (включая «не перезаписать объявленный контрактом 400» и идемпотентность) + интеграция `generateSpec(contract)` на живом контракте (DELETE 200 = `{description:'OK'}`, 400 у create/toggle, отсутствие 400 у get/delete, детерминизм двух прогонов).
  - Один `@ts-expect-error` с причиной: тип responses в openapi-types — пересечение с легаси-V3, где нет легальных в 3.1 `const` и type-массивов (сам генератор пишет `const` в схемы ошибок этой же спеки).
  - Гейты: `pnpm verify` зелёный полностью (16 шагов); `pnpm --filter @repo/contracts openapi:check` зелёный; `pnpm mutation` — score 97.18 ≥ порога 75 (выжившие ранее существовавшие, скоуп стрикера `apps/api/src/**` диффом не затронут). `pnpm verify --full` — перед PR, см. PR.
