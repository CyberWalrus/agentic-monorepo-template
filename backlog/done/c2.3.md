# C2.3. Табличные тесты «чужой ресурс — отказ»

**Проблема.** Точечные тесты доступа пишутся наугад; нужна таблица, покрывающая каждую процедуру с владельцем.

## Что сделать

- Для каждой процедуры с политикой «владелец» есть случай «чужой ресурс, отказ» и «свой ресурс, успех» — генерируются перебором контракта, а не пишутся руками.
- Таблица «процедура × случай» видна в отчёте тестов: пустая строка красит набор.

## Критерии приёмки

- Канарейка: удаление проверки владельца из любой доменной процедуры красит табличный тест без его ручной правки.

## Журнал

- 2026-11-17, план (до кода, на ревью architecture-reviewer и sanity-reviewer):
  - **Что и зачем.** Табличный тест доступа: каждая процедура с политикой `owner` получает пару случаев «чужой ресурс — отказ (FORBIDDEN)» и «свой ресурс — успех», сгенерированную перебором. Пустая строка (owner-процедура без строки сценария) и лишняя строка (сценарий не owner-процедуры) красят набор. Канарейка-свойство: сломанная owner-проверка мидлвари красит таблицу без правки теста.
  - **Домен получает владельцев** (по записи «дальше» из журнала C2.2): колонка `owner_id` (nullable) + миграция; `TaskRepository += ownerOf(id) → string|null`, `remove(id) → Task|undefined`; `create` принимает ownerId и пишет туда `context.actor?.id ?? null`; адаптер `ownerOf(input)` в `createApp` заменяет заглушку `async () => null` (условие возврата C2.2 выполнено): незнакомая форма input → null (fail-closed, как решено в C2.2).
  - **Первая owner-процедура — новая `tasks.remove`** (DELETE /tasks/{id}, output void, политика `owner`), а не перевод существующей `toggle`: перевод toggle ломает анонимный toggle веба и критический E2E AC-2 (актора в демо нет), а web/e2e — вне `touches` задачи. `remove` вебом не используется → внешние слои не трогаются. Альтернатива «только тест-инфраструктура без owner-процедуры» отклонена: таблица пуста, канарейка-AC вакуумна; `touches` (contracts + api) подтверждает контрактную правку. Условие возврата: с появлением аутентификации существующие публичные процедуры пересматриваются (задача о ней появится на доске отдельно).
  - **`TaskSchema` не расширяется**: владение — серверные данные политики, не поле вывода API; иначе обязательное поле ломает литералы Task в тестах web и e2e-сидов (обе области вне `touches`). Владение видит только `ownerOf` репозитория.
  - **Перебор — по реальному роутеру** существующими `collectProcedures` + `accessPolicyFromMeta` (уже экспортированы для router-divergence.test), а не по объекту контракта: структурное тождество «контракт ≡ роутер» держит router-divergence.test, а исполнение — только через роутер. Новых экспортов из packages/contracts не нужно (правило ADR 0011 об экспортах).
  - **Таблица в отчёте**: `it.each` с именами вида «tasks.remove — чужой ресурс — отказ»: каждая ячейка = отдельный случай в vitest-отчёте. Отказ проверяется глубже кода ошибки: ресурс не тронут (для remove — задача осталась в списке), успех — эффект домена случился (задача удалена).
  - **Слои**: contracts (remove + openapi) / api (миграция, репозитории, роутер, app, тесты: табличный + контрактный набор репозитория += ownerOf/remove + транспортные случаи в app.test) / UI, E2E — не затрагиваются.
  - **Чего не делаем**: аутентификации нет (actor в демо null), 401/403 не разделяем (C2.2), канарейка в tools/ — задача C2.4 (оператор), `toggle`/`list`/`create` остаются `public`.
  - **Канарейка-AC**: проверяется вручную в этой задаче — убрать `owner !== context.actor.id` из мидлвари → табличный тест красный без правки теста; восстановить → зелёный. Выводы обоих прогонов — в PR.
- 2026-11-17, ревью плана: `architecture-reviewer` и `sanity-reviewer` — approve (до кода). Внедрённые minor-находки:
  - **Семантика remove на неизвестном id — FORBIDDEN, не NOT_FOUND** (зафиксировано до кода): для owner-процедуры проверка владельца идёт до домена; неизвестный ресурс не имеет владельца → `ownerOf` null → отказ (fail-closed C2.2, без оракула «ресурс существует»). NOT_FOUND у remove не объявляется, у toggle остаётся (он public).
  - REST-случаи remove в app.test: чужой/анонимный → 403, свой → 204; случая 404 у remove нет по той же причине (unknown id = 403, без оракула).
  - `pnpm mutation` — обязательный шаг этой задачи (доменная логика: адаптер, remove, ownerOf/remove репозиториев); выжившие — в журнал.
  - Вторая owner-область: диспетчеризация переезжает с формы input на путь процедуры (порт получает path + input, условие возврата C2.2) — записано как условие возврата.
  - Формулировка AC «из любой доменной процедуры» держится на единственности точки исполнения (мидлварь C2.2); появление второй точки исполнения потребует пересмотра канарейки — в доказательства PR.
- 2026-11-17, контракт: `tasks.remove` (DELETE /tasks/{id}, input TaskIdInputSchema, output void, политика `owner`, NOT_FOUND не объявлен — отказ FORBIDDEN раньше домена); openapi.json перегенерирован (+96 строк, DELETE-операция). `TaskSchema` не расширен — владение не видно клиентам (литералы Task в тестах web/e2e не ломаются).
- 2026-11-17, домен: миграция 0001 `ALTER TABLE tasks ADD COLUMN owner_id text` (первый вариант колонки uuid отвергли тесты контрактного набора: Actor.id — непрозрачная строка, не uuid); `TaskRepository` += `remove(id) → Task|undefined` и `ownerOf(id) → string|null`, `create` принимает ownerId; обе реализации (in-memory, Postgres). `reset` сейтит задачи без владельца — e2e-сиды неизменны. Роутер: remove-обработчик без проверки владельца (мидлварь раньше домена), create пишет `context.actor?.id ?? null`.
- 2026-11-17, createApp: заглушка `ownerOfWithoutOwners` заменена адаптером `ownerOfThroughRepository` (условие возврата C2.2 выполнено): input парсится TaskIdInputSchema, незнакомая форма → null → отказ (fail-closed). При второй owner-области диспетчеризация по форме input переезжает на путь процедуры.
- 2026-11-17, тесты: `owner-access-table.test.ts` — таблица, сгенерированная перебором реального роутера (`collectProcedures` + `accessPolicyFromMeta`): целостность генерации (не вакуумная — ≥1 owner-процедура; нет пустых строк; нет лишних строк; каждая owner-процедура даёт оба случая) + `it.each` по ячейкам «чужой → FORBIDDEN и ресурс не тронут» / «свой → успех и эффект домена» (для remove: задача осталась / задача удалена). Тонкость oRPC: клиент — Proxy, свойства неперечислимы, вложенный клиент — гибрид «функция + proxy» — путь до процедуры только через `Reflect.get` с type-guard-ами (`in`/`Object.entries` не работают). Контрактный набор репозитория += 6 проверок (remove ×2, ownerOf ×3, reset-без-владельца) — гоняются против обеих реализаций. app.test += 5 транспортных случаев (RPC owner/чужой/проводка актора в create, REST 200-owner/403-аноним+чужой/403-неизвестный id без оракула; void-вывод OpenAPI-транспорт отдаёт 200, не 204). Канарейка наборной канарейки: `OrderingLosingTaskRepository` дополнили новые методы интерфейса.

Восстановлено → 6/6 зелёные. Удаление проверки красит таблицу, потому что исполнение политики одно (мидлварь на строителе, C2.2) — вторая точка исполнения потребует пересмотра (см. план).
