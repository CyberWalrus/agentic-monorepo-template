# C6. Гейт несовместимых изменений контракта

**Проблема.** `openapi.json` закоммичен, поэтому его можно сравнить с merge-base, но гейта сравнения нет: удаление процедуры или поля ответа, новое обязательное поле входа и сужение типа проходят молча. Ручная процедура уже описана в скиле `api-contract-change` — детерминированную её часть должен держать гейт (З1).

## Что сделать

- Гейт сравнивает `openapi.json` с merge-base. Несовместимые изменения (удаление процедуры или поля ответа, новое обязательное поле входа, сужение типа) требуют одобрения человека; добавления проходят.
- Инструмент сравнения выбрать при реализации.

## Критерии приёмки

- Канарейка: удаление поля ответа из контракта красит гейт; добавление необязательного поля проходит.

## Журнал

### План (до кода)

**Что и зачем.** Детерминированная часть ручной процедуры breaking-change из скила `api-contract-change` становится гейтом: закоммиченный `packages/contracts/openapi.json` сравнивается с его версией на базе (merge-base с main); несовместимые изменения красят существующий шаг verify `openapi`, одобрение человека — ревью PR (тот же механизм, что у bundle-growth, ADR 0013/0015).

**Критерии приёмки → тесты.**

1. «Удаление поля ответа из контракта красит гейт» → unit-тест чекера (`response-field-removed`) + end-to-end прогон реального скрипта на изменённом `openapi.json` (временный коммит-фикстура, гейт красный).
2. «Добавление необязательного поля проходит» → unit-тест (пустой список findings) + end-to-end (гейт зелёный).

**Затронутые слои.** `packages/contracts` (scripts + package.json). **`tools/**` не трогается** — и это осознанное решение: новый файл-гейт под `tools/` обязан попасть в `deny` protected-paths.json и KNOWN_GATES (tools/check-tool-class.ts) тем же PR, оба файла — deny-защищённые, агенту недоступны. Вместо этого гейт встраивается в существующий шаг verify `openapi` через скрипт `openapi:check` пакета `@repo/contracts` (рядом с уже живущим там дрейф-чекером `scripts/openapi.ts`). Новых файлов под `tools/` нет → замыкание tool-class не меняется → защищённые файлы не правятся. Все изменённые файлы — класс review (`packages/contracts/**`).

**Инструмент сравнения.** Свой структурный обход (без новых зависимостей): словарь ключей открытого API генератора (`type/const/enum/format/required/properties/items/oneOf/anyOf/min-max-границы`) мал и стабилен; npm-инструменты (oasdiff и др.) тянут supply-chain и дают лишние классы срабатываний. Правила несовместимости:

- удаление процедуры (path+method);
- удаление поля (и в ответе, и во входе — скил: «удаление поля … всё это breaking»; переименование ловится как удаление);
- новое обязательное поле входа; новое обязательное поле ответа (новое свойство, сразу required);
- сужение входа: type/enum/const/format/границы (maxLength↓, minLength↑, min/max и pattern) — старые валидные запросы становятся невалидными;
- расширение выхода: type/enum/const/format/границы — сервер может отдать значения, которые старый клиент не разберёт;
- удаление status-code ответа, удаление параметра, requestBody: absent→present(required) и present→absent.
  Добавления (процедура, опциональное поле, новый статус-код ошибки, вариант union) — проходят.

**База.** `--base <ref>` → `TURBO_SCM_BASE` (уже выставлен на уровне workflow в CI, ci.yml:29) → `git merge-base HEAD origin/main` (локально). На базе нет `openapi.json` → база пустая → все изменения — добавления (зелёный). Нет merge-base / битая спека → красный с причиной (fail-closed, как check-bundle-delta). Job static в CI имеет `fetch-depth: 0` — `git show <base>:packages/contracts/openapi.json` работает.

**Чего не делаем.** Без правок защищённых путей; без канарейки в защищённой таблице `tools/gate-canaries.ts` (deny-файл; добавление туда — отдельное решение мейнтейнера, журнализирую как известное ограничение); UI/e2e/perf не затрагиваются — шаг API-поведения не меняет продукт.

**Развилка.** Инструмент сравнения — по задаче «выбрать при реализации»: выбран свой обход, причины выше; возврат к npm-инструменту оправдан, если правила начнут отставать от эволюции генератора OpenAPI.

### Реализация

- `packages/contracts/scripts/openapi-compat.ts` — чекер: чистая функция `checkCompatibility(base, current) → Finding[]` + тонкий CLI (`--base <ref>` → `TURBO_SCM_BASE` → `git merge-base HEAD origin/main`), запуск только при прямом вызове (образец: tools/check-tool-class.ts). Правила — по плану; направление сравнения (request — сужение приёма, output — расширение выдачи) покрыто тестами.
- `packages/contracts/scripts/openapi-compat.test.ts` — 27 unit-тестов: обе канарейки AC (удаление поля ответа / добавление опционального), все классы правил, «настоящая» канарейка на закоммиченном openapi.json (чекер против самого себя зелёный, правка completed красит).
- Проводка: `openapi:check` = дрейф-чекер `&&` compat-чекер. Шаг verify `openapi` и CI (ci.yml static, fetch-depth: 0, TURBO_SCM_BASE на уровне workflow) получают гейт без правок защищённых файлов; замыкание tool-class не изменилось (новых файлов под tools/ нет — шаг tool-class зелёный).

### Канарейки end-to-end (реальный CLI на настоящем контракте)

1. Удаление `completed` из `TaskSchema` + регенерация openapi.json → гейт красный, exit 1, три находки `[response-field-removed]` с точными указателями (GET /tasks, POST /tasks, POST /tasks/{id}/toggle); дрейф-чекер при этом зелёный — красит именно compat-гейт.
2. Возврат + добавление опционального `tag` → гейт зелёный, exit 0.
3. Несуществующая база → красный с причиной (fail-closed); неизвестный аргумент → отказ с exit 2 (как check-bundle-delta).
