# C3.4. E2E и перф против production-способа запуска

**Проблема.** E2E и перф гоняются против dev/preview-способа запуска, а деплоится production-entry — тестируется не то, что едет в прод.

## Что сделать

- E2E, перф и визуальные тесты поднимают приложения тем же способом, что и production (entry из C3.2), локально и в CI.
- `vite preview` и dev-серверы остаются только для интерактивной разработки.
- Перф-метрики переснять после переключения: способ запуска меняет абсолютные числа (`perf-budgets.json` при сдвиге правит оператор отдельным PR по правилу ADR 0009, «Пороги»).

## Критерии приёмки

- `pnpm verify --full` и CI поднимают приложения production-способом; ссылок на `vite preview` в скриптах тестов не осталось.

- 2026-11-22, ревью PR #140 — блокер memory/CPU-DoS, исправлен. Кэш сжатых копий ключовался сырым pathname клиента (`new URL(c.req.raw.url).pathname`, percent-encoded), тогда как файл резолвится из декодированного пути: варианты кодирования одного URL (`%69ndex…`, подмножества заэнкоженных символов) давали разные ключи → каждая запись — навсегда удерживаемая ~150KB копия + синхронный gzipSync (~мс на ~500KB файле) без потолка; entry деплоится публичным образом (C3.3, HOST=0.0.0.0). Фикс: `resolveStaticFile` возвращает `resolvedPath` (канонический абсолютный путь) в `StaticFile`, кэш ключуется им — одна запись на существующий файл, рост ограничен структурно (файлов в dist/client конечное число, корень пишет только `vite build`); потолок на число записей признан избыточным (структурная граница вместо мёртвого кода). Кэш введён параметром фабрики (`compressedBodies`, образец `proxyFetch`) для наблюдаемости в тестах. Тесты: «два percent-кодирования одного пути → одна запись кэша» (инъекция Map, `cache.size === 1`, идентичные gzip-байты) и канонизация `resolveStaticFile` (`%61pp-%61bc123.js` → тот же `resolvedPath`). ADR 0012: строки «Фабрика» (параметр `compressedBodies`) и «Статика» (ключ кэша — канонический путь; отвергнутый вариант — в «Почему»).
