# C1.5. Изоляция E2E по рабочему пространству и распараллеливание

**Проблема.** E2E изолируются общим сбросом данных, поэтому visual и perf вынуждены идти последовательно (`SHARED_DATA_LOCK`).

## Что сделать

- Изоляция по арендатору или рабочему пространству на тест: каждый сценарий работает со своими данными и не задевает чужие.
- Снять `SHARED_DATA_LOCK`: visual и perf перестают быть последовательными.
- Миграции к этому моменту уже гейтятся (C1.3), чтобы изоляция не строилась на просядущей схеме.

## Критерии приёмки

- E2E, visual и perf идут параллельно на одном прогоне без взаимного влияния; общий сброс данных остаётся только в `/__test__/reset` для точечных сценариев.

## Журнал

### 2026-11-22 — захват и план (агент конвейера, до кода)

Захвачено: ветка `task/c1.5` от `main` (63c6acaa), worktree рядом с репозиторием; зависимости c1.3, c1.4 закрыты (в `done/`); файл перенесён в `done/` командой `pnpm backlog close c1.5`.

**План следующего шага (этап кода)** — изоляция E2E по рабочему пространству:

1. `apps/api`: внутренний `workspaceId` у задачи в хранилище (симметрично `ownerId` C2.3, `tasks/repository.ts`), `list()` фильтрует по workspace контекста; workspace читается из заголовка запроса, отсутствие заголовка — текущее поведение («ничей» workspace) — ручные клиенты и k6 не ломаются. Публичный контракт `TaskSchema` не меняется (workspace не в `packages/contracts/src/tasks.ts`) — openapi.json, вероятно, не перегенерируется; если всё же меняется — `pnpm regen`.
2. `e2e/fixtures.ts`: фикстура выдаёт каждому тесту уникальный workspace и ставит его в `extraHTTPHeaders` контекста Playwright — `apps/web` не меняется: прокси `/rpc` форвардит заголовки (`apps/web/src/server-app.ts:204`), браузер шлёт заголовок со страницей.
3. Test-API: seed пишет в workspace сценария; общий `POST /__test__/reset` сохраняется как есть для точечных сценариев (критерий).
4. Снятие `SHARED_DATA_LOCK` (`e2e/fixtures.ts:100`), `mode: 'serial'` и `lock` у visual (`e2e/features/tasks/tasks.visual.ts:15,17`), `lock` у perf (`e2e/perf/tasks.perf.ts:254`). Проектные настройки конфига Playwright (внутренняя сериализация perf для чистоты замеров, Docker-обёртка visual) — не `SHARED_DATA_LOCK`, не трогаем.
5. Тесты: юнит репозитория «два workspace не видят данные друг друга», поведение API (заголовок задаёт scope), E2E-проверка параллельности проектов на одном API; `pnpm verify --full`, `pnpm visual` — пиксели не должны измениться (UI и форма seed-данных те же), обновление базлайнов не требуется.

**Развилка** (раздела «Решение» в файле нет — выбрано по ADR 0009). Выбрано: workspace-заголовок + внутренний `workspaceId` — минимальный дифф (UI не меняется, контракт, вероятно, тоже), доменный паттерн изоляции, тиражируемый фичами (как схема c1.4 для integration-тестов), доказывает критерий на одном API-процессе. Альтернативы: (B) API-инстанс на проект/воркер — отклонена: правит защищённый `e2e/playwright.config.ts`, тяжелее, не доменный паттерн; (C) workspace в явных параметрах контракта — отклонена: правит `apps/web` (не в `touches`) и раздувает публичный контракт шаблона ради тестовой изоляции. Условие возврата: если `forwardHeaders` прокси режет кастомные заголовки или `extraHTTPHeaders` не доходит до API — переход к (B), решение фиксируется здесь же.

**Чего не делаем**: реальных арендаторов/аутентификацию (шаблонный домен), Postgres-репозиторий (вне серии), правки `.github/workflows/**` (job'ы CI уже параллельны, `ci.yml:389` сводит их needs-ом), правки локальной последовательности e2e → perf в `verify --full` (она держится на общем отчёте `reports/e2e.json` — `tools/verify-steps.ts:69-84` — а не на данных; при желании распараллелить — отдельная задача с правкой защищённых `tools/verify-steps.ts`).

**Входы человека (ADR 0009)**: приёмка PR ветки (approve/label/merge). Если реализация всё же упрётся в защищённый путь (например, отдельный отчёт perf) — «нужен вход человека» (режим обслуживания), остальное продолжается без него.

### 2026-11-22 — план-ревью: финальный план (агент)

План-ревью нашло блокеры в первоначальном плане — все приняты, план обновлён. Изменения против первоначального:

1. **Postgres — в объёме.** «Postgres вне серии» невыполнимо: `PostgresTaskRepository` реализует общий интерфейс, контрактный набор C1.1 гоняется против обеих реализаций. Обновляются обе реализации; в схему Postgres добавляется nullable `workspace_id` + миграция по правилам c1.3 ([ADR 0018], `db:generate`, гейт schema-sync в шаге `test`).
2. **Уникальные seed-id на workspace.** `makeTasks` шёл с константными id — параллельные seed-ы разных workspace перетёрли бы строки (Map по `task.id`, PRIMARY KEY на Postgres). id строятся детерминированно из `workspace:index`, title не меняется (пиксели целы). Юнит-чек «два workspace с одинаковыми id не влияют друг на друга» — в контрактном наборе, против обеих реализаций.
3. **SSR-путь в объёме** (нашёл план-ревью): лоадер `/` префетчит список напрямую в API (RPCLink, мимо прокси), при `staleTime: 10_000` сидированные задачи не появились бы на странице никогда. Кастомный server entry TanStack Start (`apps/web/src/server.ts`) кладёт workspace документа в AsyncLocalStorage, SSR-fetch RPCLink добавляет заголовок. «apps/web не меняется» снято; touches обновлены (`.github/workflows/**` убран — workflows не трогаем).
4. **ADR до кода.** Архитектурная развилка — доменный паттерн, компромисс «скоупинг не в openapi» — оформлена [ADR 0020](../docs/adr/0020-e2e-workspace-isolation.md); альтернативы и условие возврата перенесены туда из журнала.
5. **Доказательство критерия.** Каждый существующий запуск — один проект (`e2e/package.json`), поэтому «параллельно на одном прогоне» доказывается комбинированным прогоном `--project=visual --project=perf` против одного API внутри Docker-контура visual (тот же образ, что CI), плюс контрактные чеки и тесты app/web. Условие возврата прежнего плана («прокси режет заголовки») переписано: `forwardHeaders` форвардит все кастомные заголовки (server-app.ts:145-158) — реальный разрыв был в SSR.
6. **Скоупинг toggle/remove.** Решение: `toggle/remove` принимают workspace и отвечают «не найдено» на чужой scope; `ownerOf` остаётся сквозным (политика «owner» — отдельная область, C2.3). Зафиксировано в ADR 0020 и контрактном наборе.

Пороги и бюджеты не трогаются: замеры perf должны остаться в порогах `perf-budgets.json` (защищённый файл) — при выходе за порог код чинится (скил `perf-regression`), не порог. Устаревший комментарий `e2e/playwright.config.ts:100-101` («внутри сериализованы test lock'ом») остаётся — файл deny, расхождение перечисляется в разделе «Изменения гейтов» PR. После перевода seed на workspace у глобального `POST /__test__/reset` не остаётся потребителей в e2e (единственным был `seedTasks`, fixtures.ts:84) — ожидаемое состояние по критерию «общий сброс остаётся для точечных сценариев».
