# C9.4. Телеметрия обвязки: время CI, flaky rate, доля агентных PR

**Проблема.** Vision перечисляет метрики системы (время CI, flaky rate, доля агентных PR без ручных правок, пропущенные дефекты), но ни одна не собирается — механика гейтов опережает измерения.

## Что сделать

- Сбор метрик из уже существующих источников: длительность jobs из CI, flaky rate из B4.4, счётчик отказов из C9.3, метки «PR агента» из описаний PR, число конфликтов слияния между задачами доски.
- Единый отчёт трендов (nightly): метрики за период рядом с целями из vision, дельта к прошлому периоду.
- Бюджет verify (B1) и перф-тренды (A6) читают отчёт, а не считают метрики сами.

## Критерии приёмки

- Отчёт трендов содержит все метрики vision, по которым данные уже собираются; для остальных явно помечено «не собирается, чем закрыть».

  **Форма.** Job `telemetry` в `nightly.yml` + инструмент `tools/telemetry-report.ts` (ядро, тестируется) / `tools/telemetry-report.main.ts` (CLI) по образцу пары `check-perf-trend(.main).ts`. Локальный режим `pnpm telemetry:report` — только локальные источники, без GH API. Метрики без источника данных — явное «не собирается, чем закрыть» (часть критерия приёмки); кандидат — «доля агентных PR **без ручных правок**»: доля агентных PR собираема, «без ручных правок» требует конвенции (правки человека на ветке `task/*` после PR агента).
  **Решение развилки** (раздела «Решение» в задаче нет — ADR 0009): отчёт живёт артефактом и step-summary, НЕ коммитится в репо. Почему: данные меняются ежедневно, ежедневный коммит — ежедневный шум и ежедневная приёмка человеком; паттерн артефактов nightly устоялся (`flake.json`, `verify-durations.json`, `perf-baseline`). Альтернатива: ночной PR-храповик с отчётом в репо по образцу test-count-ratchet (`nightly.yml`, job `test-count-ratchet`). Условие возврата: человеку нужен отчёт файлом в репо (дашборд/внешний потребитель) — добавляем храповик тем же инструментом.
  **П. 3 «Что сделать» (B1/A6).** Их гейты не ослабляем и не переносим: отчёт читает их сырые артефакты (`reports/verify-durations.json`, `e2e/reports/perf.json`) и становится единственным местом трендовой агрегации и калибровки порогов (З7; `nightly.yml` job verify-budgets: «калибровка порога — по тренд-данным»). Точная семантика «читают отчёт, а не считают сами» — на ревью PR: если ревьюеры прочтут как «A6 берёт базу из тренд-отчёта вместо артефакта» — отдельное решение с ADR-риском, не в первом PR.
  **Не делаем (scope).** Cross-machine агрегация локальных denial-журналов (граница C9.3 от 2026-11-20, ждёт хранилище вне машины — точка интеграции A7); правки порогов `verify-budgets.json`/`perf-budgets.json` (защищены, подъём — человеческим PR); замена или перенос гейтов B1/A6; новые зависимости; дашборд/внешний бэкенд; правки продукта.
  **Затронутые слои.** `.github/workflows/nightly.yml` (deny); `tools/telemetry-report*.ts` — новый deny-инструмент ночного контура: пополнение `tools/protected-paths.json` + `KNOWN_GATES` тем же PR (ADR 0014, образец — `backlog-doctor.ts`); `tools/test/` — тесты ядра; `docs/` — architecture.md (раздел телеметрии/трендов) и vision (ссылка на отчёт).
  **Граница с человеком (ADR 0009).** `touches` сплошь deny (`.github/**`, `tools/check-perf-trend.main.ts`) — исполнение требует режима обслуживания в worktree задачи; включение через интерфейс хоста остаётся человеку/операторской сессии, агенту запись в deny-файлы запрещена.
