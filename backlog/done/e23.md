# E23. security.yml красный на каждом прогоне — 403 dependency-review и находки zizmor

**Проблема.** Workflow `security.yml` не имеет ни одного зелёного прогона в последних 40+ (проверено `gh run list --workflow=security.yml` 2026-11-22; красный и на push в main, и на PR). Два независимых корня:

1. Job `dependency-review`: `##[error] Forbidden — dependency review API` (пример: run 44991391613, job 137113002961) — 403 от `GET /dependency-graph/dependency-review` на каждом PR. Подозрения: права токена (в job объявлено только `Metadata: read` — для diff-endpoint обычно нужен доступ к dependency graph) либо вызов до публикации графа зависимостей head-коммита. Причину назвать в PR и починить конфигом workflow.
2. Job `zizmor`: аудит завершает обход всех файлов (`completed ./.github/workflows/…`) и падает на находках — по триажу 2026-11-21 их ~115. Часть — обоснованные подавления, часть — реальные фиксы workflow-файлов.

Оба чека не входят в required, поэтому мёржи идут, но каждый PR красный в 2–3 местах — шум маскирует настоящие регрессии (за время конвейера 2026-11-21/22 красные dependency-review/zizmor прошли через 13 мёржей незамеченными глазами человека).

Попутное наблюдение для триажа того же PR: job `cleanup` (preview-контур) тоже падал на ране #139 (run 44985734683) — проверить и включить в фикс, если корень тот же.

## Что сделать

- Разобрать 403 dependency-review: воспроизвести локально API-запросом, назвать причину (правила токена, порядок событий, приватность графа) и починить в `security.yml` — без отключения job-а.
- Разобрать находки zizmor: исправить реальные (пины по SHA уже сделаны #127 — остальные классы по отчёту), обоснованные — подавить точечно в конфиге zizmor с комментарием-обоснованием на каждую (не пачкой `--disable-all`).
- Итог: `security.yml` зелёный на push main и на PR; `cleanup` — если корень в этом workflow, тем же PR.

## Критерии приёмки

- `gh run list --workflow=security.yml --limit 5` — все зелёные (push main + PR).
- Ни одна находка zizmor не подавлена без обоснования в конфиге; ни один job security.yml не отключён.

## Решение

Развилка «починить конфигом workflow vs причина вне репо» для 403 dependency-review решена диагностикой 2026-11-22. Выбрано: причина — dependency graph (и весь блок Code security) не включён в настройках репозитория CyberWalrus/agentic-monorepo-template (публичный): `gh api .../dependency-graph/dependency-review` по любым SHA возвращает 404 владельческим токеном (данных графа нет), GITHUB_TOKEN в Actions получает 403 (run 45000734983), `vulnerability-alerts` тоже 404. Конфигом workflow это не включается — нужен вход человека: Settings → Code security → Dependency graph (+ Dependabot alerts). Почему: воспроизведено API-запросом с токеном владельца, статус не воспроизводится токеном с любыми scope — это серверное состояние репо. Альтернатива: править workflow под работающий граф (права, порядок событий) — отвергнута, симптом не в них; отключать job запрещено задачей. Условие возврата: если после включения графа на свежем PR 403 сохранится — разбирать права GITHUB_TOKEN/порядок публикации графа head-коммита.
