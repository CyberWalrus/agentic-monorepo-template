# B10. E2E toggle: ждать сеть перед reload

**Проблема.** `e2e/features/tasks/tasks.spec.ts:28-34`: `checkbox.check()` → `toBeChecked()` проходит на синхронном оптимистичном обновлении кэша (`setQueryData` в обработчике клика, `apps/web/src/features/tasks/use-tasks.ts:56-61`), а `page.reload()` может прервать ещё не долетевший POST `/rpc`; после reload состояние тянет сервер, где toggle может отсутствовать. Окно — миллисекунды на localhost, но `failOnFlakyTests` в CI (`e2e/playwright.config.ts:74`) превращает единичный случай в красный прогон «flaky».

## Что сделать

- Перед reload дождаться серверного подтверждения: `page.waitForResponse` на `/rpc` или проверка через API-request. «Ждать сеть перед навигацией» — обязательный паттерн для сценариев с оптимистикой.

## Решение

- **`waitForResponse`, а не polling через API-запрос.** Почему: дешевле — один сигнал на уже отправленный запрос, без второго клиента API в тесте.

## Критерии приёмки

- Тест зелёный на 20 повторов подряд (`repeat-each`); в сценарии нет ожиданий фиксированной длительности.

## Журнал

- 2026-11-20: заведена по итогам аудита обвязки (линза фронтенда). Флак прогоном не воспроизводился — вывод из чтения кода; повторы в критериях — чтобы убедиться. Номера строк — по состоянию дерева на дату аудита.
- 2026-11-20 (исполнение): в тест AC-2 (`e2e/features/tasks/tasks.spec.ts`) добавлен `page.waitForResponse` с матчером на URL `/rpc/tasks/toggle` — хук вешается до `checkbox.check()`, `await` стоит перед `page.reload()`. Матчер не «/rpc», а точный путь процедуры: RPCLink (@orpc/client 1.16.1, `toHttpPath`) дописывает `/tasks/toggle` к базовому `/rpc`, поэтому соседние запросы (`tasks/create`, refetch `tasks/list`) хук не ловят. Проверки «метод POST» и разбор тела не добавлены: все RPC-вызовы приложения POST (fallbackMethod), а статус ответа в матчере не фильтруется сознательно — упавший toggle должен упасть в reload-проверке, а не таймаутом хука.
- 2026-11-20 (исполнение): выбран вариант из раздела «Решение» — `waitForResponse` (без второго API-клиента в тесте). Альтернатива-фоллбек, если оRPC сменит форму URL: `waitForResponse((r) => r.url().includes('/rpc'))` + проверка тела ответа на id задачи. Паттерн «ждать сеть перед навигацией» в других сценариях не встречался; при появлении новой оптимистичной мутации в E2E — такой же хук до действия.
- 2026-11-20 (доказательства): критерий «20 повторов» — `pnpm e2e -- --repeat-each=20`: 200 passed (16.1s), AC-2 × 20 зелёные; `pnpm verify` PASS (11.2s), `pnpm verify --full` PASS (24.5s, включая e2e и perf). Ожиданий фиксированной длительности в сценарии нет (`waitForTimeout` отсутствует по всему e2e-правилу скила writing-tests).
