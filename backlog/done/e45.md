# E45. guard-bash: heredoc глушит хук — тело `<<EOF` вырезается до проверки правил

**Проблема.** `tools/analyze-command.ts:13`: `stripHeredocs` вырезает тело любого heredoc (`<<EOF … EOF`) до проверки правил, а `tools/hooks/guard-bash.ts:31` прогоняет через него сырую команду. Достаточно обычного `bash <<'EOF' … EOF`: внутри тела не видны ни force-push, ни `--no-verify`, ни обновление скриншот-базлайнов, ни запись в защищённый файл. Фальшивый фрейм работает так же: `echo "<<END"` первой строкой, дальше запрещённая команда, строка `END` — регулярка принимает строку в кавычках за начало heredoc и вырезает всё до `END`. Аудит владельца (2026-11-23, «Сначала чинить», находка 2) прогнал регулярки по строкам и настоящий хук (независимый критик пришёл к тому же). Записи в защищённые пути в шаблоне всё равно держат песочница и CI (ADR 0004); запреты `--no-verify`, force-push и обновления базлайнов в теле heredoc не ловит никто. Дыра гейта защиты прошла все гейты — строки в `docs/escaped-defects.md` нет.

## Что сделать

1. Регрессии в `tools/test/analyze-command.test.ts` и `tools/test/guard-bash.test.ts` (красные до фикса): heredoc с `git push --force`, `git commit --no-verify`, `playwright test -u` в теле; фальшивый фрейм с запрещённой командой после `echo "<<END"`. Контрольные (не должны ломаться): запись файла через `cat > file <<EOF` с безобидным телом; heredoc, где `EOF` — просто слово в строке.
2. Чинить в анализаторе, не в хуке. Тело heredoc — данные, только если их читает не интерпретатор: для `bash`/`sh`/`zsh`/`eval` (и по решению в «Журнале» — `node`, `python`, `perl`) тело анализируется как команды. Оператор `<<` распознавать в позиции оператора команды, а не внутри кавычек строки-аргумента.
3. Проверка настоящим хуком: саботаж «хук + `bash <<'EOF'` с `--no-verify`» обязан давать отказ (команда и вывод — в «Журнале»; проверка живёт в `tools/test/guard-bash.test.ts`, новым шагом verify не становится).
4. Замыкание: `tools/analyze-command.ts`, `tools/hooks/**`, `tools/test/**` — deny; `tools/protected-paths.json`, `tools/check-tool-class.ts`, `.claude/settings.json` — правятся тем же PR, если появляется новый файл гейт-контура (шаги `tool-class`, `sandbox` зелёные).
5. Строка в `docs/escaped-defects.md` тем же PR: дыра найдена аудитом, не канарейкой; в графе «что добавлено» — тесты из п.1.

## Решение

Логика остаётся в анализаторе, хук — тонкий адаптер (AGENTS.md, «Claude Code»: логика в `tools/`, хуки — тонкие адаптеры). Выбрано «тело интерпретатора — команды, тело записи файла — данные», а не «не вырезать heredoc вовсе»: второе даёт ложные отказы на каждой записи файла через `cat >`. Условие возврата: если после правки хук начинает отказывать на легитимных многострочных командах агентов чаще, чем раз в несколько сессий (по журналу отказов `tools/denial-journal.ts`), — сузить список интерпретаторов и записать в «Журнале».

Задача ведёт оператор (задача будет в режиме обслуживания): touches — `tools/analyze-command.ts`, `tools/hooks/**`, `tools/test/**`, замыкание (deny). Пересекается с e50 и e51 по `tools/analyze-command.ts`: кто мержит вторым — ребейз.

- 2026-11-24 — **решения** (что, почему, альтернатива, условие возврата):
  1. Список интерпретаторов: `bash`, `sh`, `zsh`, `eval` из задачи плюс `node`, `python`, `perl` — включены: их тело читает код, который может запустить любую команду (`child_process`, `subprocess`, `` `…` `` в perl), без них дыра «один heredoc» остаётся для `node <<'EOF'`. Плюс тот же интерпретатор под другим именем: `dash`, `ksh`, `mksh`, `fish`, `csh`, `tcsh`; `source` (`source /dev/stdin <<EOF`); `nodejs`, `tsx`, `ts-node`, `deno`, `bun`; `python2`, `python3`. Альтернатива — белый список читателей-«не интерпретаторов» (покрывает и неизвестных читателей) — не выбрана: длинный список и ложные отказы на неизвестных CLI. Условие возврата — из «Решения»: ложные отказы на легитимных многострочных командах чаще, чем раз в несколько сессий (журнал `tools/denial-journal.ts`) → сузить список.
  2. Где ищем интерпретатор: по всей команде вне тел heredoc'ов, а не только в команде-читателе. Тело дойдёт до интерпретатора конвейером (`cat <<'EOF'` с продолжением через `bash`), сценарием, записанным и запущенным той же командой, подстановкой процесса (`bash <(cat <<'EOF' …)`). Цена — редкий ложный отказ, когда интерпретатор назван в той же команде, а тело с запретным текстом пишется в файл. Альтернатива — только команда-читатель — не выбрана: три формы выше остаются дырой. Возврат — тот же критерий ложных отказов.
  3. `<<` — оператор только вне кавычек (включая `$'…'` с экранированием), комментария (`#` в начале слова), арифметики `(( … ))` и `${…}`: каждая из четырёх форм — фальшивый фрейм, на каждую есть регрессия. Here-string `<<<` heredoc'ом не считается. Альтернативы нет: регулярка позицию оператора не отличает.
  4. Разделитель читается как в оболочке (кавычки снимаются, `\x` экранирует): раньше `<<E"O"F` искал строку `E`. Незакрытый heredoc и разделитель с раскрытием (`<<$X`) остаются в разборе целиком — где кончается тело, неизвестно.
  5. Heredoc внутри двойных кавычек (`git commit -m "$(cat <<'EOF' … EOF` + перевод строки + `)"`) больше не вырезается — тело остаётся в разборе. Поведение изменилось: раньше регулярка его вырезала. Выбрано, потому что учёт `$(…)` внутри кавычек — второй уровень парсера с риском разъезда состояния кавычек (а это пропуск), а цена выбора — ложный отказ, только если в тексте сообщения коммита есть запретный токен или запись в защищённый путь. Условие возврата: такие отказы в журнале чаще, чем раз в несколько сессий → учесть `$(…)` внутри двойных кавычек.
  6. Без рекурсии в тело интерпретатора: вложенный heredoc внутри `bash <<'EOF'` не разбирается, всё тело — команды. Цена — ложный отказ на вложенном heredoc с запретным текстом; альтернатива (рекурсивный разбор оболочечных тел) — больше кода без пользы для критериев.
