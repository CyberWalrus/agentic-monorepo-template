**Проблема.** `tools/gate-canaries.ts:63`: для шага `boundaries` в массиве `CANARIES` пять канареек, а правил в `.dependency-cruiser.cjs` тринадцать (`product-not-to-tools`, `no-circular`, `packages-not-to-apps`, `no-app-to-app`, `e2e-black-box`, `ui-is-presentational`, `contracts-are-pure`, `no-cross-feature-imports`, `api-domain-independent-of-transport`, `web-lib-not-to-features`, `no-deep-package-imports`, `not-to-dev-dep`, `not-to-unresolvable`). По З6 каждый блокирующий шаг покрыт канарейкой — но покрыт шаг, а не правила: у восьми правил можно переименовать `name`, сузить `path` или понизить `severity` без единого сигнала. Так дыра e44 (мёртвые `ui-is-presentational`, `contracts-are-pure`, `not-to-dev-dep`) и осталась невидимой. Аудит владельца, 2026-11-23, «Средние → Гейты и защита».

## Что сделать

1. Инвентаризация в «Журнале»: таблица «правило → канарейка (`name`, `expect`)» по всем 13.
2. Канарейка на каждое правило без неё (после e44); для правила, которое на текущем дереве нельзя осмысленно саботировать, — причина в «Журнале».
3. Инвариант в `tools/test/gates-canary.test.ts`: у каждого правила гейт-контура зависимостей есть канарейка с `expect` на его `name`; новое правило без канарейки красит тест — счёт больше не разъедется.
4. Замыкание: `tools/protected-paths.json`, `tools/check-tool-class.ts`, `.claude/settings.json` — правятся тем же PR, если появляется новый файл гейт-контура (шаги `tool-class`, `sandbox` зелёные). Эти три пути в `touches` не объявлены (2026-11-24, волна seed-D7): понадобятся — мини-PR расширения touches до правки.

## Критерии приёмки

- Таблица в «Журнале»: у каждого из 13 правил канарейка или записанная причина.
- Инвариант из п.3 красный при удалении любой канарейки (саботаж — в «Журнале»), зелёный на текущем дереве.
- pnpm canaries зелёный в CI (job `canaries`); pnpm verify зелёный; шаги `tool-class` и `sandbox` зелёные.

## Решение

Покрытие по правилам, а не по шагу: канарейка шага доказывает «шаг умеет падать», но не «каждое правило живо». Альтернатива — генерировать канарейки из списка правил автоматически — отклонена как переусложнение: саботаж для каждого правила свой. Условие возврата: если прогон канареек выходит за бюджет job `canaries` — канарейки правил пускать в ночном прогоне, а в PR оставить по одной на шаг; решение и замеры записать в «Журнале».

Задача ведёт оператор (задача будет в режиме обслуживания): touches — `tools/gate-canaries.ts`, `tools/test/**` (deny); условное замыкание в touches не объявлено (2026-11-24, волна seed-D7; понадобится — мини-PR расширения touches).

  - **Причина для `no-deep-package-imports` (п. 2).** Правило недостижимо на текущем дереве, проверено прогонами dependency-cruiser 18.8.0 с пробами (потом убраны): (1) `apps/api/src/evil-deep-probe.ts` с импортом `@repo/contracts/src/evil-deep-target` даёт единственное нарушение — `not-to-unresolvable` (у модуля `couldNotResolve: true`): подпуть вне exports-карты (`{".": "./src/index.ts"}`) не разрешается; (2) единственный подпуть в exports-картах, `@repo/ui/tokens.css`, из `apps/web/src/lib/` разрешается в `packages/ui/src/tokens.css` — симлинк раскрыт (`preserveSymlinks: false` в `optionsUsed`); модулей с путём `node_modules/@repo/` в графе 0. Значит, `to.path: 'node_modules/@repo/[^/]+/.+'` не совпадёт ни с одним разрешённым модулем, и саботаж «глубокий импорт» всегда уходит в `not-to-unresolvable`. Закон (architecture.md, 2.1, «Пакет импортируется только через `exports`») фактически держат exports-карты пакетов и `not-to-unresolvable`. Правило внесено в вайтлист инварианта (`BOUNDARIES_RULE_CANARY_EXEMPT`) с этой причиной. **Нужно решение человека** (конфиг — deny, вне `touches`): убрать мёртвое правило или переписать под разрешённые пути — отдельной задачей; пока правило недостижимо, канарейки на его имя быть не может. Канарейка «глубокий импорт пакета» (`expect: /not-to-unresolvable/`) страхует закон: открой в `exports` подстановку подпутей — импорт разрешится, шаг останется зелёным, канарейка скажет «НЕ УПАЛ».
