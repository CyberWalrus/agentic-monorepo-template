# C9.1. Эталонные задачи: раннер агентных прогонов

**Проблема.** Метрики системы из vision (доля агентных PR без ручных правок, время, итерации) не собираются: нет эталонных задач, на которых их мерить. Аудит трендов 2026-11-14 назвал evals первоочередным гэпом.

## Что сделать

- Набор типовых фич («добавь удаление задачи», «добавь срок») как эталонные сценарии в `tools/` или `docs/`.
- Раннер: агент без участия человека выполняет эталон в чистом worktree; измеряется — дошёл ли до зелёного `verify --full`, число итераций, время, расход токенов.
- Запускать при изменении `.claude/`, `AGENTS.md`, `tools/` и раз в неделю; в каждом PR не нужно (дорого).
- Результаты пишутся в артефакт прогона, тренд — в отчёт nightly.

## Критерии приёмки

- Прогон одного эталона воспроизводим: два запуска подряд дают сопоставимые числа; отчёт содержит все четыре метрики.

## Журнал

- 2026-11-19 захват оператором (`start --operator`), перенос в `done/`, режим обслуживания включён 18:40 UTC.
- 2026-11-19 режим обслуживания выключен <время до PR>.

### Решение (ADR 0009, раздел «Развилки»)

**Выбран вариант:** эталонный раннер как L5-контур `tools/evals/` (не шаг verify), класс защиты `deny` по замыканию контура (ADR 0014), сценарии — markdown с frontmatter, агент по умолчанию — Claude Code headless (`claude -p --output-format json`), адаптер отделяет разбор результата от команды.

**Почему:** (1) тяжёлый агентный прогон в каждом PR противоречит условию задачи; это измерение после merge, как у тренд-job nightly (тот же класс исключения З5 — «не в каждом PR», но семантика пост-merge, не канареечная): пуш в `main` с путями `.claude/**`, `AGENTS.md`, `tools/**` + недельный cron. (2) Ссылка workflow на `tools/evals/run.ts` попадает в замыкание гейт-контура — по ADR 0014 файлы раннера получают `deny` (`tools/evals/*.ts`) и `KNOWN_GATES` тем же PR, как `backlog-doctor.ts` для nightly; сценарии `.md` — данные, а не контур merge: остаются под review-классом blanket `tools/**` (находка architecture/sanity-ревью: blanket `tools/evals/**` уронил бы гейт tool-class — .md вне замыкания). (3) Метрика «дошёл до зелёного» считается самим раннером (`pnpm verify --full` в worktree после выхода агента), а не самоотчётом агента — иначе метрика доверяет проверяемому. (4) Сценарии — фичи, которых в продукте ещё нет: «срок задачи» (dueDate) и «приоритет задачи» (low/medium/high); «удаление задачи» из примера задачи уже реализовано (c2.3). (5) Поставка CLI в CI — `pnpm add -g @anthropic-ai/claude-code@<pin>` в evals.yml (версия пин-литералом в workflow, З10): `pnpm add` — встроенная команда, гейт tool-class пропускает её как `pnpm install`; отклонены обход парсера через composite action (игра с гейтом) и devDependency (тяжёлая каждому worktree). (6) Сценарий без guards отсутствия фичи — метрика тихо инвертирует смысл, когда фичу реализуют обычным PR (находка architecture-ревью): frontmatter обязан объявлять `guards-not-present`, раннер перед прогоном проверяет продуктовый код и громко отказывает.

**Альтернатива:** гейт в `pnpm verify` каждого PR — отвергнута: минуты агента и доллары токенов на каждый PR, задача прямо говорит «в каждом PR не нужно».

**Условие возврата:** если прогон в CI окажется дороже недельного бюджета или раннер начнёт флейпить у границ цены — сузить до одного сценария за прогон (ротация) или перевести на ручной dispatch.

### Протокол AC (записан до прогонов, находка sanity-ревью)

Два запуска сценария `due-date` подряд: один коммит, один и тот же локальный claude CLI, сырые отчёты целиком прикладываются к PR. Критерий сопоставимости: `pass` совпадает; `timeMs`/`tokens` — один порядок величины; расхождение `iterations` фиксируется как первая оценка вариативности раннера (подгонка/перезапуски до похожих чисел запрещены — расхождение честно пишется в журнал).

### Калибровка таймаута (2026-11-19, до AC-прогонов)

Первый пробный прогон (base 464ebdb, claude 2.1.267, дефолтная модель) упёрся в таймаут агента 45 мин: 29 файлов правок, агент был в фазе собственных проверок — полный стек-эталон с холодным worktree (турбо-кэша в свежем worktree нет) не укладывается в 45 мин. Прогон отбракован как калибровочный, в AC не идёт. Таймаут агента поднят до 90 мин (дефолт раннера), job CI — 150 мин; оба AC-прогона идут с одного коммита с этим дефолтом.

### AC-прогон 1 (2026-11-19, base 860c2bc)

**FAIL** — агент отчитался «готово», но verify раннера красный (код 1). Четыре метрики в отчёте `reports/evals-ac/report-2026-11-19T20-00-17.645Z.json`: pass=false, iterations=207, timeMs=5121с, tokens=23 181 313 (каноническая сумма: вход+выход+оба кэша — доминирует cache-read). Агент в worktree вёл себя по правилам шаблона: 4 атомарных коммита контракт→API→UI/e2e→храповик тест-каунта (пин `evals-ac1-agent-final` = 3f6c3d5), дерево чистое перед финальным verify. Причина красного без диагностики неизвестна — **находка для раннера: на FAIL сохранять хвост вывода verify в отчёт** (worktree убран, воспроизводить причину дорого). Диагностика финала агента — после AC-прогона 2 (чтобы не грузить машину посреди сопоставимого замера).

### План

1. `tools/evals/`: `run.ts` (CLI-оркестрация + ядро `runEvals` для тестов), `agent.ts` (команда + разбор JSON Claude Code: num_turns, usage, duration), `scenarios.ts` (поиск/разбор frontmatter + guards, без зависимостей — идиома tools; комментарий «почему не parseTask»), `worktree.ts` (чистый detached-worktree от HEAD + удаление), `exec.ts` (spawn: stdin/stdout/таймаут), `report.ts` (схема отчёта: pass/iterations/timeMs/tokens + контекст коммита, промпта, агента).
2. Сценарии `tools/evals/scenarios/{due-date,task-priority}.md`: frontmatter с обязательным `guards-not-present` (идентификаторы, которых не должно быть в продуктовом коде), пользовательская история + критерии + «зелёный `pnpm verify --full`» как DoD; промпт требует прочитать AGENTS.md и не трогать защищённые пути.
3. Тесты `tools/test/evals-*.test.ts` (попадают в `test:hooks`/verify, бюджет 50 с): разбор результата агента, frontmatter/guards, интеграционный — `runEvals` на временном мини-репозитории с заглушками агента/install/verify (инлайн-фикстуры в tmp, без файлов в репо и без касания .git основного репо).
4. `.github/workflows/evals.yml`: push в main с путями `.claude/**`, `AGENTS.md`, `tools/**` + недельный cron + dispatch; concurrency-группа; job `evals` скипается без секрета `ANTHROPIC_API_KEY` (env-косвенность, секрет ставит человек), при скипе по cron/dispatch — напоминание в tracking-issue; job `report` заводит issue при падении (по образцу nightly); CLI — `pnpm add -g @anthropic-ai/claude-code@<pin>` (пин в env workflow); таймаут job как бюджет (З6); артефакт `evals-<run_id>`, retention 90 (схема — для c9.4, тренд-отчёт собирает она).
5. `tools/protected-paths.json`: deny += `tools/evals/*.ts`; `tools/check-tool-class.ts`: KNOWN_GATES += `tools/evals/run.ts`; knip.json entry += `tools/evals/*.ts`; `package.json`: скрипт `evals`; `docs/adr/0016-agent-evals.md` + обновление `docs/architecture.md` (§3.1, исключение З5, §5) тем же PR; `docs/evals.md` (контур, метрики, guards, как добавить сценарий — обычный PR, файлы .md review-класса); строка в таблице команд AGENTS.md.
6. AC: два реальных прогона сценария `due-date` подряд локально (claude CLI) по протоколу выше, все 4 метрики в отчёте.
