# E2. Замер CI по первым 45 PR против бюджетов vision

**Проблема.** `docs/vision.md` задаёт бюджеты контуров: L3 (PR) — p50 меньше 10 минут, L4 — p50 меньше 15 минут. В таблице 3.1 `docs/architecture.md` напротив L3 и L4 до сих пор стоит «в CI не измерялось», хотя через CI прошло 45 PR. Цель G3 («проверки быстрые») подтверждена только локально. Неизвестно и то, сколько прогонов перезапускалось, — единственный доступный сейчас косвенный признак флаков (цель G4).

## Что сделать

- Собрать историю прогонов `ci.yml`, `gate-integrity.yml` и `nightly.yml`: `gh run list` и `gh run view --json jobs` по всем PR с начала репозитория.
- Посчитать p50 и p95 длительности: всего прогона и каждой job (`static`, `unit`, `mutation`, `e2e`, `visual`, `perf`, `gate`); отдельно — холодный и тёплый кэш, если различимы.
- Посчитать долю прогонов с перезапуском (`run_attempt > 1`) и долю красных прогонов, ставших зелёными без изменения кода, — нижняя оценка flaky rate.
- Сравнить с бюджетами vision; назвать самую долгую job и что в ней занимает время.
- Результат: `docs/research/2026-11-ci-timing.md` с таблицей и командами сбора (чтобы замер можно было повторить) и таблица 3.1 `docs/architecture.md` без «не измерялось».

## Что учесть

- Нужен доступ к GitHub API. В песочнице Claude Code сеть до GitHub закрыта (ADR 0004) — задачу берёт сессия, у которой `gh` работает (ZCode), либо человек выполняет команды сбора и отдаёт вывод.
- Это разовый снимок. Постоянный сбор — задача C9.4; здесь не строить телеметрию.
- Если бюджет превышен — не чинить в этой задаче, а завести задачу с доказательством.

## Критерии приёмки

- В `docs/research/2026-11-ci-timing.md` — p50 и p95 по прогонам и по job, доля перезапусков, команды сбора.
- В таблице 3.1 `docs/architecture.md` у L3 стоит измеренное значение и вывод «в бюджете» или «превышен».
