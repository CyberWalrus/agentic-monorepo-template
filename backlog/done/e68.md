# E68. API: состав /health и глобальный тестовый сброс

<!-- 2026-11-24: depends_on: e72 — работа вне доски, волна seed-D7. Задача объявляет docs/architecture.md; пока D7 считает этот путь пересечением (правка — задача e72), такие задачи захватываются по одной. e72 отклонена или остановлена — зависимость снять тем же PR. -->

**Проблема.**

- `apps/api/src/app.ts:240`: `/health` отвечает `{ status: 'ok', instance: instanceId ?? null }` — публичный эндпоинт отдаёт идентификатор экземпляра (`INSTANCE_ID`).
- `apps/api/src/app.ts:282`: `POST /__test__/reset` без workspace-заголовка стирает все workspace (легаси-семантика общего сброса, `apps/api/src/tasks/repository.ts:112-114`): в тестовом окружении одна забытая шапка в параллельном тесте очищает чужие данные.

Аудит владельца, 2026-11-23, «Низкие → Безопасность и стабильность». Строк в `docs/escaped-defects.md` нет.

## Что сделать

1. `/health`: убрать `instance` из публичного ответа либо отдавать его только на внутреннем эндпоинте диагностики; потребность в `instanceId` закрыть логами и метриками (`apps/api/src/observability.ts`). Если `/health` описан в спеке — перегенерировать `openapi.json` (путь в touches нет — расширить отдельным PR в main до такой правки).
2. `/__test__/reset` без заголовка — отказ с названием причины (400); глобальный сброс — только явным запросом (явный заголовок или параметр). Обновить потребителей: `e2e/fixtures.ts`, `e2e/global-setup.ts`.
3. Тесты (`apps/api/src/app.test.ts`): состав `/health`; сброс без заголовка не трогает данные и отвечает 400; явный глобальный сброс работает.
4. В `docs/architecture.md` — контур тестового API (если описание меняется).
5. Строка в `docs/escaped-defects.md` тем же PR.

## Критерии приёмки

- В ответе `/health` нет идентификатора экземпляра (тест зелёный).
- Сброс без заголовка не стирает данные (тест красный до правки); e2e и интеграционные тесты зелёные на новом контуре.
- pnpm verify зелёный; строка добавлена в `docs/escaped-defects.md`.

## Решение

Публичный эндпоинт отдаёт минимум, тестовый сброс требует явного намерения: оба изменения сужают поведение без изменения продуктовых сценариев. Условие возврата: если глобальный сброс нужен смокам окружения (документация развёртывания) — оставить его за явным заголовком и описать в `docs/architecture.md`, а не возвращать молчаливый сброс.

- 2026-11-25 — **Развилка «куда девать идентификатор экземпляра» — решение.** Выбрано: публичный `/health` отвечает только `{ status: 'ok' }`, без условий; идентификатор живёт в двух внутренних местах — штамп `instanceId` в каждой записи лога (`createLogger({ instanceId })`, `apps/api/src/observability.ts`) и `GET /__test__/instance` под флагом тестового API (`{ status: 'ok', instance }`), откуда его читает global setup Playwright (гейт «свой сервер», З9; `tools/instance.ts` не менялся). Почему: закрывает обе находки сразу — публичный ответ минимален в любом режиме, гейт «свой сервер» сохраняет прежнюю диагностику (чужой токен → «belongs to another instance»). Альтернатива — условный `/health`, где `instance` появляется только при включённом тестовом API, без нового маршрута, — отклонена: защита та же (раскрытие ⇔ тестовый API), но публичный маршрут узнал бы о тестовом режиме, а критерий «в `/health` нет идентификатора» выполнялся бы с оговоркой. Условие пересмотра: понадобится видеть идентификатор публично (диагностика развёрнутых реплик) — отдельный внутренний эндпоинт за явной настройкой, через ADR; в `/health` не возвращать.
- 2026-11-25 — **`/__test__/reset` — решение.** Носитель явного намерения — поле тела `"scope": "global"` (не заголовок и не query): тело и так строгий контракт эндпоинта (`strictObject`), а поле нельзя незаметно унаследовать от клиента или контекста, как заголовок. Таблица: валидный `x-workspace-id` → сброс одного workspace; `"scope": "global"` без валидного заголовка → всё хранилище; без заголовка и без `scope` → 400 «Reset scope is not named…»; мусорный заголовок без `scope` → 400 «Invalid x-workspace-id header…» (прежде парсился в `null` и стирал всё — вторая дверь к той же порче); валидный заголовок вместе с `scope` → 400 «Ambiguous reset scope…»; неизвестное значение `scope` → 400 «Invalid seed data». Тело валидируется раньше сферы — прежние отказы не изменились. Уровень репозитория не тронут: `reset(tasks, undefined)` по-прежнему значит «всё хранилище», явность требует только HTTP-слой. Альтернатива — заголовок `x-reset-scope: all` — отклонена: заголовки распространяются с клиентом и контекстом. Условие возврата — как в разделе «Решение»: глобальный сброс остаётся за явным запросом, молчаливый не возвращается.
