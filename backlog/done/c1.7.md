# C1.7. API hardening: таймауты пула, лимит тела, двойные guard'ы

**Проблема.** Образец «продакшн-хранилища» пропускает класс дешёвых страховок (аудит 2026-11-20, линза бэкенда): пул Postgres без таймаутов (`apps/api/src/tasks/database.ts:22-26` — зависший запрос держит соединение вечно, дефолтный `max` — 10); `/rpc` и `/api` читают произвольный JSON без `bodyLimit` и таймаута запроса (`app.ts:145-179`); guard «не в production» у тестового API исполняется только в `loadServerEnv`, а `createApp({ enableTestApi: true })` сам `NODE_ENV` не проверяет (`server-config.ts:63-71`, `app.ts:167-179`) — другой вход поднимет reset-эндпоинт в проде.

## Что сделать

- Пулу — явные `max`, `connectionTimeoutMillis`, `idleTimeoutMillis`, `statement_timeout`.
- `bodyLimit` и таймаут-мидлварь на API-маршрутах.
- Дубль-проверка production-запрета внутри `createApp` (defence in depth).
- `z.strictObject` для reset-сидирования: опечатка в e2e-фикстуре должна давать громкий 400, а не молчаливый стрип (`z.object` стрипает лишние ключи).
- Тест на поведение owner-процедур: не-uuid `id` в `tasks.remove` отвечает 403 — авторизация исполняется до валидации входа (проверено чтением dist oRPC 1.16.1), и потребитель не отличит «битый формат» от «нет доступа»; поведение закрепить тестом и пометкой в описании операции контракта.
- Опционально отдельным шагом: индекс под `ORDER BY created_at DESC` и пагинация list (сейчас full scan без LIMIT).

## Решение

- **bodyLimit константой в коде, без env-ручки.** Почему: потолок — свойство контракта, а не настройка развёртывания; env-ручка — место дрейфа между окружениями.
- Условие возврата: реальному потребителю понадобится другой потолок — заводим переменную окружения с валидацией в env-модуле.

## Критерии приёмки

- Тесты: тело сверх лимита отклоняется, `createApp` с тестовым API при production бросает на старте, лишнее поле в reset — 400, не-uuid id — 403.

  - **Пул** (`tasks/database.ts`): экспортированный `TASK_POOL_OPTIONS` — `max: 10` (явная ёмкость вместо дефолта), `connectionTimeoutMillis: 5_000`, `idleTimeoutMillis: 30_000`, `statement_timeout: 15_000`. Значения закреплены unit-тестом «как контракт» (по образцу ключа advisory-лока) и integration-тестом `SHOW statement_timeout` на настоящем Postgres (`test/task-pool.test.ts`) — доказывает, что Pool доводит настройку до сессии.
  - **HTTP-границы** (`app.ts`): hono-мидлварь `bodyLimit` (дефолт `REQUEST_BODY_LIMIT_BYTES = 1 МиБ`) и собственный таймаут-мидлварь (дефолт `REQUEST_TIMEOUT_MS = 30_000`, гонка «обработчик vs таймер», ответ 504) на `/rpc/*`, `/api/*` и `/__test__/*`. Таймаут больше `statement_timeout`: медленная СУБД сначала отвечает ошибкой через oRPC, 504 остаётся зависаниям вне БД. RPCHandler oRPC 1.16.1 не принимает `signal` (проверено типами `StandardHandleOptions`), поэтому обработчик не прерывается — БД-часть добивается `statement_timeout`. Инъекции `bodyLimitBytes`/`requestTimeoutMs` в `AppOptions` — только для тестов, не env-ручки.
  - **Дубль-guard** (`server-config.ts`): `assertTestApiNotInProduction` зовётся в `createApp` до любых маршрутов; чтение `process.env['NODE_ENV']` осталось в env-модуле (C3.0); текст совпадает с первым рубежом.
  - **strict reset** (`app.ts`): `z.strictObject` и для тела, и для формы seed-задачи (`TaskSchema.shape`) — лишний ключ даёт 400 с `unrecognized_keys` на пути объекта-нарушителя (особенность zod v4 отмечена в тесте). E2E-фикстуры (`e2e/fixtures.ts`) шлют ровно контрактную форму — не сломаны.
  - **Контракт** (`packages/contracts/src/tasks.ts`): у `remove` — `description` в OpenAPI «Authorization runs before input validation: malformed id → 403 FORBIDDEN…»; `openapi.json` перегенерирован. Поведение закреплено тестами обоих транспортов (REST 403, RPC FORBIDDEN на не-uuid).
