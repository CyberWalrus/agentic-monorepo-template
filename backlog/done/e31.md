# E31. Ночной контур: браузер Playwright не установлен на раннере

**Проблема.** Ночь 45013082390 (2026-11-22), три джобы красные с одной вероятной причиной:

- «test count ratchet»: `@repo/ui#test` падает — `browserType.launch: Executable doesn't exist at /home/runner/.cache/ms-playwright/chromium_headless_shell-1255/...` — браузерной сборки 1255 нет ни в кэше, ни установленной на раннере.
- «e2e flake hunt»: playwright-шаг (continue-on-error) не запустил тесты по той же причине, после чего `tools/check-flaky-rate.ts:140` упал на пустом/битом flake.json — каскад.
- PR CI в тот же день зелёный (visual 48 с, e2e 31 с в проверках PR #154) — значит, расхождение в установке/кэше браузера именно у ночных джоб: либо шаг установки отсутствует, либо cache-ключ не учитывает версию браузера Playwright (меняется с обновлением пакета, а не lockfile).

## Что сделать

1. Диагноз: сравнить setup ночных джоб с setup ci.yml (общий ли action, какие шаги установки браузера, ключи кэша); найти, когда началось (между ночами 44722046495 — зелёный flake hunt — и 44894601530 — красный).
2. Фикс установки браузера (шаг `playwright install` с правильным cache-ключом или без кэша) так, чтобы и PR CI, и ночь ставили одну и ту же сборку.
3. Устойчивость `tools/check-flaky-rate.ts` к отсутствию/битому flake.json — отсутствие данных не должно крашить чекер с неинформативной ошибкой (З11); сообщение обязано называть причину.
4. Диспетч ночной — «test count ratchet» и «e2e flake hunt» зелёные (flaky-тесты, найденные честным прогоном, — отдельные issues по контуру b4.4, это не краснота джобы).

## Решение

Править общий setup так, чтобы одна причина работала в обоих контурах; дублирование шага установки только в nightly отклонено как источник следующего расползания. Условие возврата: если окажется, что ci.yml использует другой путь установки — синхронизировать оба на один action.

## Критерии приёмки

- Диспетч ночной: «test count ratchet» и «e2e flake hunt» зелёные.
- check-flaky-rate на пустом входе пишет внятную причину, а не стек.
- PR CI (обычный прогон) остаётся зелёным.

Гипотеза задачи («браузера нет на раннере у обеих джоб») подтвердилась наполовину:

Джоба появилась в `aae6d1ae` (A10 #109) между ночами 13 (20.11) и 14 (21.11) — и **с первого прогона красная**: в nightly.yml setup вызван БЕЗ `playwright: 'true'`, шаги Cache/Install Chromium `outcome=skipped` (логи run 14 и 15), `pnpm turbo run test` падает на `@repo/ui#test`: `Executable doesn't exist ... chromium_headless_shell-1255` (run 15, на Playwright 1.65.1; run 14 — `-1248` на 1.64.1). Локальная сверка: каталог Playwright 1.65.1 = сборка chromium 1255 — ошибка соответствует версии из lockfile, кэш-ключ (`hashFiles('pnpm-lock.yaml')`) при бампе C11 обновился корректно. Фикс: флаг в вызове setup — как у job unit ci.yml.
- **B — e2e flake hunt**: НЕ браузер (Install Chromium `outcome=success`, кэш восстановлен). Две независимые причины, обе внесены тем же окном (e717f44c..f56aeb8d):
  - **B1** — гонка канарейки отчётов API (`e05f8605` c4 #103, тест появился между ночами): при `--repeat-each=5 --shuffle` два повтора теста идут параллельно и делят `e2e/reports/instance-token` (перерезапись между записью живого значения и чтением её дочерним прогоном → «belongs to another instance») и `test-results-canary` (старт дочернего прогона чистит outputDir соседа → «attachment file does not exist»). Воспроизведено локально: `--workers=2` → 2 failed + 1 flaky (18.3с, та же сигнатура, что в CI), `--workers=1` → 60 passed (30.9с). Фикс: `--workers=1` в строке nightly (серийность детерминированная, shuffle и repeat-each остаются; параллельные гонки повторов продолжает ловить PR CI).
  - **B2** — путь flake.json: `pnpm --filter @repo/e2e exec` исполняет команду в каталоге пакета (проверено: `pnpm --filter @repo/e2e exec pwd` → `…/e2e`), поэтому `PLAYWRIGHT_JSON_OUTPUT_NAME=e2e/reports/flake.json` писал бы `e2e/e2e/reports/flake.json`; чекер читает `e2e/reports/flake.json` от корня → ENOENT был бы даже на зелёном playwright-шаге. Фикс: путь от пакета `reports/flake.json`.
- **C — каскад чекера**: `tools/check-flaky-rate.ts` (строка 140 в версии ночи) падал `ENOENT`-стеком на отсутствующем отчёте; то же случилось бы на битом JSON.

### 2026-11-22, решение по тесту чекера (эскалация владельцу)

Автотест фикса C обязан лежать в `tools/test/check-flaky-rate.test.ts` (конвенция tools/test), но:

- путь не входит в touches задачи, а branch-scope читает touches из main (проверено эмпирически: probe-файл в tools/test/ красит гейт, выход гейта — «расширь touches PR-ом в main»);

- пуш и PR протоколом задачи запрещены.

Решение владельца (эскалация): **вариант (б)** — тест в этот PR не включать; фикс C верифицируется ручными прогонами (выше); автотест — отдельной задачей **e36** (touches: `tools/test/check-flaky-rate.test.ts`, depends_on e31), которую владелец ставит в операторскую очередь. В теле PR/«Как проверено» указать: «автотест классификации ответов — задача e36, D7-ограничение touches».
