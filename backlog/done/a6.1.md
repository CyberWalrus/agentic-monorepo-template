# A6.1. PR-3 задачи A6: ночное медианное сравнение времени

Продолжение [A6](a6.md) после смерженного PR-2 (#63): временнóй канал остаётся
открытым — 200-миллисекундную задержку в обработчике в PR не ловит ни одна метрика
(записанное решение человека в [ADR 0006](../../docs/adr/0006-perf-strategy.md)).

## Что сделать

По плану из журнала a6 (2026-11-14, решения человека):

1. Артефакт `perf-baseline` (отчёт `e2e/reports/perf.json` + SHA прогона) пишет job
   `perf-trend` nightly, и только при зелёном сравнении — иначе база не двигается.
2. `tools/check-perf-trend.ts`: сравнение кандидата с последним зелёным базлайном.
   Допуски: запросы — точное совпадение; байты — `maxPrGrowthKb`; время —
   max(абсолютный floor, %), калибровка 20-прогонной валидацией; long tasks —
   медиана + 1. Метрика отсутствует в кандидате или базе — красный (fail-closed).
3. `nightly.yml`: permissions += `actions: read` (чтение артефакта базлайна).
4. Предел свежести базлайна: старше 7 дней или больше 20 зелёных прогонов подряд —
   issue, сравнение не молчит.
5. Первый запуск — «baseline recorded», зелёный.
6. Канарейка 200 мс — job `perf-canary` в nightly (инверсия: красное сравнение =
   job зелёный).
7. Красное сравнение → issue с диапазоном `baseline-SHA..head-SHA`, владельцем из
   CODEOWNERS и дедупом по открытому issue с label `perf-regression`.
8. Валидация 20× без изменений покрывает все сравниваемые метрики.

## Критерии приёмки

- Канарейка (+200 мс в обработчике create-task) делает сравнение красным, job
  `perf-canary` при этом зелёный (инверсия).
- Двадцать прогонов без изменений не дают ни одного ложного падения (все
  сравниваемые метрики).
- Решения записаны в ADR (ADR 0006, строка уровня 2; расхождения с планом — в
  журнале задачи).
