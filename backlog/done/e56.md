# E56. Спека OpenAPI: формы ошибок и список операций с 400 разошлись с рантаймом

**Проблема.** `packages/contracts/scripts/openapi-spec.ts`:

- `:71-73` — тело 400 объявлено с `required: ['defined', 'code', 'status', 'message', 'data']`, но 400 на битый JSON (ошибка парсинга тела) приходит без обязательного `data`; ответы 413 и 504 другой формы и в спеке не описаны.
- `:33` — `OPERATIONS_WITH_INPUT_VALIDATION` ведётся руками (`POST /tasks`, `POST /tasks/{id}/toggle`); `pnpm gen feature` создаёт домен с валидацией входа, но в список его не добавляет — у сгенерированного домена 400 в спеке отсутствует.
- `:148` — `info.version: '0.0.0'`: версия API не ведётся.

Гейт дрейфа сверяет артефакт с генератором, а не с рантаймом, поэтому всё прошло. Аудит владельца, 2026-11-23, «Средние → Контракты» и «Низкие → Контракты» (три находки в одном файле).

## Что сделать

1. Зафиксировать форму реальных ответов тестом на рантайме API (`apps/api/src/app.test.ts`): битый JSON, тело сверх лимита, таймаут — дословно; формы 400, 413 и 504 в спеке вывести из них: 400 без `data` описать отдельной схемой (`oneOf`), 413 и 504 добавить.
2. `OPERATIONS_WITH_INPUT_VALIDATION` вычислять из роутера контракта (процедуры с валидируемым входом, где 400 достижим), а не вести руками; тест — у каждой такой процедуры в спеке есть 400. Альтернатива (шаблон генератора дописывает запись) делает задачу операторской: `tools/gen.ts`, `tools/test/gen.test.ts` в touches нет.
3. `info.version` — по решению в «Решении»; источник версии один.
4. Перегенерировать `openapi.json` (`pnpm --filter @repo/contracts openapi`); гейт дрейфа и `openapi-compat` зелёные — если гейт красит снятие обязательности `data` или новые ответы как breaking, разобраться по правилам гейта, не ослабляя его.
5. Строка в `docs/escaped-defects.md` тем же PR.

## Критерии приёмки

- Тесты рантайм-форм из п.1 зелёные и совпадают со спекой (`openapi-spec.test.ts` сверяет формы с теми же фикстурами).
- У каждой процедуры с валидируемым входом в `openapi.json` есть 400; тест красный при добавлении процедуры без 400.
- Версия в `info.version` берётся из одного источника, либо «не ведётся» зафиксировано осознанным комментарием (записать в «Журнале»).
- Гейт дрейфа зелёный; строка добавлена в `docs/escaped-defects.md`; pnpm verify зелёный.

## Решение

Спека выводится из рантайма и из роутера, а не из ручных списков: ручной список расходится с генератором по построению. Для версии по умолчанию — версия из ответов copier, если скрипту они доступны; иначе `0.0.0` остаётся с комментарием «версия не ведётся до первого потребителя». Условие возврата: у потребителей появляется потребность в независимой версии API — семвер контракта через ADR.

- 2026-11-25 — правки по двум обязательным находкам ревью (обе major, обе подтверждены на проводе — оспаривать нечего).   - **Находка 1 — спека не описывала достижимые ответы.** Подтверждено: `DELETE /api/tasks/{id}` с битым телом → 400 (`malformedBody`); `POST /api/tasks/{id}/toggle` и `DELETE /api/tasks/{id}` с телом сверх лимита → 413 — в спеке их не было. Решение — вариант «а» ревью: ответы HTTP-слоя вешаются по методу, а не по объявлению операции (`documentErrorResponses`): 413 и 400 на битое тело — методам, которым адаптер передаёт тело (все, кроме GET и HEAD); 504 — всем; 400 теперь у каждой операции, и варианты у неё только достижимые — валидация операциям из `operationsWithInputValidation`, у remove (owner) только битое тело, потому что валидацию опережает FORBIDDEN. Условие возврата: у метода с телом появляется клиент без потока тела при объявленном теле — тогда 400 ограждения вешается и на него.
  - **Найдено при проверке находки 1 (ревью GET оставил непроверенным).** На настоящем адаптере GET с объявленным телом (`Content-Length` или `Transfer-Encoding`) → `400 {"error":"Request body is not readable"}`: поток тела адаптер для GET и HEAD не передаёт, ограждение формы отвечает до лимита и до процедуры — 413 и битое тело для GET недостижимы. Тем самым сработало условие возврата из записи выше («найдётся клиент, который его получает»): фикстура `errorResponses.unreadableBody` добавлена, у GET 400 описывает ровно её.
  - **Находка 2 — `hasValidatedInput` давал ложное отрицание.** Подтверждено, в том числе на проводе (фикстурный домен через настоящий `OpenAPIHandler`): `.optional()` и `.default()` принимают `undefined`, но `POST` с `{"q":"a"}` → 400 валидации, а спека 400 не обещала. Признак теперь: схема отвергает хотя бы одну пробу из фиксированного набора `INPUT_PROBES` (`undefined`, `{}`, `[]`, `null`, `''`, `0`, `false`). Уточнение попутно: `z.void()` валидирует — `POST` с любым непустым телом → 400 (прежний комментарий «через z.void() 400 не получить» неверен); не валидируют только схемы, принимающие всё (`z.any()`, `z.unknown()`), и процедуры без входа. На настоящем контракте список операций с 400 валидации не изменился (`POST /tasks`, `POST /tasks/{id}/toggle`). Остаточный риск осознанный: схема, принимающая все пробы, но отвергающая что-то ещё, считается не валидирующей; условие возврата — первый такой случай, набор проб расширяется.
  - **Тавтология в тестах снята.** `documents 400 for every computed operation and for no other` сравнивал спеку с той же функцией, что её строит. Заменено ожиданием, записанным руками, и независимой свёрткой (`answers400`): какие из трёх форм 400 с провода пропускает схема ответа операции. То же для 413. Красный, если операция отвечает недокументированным статусом, — в том числе при добавлении процедуры с валидируемым входом без 400 (критерий приёмки).
