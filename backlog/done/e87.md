## Решение

- **По обоим шагам — пересчёт от факта раннера, а не разгон шага (вариант по умолчанию).** Для `lint` ускорять нечего: входы линтера между `de9ce87a` и `6997ff4d` не менялись (`git diff --stat de9ce87a..6997ff4d -- .oxlintrc.json package.json pnpm-workspace.yaml pnpm-lock.yaml` — пусто), а ряд растёт синхронно с шагами вне диффа: седьмой прогон ряда против пятого — `lint` ×1.38, `typecheck` ×1.47, `test` ×1.49, `knip` ×1.52, `test:hooks` ×1.34 (расчёт по ряду из «Проблемы»). Для `test:hooks` разгон меньше шума: варианты из `backlog/done/e14.md:35` — `isolate: false` даёт ~4 с по оценке vitest (в корневом `vitest.config.ts` не включён: `grep -n isolate` пуст), а полоса шума даёт +15 с к медиане успешных (51.1 против 36.3 с). Разгон отодвинет следующий красный, но не снимет его.
- **Формула правила (проект; числа в PR — от свежих артефактов):** порог = медиана последних 5 успешных ночных прогонов × 1.8, вверх до целой секунды. Множитель выше полосы шума — она до ×1.7 (`backlog/done/e12.md:34`, сбойный прогон медленнее успешных в ×1.5–1.7; 25.11 `lint` — ×1.47) — и ниже ×2: детектор регрессии сохраняется. Окно из пяти прогонов, а не десяти: факт меняется за дни — e12 перекалибровалась через день после мержа e9 (`backlog/done/e12.md:35`). Ориентир по артефактам 23.11–25.11 (пять успешных прогонов перед красным; для PR пересчитать на свежем ряду): `lint` — медиана 12.776 с → 23 с (сейчас 16); `test:hooks` — медиана 38.141 с → 69 с (сейчас 50).
- **Триггер и классификация (проект).** Красный по времени шага разбирают в три действия, в этом порядке. Действие 1 — перезапуск прогона: подтверждающий замер при любом красном, исход и время шага — в «Журнале»; зелёный перезапуск подтверждает шум, красный без признака (а) — изменение устойчивое, дальше (б) или (в), красный снова с признаком (а) — второй красный шага, идёт в счёт Т2. Действие 2 — причина по трём признакам, при совпадении действует первый по списку: (а) шум раннера — три и больше шагов вне диффа одновременно медленнее медиан своих последних 5 успешных прогонов на 30% и больше (вне диффа — дифф с последнего зелёного не меняет работу шага, то есть у шага нет признака (б)); (б) запланированный рост — в диффе с последнего зелёного выросла работа шага; (в) регрессия шага — ни то, ни другое. (а) сильнее (б): шум измеряют на шагах вне диффа, от диффа он не зависит, а долю запланированного роста внутри шума отделить нельзя — её записывают оценкой сверху. Действие 3 — решение по порогу: (в) — чинить шаг, порог не трогать; (б) без (а) — пересчёт по формуле, доля роста — в «Журнале» задачи; (а) — пересчёт по формуле только по триггеру калибровки: Т1 — шаг уже выходил на 85% бюджета и больше в успешном прогоне из последних десяти ночных прогонов (запас внутри полосы шума, красный — вопрос времени) или Т2 — красный этого шага повторился в двух из последних пяти прогонов; ни Т1, ни Т2 — порог не трогать, перезапуск закрыл красный, пересчёта нет. Остальные шаги тем же PR не пересчитывают, кроме тех, у кого максимум ряда, включая красный прогон, ≥ 85% бюджета, — они в том же шуме.
- **Применение правила к этой задаче (артефакты 23.11–25.11).** Пересчёт `lint` и `test:hooks` правомерен по самому правилу, без исключений. Красный 45680346493 — (а): к медианам пяти успешных прогонов перед ним `typecheck` ×1.39, `boundaries` ×1.56, `registries` ×1.56, `sandbox` ×1.93 — входы этих шагов дифф `de9ce87a..6997ff4d` не трогает, — и ещё `knip` ×1.35, которому дифф добавил новый файл теста; `test` — ×1.27, до 30% не дотягивает (×1.47–1.52 выше посчитаны против пятого прогона ряда, не к медианам). Для `lint` признака (б) нет; для `test:hooks` он есть, но действует (а): рост 38.1 → 48.7 с пришёлся на прогон до диффа, на запланированный рост остаётся не больше 2.4 с из +13.0 с. Триггер для обоих — Т1: `lint` выходил на 15.4 из 16 с (96%, прогон 45400346818), `test:hooks` — на 48.7 из 50 с (97%, прогон 45646832636); в прогоне перед красным — 94% и 97%. Т2 нет: красный по бюджету времени в последних 14 ночных прогонах один — 45680346493; 21.11 (`backlog/done/e14.md:35`) — раннер CI в job `canaries`, не ночной прогон. Повтор класса (19.11, 21.11, 25.11) — не триггер, а довод для строки реестра и для запасного варианта.
- **Правило первым PR, пересчёт вторым, строка реестра в PR 1.** Почему: по `docs/adr/0009-operator-delegation.md:36` пересчёт без правила — ослабление, которое предлагает только человек; после merge правила оператор ставит число по правилу, а человек принимает PR. Строка реестра идёт с правилом: контур, который должен был поймать случай, появляется в PR 1. Альтернатива — один PR на всё: отклонена, смешивает review-класс и `deny` и не даёт принять правило отдельно от чисел.
- **Реестр пропущенных дефектов: строка нужна.** Почему: числа e12 прошли все гейты (защищённый файл, одобрен человеком в PR), а запас оказался внутри полосы шума — после merge тот же порог `test:hooks` красил `canaries` на раннере CI 21.11 (`backlog/done/e14.md:35`), а 25.11 — ночной `verify budgets`. Разбор считает, что гейт сработал как задумано; для самого превышения это верно, но в реестр идёт не превышение, а калибровка, которая его допустила. Текст строки: 2026-11-25 — калибровка бюджетов времени verify (`verify-budgets.json`, e12 — #72, #74, 19.11): запас «факт + ~30%» меньше полосы шума раннера (до ×1.5–1.7), правила пересчёта в ADR 0009 не было; нашёл ночной `verify budgets`, повтор после merge — 21.11 и 25.11; контур — правило ADR 0009 (эта задача); автоматический гейт невозможен, потому что полоса шума видна только из истории ночных прогонов, которой нет на PR. Альтернатива — не регистрировать: отклонена, иначе третий повтор класса за неделю не попадёт в метрику (`docs/escaped-defects.md:3`, `docs/vision.md`, «Метрики системы»). Перед записью сверить даты и номера PR с git и `backlog/done/`.
- **Запасной вариант — разгон шага.** Условие переключения: после пересчёта `test:hooks` снова красный по времени в течение пяти ночных прогонов или медиана успешных прогонов без сигнатуры шума выше 85% нового порога — заводится задача на разгон сюита по вариантам `backlog/done/e14.md:35` с замером до/после; для `lint` то же условие даёт задачу на профиль шага. Третий подъём порога по одному шагу без такого замера не делать.
- **Отклонено: автоматический пересчёт ночью** (ночная джоба готовит PR по образцу храповиков b2.4 и e85). Нужны новый инструмент в `tools/` и правка `nightly.yml` — отдельная задача. Условие возврата: пересчёты по правилу чаще одного в месяц.
- **Отклонено: шумоустойчивый детектор в `tools/verify.ts`** (красить шаг только без сигнатуры шума). Правка гейта и его замыкания (ADR 0014), риск пропустить реальную регрессию вперемешку с шумом. Условие возврата то же.
- **Отклонено: триггер «повтор красного класса за N прогонов».** Почему: класс («любой бюджет времени») смешивает шаги и раннеры — калибровку одного шага оправдывал бы красный другого шага на другом раннере (21.11 — CI-раннер job `canaries`, не ночной прогон); повтор класса остаётся доводом для строки реестра и для запасного варианта. Условие возврата: красные класса идут чаще двух в месяц, а Т1 и Т2 не срабатывают.
- `touches`: `verify-budgets.json` и `docs/adr/0009-operator-delegation.md` правятся наверняка. `docs/escaped-defects.md` — общий путь, в `touches` не объявляется. `.github/workflows/nightly.yml` и `docs/architecture.md` (З7, `:40`, если ревью попросит оговорку) — только через мини-PR расширения `touches`. Новых файлов гейт-контура задача не создаёт.
