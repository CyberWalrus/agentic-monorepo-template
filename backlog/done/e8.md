# E8. `pnpm backlog inbox` — что ждёт человека

**Проблема.** Человек — единственный приёмщик (approve, label, merge) и узкое место системы: доска читается из `main`, зависимые задачи открываются только после merge (ADR 0007). При этом у него нет одного места, где видно, что именно его ждёт и в каком порядке это разблокирует работу. Сейчас это собирается вручную из списка PR, `pnpm backlog list` и журналов задач. Каждый час простоя приёмки останавливает всех агентов сразу.

## Что сделать

- Команда `pnpm backlog inbox` (и `--json`): список действий человека, отсортированный по числу задач, которые действие разблокирует. Источники:
  - открытые PR веток `task/*`: ждёт approve; ждёт label `gate-change-approved` (label снят новым push — отдельной строкой); зелёный и готов к merge;
  - задачи с `needs_human: человек: …`, у которых закрыты все `depends_on`;
  - задачи `отложено: …` — только перечислить условие, без призыва к действию;
  - брошенные захваты (ветка без коммитов дольше порога) — кандидат на `pnpm backlog release`;
  - оставленный файл `.claude/settings.local.json` (после D13 это находка `doctor`).
- Без `gh` команда честно пишет, какие строки неполны, а не выдаёт пустой список.
- Описать команду в скиле `task-board` и в `AGENTS.md` (кто вызывает: человек; агент — в конце сессии, чтобы назвать человеку следующее действие).

## Решение (2026-11-15)

- **Команда доски, а не отдельный дашборд.** Почему: данные те же, что у `list` и `doctor`; один инструмент — одно место правды о статусах.
- Альтернатива: GitHub Project с автоматизацией. Отклонена: вторая система статусов рядом с вычисляемой доской (ADR 0007 отказался от хранимого статуса).
- Условие возврата: приёмщиков стало больше одного — тогда нужна маршрутизация по людям, которую команда не даёт.

## Критерии приёмки

- Тесты на парсере и сортировке: PR, разблокирующий три задачи, стоит выше PR, разблокирующего одну; задача `человек:` с незакрытой зависимостью в список не попадает.
- Без `gh` вывод содержит явное предупреждение о неполноте.

## Журнал

- 2026-11-15: заведена по итогам аудита. Зависит от D13: использует различение видов `needs_human` и находки `doctor`, которые D13 вводит. Задача режима обслуживания: ведёт оператор.
- 2026-11-21: пометка «режим обслуживания» от 2026-11-15 устарела — сужение классов (ADR 0014, e9/e11) прямо называет e8 среди освобождённых, доска считает её свободной, захвачена обычной сессией.
- 2026-11-21: реализовано. Команда `pnpm backlog inbox` (+ `--json`) в `tools/backlog.ts`; чистая логика (парсер вывода gh, сборка и сортировка строк) — новый review-модуль `tools/backlog-inbox.ts`. Источники по задаче: открытые PR веток `task/*` (approve; label `gate-change-approved`, в отдельной строке — снятый новым push; зелёный и готов к merge), задачи «человек: …» с закрытыми зависимостями, «отложено: …» без призыва к действию, брошенные захваты (порог — `DOCTOR_IDLE_HOURS` из backlog-board, тот же, что у doctor), забытый `.claude/settings.local.json` основного checkout. Сортировка: файл режима обслуживания всегда первый (угроза гейтам всех сессий, не счёт задач), затем действия по числу разблокированных задач (`openDependentsCount`), затем пассивные строки.
- 2026-11-21: решения. (1) Вердикт label не переписывается: переиспользованы `evaluateApproval`/`lastLabeledEvent` из `gate-approval-core` (та же семантика, что у CI: label действителен после последнего push от владельца CODEOWNERS; направление review→deny безопасно, ADR 0014); «нужен ли label» — пересечение файлов PR с deny через `protectionOf`. (2) Полную сверку файлов режима обслуживания оставила за doctor (его логика в deny, дублировать её в review значило бы разойтись): инбокс проверяет основной checkout безусловно и ссылается на `pnpm backlog doctor` для остального. (3) Не-PR-состояния («CI красный», черновик, конфликт с main) — пассивные строки без призыва: человек не исполнитель этих действий.
- 2026-11-21: развилка по тестам — выбран вариант, записываю по правилу ADR 0009. Тесты критериев приёмки (18 шт., `pnpm test:inbox`) лежат рядом с логикой (`tools/backlog-inbox.test.ts`), а не в `tools/test/`: каталог под deny целиком (ADR 0014 — «дешевле держать deny целиком»), правка требует режима обслуживания. Альтернатива «проводка теста в гейт» отвергнута: литеральная ссылка `tools/…` в скрипте контура (`test:hooks` в package.json) втянула бы файл в замыкание `check-tool-class` и покрасила verify инвариантом (а), а новый vitest-конфиг по §3.5 architecture.md обязан попадать в `deny` тем же PR — обычной сессии это недоступно; обход детектора (неименной конфиг, ссылка без литерала) был бы скрытым ослаблением границы классов. Следствие — осознанный разрыв: тесты не исполняются гейтами verify/CI, регрессии инбокса ловит только ручной `pnpm test:inbox` и ревью. Хвост: операторским PR перенести файл в `tools/test/backlog-inbox.test.ts` (переименование без правки логики) — тогда его подхватит корневой vitest и гейты отчёта. Условие возврата: появление второго приёмщика — тогда нужна маршрутизация по людям, которой команда не даёт (из раздела «Решение» задачи).
- 2026-11-21: без `gh` команда печатает список неполных строк (консоль ошибок + `complete: false` и `incomplete` в `--json`) и не подставляет пустой инбокс за «делать нечего» (З11) — критерий приёмки покрыт тестом.
