# C1.1. Контрактный набор тестов репозитория задач

**Проблема.** `TaskRepository` имеет одну in-memory реализацию без набора тестов, который зафиксировал бы поведение интерфейса. Прежде чем добавлять Postgres, поведение нужно зафиксировать.

## Что сделать

- Собрать контрактный набор: один набор прогоняется против любой реализации `TaskRepository` (подстановка реализации — параметр набора).
- Набор покрывает: CRUD, порядок, граничные случаи статусов, поведение при отсутствии ресурса.
- Пока единственная реализация — in-memory, набор гоняется против неё.

## Критерии приёмки

- Канарейка: намеренно сломанная in-memory реализация (например, потеря порядка) красит контрактный набор.

## Журнал

### 2026-11-14 — набор реализован, задача готова к PR

**Что сделано.** Контрактный набор — `apps/api/test/task-repository-contract/`:

- `contract.ts` — тип `TaskRepositoryContractCheck { name, check(repo) }` и массив `taskRepositoryContractChecks` (9 проверок). Прогон против реализации — `it.each(taskRepositoryContractChecks)('$name', …)` в тесте реализации; фабрика даёт свежий экземпляр.
- `in-memory.test.ts` — прогон против `InMemoryTaskRepository`.
- `in-memory.canary.test.ts` — постоянная канарейка критерия приёмки: `OrderingLosingTaskRepository` (реверс `list()`) валит проверку порядка; здоровая реализация через тот же механизм проходит все проверки (защита от вакуумно-зелёной канарейки).
- `apps/api/src/tasks/repository.test.ts` — оставлено только реализационно-специфичное (инъекция часов/id, порядок по захваченным часам); поведение интерфейса переехало в набор.
- `apps/api/tsconfig.json` — `include += "test"` (иначе typecheck не видит тесты в `test/`).

**Решения (ревью плана architecture-reviewer/sanity-reviewer — approve):**

- Часы/генератор id не входят в контракт фабрики: все проверки порядка — через `reset()`-сидирование с явными `createdAt` (minor от architecture-reviewer). Итог: набор без изменений прогоняется против будущего Postgres с серверными id и датами.
- Канарейка — живущий тест, а не разовая демонстрация: критерий приёмки становится постоянно проверяемым, и это единственный способ выразить его при запрещённых `test.fails`/`.skip` (гейт test-integrity).
- Регистрация через `it.each(checks)('$name', …)` с литеральным заголовком и ассертом «проверка разрешается без падения» — по прецеденту `it.each` из `app.test.ts`: динамический `it(check.name)` ломает линтер (vitest/valid-title, expect-expect), конфиг линтера защищён.
- `touches` дополнен `apps/api/tsconfig.json` (minor от architecture-reviewer).

**Доказательства:** `pnpm verify --full` PASS (21.0s); vitest apps/api — 27 тестов (было 19: 14 app + 5 repository), покрытие 100%; `pnpm mutation` — 100% (65/65 мутантов убиты, repository.ts 21/21); канарейка падает на реализации с потерей порядка и зелёная на здоровой. Базлайн храповика `test:count` поднят (только ужесточение, попутно догнал отставшие ui/web/hooks от смерженных PR). Ревью диффа: test-quality/security/product-logic — approve; по замечаниям дополнены docstring (тай-брейк вне контракта), журнал (было 19) и `touches`.
