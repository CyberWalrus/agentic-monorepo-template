# C4. Логи API в отчёте Playwright при падении E2E

**Проблема.** Агент при падении E2E не видит логов API: причину на стороне сервера приходится угадывать по поведению интерфейса. То, что можно показать детерминированно, не показывается ничем (З11).

## Что сделать

- При падении теста логи API за время сценария прикладываются к отчёту Playwright (attachment). Записи отбираются по идентификатору запроса из C4.1, а не по времени: E2E идут параллельно.
- `pnpm verify --json` при красном шаге `e2e` называет путь к приложенным логам.

## Критерии приёмки

- При падении E2E артефакт отчёта содержит логи API этого сценария и не содержит записей соседних параллельных тестов.
- Канарейка: намеренно падающий сценарий даёт отчёт с непустым вложением логов.

## Журнал

- 2026-11-15: по итогам аудита задача сужена до доставки логов в отчёт. Структурные логи, идентификатор запроса и таксономия ошибок вынесены в C4.1 (свободна для обычного агента). Задача режима обслуживания (`tools/**` и конфиг Playwright под deny): ведёт оператор.
- 2026-11-20, захват: доска вычислила статус «свободна» — запись от 2026-11-15 о режиме обслуживания устарела: `protectionOf` считает класс по литералу записи touches, `tools/**` целиком — класс review (blanket инструментов разработчика, ADR 0014), `e2e/**` не защищён. Условие реализации: ни один deny-файл не трогается (конфиг Playwright и шаги verify не менялись — так и вышло, правки только `apps/api/**` и `e2e/**`).
- 2026-11-20, план (без ревью субагентов — их в этой сессии нет, план и решения здесь; ревью-проход сделан по диффу перед PR):
  - **API**: при `enableTestApi` каждое событие лога параллельно пишется в кольцевой буфер (`createLogBuffer`, ёмкость 4096, вытеснение старых — буфер для диагностики, не аудит; нулевой оверхед без тест-API). Срез по идентификаторам: `GET /__test__/logs?requestId=…` — тот же whitelist формы id, что у C4.1, невалидный/отсутствующий → 400 (не отдаём буфер целиком). Тест-API остаётся вне открытого контракта (прецедент `/__test__/reset`), contracts не менялись; в проде ENABLE_TEST_API запрещён на старте (server-config). Чувствительность: записи `unhandled` могут нести данные запроса — буфер недолговечен и локален, ретенции нет (замечание c4.1 учтено в комментарии).
  - **E2E**: авто-фикстура `apiRequestIds` собирает `x-request-id` из заголовков ответов страницы; в teardown при падении (`status !== expectedStatus`) — срез с `/__test__/logs`, файл `api-logs.json` через `testInfo.outputPath`, attach в отчёт и строка `[api-logs] attached: <path>` в stdout. Диагностика не меняет исход: недоступные логи (частый случай — упал сам API) — `console.warn`, не новый failure.
  - **Канарейка (AC-2)**: намеренно падающий сценарий нельзя держать в functional-прогоне, поэтому он в проекте `agents` (default: false, но матчится knip-ом) и запускается мета-тестом `e2e/features/e2e-reporting/api-logs.spec.ts` как подпроцесс `playwright test --project=agents` с `REUSE_SERVER=1` и своим outputDir — серверы того же прогона переиспользуются, артефакты не мешают основным. Синтетический «сосед» (запрос с известным id в живой API) доказывает изоляцию AC-1: маркер канарейки во вложении есть, соседа нет.
  - **AC-3** (`verify --json` называет путь): красный вывод подпроцесса содержит строку фикстуры с путём вложения — это ровно тот stdout, который verify кладёт в поле `output` шага; мета-тест ассертит и его.
  - Найдено при реализации: воркеры Playwright переоценивают playwright.config.ts и перезаписывают `e2e/reports/instance-token` свежим случайным id (для обычного прогона безвредно — globalSetup уже прошёл). Мета-тест перед spawn подкладывает в токен живое значение `/health`, иначе canary честно падает по гейту «свой сервер».
  - Подключение канарейки как отдельного шага verify/CI — правка deny-файлов (tools/verify*.ts, конфиг Playwright) — оператору, не делалось.
- 2026-11-20, реализация: api — `observability.ts` (+`isSafeRequestId`, `createLogBuffer`), `app.ts` (tee-sink + `/__test__/logs`); тесты api 190→191 (буфер: заполнение/вытеснение/снимок, предикат id; срез: изоляция соседа, поиск по сгенерированному id, 400 на пустые/битые/микс id). Мутации: `pnpm mutation` 96.92% (break 75); выжившие в изменённой логике: `every→some` убит тестом-миксом; три эквивалента подтверждены ручным прогоном мутанта на зелёных тестах — spread-тернарник sink (`{sink: undefined}` ≡ `{}` через `sink ?? consoleSink`, класс из журнала c4.1), `header !== null` перед whitelist (`test(null)` тоже false, задокументирован в c4.1), `typeof requestId === 'string'` перед `Set<string>.has` (`has(undefined)` и так false).
