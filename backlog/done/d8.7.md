# D8.7. Синтетический потомок: проверка `copier update`

**Проблема.** Механика обновления (`copier update` переносит разницу версий, сохраняя правки проекта) не проверяется, пока обновлять нечего: с одним тегом потомков не бывает (ADR 0008, «Проверка» — «со второго тега»).

Задача ведёт оператор (задача будет в режиме обслуживания): `touches` — `tools/**`, `.github/workflows/**`. Блокировка снимается PR с доказательством существования второго тега (ADR 0007, «отложено»).

## Что сделать

- Расширение канарейки d8.3: во временном каталоге — копия из **предыдущего** тега, синтетическая правка «проекта» (например, строка в README), `copier update` до следующего тега, затем `pnpm verify`.
- Проверка: правка «проекта» переживает обновление; файлы разработки шаблона не приезжают повторно; демо-домен при обновлении не дублируется (решение d8); конфликт обеих сторон помечается маркерами, канарейка красная.
- Запуск — там же, где канарейка d8.3 (CI и человек; исключение из З5 уже записано d8.3).

## Критерии приёмки

- На втором теге канарейка потомка зелёная: правка «проекта» сохранилась, `pnpm verify` в обновлённой копии зелёные, повторно приехавших файлов разработки нет.
- Поломка детектируется: утерянная правка «проекта» или приехавший excluded-файл красят канарейку.

- 2026-11-26: решения (развилки закрыты здесь, ADR 0009). (1) Пара обновления — копия из **последнего** тега `v*` → закоммиченный HEAD, а не замороженная пара двух существующих тегов (v0.1.0 → v0.2.0, как предполагала запись выпуска). Почему: это путь человека — копирует последний тег, обновляет до следующего; на коммите выпуска HEAD и есть следующий тег, критерий «на втором теге зелёная» выполнен (v0.2.0 → HEAD). Замороженная пара краснеет только при смене copier — PR, меняющий шаблон, она не судит. Альтернатива: вторая пара (v0.1.0 → v0.2.0) дополнительно. Условие добавления: понадобится постоянно судить обновление через выпуск с сотнями файлов. (2) База сравнения контракта в потомке — пуш обновлённого коммита в origin копии (документированный канал раздела 8 — `origin/main`); `OPENAPI_COMPAT_ALLOW_HEAD_BASE=1`, `TURBO_SCM_BASE` и `--base` не ставятся: после d8.8 ни один путь шаблона не ставит флаг, шаг вне инструкции — дефект класса d8.8; без пуша шаг `openapi` судил бы совместимость контракта между выпусками шаблона (база — коммит до обновления), а это не предмет канарейки. Условие возврата: появится документированный рецепт обновления для человека (D10) — канарейка переходит на него дословно, как на раздел 8. (3) Место правки «проекта» — строка README дальше всего от переписанных шаблоном строк (между версиями README не менялся — после заголовка), по `git diff --no-index -U0` двух рендеров; фиксированная строка отвергнута: правка шаблона по соседству дала бы ложный конфликт. (4) «Демо-домен не дублируется» проверяется инвариантом дерева: обновлённый потомок = дерево целевой версии + файлы самого проекта (файл прежней версии, переживший обновление, и лишний файл — красные); плюс чекер копии (`checkCopySide`) — файлов разработки нет. (5) Живость детектора — негатив-контроль конфликта (настоящий `copier update` на втором потомке: проект заменяет первую строку, которую шаблон переписал; README предпочитается) и инверсионная проба на дереве счастливого пути — шесть мутаций; если шаблон между версиями не переписал ни одной текстовой строки, негатив-контроль громко пропускается (конфликту взяться неоткуда). Логика и пробы — в самом раннере (`touches` задачи), по прецеденту d8.8; вынос в модуль с юнит-тестами в `tools/test/` требует расширения `touches` — не делал. (6) `pnpm install && pnpm verify` в копии прошлого тега до обновления не запускается: зависимостей обновлению не нужно, свежая копия HEAD проверена первой половиной прогона.
