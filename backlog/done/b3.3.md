# B3.3. Образ с зависимостями для локального визуального прогона

**Проблема.** `pnpm visual` копирует репозиторий в контейнер и ставит зависимости при каждом запуске; на Apple Silicon добавляется эмуляция amd64.

## Что сделать

- Собрать образ с предустановленными зависимостями, слой привязать к `pnpm-lock.yaml`.
- `pnpm visual` переиспользует образ, установка идёт только при смене локфайла.

## Подводные камни

- Бинарные базлайны и образ разделяют одну истину рендеринга: локальный прогон остаётся средством предпросмотра, источником базлайнов остаётся CI (B3.1).

## Критерии приёмки

- Повторный `pnpm visual` без смены локфайла не ставит зависимости; время локального прогона падает замеряемо.

## Журнал

- Сделано: `tools/visual.Dockerfile` — образ с предустановленными зависимостями, слой установки привязан к локфайлу (манифесты копируются до всякого другого ввода, исходников в образе нет — рабочее дерево кладёт в контейнер `visual.sh` при каждом запуске). `tools/visual.sh` строит образ при первом запуске и дальше переиспользует: тег несёт отпечаток всех вводов установки (pnpm-lock.yaml + манифесты + версии pnpm/Playwright).
- Решение — тег по отпечатку локфайла **и манифестов**, не локфайла одного: иначе смена манифестов без локфайла (например, скрипты package.json) молча оставляла бы в образе старые node_modules. Отпечаток превращает смену любого ввода установки в пересборку, где `--frozen-lockfile` даёт ту же ясную красную, что и раньше. Альтернатива (только локфайл) отклонена; условие возврата — если пересборки при смене одних скриптов станут частыми.
- Решение — store внутри слоя образа, а не buildkit cache-mount: node_modules держат жёсткие ссылки на store, образ должен быть самодостаточным; содержимое cache-mount при экспорте слоя не сохраняется.
- Истина рендеринга не тронута (подводный камень задачи): база `mcr.microsoft.com/playwright:v…-noble` той же версии, что и CI (версию сверяет гейт visual-image, A8), `--platform linux/amd64`, `--ipc=host`, `tools/visual-inner.sh` не менялся; базлайны создаёт CI (b3.1, ADR 0015), локальный прогон — предпросмотр.
- Замеры (Apple Silicon, docker 29.2.0 arm64, машина под нагрузкой параллельных сессий): старый поток — 38.50s и 38.44s на прогон, его сегмент установки (npm i -g pnpm + pnpm install на тёплом store-volume) — 9.84s изолированно. Новый поток: первый запуск 69.00s (разовая сборка образа: 4.6s npm i + 5.5s install + экспорт слоя ~20s), повторные — установки нет (в логе «образ … уже собран — зависимости не ставятся»), 32.73s back-to-back против 38.44s старого; сегмент набора идентичен (12.7s против 13.5s) — дельта и есть устранённая установка. Холодный store: раньше — полная загрузка при каждом таком запуске, теперь — раз на смену локфайла.
- Тесты: unit на скрипт не пишется — это shell/docker-инструмент, как и прежний visual.sh (shell-тестов в tools/test/ нет, путь deny обычной сессии); критерий приёмки покрыт замерами реальных прогонов (логи и времена выше).
- Дальше по желанию человека: теги прошлых отпечатков сами не удаляются (`docker image prune`/`docker rmi` на руки), docker-volume `agentic-template-pnpm-store` больше не используется — можно удалить.
- CI PR (#97): 10 из 11 jobs зелёные; job `canaries` красный тремя бюджетными флаками, не связанными с диффом: (1) таймаут 5000ms теста `schema-sync-cli` в копии шаблона, (2,3) `test:hooks` 51.6s и 53.7s при бюджете 50s в негативном контроле. Те же два режима падают на ветках `task/e1` (51.1s, три прогона) и `task/b6` (копия шаблона), e1 — раньше создания этого PR; у `task/b6` тот же негативный контроль прошёл в 19:18 — дисперсия вокруг тесного порога `test:hooks` (~48–54s на 2-ядерных рантаймах). Локально `pnpm verify` и `pnpm verify --full` зелёные. Правка порога — `verify-budgets.json` (deny, режим обслуживания); тройной перезапуск red не чинит, перезапуски прекращены.
