# E51. Снимок защищённых путей: подмена pull-а и потери в именах копий

**Проблема.**

- `tools/snapshot.ts:328`: перебазировка снимка считает «совпадение содержимого с blob текущего HEAD» легитимным движением ветки (pull/merge принёс изменения гейтов). Команда вида `perl -pi -e '…' tools/protected-paths.json && git commit -am x` (также `python`, `node -e`, редирект `1>`) меняет защищённый файл и коммитит его одним вызовом: к проверке по результату файл уже равен blob HEAD — чекер принимает это за pull, перебазирует снимок и не восстанавливает файл. Запись через `perl -pi`, `python`, `node -e`, `1>` в `writeTargets` не распознаётся. В шаблоне запись в защищённые пути держит песочница ОС (ADR 0004); у потребителей плагина `agent-harness` песочницы нет — там это дыра.
- `tools/snapshot.ts:185`: `copy = join(dir, path.replaceAll('/', '__'))` — имена копий с потерями: `a/b__c` и `a__b/c` дают одно имя.

Аудит владельца, 2026-11-23, «Средние → Гейты и защита» и «Низкие → Безопасность и стабильность». Дыры прошли все гейты — строк в `docs/escaped-defects.md` нет.

## Что сделать

1. Регрессии в `tools/test/snapshot.test.ts`: (а) защищённый файл изменён командой из «нераспознанных» и закоммичен одной командой — после проверки файл равен снимку начала сессии (восстановлен), отказ журналируется; (б) честный pull/merge, изменивший защищённый файл, — по-прежнему перебазирует снимок; (в) `a/b__c` и `a__b/c` — разные копии.
2. Легитимность движения ветки определять по факту движения `HEAD` до команды (снимок `HEAD` на старте сессии и перед проверкой), а не по равенству blob: `HEAD` не менялся — это не pull.
3. `writeTargets` в `tools/analyze-command.ts`: распознавать `perl -pi`, `python -c`, `node -e`, `n>` (тест в `tools/test/analyze-command.test.ts`).
4. Имена копий — без потерь: обратимое кодирование пути (процентное кодирование `/` и `%`) либо хэш пути с именем в манифесте.
5. Замыкание: `tools/protected-paths.json`, `tools/check-tool-class.ts`, `.claude/settings.json` — правятся тем же PR, если появляется новый файл гейт-контура (шаги `tool-class`, `sandbox` зелёные).
6. Строка в `docs/escaped-defects.md` тем же PR: в графе «что добавлено» — регрессии из п.1.

## Критерии приёмки

- Тест (а) красный до правки и зелёный после; (б) зелёный всегда; (в) зелёный после правки.
- `writeTargets` распознаёт формы из п.3 (тест зелёный).
- Строка добавлена в `docs/escaped-defects.md`; pnpm verify зелёный; шаги `tool-class` и `sandbox` зелёные.

## Решение

Признак «pull» — движение `HEAD`, а не совпадение содержимого: совпадение можно создать командой, движение ссылки — нет. Альтернатива — только расширить список распознаваемых записей — отклонена: список форм всегда неполон. Обе правки делаются вместе. Условие возврата: если определение движения `HEAD` ломает легитимные сценарии (rebase, switch веток в сессии) — вернуться к равенству blob плюс требование «ссылка менялась после старта команды», записать в «Журнале».

Задача ведёт оператор (задача будет в режиме обслуживания): touches — `tools/snapshot.ts`, `tools/analyze-command.ts`, `tools/test/**`, замыкание (deny). Пересекается с e45 и e50 по `tools/analyze-command.ts`: кто мержит вторым — ребейз.
