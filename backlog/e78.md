# E78. CI: перезапуск на смену head и base, а не на правку тела PR

**Проблема.**

- `.github/workflows/ci.yml` слушает `pull_request` с типами `[opened, synchronize, reopened, edited]`. Тип `edited` нужен ради смены base-ветки (комментарий в файле: смена base не порождает `synchronize`, а check привязан к head SHA), но срабатывает на любую правку PR — в том числе на тело и заголовок.
- `concurrency` для `pull_request` отменяет идущий прогон. 24.11.2026 на PR #239 (head `fea3de54`) правка тела через `gh api … -F body=@файл` в 20:32:31Z создала второй прогон CI (45481883825) и отменила первый (45481691270); на PR #242 то же дало по два зелёных `gate` на одном head.
- Последствие: потерянные минуты раннеров, отменённые прогоны в истории (поезд и ревьюеры видят «CANCELLED» отдельной записью чека), задержка мержа. Тела PR правятся регулярно — исполнителем, ревьюерами, конвейером (раздел «Ревью», доказательства).

Наблюдение при мерже PR #239 (задача e57), 2026-11-24.

## Что сделать

1. Правка тела и заголовка PR не должна ни создавать новый прогон CI, ни отменять идущий. Условие уровня job не годится: запуск всё равно создаётся, а `concurrency` отменяет предыдущий до вычисления условий — нужен отдельный вход для смены base.
2. Смену base держать: отдельный лёгкий workflow на `pull_request: edited`, который при `github.event.changes.base` диспатчит CI на head ветки PR (по образцу `visual-approve`, b3.1), а `ci.yml` слушает `[opened, synchronize, reopened]` и `workflow_dispatch`.
3. Канарейка на проводку (З6) и строка в `docs/architecture.md`.

## Критерии приёмки

- Правка тела открытого PR не меняет число прогонов `CI` на head и не отменяет идущий (проверка на тестовом PR во время идущего прогона).
- Смена base-ветки создаёт прогон на том же head.
- `pnpm verify` зелёный; канарейка красная до изменения и зелёная после; шаги `tool-class`, `sandbox`, `test:hooks` зелёные.

## Решение

Выбрано: отдельный вход для смены base вместо условия уровня job. Почему: `edited` снимает проблему только вместе с гарантией, что смена base не оставит старый check без пересмотра. Альтернатива — убрать `edited` совсем — отклонена по той же причине. Условие возврата: если GitHub начнёт присылать `synchronize` на смену base — отдельный вход не нужен.

Задачу ведёт оператор: `touches` — защищённые пути (CI, канарейки), режим обслуживания по ADR 0009; новый workflow-файл — условное замыкание `touches` мини-PR-ом.

## Журнал
