# E24. Доверенный workflow visual-approve исполняет код PR с write-токеном

**Проблема.** Шаг «Commit baselines» после checkout head-коммита PR (visual-approve.yml:104-110) выполняет pnpm install --frozen-lockfile (:180) уже в дереве PR: pnpm исполняет prepare-скрипт из package.json PR (package.json:6 — lefthook install) и ставит хуки по PR-версии lefthook.yml; git commit (:190) и git push (:197) запускают pre-commit/pre-push, гоняющие turbo по коду PR (lefthook.yml:3-27; комментарии :45-47 и :177-180 сами это признают). Шаг держит GH_TOKEN в env (:168-169) при permissions contents: write, actions: write, pull-requests: write (:25-28) — нагрузка в prepare или в тесте pre-push доходит до исполнения с write-токеном в окружении процесса. Шапка файла (:2-5) ложно заявляет «код PR не исполняется ни на одном шаге», zizmor-подавление (.github/zizmor.yml:17-23) опирается на то же утверждение. Реальный противник — свои агенты в ветках task/<id> того же репозитория (форк-PR отсечены :62-69 и check-visual-approval.ts:77-91). Дополнительно: post-save кэша setup-node (cache: pnpm, .github/actions/setup/action.yml:19) пишет store, собранный из PR-локфайла, в скоуп default-ветки (ключ считается по lockfile main до checkout PR; окно — когда ключа ещё нет).

## Что сделать

- Убрать pnpm install из PR-дерева: node_modules доверенной установки setup (:48) — untracked, переживает git checkout; использовать его. Если переустановка необходима — только до checkout PR head.
- Отключить lefthook в этой джобе (LEFTHOOK=0 или git config core.hooksPath — доверенный CI-контур, а не обход локальных гейтов агентом); push базлайнов выполняется без прогонов кода PR.
- GH_TOKEN оставить только на шаге push; из остальных шагов убрать. Пересмотреть права job (actions: write нужен только при перезапуске чужих прогонов — убрать, если не используется).
- Кэш: передать в composite setup input cache:false для этого workflow, либо осознанно задокументировать риск в ADR 0015.
- Исправить шапку visual-approve.yml и zizmor-комментарий так, чтобы они описывали фактическое поведение; обновить ADR 0015.

## Критерии приёмки

- В job нет ни одного шага, исполняющего скрипты/конфиги из PR-дерева: grep по workflow — нет pnpm install после checkout head-SHA, push выполняется с отключёнными хуками.
- GH_TOKEN отсутствует в env всех шагов, кроме собственно push; права job сведены к необходимому минимуму.
- Тестовый PR с изменёнными package.json/lefthook.yml проходит /approve-visual; лог джобы приложен к PR как доказательство неисполнения PR-кода.
- Post-save кэша setup-node для этого workflow отключён (cache:false) или риск задокументирован в ADR 0015.
- Шапка и zizmor-комментарий не содержат ложных утверждений; ADR 0015 обновлён; pnpm verify зелёный.

## Решение

Выбран минимальный точечный фикс из перепроверки: «без pnpm install в PR-дереве + хуки выкл в джобе + токен только на push + cache:false». Альтернатива (защита в глубину): валидатор одобрения требует совпадения package.json/lockfile/pnpm-workspace.yaml PR с main (сейчас check-visual-approval.ts:3-5,103-104 манифесты не смотрит) — заводится отдельной задачей при желании, не блокер. Условие возврата: если без pre-push-прогонов базлайны начинают течь в main — гнать boundaries из доверенной установки в trusted-контексте, не из PR-дерева.

Задача ведёт оператор (задача будет в режиме обслуживания): touches — .github/** (deny, tools/protected-paths.json:22).
