# B4.4. Учёт флаков: repeat-each, дедупликация issues, карантин

**Проблема.** Nightly при каждом падении заводит новый issue без дедупликации; flaky rate (цель в vision меньше 1%) не измеряется.

## Что сделать

- Nightly с `--repeat-each` даёт список нестабильных тестов; на тест заводится один issue с поиском существующего.
- Измерять flaky rate и показывать его в nightly-отчёте рядом с целью из vision.
- Карантин — защищённый файл со списком тестов и сроком: тест из карантина исполняется, но не блокирует. `.skip` остаётся запрещённым.
- Карантин протухает по сроку автоматически: истёкшая запись красит nightly-задачу.

## Решение (2026-11-15)

Выбор делегирован человеком агенту в сессии 2026-11-15; принимается merge PR с этой правкой (ADR 0009, «Развилки в задачах» и «Пороги»).

- **Порог flaky rate — меньше 1 %** (цель G4 из vision). Считается в nightly как доля тестов, у которых повторы одного прогона `--repeat-each` дали разный результат. Значение 1 % и выше красит nightly-задачу.
- **Порядок карантина.** Тест попадает в карантин только PR-ом, который меняет защищённый файл карантина (ведёт оператор, принимает человек) и ссылается на issue с причиной. Срок — 14 дней без продления: истёкшая запись красит nightly, повторный карантин того же теста требует нового issue. В карантине одновременно не больше трёх тестов. Тест с меткой `@critical` в карантин не попадает — его чинят сразу.
- Почему так: карантин без срока и предела превращается в узаконенный `.skip`; `@critical` — продуктовые инварианты, которые по vision защищены всегда.

## Критерии приёмки

- Повторное падение одного теста не создаёт второй issue; тест в карантине виден в отчёте с пометкой и сроком; попытка положить тест в карантин без срока красит доску.
- Четвёртая запись в карантине и запись для теста `@critical` красят проверку.
