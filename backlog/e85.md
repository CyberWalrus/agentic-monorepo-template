# E85. PR храповиков открываются вручную — три за день: выполнить условие возврата e82

**Проблема.** Автоматика PR храповика не открывает — так решил владелец в e40 (`backlog/done/e40.md:24`, `:45`) и повторил в e82 (`backlog/done/e82.md:53`), оба раза с одним условием возврата: вернуться к вопросу токена отдельной задачей, «если ручное открытие PR храповика станет узким местом (чаще одного PR в неделю)». Условие выполнено за один день, 25.11: #285 (merge 13:36:45Z), #288 (создан 15:40:04Z), #289 (создан 15:48:54Z).

Механика. Workflow право даёт — `permissions: contents: write, pull-requests: write` (`.github/workflows/nightly.yml:291-293`), но настройка репозитория выключена, и `gh pr create` отклоняется: «GitHub Actions is not permitted to create or approve pull requests (createPullRequest)». Выход 1 заложен по замыслу: печать действия человека и `commandFailed('gh pr create', …)` (`tools/check-test-count.ts:594-596`, выход — `:610-611`; `tools/check-mutation-ratchet.main.ts:984-986`, выход — `:1003-1007`). В ночи 45646832636 обе джобы храповика красные по этой причине — job 139319977703 и 139325383048 — и ночь красная. При уже открытом PR шаг выходит нулём с «PR #N уже открыт» (`tools/check-test-count.ts:554`, `tools/check-mutation-ratchet.main.ts:943`): красной ночь остаётся от публикации ветки до того, как человек откроет PR. Храповика два, поэтому рук — до двух за ночь.

## Что сделать

1. Владелец выбирает вариант и записывает решение с датой в «Журнал»:
   - **А. Включить настройку** «Allow GitHub Actions to create and approve pull requests» и завести запуск проверок на PR автоматики. Права у workflow уже есть (`.github/workflows/nightly.yml:138-141`, `:291-293`), но одной настройки мало: шаг публикации ходит в GitHub под `github.token` (`:216`, `:318`), а события от него прогонов не рождают ([документация GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow), раздел о запуске workflow из workflow). `pull_request`-прогоны `ci.yml` (на PR слушает только `pull_request` и `workflow_dispatch` — `.github/workflows/ci.yml:5-11`, `:19`) создаются в состоянии approval-required и ждут человека с правом записи («Approve workflows to run»); прочие события прогонов не создают — для `pull_request_target` страница отдельной оговорки не даёт, применено общее правило, — а `gate-integrity.yml` слушает только `pull_request_target` и `merge_group` (`.github/workflows/gate-integrity.yml:10-15`). Без триггера проверки на таком PR не придут, и PR не смержить, пока человек не запустит их сам — ручное действие вернётся в другом виде; то же для push уже записано в `tools/check-test-count.ts:56-59`. Код при А: (а) после create запускать `ci.yml` диспатчем на head-ветке PR, как visual-approve (`.github/workflows/ci.yml:15-19`; прогон без merge-ref — всё дерево вместо `--affected`, `:31`); (б) заводить запуск `gate-integrity.yml` на таком PR — `workflow_dispatch` у него нет, события триггеров запрещено добавлять вне режима обслуживания и ревью мейнтейнера (`:4-5`), джобы `integrity` и `bundle-approval` идут только на `pull_request_target` (`:59`, `:158`); (в) править логику публикации и её канарейки — `tools/check-test-count.ts`, `tools/check-mutation-ratchet.main.ts`, `tools/test/test-count-ratchet.test.ts`, `tools/test/check-mutation-ratchet.test.ts`. Как именно запускать проверки, выбирает исполнитель и записывает сюда решение, альтернативу и условие возврата (ADR 0009). Правится и описание контура — `docs/architecture.md:216-217` («а PR по ней открывает человек»). Отклонено в e40 как «разрешение автоматике создавать и одобрять PR ради одной джобы» (`backlog/done/e40.md:45`); с b2.4 джоб две.
   - **Б. Выдать джобам PAT или токен App.** Секрет вводит человек, агент токенов не касается. Передача токена джобам — правка `.github/workflows/nightly.yml` (в `touches` нет — мини-PR расширения touches) и `docs/architecture.md:216-217`. Триггер проверок не нужен: под PAT или токеном App `pull_request`-прогоны идут сами (та же страница документации). Отклонено в e40 как «новый секрет и новое доверие» (`backlog/done/e40.md:45`).
   - **В. Принять ручное открытие** как норму: правок нет, задача закрывается записью в «Журнале».
2. При А и Б сохранить канал «PR создан или громкая ошибка» (e40, e82): отказ create, не являющийся «уже открыт», остаётся exit 1 с причиной дословно (`tools/check-test-count.ts:594-596`, `tools/check-mutation-ratchet.main.ts:984-986`); при А тот же канал для запуска проверок — не запустились, шаг красный с причиной и действием человека; канарейки в `tools/test/test-count-ratchet.test.ts` и `tools/test/check-mutation-ratchet.test.ts` зелёные.
3. Доказательство: ближайший ночной прогон с предложением и без открытого PR — PR создан автоматикой, джоба зелёная, на этом PR `ci.yml` и `gate-integrity.yml` запустились без действий человека; ссылки на PR и прогоны — в «Журнале».

## Критерии приёмки

- В «Журнале» — решение владельца: вариант и дата.
- При А и Б: ночной прогон с предложением и без открытого PR — шаг публикации зелёный, PR создан автоматикой (ссылка на PR и прогон в «Журнале»); на PR, созданном автоматикой, `ci.yml` и `gate-integrity.yml` запустились без действий человека — при А триггером из пункта 1, при Б сами (ссылки на прогоны в «Журнале»); `docs/architecture.md:216-217` описывает фактический контур; отказ create по-прежнему красит шаг, канарейки «PR создан или громкая ошибка» зелёные; токен в логе не появляется; `pnpm verify` зелёный.
- При В: задача закрыта записью в «Журнале», правок нет.

## Решение

- **Задача — выполнение условия возврата e40/e82.** Выбранного варианта у задачи нет: включение настройки репозитория, токен, секрет — действия, которые остаются человеку (ADR 0009, «Что остаётся человеку»); агент их не выполняет ни при каком тексте задачи. Поэтому `needs_human` — «человек: …», а сравнение вариантов вынесено в «Что сделать», чтобы решение принималось по фактам, а не по памяти.
- **Почему не оставить ручное открытие молча.** Мера из e40 — «чаще одного PR в неделю» — превышена за день, и с каждым новым храповиком ручных PR становится больше.
- **Альтернатива — не заводить вопрос вовсе** (продолжать открывать руками): совпадает с вариантом В, но должна быть записанным решением, а не умолчанием. Условие возврата при В: та же мера остаётся — вернуться, если ручное открытие снова станет узким местом (чаще одного PR в неделю).
- **А не свободен от кода и не дёшев по гейту; Б — по секрету.** У А нет нового секрета, но без нового способа запуска проверок на PR автоматики они не придут, а события доверенного `gate-integrity.yml` запрещено добавлять вне режима обслуживания и ревью мейнтейнера (`.github/workflows/gate-integrity.yml:4-5`). У Б новый секрет и новое доверие (возражение e40), зато `pull_request`-прогоны идут сами и гейт не трогается. Вариант — за владельцем, маршрут запуска при А — за исполнителем.
- **Очередность с e83.** Не пересекаются по `touches`; e83 до исправления блокирует merge PR #289, на исход e85 не влияет. При А правки могут пересечься с `touches` e83 (`tools/test/check-mutation-ratchet.test.ts` — канарейка текста шага публикации): браться после закрытия e83.

`touches` — `docs/architecture.md`: правится при А и Б, это мягкий путь, объявлять обязательно (ADR 0023), пересечением не считается. Защищённые пути задача правит и при А, и при Б; в `touches` их нет — добавит мини-PR расширения, когда выбран вариант и известен список файлов. При А: `.github/workflows/nightly.yml` (запуск проверок после create), `.github/workflows/gate-integrity.yml` (запуск на PR автоматики), логика публикации `tools/check-test-count.ts` и `tools/check-mutation-ratchet.main.ts` с канарейками `tools/test/**` — deny (`tools/protected-paths.json:29`, `:74`, `:58`, `:114`). При Б: `.github/workflows/nightly.yml` (передача токена) — deny (`:29`). При В правок нет. Задачу ведёт оператор при А и Б (режим обслуживания, ADR 0009); без защищённых путей только В. Условное замыкание в `touches` не объявлено: новых файлов гейт-контура задача заведомо не создаёт, появится — добавит мини-PR расширения. Label и merge — поезд по поручению владельца.
