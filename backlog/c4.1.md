# C4.1. Структурные логи, идентификатор запроса и таксономия ошибок

**Проблема.** Логи API неструктурированы, запрос нельзя проследить от web до домена, ошибки домена не отличимы по таксономии. Без этого нечего прикладывать к отчёту E2E (задача C4) и нечем разбирать дефект после деплоя (C3.2).

Продуктовая часть бывшей C4: защищённых путей не трогает, её берёт обычный агент.

## Что сделать

- Структурные логи API (JSON, одна запись — одно событие) с идентификатором запроса. Идентификатор принимается из заголовка или создаётся на входе, возвращается в ответе и проходит через прокси `/rpc` из web (ADR 0005).
- Единая таксономия ошибок на основе типизированных ошибок oRPC в `packages/contracts`: клиент различает ошибки по коду, а не по тексту. Contract-first: сначала контракт, затем `openapi.json` (скил `api-contract-change`).
- В лог не попадают тела запросов и значения секретов; тест на это обязателен.
- Трейсы OpenTelemetry — только если обходится без новой инфраструктуры в тестах; иначе записать в «Журнал» как отложенное с условием.

## Решение (2026-11-15)

- **Логгер без новой зависимости, если хватает `console` с JSON-сериализацией и middleware Hono.** Почему: правило репозитория — зависимости только при реальной необходимости; формат записи важнее библиотеки.
- Альтернатива: `pino`. Взять, если понадобятся уровни по окружению, редактирование полей или производительность под нагрузкой перфа; версия — в `catalog:`, обоснование — в PR.
- Условие возврата: перф-бюджет p95 API краснеет из-за логирования.

## Критерии приёмки

- Каждое событие лога несёт идентификатор запроса; идентификатор из ответа находит записи этого запроса в логе (тест).
- Ошибки домена типизированы и различимы клиентом по коду; тесты обоих транспортов.
- Тест: тело запроса и значения секретов в лог не попадают.

## Журнал

- 2026-11-15: выделена из C4 по итогам аудита; C4 сужена до доставки логов в отчёт Playwright и зависит от этой задачи.
