# C3.2. Production-сервер: entry, Dockerfile, readiness

**Проблема.** Web запускается через `vite preview` — это не production-сервер; production-способа запуска нет ни у человека, ни у агентов.

## Что сделать

- Добавить серверный entry в оба приложения (выбор — в разделе «Решение»).
- Dockerfile и readiness-проверка: контейнер стартует, readiness отвечает, сборка минимальна по размеру.
- E2E и перф позже переключаются на тот же способ запуска (отдельная задача C3.4), чтобы тестировалось то, что деплоится.

## Решение (2026-11-15)

Выбор делегирован человеком агенту в сессии 2026-11-15; принимается merge PR с этой правкой (ADR 0009, «Развилки в задачах»).

- **Node без Nitro.** API уже работает на `@hono/node-server`; web получает тонкий собственный entry на Node: раздаёт статику сборки, проксирует `/rpc` на `API_URL` (ADR 0005) и отдаёт остальное обработчику TanStack Start из серверной сборки.
- Почему: одна модель запуска для обоих приложений; прокси `/rpc` и readiness остаются явным кодом под тестами, а не конфигурацией пресета; Nitro добавляет слой сборки и меняет раскладку артефактов, что потянуло бы правку бюджета бандла; меньше зависимостей.
- **Запасной вариант без вопроса человеку.** Перед реализацией сверить по актуальной документации TanStack Start версии из `catalog:`, отдаёт ли серверная сборка fetch-обработчик без Nitro. Если нет — взять Nitro с пресетом `node-server`, записать в «Журнал» версию и ссылку на документацию и продолжить.
- Условие возврата к Nitro как основному варианту: появляется цель деплоя не на Node (serverless, edge).
- Решение оформляется ADR «production-сервер и деплой» тем же PR (architecture.md, раздел 5).

## Критерии приёмки

- Локальный запуск production-entry зелёный; Docker-образ собирается, readiness отвечает; `vite preview` больше не упоминается как способ запуска web.
