# E86. Доказательство e85 живым прогоном: ссылки в «Журнале» и сверка допущений

**Проблема.** Критерий приёмки e85 — доказательство живым прогоном: ночной прогон с предложением и без открытого PR создаёт PR автоматикой, на нём без действий человека запускается `ci.yml` (`backlog/done/e85.md`, «Что сделать», п. 3, и «Критерии приёмки»; ссылки на PR и прогоны — в «Журнале»). До merge его исполнить нельзя: PR создаёт ночная джоба на `main`. Исполнитель перенёс доказательство записью «после merge» в «Журнале» e85, но файл задачи закрывается тем же PR (`git mv backlog/e85.md backlog/done/e85.md`), и после merge ссылкам взяться неоткуда — первый ночной прогон с критериями никто не сверит. Допущения маршрута (а) «`ci.yml` диспатчем» и (б1) «гейт запускает событие человека» приняты по документации GitHub и по исходникам, на живом прогоне не воспроизводились. Обязательная находка ревью PR e85 (major).

Вне задачи: правки кода и workflow. Подтверждённое расхождение — запись в «Журнале» и новая задача со своими `touches` (защищённые пути — оператор, ADR 0009); «подкрутить» поведение здесь нельзя.

## Что сделать

Условие открытия — в `needs_human`: снимается PR-ом в main (как `work/e85-decision`, #291), когда ночной прогон уже создал PR автоматики. Дальше — по первому такому PR:

1. **Ночной прогон.** `gh run list --workflow nightly.yml --branch main --limit 10 --json databaseId,createdAt,conclusion`: джоба `test-count-ratchet` (шаг «PR with raised baseline», `.github/workflows/nightly.yml:329-332`) или `mutation-ratchet` (шаг «PR with raised thresholds», `:220-223`) зелёная; в логе шага — «PR храповика создан: …» (`tools/check-test-count.ts:626`, `tools/check-mutation-ratchet.main.ts:1017`) и остаточное событие человека (`GATE_NOTE` — `tools/check-test-count.ts:282`, `tools/check-mutation-ratchet.main.ts:574`).
2. **PR.** `gh pr view <N> --json author,createdAt,headRefName,headRefOid`: автор — `github-actions[bot]`.
3. **`ci.yml` — маршрут (а).** Прогон на ветке PR: событие `workflow_dispatch`, head SHA прогона равен head SHA PR на момент создания, check `gate` зелёный. Записать, не было ли на PR `pull_request`-прогона `ci.yml` (workflow слушает `pull_request`, `merge_group`, `push` в `main` и `workflow_dispatch` — `.github/workflows/ci.yml:4-19`) и каким прогоном закрыт обязательный check `gate`.
4. **`gate-integrity.yml` — маршрут (б1).** Прогон пришёл событием человека: для храповика числа тестов — synchronize либо reopened, для мутационного — `labeled` (обязательный label); какое именно — по timeline PR. `gate-integrity` и `bundle-approval` зелёные; действий сверх обязательного label — ноль.
5. **Токен.** В логе шага публикации значения токена нет.
6. **Бюджет `test:hooks`.** Ночной job `verify-budgets` зелёный: в e85 добавлено два запуска шага, порог 50 с не трогать — красный значит, что калибровку решает человек.
7. **Допущения** — по каждому строка в «Журнале»: «подтвердилось» / «не подтвердилось» / «не было повода», со ссылкой на прогон:
   - Д1. На PR, созданном и обновлённом под `github.token`, события `pull_request_target` прогонов `gate-integrity.yml` не рождают — без действия человека гейт не приходит. Принято по общему правилу [страницы GitHub](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow) о запуске workflow из workflow: про `pull_request_target` она не говорит («Журнал» e85, круги ревью 1–2).
   - Д2. `pull_request`-прогоны на таком PR не появляются либо ждут одобрения человека («Approve workflows to run») и merge не блокируют: обязательный check `gate` закрывает диспатчевый прогон. Если на ветке появился ожидающий `pull_request`-прогон — записать, держит ли он check `gate` и merge (гипотеза, не факт).
   - Д3. Диспатч сразу после push попадает в текущий head ветки, а не в прежний коммит (`startCi` — `tools/check-test-count.ts:471`, `tools/check-mutation-ratchet.main.ts:742`; вызов после push под открытым PR — `:605`, `:996`). Условие возврата e85: ненадёжно — REST `…/dispatches`, как в `.github/workflows/visual-approve.yml:256`.
   - Д4. `bundle-approval` зелёный без единого `pull_request`-прогона `ci.yml`: job идёт только на `pull_request_target` (`.github/workflows/gate-integrity.yml:158`), check-run `bundle-delta` ищет по head SHA через API, без единого check-run — красный (`:152-155`, `:194-199`). Должен находить check-run диспатчевого прогона (гипотеза ревью e85, не установленный дефект). Проверяется на первом PR автоматики любого храповика: `ci.yml` на обоих приходит только диспатчем.
   - Д5. Под открытым PR ночь с превышением добавляет коммит: новый head SHA, `gate` перезапускается диспатчем, событие для `gate-integrity` нужно заново — «не больше одного действия на PR» держится, пока PR смержен до следующей ночи (расписание — `.github/workflows/nightly.yml:6`; находка e85 без исправления). Повод — только если PR пережил ночь.
8. Ссылки на ночной прогон, PR, прогоны `ci.yml` и `gate-integrity.yml` — в «Журнале» этой задачи. В «Журнал» e85 дословно их не дублировать: правка чужого файла доски на ветке задачи запрещена (`tools/check-docs.ts:371`), указатель на эту задачу в «Журнале» e85 уже стоит.

## Критерии приёмки

- В «Журнале» — ссылки на ночной прогон, PR автоматики, прогон `ci.yml` (диспатч) и прогон `gate-integrity.yml` с названным событием; `gate`, `gate-integrity` и `bundle-approval` на PR зелёные — выводы `gh` приведены.
- Допущения Д1–Д4 — по каждому «подтвердилось» или «не подтвердилось» со ссылкой на прогон; «не было повода» — только для Д5 (PR смержен до следующей ночи) и для остаточного события того храповика, чей PR не возникал, — с тем, что смотрел.
- «Не подтвердилось» — новая задача (для маршрута (б2) — задача на ADR) записана в «Журнале» и заведена в `backlog/`; код и workflow здесь не правились: `git diff origin/main...HEAD --stat` — только файл задачи.
- Токен в логе шага публикации не появился.

## Решение

- **Задача-продолжение вместо записи «после merge» в e85** (решение по находке ревью, 25.11). Почему: у e85 после merge нет ни ветки, ни исполнителя — запись «ссылки добавить сюда» некому исполнить; открытая задача видна в `pnpm backlog list` и `pnpm backlog inbox`. Альтернатива — оставить как есть: отклонена, это и есть находка. Альтернатива — дописать ссылки в «Журнал» e85 с ветки этой задачи: отклонена, `tools/check-docs.ts:371` запрещает менять чужой файл доски на `task/<id>`; ссылки идут в «Журнал» e86, в e85 — указатель.
- **`needs_human: отложено:`** — задача ждёт проверяемого условия (ADR 0009): до первого PR автоматики браться не за что, захват раньше времени дал бы брошенную ветку. Снимается PR-ом в main.
- **Закрытие по первому PR автоматики, любого храповика.** Почему: непроверенное в e85 — поведение GitHub в отношении PR, созданного ботом (Д1–Д4), оно от храповика не зависит; различие храповиков — только остаточное событие (`GATE_NOTE`), его держат канарейки, исполняющие текст шагов (`tools/test/test-count-ratchet.test.ts`, `tools/test/check-mutation-ratchet.test.ts`). Альтернатива — ждать PR обоих храповиков: отклонена, мутационный PR возникает редко, задача висела бы без работы. Условие возврата: расхождение на первом PR второго храповика — обычный дефект (PR-исправление и строка в `docs/escaped-defects.md`), эта задача не переоткрывается.
- `touches` пуст: правится только файл задачи. Защищённых путей нет — ведёт обычная сессия.
- Условие возврата e85 сохраняется: остаточное действие стало чаще одного PR в неделю — задача на ADR по маршруту (б2).

## Журнал

Допущения Д1–Д5 собраны из «Журнала» e85 и находки ревью; строки кода и workflow сверены в worktree (HEAD `91918f7b`; `grep -n`, `sed -n`).
