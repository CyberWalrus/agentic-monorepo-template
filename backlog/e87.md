## Решение

- **По обоим шагам — пересчёт от факта раннера, а не разгон шага (вариант по умолчанию).** Для `lint` ускорять нечего: входы линтера между `de9ce87a` и `6997ff4d` не менялись (`git diff --stat de9ce87a..6997ff4d -- .oxlintrc.json package.json pnpm-workspace.yaml pnpm-lock.yaml` — пусто), а ряд растёт синхронно с шагами вне диффа: седьмой прогон ряда против пятого — `lint` ×1.38, `typecheck` ×1.47, `test` ×1.49, `knip` ×1.52, `test:hooks` ×1.34 (расчёт по ряду из «Проблемы»). Для `test:hooks` разгон меньше шума: варианты из `backlog/done/e14.md:35` — `isolate: false` даёт ~4 с по оценке vitest (в корневом `vitest.config.ts` не включён: `grep -n isolate` пуст), а полоса шума даёт +15 с к медиане успешных (51.1 против 36.3 с). Разгон отодвинет следующий красный, но не снимет его.
- **Формула правила (проект; числа в PR — от свежих артефактов):** порог = медиана последних 5 успешных ночных прогонов × 1.8, вверх до целой секунды. Множитель выше полосы шума — она до ×1.7 (`backlog/done/e12.md:34`, сбойный прогон медленнее успешных в ×1.5–1.7; 25.11 `lint` — ×1.47) — и ниже ×2: детектор регрессии сохраняется. Окно из пяти прогонов, а не десяти: факт меняется за дни — e12 перекалибровалась через день после мержа e9 (`backlog/done/e12.md:35`). Ориентир по ряду разбора (не замер): `lint` — медиана 12.8 с → 24 с (сейчас 16); `test:hooks` — медиана 38.1 с → 69 с (сейчас 50).
- **Триггер и классификация (проект).** Один красный по времени шага — сначала причина, по трём признакам: (а) три и больше шагов вне диффа одновременно медленнее своих медиан на 30% и больше — шум раннера: перезапуск прогона — подтверждающий замер, порог не трогать, пока красный не повторится в двух из последних пяти прогонов; (б) в диффе с последнего зелёного выросла работа шага — запланированный рост: пересчёт по формуле, доля роста — в «Журнале» задачи; (в) ни то, ни другое — регрессия шага: чинить шаг, порог не трогать. Остальные шаги тем же PR не пересчитывают, кроме тех, у кого максимум ряда ≥ 85% бюджета, — они в одном шуме от красного. Для этой задачи триггер уже есть: третий красный класса за неделю (19.11, 21.11, 25.11) и 97% / 94% в прогоне перед красным.
- **Правило первым PR, пересчёт вторым, строка реестра в PR 1.** Почему: по `docs/adr/0009-operator-delegation.md:36` пересчёт без правила — ослабление, которое предлагает только человек; после merge правила оператор ставит число по правилу, а человек принимает PR. Строка реестра идёт с правилом: контур, который должен был поймать случай, появляется в PR 1. Альтернатива — один PR на всё: отклонена, смешивает review-класс и `deny` и не даёт принять правило отдельно от чисел.
- **Реестр пропущенных дефектов: строка нужна.** Почему: числа e12 прошли все гейты (защищённый файл, одобрен человеком в PR), а запас оказался внутри полосы шума — после merge тот же порог `test:hooks` красил `canaries` на раннере CI 21.11 (`backlog/done/e14.md:35`), а 25.11 — ночной `verify budgets`. Разбор считает, что гейт сработал как задумано; для самого превышения это верно, но в реестр идёт не превышение, а калибровка, которая его допустила. Текст строки: 2026-11-25 — калибровка бюджетов времени verify (`verify-budgets.json`, e12 — #72, #74, 19.11): запас «факт + ~30%» меньше полосы шума раннера (до ×1.5–1.7), правила пересчёта в ADR 0009 не было; нашёл ночной `verify budgets`, повтор после merge — 21.11 и 25.11; контур — правило ADR 0009 (эта задача); автоматический гейт невозможен, потому что полоса шума видна только из истории ночных прогонов, которой нет на PR. Альтернатива — не регистрировать: отклонена, иначе третий повтор класса за неделю не попадёт в метрику (`docs/escaped-defects.md:3`, `docs/vision.md`, «Метрики системы»). Перед записью сверить даты и номера PR с git и `backlog/done/`.
- **Запасной вариант — разгон шага.** Условие переключения: после пересчёта `test:hooks` снова красный по времени в течение пяти ночных прогонов или медиана успешных прогонов без сигнатуры шума выше 85% нового порога — заводится задача на разгон сюита по вариантам `backlog/done/e14.md:35` с замером до/после; для `lint` то же условие даёт задачу на профиль шага. Третий подъём порога по одному шагу без такого замера не делать.
- **Отклонено: автоматический пересчёт ночью** (ночная джоба готовит PR по образцу храповиков b2.4 и e85). Нужны новый инструмент в `tools/` и правка `nightly.yml` — отдельная задача. Условие возврата: пересчёты по правилу чаще одного в месяц.
- **Отклонено: шумоустойчивый детектор в `tools/verify.ts`** (красить шаг только без сигнатуры шума). Правка гейта и его замыкания (ADR 0014), риск пропустить реальную регрессию вперемешку с шумом. Условие возврата то же.
- `touches`: `verify-budgets.json` и `docs/adr/0009-operator-delegation.md` правятся наверняка. `docs/escaped-defects.md` — общий путь, в `touches` не объявляется. `.github/workflows/nightly.yml` и `docs/architecture.md` (З7, `:40`, если ревью попросит оговорку) — только через мини-PR расширения `touches`. Новых файлов гейт-контура задача не создаёт.
