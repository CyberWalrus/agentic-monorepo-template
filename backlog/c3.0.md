# C3.0. Схема окружения на Zod: один модуль чтения в каждом приложении

**Проблема.** Схемы окружения нет: переменные читаются напрямую — `process.env` в `apps/api/src/server.ts`, окружение в `apps/web/src/lib/api-client.ts`. Неверное или пропущенное значение обнаруживается в момент использования, а не при старте.

Продуктовая часть бывшей C3.1: защищённых путей не трогает, её берёт обычный агент. Правило линтера и проверку примера окружения подключает оператор задачей C3.1.

## Что сделать

- В каждом приложении — один модуль окружения: читает переменные, проверяет схемой Zod и отдаёт типизированный объект. В API опереться на существующий `apps/api/src/server-config.ts`: расширить его, а не заводить второй.
- Остальной код `src/` получает значения из модуля; прямых обращений к `process.env` и `import.meta.env` вне модуля не остаётся.
- Невалидное окружение — отказ при старте с перечнем переменных и причин, без значений секретов в сообщении.
- Тесты модуля: пропущенная обязательная переменная, неверный формат, значения по умолчанию.

## Что учесть

- Конфиги сборки и тестов (`vite.config.ts`, `vitest.config.ts`, `e2e/playwright.config.ts`) читают окружение сами — это не код приложения, и часть из них защищена. Их задача не трогает; исключения для них оформит C3.1 в правиле линтера.
- Файл примера окружения здесь не создавать: его имя и проверка — решение C3.1.

## Критерии приёмки

- В `apps/api/src` и `apps/web/src` окружение читает ровно один модуль на приложение (в PR — вывод поиска по `process.env` и `import.meta.env`).
- Тесты модуля зелёные; старт с невалидным окружением завершается ошибкой с перечнем переменных.

## Журнал

- 2026-11-15: выделена из C3.1 по итогам аудита, чтобы C3.2 (production-сервер) не ждал оператора. Осознанный компромисс: до C3.1 правило «только один модуль» держится тестом и ревью, а не линтером.
