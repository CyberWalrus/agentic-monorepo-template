# C1. Постоянное хранилище: Postgres и Drizzle

**Проблема.** Демо-домен хранит данные в памяти. Шаблону нужен образец работы с постоянным хранилищем — области, где сгенерированный код ошибается чаще всего. Задача декомпозируется: репозиторий, контрактные тесты, миграции и изоляция — отдельные задачи.

## Что сделать

- Реализация `TaskRepository` на Postgres за существующим интерфейсом.
- Контрактный набор тестов репозитория: один набор прогоняется против обеих реализаций.
- Миграции: гейт «схема совпадает с миграциями», правило expand/contract, каталог миграций в классе `review`.
- Изоляция тестов. Unit и integration: Postgres внутри процесса (PGlite) или база на воркер из шаблона. E2E: изоляция по арендатору или рабочему пространству на тест вместо общего сброса данных. Тогда `SHARED_DATA_LOCK` не нужен, а visual и perf перестают быть последовательными.

## Подводные камни

- PGlite не является полным Postgres (расширения, блокировки, параллелизм), поэтому контрактный набор обязан идти и против настоящего Postgres в CI.
- Drizzle остаётся на 0.45.x, версия 1.0 не вышла: закрепи точную версию и не выпускай типы Drizzle за пределы репозитория.
- Эндпоинт сброса данных с настоящей базой опаснее, чем с памятью.
- Перф-бюджет API придётся перекалибровать.

## Критерии приёмки декомпозиции

- Файлы задач с `depends_on` и `touches`; контрактный набор тестов — отдельная задача от реализации репозитория, миграции идут раньше изоляции E2E.
