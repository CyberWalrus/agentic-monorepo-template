# E15. Границы: три дыры dependency-cruiser и их канарейки

**Проблема.** Три правила границ не покрывают весь путь нарушения (аудит 2026-11-20, линза архитектуры; сейчас код чист — дыры гипотетические, это укрепление, не починка):

1. `not-to-dev-dep` матчит `from.path: '^(apps|packages)/[^/]+/src/'` и не покрывает production-entry `apps/web/server.ts` (корень пакета — слот TanStack по ADR 0012): импорт devDependency в entry пройдёт гейт и сломается только в рантайме образа (`pnpm deploy --prod` прунит devDeps).
2. Нет правила «общий слой не импортирует фичи»: `apps/web/src/lib/**` → `features/**` не ловится, хотя lib обязан быть общим дном (обратное правило для фич есть).
3. Правило «домен не знает о транспорте» блокирует только `app.ts|router.ts|server.ts`, но `src/authorization.ts` импортирует `@orpc/server` — модуль `src/tasks/*` может протянуть oRPC в домен через него мимо гейта.

## Что сделать

- Расширить `from` правила dev-dep на production-entry (`apps/*/server.ts`).
- Правило `web-lib-not-to-features`.
- Расширить правило домена на пограничные адаптеры (`authorization.ts`, `observability.ts`, `server-config.ts`) — модулям домена запрещены и они.
- Каждому правилу — канарейка-нарушитель в `tools/test/` по З6: новое правило границ добавляется вместе с канарейкой.

## Решение

- **Расширение правил вместо документирования исключений.** Почему: машинная проверка держится сама, соглашение в architecture.md — дрейфует; прецедент уже есть — все три запрета из AGENTS.md закрыты правилами, у каждого есть живой нарушитель в классе.

## Критерии приёмки

- Канарейки: каждое из трёх правил красится тестом-нарушителем; `pnpm verify` зелёный на чистом дереве.
