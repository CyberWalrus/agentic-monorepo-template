## Claude Code

### Что работает автоматически (хуки в `.claude/settings.json`)

- **Запись в защищённые пути** (`Edit`/`Write`) блокируется хуком `protect-paths`. Причина приходит тебе в ответе инструмента.
- **Опасные команды** блокируются хуком `guard-bash`: обновление базлайнов (включая `playwright test -u`), пропуск git-хуков (`--no-verify`, `commit -n`, `core.hooksPath`, `LEFTHOOK=false`/`LEFTHOOK_EXCLUDE`), force-push (включая refspec `+HEAD:branch`), запись в защищённые файлы через shell (учитывает `cd` внутри команды).
- **Проверка по результату**: на старте сессии снимается содержимое защищённых файлов. Если после команды Bash защищённый файл изменился — даже способом, прошедшим мимо запретов, — хук вернёт файл к снимку и объяснит отмену; на Stop это блокирует завершение. Дрейф, совпавший с новым HEAD (pull/merge принёс изменения), перебазирует снимок. Новые файлы под защитой не удаляются — только сообщаются ([ADR 0003](docs/adr/0003-result-based-protection.md)).
- **Песочница ОС** ([ADR 0004](docs/adr/0004-sandbox.md)): команды Bash исполняются в песочнице — запись в защищённые пути запрещена на уровне ОС, сеть ограничена (npm-реестр и localhost), выход из песочницы запрещён. Не пытайся обойти её и не проси пользователя отключить её: если легитимной команде не хватает доступа, остановись и объясни, какого пути или домена не хватает.
- **Хуки защиты падают закрытыми**: при сбое действие блокируется (exit 2), а не пропускается. Хуки не зависят от `node_modules`: общая логика живёт в `tools/`, хуки — тонкие адаптеры. Тесты гейтов — `tools/test/` (шаг `test:hooks` в `pnpm verify`).
- **После каждой правки** файл форматируется Oxfmt и проверяется Oxlint (type-aware). Ошибка линта приходит тебе сразу, исправь её до следующего шага.
- **Перед завершением** хук `Stop` запускает `pnpm verify --json`, если относительно merge-base с `main` есть изменения кода — в том числе закоммиченные; docs-only изменения проверку не запускают. Повторный Stop на том же состоянии не гоняет verify повторно (хранится отпечаток зелёного прогона вне репозитория). Пока verify красный, завершить работу нельзя; после 3 неудачных попыток подряд хук отпускает, но ты обязан сообщить пользователю, что гейты красные.

Файлы пиши через Edit/Write, а не через `cat > file` или `sed -i`: shell-guard проверяет команды по смыслу и может отказать там, где Write прошёл бы.

### Если человек поручил изменить сам гейт

Иногда изменение гейта осознанно: новый бюджет, правка CI, обновление правил. Агент сам этого сделать не может. Человек включает режим обслуживания на время сессии: создаёт `.claude/settings.local.json` с `{"disableAllHooks": true, "sandbox": {"enabled": false}}` (файл в `.gitignore`, агенту запись в него запрещена; песочница отключается отдельно — `disableAllHooks` её не выключает, а `denyWrite` на `tools/**` сделал бы обслуживание невозможным) и **обязан удалить файл после работы**: пока файл существует, хуки и песочница выключены, и напомнить об этом нечем — напоминание технически невозможно, границей остаётся CI ([ADR 0004](docs/adr/0004-sandbox.md)). В CI такое изменение всё равно требует label `gate-change-approved` и ревью CODEOWNERS. Label действителен, только если его поставил мейнтейнер (глобальный владелец CODEOWNERS) **после последнего push** PR: `gate-integrity` снимает label на новый push и проверяет автора события ([ADR 0002](docs/adr/0002-gate-integrity.md)). Ставь label последним шагом, после финального пуша.

### Скилы (`.claude/skills/`)

| Скил                  | Когда                                             |
| --------------------- | ------------------------------------------------- |
| `feature-workflow`    | Любая новая фича или заметное изменение поведения |
| `writing-tests`       | Пишешь или правишь тесты любого уровня            |
| `api-contract-change` | Меняешь API или контракт                          |
| `visual-diff-triage`  | Упали скриншот-тесты                              |
| `perf-regression`     | Упал перф-бюджет или бюджет бандла                |

### Субагенты-ревьюеры (`.claude/agents/`)

Ревьюеры только читают и возвращают находки с серьёзностью. Код они не правят.

| Агент                    | Этап      | Фокус                                                                                  |
| ------------------------ | --------- | -------------------------------------------------------------------------------------- |
| `architecture-reviewer`  | План и PR | Границы, слои, связность, нужен ли ADR                                                 |
| `sanity-reviewer`        | План и PR | Здравый смысл: решает ли изменение задачу, нет ли переусложнения и лишних зависимостей |
| `test-quality-reviewer`  | PR        | Полнота и качество тестов, флак-риски, выжившие мутанты                                |
| `security-reviewer`      | PR        | Валидация входа, секреты, CORS, тестовые эндпоинты, зависимости                        |
| `product-logic-reviewer` | PR        | Соответствие требованиям, состояния UI (пусто/ошибка/загрузка), доступность            |

Запускай независимых ревьюеров параллельно. Блокеры исправь, спорное вынеси пользователю.

### Playwright Test Agents

`playwright-test-planner`, `playwright-test-generator`, `playwright-test-healer` сгенерированы `tools/playwright-agents.sh` и дополнены политикой репозитория: Healer не имеет права помечать тест `fixme`/`skip`. Если приложение работает неправильно, это баг, о котором надо сообщить. Перегенерируй агентов после обновления Playwright тем же скриптом.

### MCP (`.mcp.json`)

- `playwright` — управление браузером для исследования и воспроизведения багов (accessibility-снапшоты, а не скриншоты).
- `playwright-test` — test runner для Test Agents (запуск, отладка, генерация локаторов).
- `chrome-devtools` — perf-трейсы, Lighthouse, heap snapshots при разборе перф-регрессий. Телеметрия выключена.

Агентный прогон по UI дорогой: $15–30, контекст растёт со снапшотами. Используй его для исследования и отладки, а регрессию закрепляй детерминированными тестами.
