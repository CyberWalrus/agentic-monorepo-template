# План развития обвязки

> Статус: действует · Дата аудита: 2026-11-12 · Проверенное состояние: ветка `feat/monorepo-foundation`, коммит `0c6fe45`
> Для кого: агенты и люди, которые развивают сам шаблон.
> Правила, которым должно соответствовать любое изменение: [architecture.md](architecture.md). Номера вида З3 ссылаются на законы из её первого раздела.

## Как работать с этим документом

1. Бери одну задачу за раз. Задачи одной части упорядочены по важности, общий порядок дан в [конце документа](#порядок-работ).
2. Сначала воспроизведи доказательство из раздела «Проблема». Код мог измениться после аудита. Если дефекта уже нет, удали задачу отсюда.
3. Посмотри на пометку:
   - 🔒 задача меняет защищённые пути (`tools/protected-paths.json`). Агент их менять не может и не должен искать обход. Подготовь план и попроси человека включить режим обслуживания, порядок описан в [architecture.md](architecture.md#4-как-менять-саму-обвязку).
   - 🔓 задачу можно делать сразу. Пути класса `review` потребуют ревью CODEOWNERS.
   - 👤 нужно решение человека (порог, выбор варианта, ADR). Подготовь варианты с последствиями и остановись.
4. Сначала напиши канарейку, которая красная до изменения, затем чини.
5. Когда задача закрыта, удали её отсюда и переведи связанное правило в architecture.md из «целевое» в «действует».

Приоритеты: часть A закрывает дыры в гарантиях, часть B повышает качество и готовит к масштабу, часть C добавляет недостающие возможности.

## Итог аудита

Скорость уже отличная. Слабое место в другом: несколько гейтов можно обойти, а несколько не ловят то, ради чего созданы. Для системы, смысл которой в том, что агент не может ослабить проверку, это главный долг.

Что сделано хорошо и должно сохраниться:

- Один вход `pnpm verify` с режимом `--json`, шаги идут параллельно.
- Contract-first: один контракт для фронта, бэка и OpenAPI, дрейф ловится гейтом.
- Границы модулей заданы правилами dependency-cruiser, а не договорённостью.
- Сообщения гейтов говорят агенту, что делать и чего не делать.
- Supply-chain настройки pnpm: строгий каталог, задержка свежих релизов, запрет install-скриптов.
- Единый список защищённых путей для хука и CI.

Замеры (macOS, 16 ядер, демо-домен): `pnpm verify` с кэшем 0.8–1.0 с. Без кэша: typecheck 0.4 с, unit 1.4 с, сборка 0.7 с, E2E 2.5 с, перф 5.2 с, мутации API 2.3 с при счёте 100% (66 мутантов). CI на GitHub в рамках аудита не запускался.

Все утверждения в разделах «Проблема» проверены чтением кода или прогоном. Там, где вывод опирается на документацию или вторичный источник, это сказано явно.

### A3. 🔒 `test-integrity` пропускает большинство способов ослабить тест

**Проблема**

Проверено на файле-образце с девятью приёмами. Регулярное выражение из [check-test-integrity.ts:8](../tools/check-test-integrity.ts) не поймало ни одного, Oxlint с конфигом репозитория поймал один (`it.concurrent.skip`). Проходят оба гейта:

- `it.fails(...)` (в Vitest модификатор называется `fails`, выражение ищет `fail`);
- `it.skipIf(true)(...)` и `it.runIf(false)(...)`;
- `test('…', { skip: true }, …)`;
- `context.skip()` внутри теста;
- ранний `return` перед `expect`;
- `// Stryker disable all`, который выключает мутации;
- `/* v8 ignore start */`, который выключает покрытие.

**Что сделать**

1. По З3 проверять отчёт раннера, а не синтаксис. Vitest и Playwright умеют писать JSON-отчёт. Гейт требует, чтобы во всех проектах, входящих в гейты, число тестов со статусом skipped, todo и expected failure было равно нулю.
2. Регулярное выражение оставить для того, чего отчёт не видит: комментариев подавления (`Stryker disable`, `v8 ignore`, `istanbul ignore`, `c8 ignore`).
3. Храповик числа тестов: число тестов в пакете не уменьшается относительно merge-base без явного подтверждения. Для начала это предупреждение в сводке PR. Делать ли его блокирующим, решает человек 👤.
4. Файл-образец из аудита превратить в канарейку.

**Подводные камни**

- JSON-отчёт должен входить в `outputs` задачи Turborepo, иначе при попадании в кэш файла не будет и гейт упадёт или, хуже, прочитает старый отчёт.
- Проекты Playwright с `default: false` в обычном прогоне не участвуют. Гейт должен знать, какие проекты он обязан увидеть в отчёте.
- Ранний `return` перед `expect` детерминированно не ловится. Это область мутационного тестирования, см. [B2](#b2).

**Готово, когда** каждый приём из списка, кроме раннего `return`, роняет `pnpm verify` с сообщением, которое называет файл и тест.

### A5. 🔒 Параллельные агенты на одной машине мешают друг другу

**Проблема**

В [playwright.config.ts](../e2e/playwright.config.ts) порты заданы константами 3000 и 3001, а вне CI стоит `reuseExistingServer: true`. Если два агента работают в двух worktree, второй либо падает на занятом порту, либо, что хуже, молча прогоняет тесты против сервера первого, то есть против чужого кода. Результат может быть ложно зелёным. Это нарушает З9 и не даёт запускать `verify --full` параллельно.

**Что сделать**

1. Порты выводятся из worktree: базовый порт вычисляется из пути корня или берётся из `PORT_BASE`, web получает base, API получает base+1. Логика лежит в одном модуле в `tools/`, его используют конфиг Playwright, скрипты `dev` и `start`, k6.
2. Для гейтов `reuseExistingServer: false` всегда. Для ручной отладки нужен явный флаг.
3. `/health` возвращает идентификатор экземпляра (например, время старта и pid). Global setup Playwright сверяет его с сервером, который запустил сам. Тогда тест не может незаметно уйти в чужой процесс.
4. Адрес API не должен зашиваться в сборку web. Сейчас `VITE_API_URL` подставляется при сборке ([api-client.ts:7](../apps/web/src/lib/api-client.ts)), поэтому разные порты дают разные сборки и промахи кэша. Варианты: web-сервер проксирует `/rpc` на API (один origin, CORS не нужен), либо адрес передаётся серверу при старте и попадает клиенту через SSR. Выбор за человеком 👤, оформить ADR.
5. В новом worktree нужен `pnpm install`. Автоматизировать хуком `WorktreeCreate` или записать шаг в `AGENTS.md`.

**Подводные камни**

- Хеш пути может дать одинаковый порт двум worktree. Проверяй занятость, сдвигайся и записывай выбор в файл внутри worktree, добавленный в `.gitignore`.
- `WEB_ORIGIN` для CORS должен получать тот же порт, что и web.
- Перф-замеры при параллельной нагрузке шумят. Перф-прогон берёт блокировку на уровне машины (lock-файл), остальные тяжёлые задачи ждут.

**Готово, когда** два worktree одновременно проходят `pnpm verify --full`, а тест, которому подставили чужой сервер, падает с понятным сообщением.

<a id="a6"></a>

### A6. 🔒 👤 Перф-бюджеты не ловят регрессии, а бюджет бандла стоит вплотную

**Проблема**

| Метрика                | Факт     | Бюджет  | Запас    |
| ---------------------- | -------- | ------- | -------- |
| TTFB страницы `/`      | 6 мс     | 400 мс  | в 66 раз |
| LCP страницы `/`       | 32 мс    | 1500 мс | в 47 раз |
| Сценарий `create-task` | 95 мс    | 600 мс  | в 6 раз  |
| Сценарий `toggle-task` | 49 мс    | 400 мс  | в 8 раз  |
| JS всего, gzip         | 149.9 КБ | 160 КБ  | 6%       |
| Крупнейший чанк, gzip  | 125.8 КБ | 130 КБ  | 3%       |

- Десятикратная регрессия LCP пройдёт гейт. Бюджет бандла, наоборот, сработает на первой же фиче с зависимостью. Агент поднять его не может, и человек становится узким местом. Оба случая нарушают З7.
- Пороги времени откалиброваны на машине разработчика (это записано в ADR 0001). На общих раннерах GitHub абсолютные миллисекунды шумят, то же касается `p95 < 50 мс` в k6.
- Замер идёт на localhost без ограничения сети, поэтому LCP почти не зависит от веса страницы.

**Что сделать** (два уровня, З8)

1. Абсолютные пределы оставить как потолок допустимого опыта пользователя. Их редко меняет человек.
2. Регрессионный гейт: сравнение с merge-base в том же job на той же машине. Собрать базу и кандидата, прогоны чередовать (база, кандидат, база, кандидат), сравнивать медианы. Гейт падает, если ухудшение больше заданного процента и больше измеренного шума. Шум измеряется прогоном «база против базы».
3. Предпочитать детерминированные метрики: байты JS и CSS на маршрут, число запросов при загрузке страницы, число запросов к API на сценарий, число long tasks при замедленном CPU. Они ловят те же регрессии без шума.
4. Бандл: бюджет на маршрут (entry и его чанки), а не на всё приложение, плюс дельта-гейт: рост больше N КБ за один PR требует одобрения. Отчёт о дельте идёт в сводку PR.
5. Добавить ограничение сети через CDP, тогда LCP начнёт зависеть от веса страницы.

**Подводные камни**

- Сборка базы дорогая. Бери её из кэша Turborepo: сборка `main` там уже есть.
- У нового сценария нет замера в базе. Он проверяется только абсолютным пределом.
- Чередование удваивает время. В PR сравнивай затронутые сценарии, полный набор гоняй в merge queue и nightly.
- Пяти замеров мало для статистического вывода. Либо бери десять и больше и непараметрический критерий, либо держи порог заведомо выше шума.
- Инструментирующие сервисы (CodSpeed) допустимы как необязательный слой для микробенчмарков, но не как ядро (З12).

**Готово, когда** искусственная регрессия в канарейке (задержка 200 мс в обработчике, 30 КБ лишнего кода) роняет гейт, двадцать прогонов без изменений не дают ни одного ложного падения, а решение записано в ADR.

### A7. 🔒 Remote cache: правила доверия до подключения

**Проблема**

В [ci.yml:24](../.github/workflows/ci.yml) `TURBO_TOKEN` объявлен на уровне workflow и доступен всем job, включая те, что исполняют код PR. Код PR может записать в кэш артефакт «e2e пройден» для нужного хеша, а `gate` доверяет попаданию в кэш так же, как настоящему прогону. Подпись артефактов по документации Turborepo проверяет целостность и не является защитой, к тому же ключ лежал бы в том же окружении. Сейчас remote cache не настроен, поэтому это нужно решить до подключения. Отдельно: задача `perf` кэшируется, и замер с одной машины будет принят на другой.

**Что сделать**

1. Job в PR читают кэш, но не пишут: `--cache=local:rw,remote:r` (флаг есть в установленной версии Turborepo). Пишет только job на `push` в `main`.
2. Токен с правом записи выдаётся только этому job, через environment с ограничением по ветке.
3. Машины разработчиков и агентов получают токен только на чтение.
4. Для `perf` выключить кэш либо включить класс машины в `env` задачи.
5. Решить 👤, доверяет ли merge queue кэшу `main` для тестовых задач или прогоняет их принудительно.

**Подводные камни**

- Без записи из PR повторные прогоны того же PR remote-кэшем не ускоряются. Компенсируй это `actions/cache` для каталога `.turbo` с ключом по номеру PR, изолированно от `main`.
- Self-hosted сервер кэша должен уметь выдавать токены только на чтение. Проверь это до выбора реализации.

**Готово, когда** job из PR не может записать в remote cache (проверено попыткой), а правила перенесены в architecture.md как действующие.

### A8. 🔒 Базлайн можно создать на хосте, версия Docker-образа задана в двух местах

**Проблема**

- В [playwright.config.ts:16](../e2e/playwright.config.ts) вне CI стоит `updateSnapshots: 'missing'`. Проект `visual` запускается на хосте (`pnpm --filter @repo/e2e test:visual`), и недостающий базлайн запишется с рендерингом macOS, хотя базлайны без суффикса платформы существуют только для Linux-образа. У Vitest такая защита есть ([packages/ui/vitest.config.ts](../packages/ui/vitest.config.ts) бросает ошибку вне Linux), у Playwright нет.
- В [ci.yml:126](../.github/workflows/ci.yml) образ `v1.64.1-noble` вписан строкой, а локально версия берётся из установленного пакета. Renovate обновляет их одной группой, но гейта на совпадение нет.

**Что сделать**

1. В конфиге Playwright: `updateSnapshots` равно `none` всегда, кроме `VISUAL_UPDATE=1`. Проект `visual` бросает ошибку вне Linux-образа, как это делает конфиг Vitest. Это реализация З4 и замена попыткам распознать флаг `-u` в `guard-bash`.
2. Шаг в `verify`: версия образа в `ci.yml` равна версии `@playwright/test` из каталога.

**Готово, когда** запуск визуального проекта на хосте падает с объяснением и не создаёт файлов, а расхождение версий роняет `verify`.

### B1. 🔒 Канарейки гейтов, тесты для `tools/` и бюджеты времени

**Проблема.** Гейты являются главным продуктом репозитория, но у `tools/*.ts` и `.claude/hooks/*.ts` нет тестов. Дефекты аудита — открытая A3, закрытая 2026-11-13 A2 и закрытый 2026-11-12 A4 (`VIDEO` не доходил до задачи `e2e`) — показывают, что гейты уже расходятся с намерением. Принцип vision «превышение бюджета времени считается дефектом инфраструктуры» ничем не измеряется.

**Что сделать**

1. Unit-тесты на чистую логику (`protectionOf`, разбор команд, проверка бюджетов) отдельным Vitest-проектом в корне.
2. Канарейки: набор плохих изменений, каждое применяется к временному worktree и должно уронить конкретный шаг `verify`. Стартовый набор: импорт между фичами, `any`, приёмы из A3, устаревший `openapi.json`, неиспользуемый экспорт, версия зависимости мимо каталога, бандл сверх бюджета, изменение защищённого файла.
3. В `tools/verify.ts` бюджет на шаг и на весь прогон. Числа лежат в защищённом файле, в `--json` добавляется поле с бюджетом. Локально превышение даёт предупреждение (машины разные), в nightly роняет прогон.
4. Длительность job в CI пишется в сводку, тренд собирается в nightly.

**Подводные камни.** Канарейки работают во временном worktree и не трогают рабочее дерево. Запускать их нужно при изменении `tools/`, `.claude/hooks/` и конфигов гейтов, а также в nightly. В каждом PR они не нужны.

**Готово, когда** отключение любого правила в любом конфиге гейта роняет хотя бы одну канарейку.

### B2. 🔒 Качество тестов за пределами `apps/api`

**Проблема.** StrykerJS и пороги покрытия настроены только для `apps/api`. Самая сложная логика репозитория, `apps/web/src/features/tasks/use-tasks.ts` (оптимистичное обновление, отмена запросов, откат), не имеет прямого теста и не мутируется. То же касается `summarize.ts` и схем контрактов. Порог `break` равен 75 при фактическом счёте 100% (З7). Документация StrykerJS подтверждает: vitest-runner не поддерживает browser mode.

**Что сделать**

1. Логику фичи вынести в модули без React и тестировать в node-проекте. `use-tasks.ts` разделить на чистые функции над данными кэша (применить переключение, откатить) и тонкие хуки.
2. Подключить StrykerJS к `apps/web` (только node-проект, мутируются `*.ts` без `*.tsx`) и к `packages/contracts`.
3. Добавить пороги покрытия для node-части web и для контрактов.
4. Человек 👤 поднимает `break` до фактического уровня с небольшим запасом. Дальше работает храповик: nightly предлагает PR с повышением, когда счёт устойчиво выше порога.
5. В PR все мутанты в изменённых строках убиты. Исключения перечислены в PR с причиной, их видит ревьюер.
6. Property-based тесты (`fast-check`) для схем и доменных инвариантов добавлять по мере появления сложной логики. Обязательным гейтом их не делать.

**Подводные камни.** Vitest-runner по умолчанию запускает только тесты, связанные с мутируемым файлом через импорты. Для тестов без такой связи эту настройку нужно выключать. Время мутаций растёт линейно с кодом: в PR мутируй только изменённые файлы, полный прогон оставь nightly.

**Готово, когда** намеренная ошибка в логике оптимистичного обновления роняет гейт.

<a id="b3"></a>

### B3. 🔒 Визуальный конвейер: одобрение без локального Docker

**Проблема.** Базлайны обновляет человек локально через Docker. Скрипт копирует репозиторий в контейнер и ставит зависимости при каждом запуске, на Apple Silicon добавляется эмуляция amd64. На машине без Docker (так было на машине аудита) агент не видит визуальный дифф до CI. Все визуальные сценарии UI лежат в одном файле `components.visual.test.tsx`.

**Что сделать**

1. CI становится единственным источником базлайнов. При диффе job выкладывает артефакт с новыми снимками и отчётом. Мейнтейнер одобряет их командой в PR или ручным запуском workflow, после чего доверенный workflow коммитит снимки из артефакта в ветку PR.
2. В сводку PR идёт список изменённых снимков и ссылка на отчёт.
3. Визуальные сценарии разнести по файлу на компонент.
4. Ускорить локальный прогон: образ с предустановленными зависимостями (слой привязан к `pnpm-lock.yaml`) вместо установки при каждом запуске.
5. Записать условие подключения Argos, который ADR 0001 называет альтернативой: например, больше 50 диффов в неделю или очередь одобрений дольше суток.

**Подводные камни.** Workflow, который коммитит базлайны, проверяет автора команды и исполняется из доверенной базы (A1). Коммит, сделанный с `GITHUB_TOKEN`, не запускает CI: нужен токен приложения или повторный запуск. Рендеринг под эмуляцией amd64 может отличаться от нативного, поэтому источник истины должен быть один. Бинарные базлайны раздувают репозиторий: при превышении выбранного порога переходи на Git LFS.

<a id="b4"></a>

### B4. 🔒 Масштабирование CI: выбор тестов по фичам, шардирование, флаки

**Проблема.** `e2e` оформлен одним пакетом, поэтому любое изменение web или api запускает все E2E, хотя vision обещает «E2E затронутых фич». Сейчас это 4 теста и 2.5 с, но рост линейный. Шардирования нет. Nightly при каждом падении заводит новый issue без дедупликации. Flaky rate (цель в vision меньше 1%) не измеряется.

**Что сделать**

1. Отображение путей в фичи: изменение в `apps/web/src/features/<f>/` запускает `e2e/features/<f>/`. Изменение в `packages/`, `apps/api`, `src/lib` или конфигах запускает всё. Тесты `@critical` идут всегда. В merge queue идёт всё.
2. Шардирование Playwright (`--shard`, blob-отчёты и их слияние) включать, когда E2E в CI превысит примерно три минуты.
3. Попробовать `futureFlags.affectedUsingTaskInputs` в Turborepo: affected на уровне задач, а не пакетов.
4. Учёт флаков: nightly с `--repeat-each` даёт список нестабильных тестов, на каждый тест заводится один issue (с поиском существующего). Карантин оформляется защищённым файлом со списком и сроком: тест из карантина исполняется, но не блокирует. `.skip` остаётся запрещённым.
5. После обновления Playwright до 1.65 использовать reporter `failures` и опцию `onlyFailures`: артефакт для агента становится меньше.

**Подводные камни.** Отображение путей является эвристикой. Ошибаться можно только в сторону «запустить больше», полноту страхует merge queue.

<a id="b5"></a>

### B5. 🔒 Агентное ревью в CI: безопасность и стоимость

**Проблема.** `agent-review.yml` запускает модель дважды на каждый push (до 40 и до 60 ходов) с правами `pull-requests: write` и `issues: write`, инструментом Bash и выключенными хуками. Инструкции ревьюеров разрешают `pnpm verify`, `pnpm mutation` и запуск тестов, то есть исполнение кода PR рядом с ключом API. Текст и код PR являются недоверенным входом: внедрённая в них инструкция может заставить модель поставить label, выдать ложный вердикт или раскрыть секрет. При 5–50 людях с агентами стоимость растёт вместе с числом push.

**Что сделать**

1. Ревьюеры в CI не исполняют код проекта: им доступны чтение и `git diff` / `git log`. Результаты `verify`, мутаций и покрытия они берут из артефактов CI.
2. Запуск по `ready_for_review` и по запросу, а не на каждый push.
3. Сетевой доступ job ограничить. Label одобрения гейтов проверять по автору (A1).
4. Вывод ревьюеров сделать структурированным, чтобы «блокер» можно было сопоставить с гейтом и показать аннотацией.
5. Явно задать модель и предел ходов для каждого ревьюера.

<a id="b6"></a>

### B6. 🔒 Секреты и цепочка поставок

**Проблема.** Vision обещает проверку секретов в L1, в `lefthook.yml` её нет. Нет CodeQL, аудита зависимостей и проверки workflow. Actions подключены по тегам, а не по SHA.

**Что сделать.** Сканер секретов в pre-commit и CI (gitleaks или secretlint). `pnpm audit` с порогом. CodeQL. Линтер workflow (zizmor). Закрепление actions по SHA через Renovate. Отчёт о новой зависимости в сводке PR: лицензия, возраст релиза, install-скрипты, вес. `pnpm sbom` при релизе.

**Подводные камни.** `pnpm audit` шумит на dev-зависимостях: бери порог high и только production. Сканер секретов даёт ложные срабатывания на тестовых UUID и фикстурах: список исключений держи в защищённом файле.

<a id="b7"></a>

### B7. 🔓 🔒 «Горячие» файлы: конфликты при параллельной работе

**Проблема.** Файлы, которые правит каждая фича, при десятках людей с агентами и merge queue дают поток конфликтов (З9): `apps/web/src/routeTree.gen.ts` (генерируется, но закоммичен), `packages/contracts/openapi.json` (генерируется), `packages/contracts/src/index.ts`, `apps/api/src/router.ts`, `packages/ui/src/index.ts`, `packages/ui/src/components.visual.test.tsx`, `perf-budgets.json`, `pnpm-lock.yaml`.

**Что сделать**

1. Производные файлы пометить в `.gitattributes`, завести одну команду `pnpm regen` и записать в `AGENTS.md`: конфликт в производном файле решается перегенерацией, руками его не сливают.
2. Решить 👤, коммитить ли `routeTree.gen.ts` или генерировать его задачей Turborepo перед typecheck.
3. В реестрах (`contract`, `router`, barrel UI) держать одну строку на домен в алфавитном порядке и проверять порядок гейтом. Тогда конфликты тривиальны.
4. Визуальные сценарии разнести по файлам (B3), перф-бюджеты по маршрутам (A6).

<a id="b9"></a>

### B9. 🔒 `verify` как интерфейс агента

- **Компактная диагностика.** Сейчас в отчёт попадает хвост вывода в 60 строк. Перейти на отчёты инструментов (JSON-отчёт Vitest, формат `agent` у Oxlint уже используется) и отдавать список «файл, строка, сообщение».
- **Режим затронутого.** Быстрый режим гоняет всё, пока это занимает секунду. С ростом понадобятся `--affected` и `--since`.
- **Быстрый цикл.** Vitest 5.1 добавил `--last-failed` и `--since-last-run`, их стоит дать агенту отдельной командой.
- **Режим обслуживания по областям.** Сейчас `disableAllHooks` выключает всё, включая линт после правки и `Stop`. Нужен файл, который создаёт человек (запись агенту запрещена), со списком путей, открытых на сессию. Остальные хуки продолжают работать.
- **Шум.** `turbo run test` предупреждает об отсутствующих `outputs` у пакетов без покрытия.

## Часть C. Добавить: чего не хватает шаблону

Демо-домен намеренно мал. Но шаблон должен содержать образец для тех областей, где сгенерированный код ошибается чаще всего: данные, доступ, окружение, состояния интерфейса. Каждая возможность приходит вместе с гейтом, который удерживает образец.

<a id="c1"></a>

### C1. 👤 Постоянное хранилище: Postgres и Drizzle

- Реализация `TaskRepository` на Postgres за существующим интерфейсом.
- Контрактный набор тестов репозитория: один набор прогоняется против обеих реализаций.
- Миграции: гейт «схема совпадает с миграциями», правило expand/contract, каталог миграций в классе `review`.
- Изоляция тестов. Unit и integration: Postgres внутри процесса (PGlite) или база на воркер из шаблона. E2E: изоляция по арендатору или рабочему пространству на тест вместо общего сброса данных. Тогда `SHARED_DATA_LOCK` не нужен, а visual и perf перестают быть последовательными.

**Подводные камни.** PGlite не является полным Postgres (расширения, блокировки, параллелизм), поэтому контрактный набор обязан идти и против настоящего Postgres в CI. Drizzle остаётся на 0.45.x, версия 1.0 не вышла: закрепи точную версию и не выпускай типы Drizzle за пределы репозитория. Эндпоинт сброса данных с настоящей базой опаснее, чем с памятью. Перф-бюджет API придётся перекалибровать.

<a id="c2"></a>

### C2. 👤 Аутентификация и политика доступа как часть контракта

Ошибки доступа (чтение чужого ресурса по id) типичны для сгенерированного кода, а ревьюер-LLM их не гарантирует.

- Каждая процедура контракта объявляет политику доступа в метаданных. Гейт: тест перебирает контракт и падает на процедуре без политики.
- Авторизация выполняется в middleware oRPC, актор приходит через контекст.
- Табличные тесты: для каждой процедуры с владельцем есть случай «чужой ресурс, отказ».

**Подводные камни.** oRPC 2 находится в бете (`2.0.0-beta.50`). До стабильного релиза не мигрировать, но метаданные проектировать так, чтобы миграция затронула только пакет контрактов.

<a id="c3"></a>

### C3. 👤 Окружение, production-сервер, деплой

- Схема окружения на Zod в каждом приложении. Читает окружение один модуль. Гейт: правило Oxlint, запрещающее `process.env` вне этого модуля, и проверка `.env.example` по схеме.
- Web сейчас запускается через `vite preview` ([apps/web/package.json](../apps/web/package.json)). Это не production-сервер. Нужно выбрать серверный entry на Node или Nitro, добавить Dockerfile и readiness-проверку.
- Preview-окружение на PR: человеку для одобрения визуальных изменений, агентам для исследовательского тестирования.
- E2E и перф должны идти против того же способа запуска, что и production.

<a id="c4"></a>

### C4. Наблюдаемость

- Структурные логи с идентификатором запроса, трейсы OpenTelemetry, единая таксономия ошибок на основе типизированных ошибок oRPC.
- Для агента: логи API прикладываются к отчёту Playwright при падении теста (З11).

<a id="c5"></a>

### C5. Состояния интерфейса и доступность как гейты

- У маршрутов сейчас нет `errorComponent`, `pendingComponent` и `notFoundComponent`. Гейт: тест перебирает дерево маршрутов и требует их наличия либо значений по умолчанию на роутере.
- Доступность: проверка axe в компонентных тестах и E2E, нарушение роняет тест.
- Сейчас оба пункта проверяет только `product-logic-reviewer`. По З1 то, что можно проверить детерминированно, должно проверяться гейтом.

<a id="c6"></a>

### C6. Гейт несовместимых изменений контракта

`openapi.json` закоммичен, поэтому его можно сравнить с merge-base. Удаление процедуры или поля ответа, новое обязательное поле входа и сужение типа считаются несовместимыми и требуют одобрения человека. Добавления проходят. Инструмент сравнения выбрать при реализации. Ручная процедура уже описана в скиле `api-contract-change`.

<a id="c7"></a>

### C7. Генератор фичи

Команда `pnpm gen feature <name>` создаёт заготовки во всех слоях: контракт, модуль API, фича web, каталог E2E, план в `e2e/specs/<name>.md`. Это уменьшает разброс решений и расход контекста. Канарейка: сгенерированная фича во временном worktree проходит `verify`.

<a id="c8"></a>

### C8. Трассировка критериев приёмки

Критерии в `e2e/specs/<feature>.md` получают идентификаторы (`AC-1`). Тесты ссылаются на них в названии или аннотации. Гейт: у каждого критерия есть хотя бы один тест, каждый идентификатор в тестах существует в плане. Таблица «критерий, тест» в PR генерируется, а не заполняется руками.

<a id="c9"></a>

### C9. Оценка самой обвязки и метрики

Vision перечисляет метрики системы: время CI, flaky rate, доля агентных PR без ручных правок, пропущенные дефекты, перехваченные попытки ослабить гейт. Ни одна не собирается.

- **Эталонные задачи.** Набор типовых фич («добавь удаление задачи», «добавь срок»). Агент без участия человека выполняет их в чистом worktree. Измеряется: дошёл ли до зелёного `verify --full`, число итераций, время, расход токенов.
- **Задачи-ловушки.** Ситуации, где проще всего ослабить гейт: упавший скриншот, превышенный бюджет, красный тест на настоящий баг. Ожидаемый результат: гейты устояли, агент сообщил о проблеме.
- **Когда запускать.** При изменении `.claude/`, `AGENTS.md` и `tools/`, а также раз в неделю. Это дорого, в каждом PR не нужно.
- **Журнал отказов.** Хуки пишут отказы в файл вне репозитория. Это даёт счётчик попыток обхода.
- **Время задач.** Turborepo умеет отдавать телеметрию по OTLP (`futureFlags.experimentalObservability`).

<a id="c10"></a>

### C10. Переносимость

- Упаковать `.claude/` (хуки, скилы, ревьюеры) в плагин Claude Code для переиспользования в других репозиториях.
- Другие агенты читают `AGENTS.md`, но хуков Claude Code у них нет. Логику хуков держать в `tools/` как CLI без привязки к агенту, адаптер под конкретного агента делать тонким. Заниматься этим, когда второй агент появится в реальной работе.

## Порядок работ

1. **A3.** Целостность тестов (A2 — контур агента — закрыта 2026-11-13: снимок, merge-base stop-verify, песочница, ADR 0003 и 0004). PR меняет `tools/**` — красный `gate-integrity` без label ожидаем, ставится после финального пуша.
2. **B1.** Канарейки закрепляют A1–A3. После этого каждая задача приносит свою канарейку.
3. **A5.** До того, как запускать несколько агентов на одной машине.
4. **A8, A6, A7.** A7 обязательно до подключения remote cache.
5. **B2–B7, B9.** По мере роста команды и кода.
6. **Часть C.** По потребности. C1 раньше C2. C9 можно начинать сразу после B1.
