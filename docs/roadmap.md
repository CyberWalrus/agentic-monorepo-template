# План развития обвязки

> Статус: действует · Дата аудита: 2026-11-20 · Проверенное состояние: ветка `main`, коммит `e717f44` · Предыдущие аудиты: 2026-11-15 (`ea9f220`), 2026-11-12 (`0c6fe45`)
> Для кого: агенты и люди, которые развивают сам шаблон.
> Правила, которым должно соответствовать любое изменение: [architecture.md](architecture.md). Номера вида З3 ссылаются на законы из её первого раздела.

## Где задачи

Задачи развития живут на доске `backlog/` — один файл на задачу (ADR 0007, перенесены задачей D6). Доска читается командой `pnpm backlog` (`next`, `start`, `resume`), протокол — в разделе «Начало сессии» в `AGENTS.md` и скиле `task-board`. Статус в файле не хранится, а вычисляется: ветка `task/<id>` — в работе; незакрытые `depends_on` или заполненное `needs_human` — заблокирована (вместо пометки 👤); путь из `touches` попадает под `deny` из `tools/protected-paths.json` — нужен режим обслуживания (вместо пометки 🔒). Порядок задают `priority` и `depends_on`.

Часть A — дыры в гарантиях, часть B — качество и масштаб (по мере роста команды и кода), часть C — недостающие возможности (по потребности), часть D — параллельная работа агентов и распространение шаблона, часть E — удобство, простота, скорость и универсальность самой обвязки (заведена аудитом 2026-11-15). Демо-домен намеренно мал, но шаблон содержит образец для областей, где сгенерированный код ошибается чаще всего: данные, доступ, окружение, состояния интерфейса. Каждая возможность приходит вместе с гейтом, который удерживает образец.

Правило декомпозиции с 2026-11-15: если задача смешивает продуктовый код и правку защищённого пути, она делится на два файла — продуктовую часть берёт обычный агент, гейт подключает оператор отдельным маленьким PR. Цена записана в задачах: гейт догоняет образец с опозданием на один PR. Закрепление правила в ADR — задача E3.

## Кто что делает (с 2026-11-15)

2026-11-15 на доске не осталось свободных задач: 18 требовали режима обслуживания, 9 ждали выбора варианта. Решение — [ADR 0009](adr/0009-operator-delegation.md): развилки закрыты записанными решениями, действия человека переданы операторской сессии, человеку оставлена приёмка PR. Задачи больше не содержат вопросов: агент, которому не хватает решения, берёт вариант из раздела «Решение» своей задачи или запасной вариант оттуда же.

Роли, границы оператора и виды `needs_human` здесь не дублируются: правила разошлись между шестью документами и сведены к канону (аудит 2026-11-20, задача E13) — [ADR 0009](adr/0009-operator-delegation.md), краткая таблица — раздел «Оператор» в [AGENTS.md](../AGENTS.md).

### Очередь

Источник правды — `pnpm backlog list`: эта очередь — снимок порядка на 2026-11-15 (после аудита), статус по ней не ведётся. Правило порядка: приоритет, при равном — задача, которая открывает больше зависимых.

Агенты (параллельно, сразу после merge правок аудита — свободных задач становится восемь):

1. C2.0 → C2.2 → C2.3 — политики доступа и авторизация.
2. C3.0 → C3.2 — окружение и production-сервер.
3. C4.1 — структурные логи и таксономия ошибок.
4. E2 — замер CI (нужна сессия с рабочим `gh`), E5 — README, E7 — реестр пропущенных дефектов.
5. E3 — ADR о классах защиты `tools/`, E6 — исследование опциональных частей шаблона.

Оператор (несколько параллельно, если `touches` не пересекаются — D7; один гейт — один PR):

1. D13 — режим оператора в `pnpm backlog`: убирает ручной захват для всех следующих задач.
2. C10.1 → C10.3 — контур L0 для основного клиента (ZCode). Поднято выше цепочки окружения: та теперь идёт силами агентов, а L0 в основном клиенте отсутствует целиком.
3. E1 — быстрый verify под кэшем: ускоряет каждую следующую сессию, включая операторскую.
4. A9 — строгая база в снимке ruleset (применяет человек: A9.1).
5. C2.1, C3.1 — канарейки и правило линтера вдогонку к C2.0 и C3.0, маленькими PR сразу после их merge.
6. B4.1 → B4.2.
7. B2.2 → B2.3 → B2.4.
8. C1.3 → C1.5.
9. Остальные задачи высокого приоритета: C9.1 → C9.2, B3.1, A6, A7, B5, B6; после C3.2 — C3.3 и C3.4.

Что может остановить очередь: непринятые PR. Доска читается из `main`, поэтому зависимые задачи открываются только после merge — узкое место по-прежнему приёмка человеком (ADR 0007). Решение E3 может изменить состав очереди оператора: часть задач на `tools/` станет свободной.

## Итог аудита 2026-11-15

Вопрос аудита: качественно ли сделанное и то ли это, что задумано в [vision.md](vision.md).

Коротко: гейты сделаны добротно и честно, но система пока лучше защищает себя, чем помогает работать. За четыре дня принято 45 PR; из последних 27 двадцать — про доску, процесс и документы, семь — про гейты и возможности продукта. Обвязка (`tools/`, хуки, `.github/`) — около 10 100 строк, продукт (`apps/`, `packages/`, `e2e/`) — около 4 900, документы — около 4 400.

### Что проверено и чем

- `pnpm verify --json`: зелёный, 7,1 с; из них шаг `test:hooks` — 6,8 с (без кэша).
- `pnpm verify --full --json`: зелёный, 7,5 с, всё кроме `test:hooks` из кэша.
- `pnpm backlog doctor`: расхождений нет; без `gh` сверка с открытыми PR неполна.
- Тесты: обвязка 290, API 48, web 26, контракты 7, UI 21.
- Доска до правок аудита: 48 открытых задач — 26 «режим обслуживания», 22 заблокированы, свободных нет; закрыто 23.
- Не проверено: CI на GitHub (сеть до GitHub из песочницы закрыта, ADR 0004). Время CI, перезапуски и состояние веток в origin — задача E2.

### Что сделано хорошо и должно сохраниться

- Законы обвязки с честным статусом «действует», «частично», «не определено» вместо заявлений.
- Канарейка на каждый блокирующий шаг; хуки защиты падают закрытыми; защита по результату (снимок защищённых файлов), а не только по запрету команд.
- `gate-integrity` исполняется из доверенной базы; label действителен только после последнего push.
- Решения записаны с альтернативой и условием возврата — их можно пересмотреть по факту, а не по памяти.
- Всё, что отмечено в исходном аудите (ниже), сохранилось.

### Что слабо, по убыванию важности

1. **Доска остановлена по построению.** Весь каталог `tools/` и `.github/` под `deny`, а закон З5 требует на каждый гейт правки в трёх защищённых местах. Почти любая задача идёт через оператора по одной и ждёт label от человека. Ответ: разделение цепочек C2, C3, C4 (сделано этим аудитом), D13, E3.
2. **Контур L0 построен не для основного клиента.** Хуки, песочница и снимок работают в Claude Code; основной клиент — ZCode. Ответ: C10.1 → C10.3 подняты в очереди.
3. **L4 отсутствует, а в README описан как действующий.** Ответ: A9, A9.1, E5.
4. **Храповик числа тестов отстал** (API 43 → 48, web 19 → 26, обвязка 273 → 290): 29 тестов можно удалить без предупреждения. Ответ: A10.
5. **Быстрая петля медленнее заявленной** из-за некэшируемого `test:hooks`. Ответ: E1.
6. **Документ для человека устарел и не объясняет, как системой пользоваться.** Ответ: E5.
7. **Форма проекта одна.** Что сломается при удалении web, API или Postgres — не проверено. Ответ: E6.
8. **Мелочи.** Запрет чтения `.env.*` закрывает и `.env.example` (учтено в C3.1). `touches: apps/web/**` не выдаёт защищённый `vitest.config.ts` внутри каталога — доска занижает число задач оператора (учесть в E3). Turborepo локально шлёт телеметрию, Knip выдаёт две подсказки по конфигу (записано в B9). Локальная ветка `task/evil-probe` без задачи (удаляется `git branch -d`, команду печатает `pnpm backlog list`); ветки закрытых задач остаются в origin — их чистит A9.1. Окружение проверяется только падением verify (E4).

### Исходный аудит 2026-11-12

Вывод того аудита: скорость уже отличная, а слабое место — несколько гейтов можно обойти, а несколько не ловят то, ради чего созданы. Задачи части A, заведённые по нему, в основном закрыты (A1–A5, A8); открытыми остаются A6 и A7.

Что было отмечено как сделанное хорошо:

- Один вход `pnpm verify` с режимом `--json`, шаги идут параллельно.
- Contract-first: один контракт для фронта, бэка и OpenAPI, дрейф ловится гейтом.
- Границы модулей заданы правилами dependency-cruiser, а не договорённостью.
- Сообщения гейтов говорят агенту, что делать и чего не делать.
- Supply-chain настройки pnpm: строгий каталог, задержка свежих релизов, запрет install-скриптов.
- Единый список защищённых путей для хука и CI.

Замеры 2026-11-12 (macOS, 16 ядер, демо-домен): `pnpm verify` с кэшем 0.8–1.0 с. Без кэша: typecheck 0.4 с, unit 1.4 с, сборка 0.7 с, E2E 2.5 с, перф 5.2 с, мутации API 2.3 с при счёте 100% (66 мутантов). Рост быстрого verify с 1 до 7 с за три дня — целиком тесты обвязки (задача E1).

Все утверждения обоих аудитов проверены чтением кода или прогоном; доказательства задач живут в файлах доски. Там, где вывод опирается на документацию или вторичный источник, это сказано явно.

### Порядок взятия

Агенты: E13 (P0 — дрейф канона воспроизводится агентами в каждой сессии), затем P1-мины C1.6, B10, B11, далее C1.7, C12, E14, B12. Оператор (параллельно по дорожкам без пересечения `touches`, D7): D17 (потребители шаблона тихо недополучают гейт бандла), E15, E16, C13.

### Актуальность стека (сверка с рынком на 2026-11-20)

Стек на переднем крае: Node 26.13 — точная Active LTS (с 28.10.2026), pnpm 12 со всеми supply-chain фичами (`catalogMode: strict`, `minimumReleaseAge`, `allowBuilds`), StrykerJS на последней версии, закрепление Drizzle ~0.45.4 корректно (1.0 всё ещё в rc), Renovate с задержкой релизов лучше типичной конфигурации — факт атаки CVE-2026-45321 (май 2026, 84 вредоносных версии в пакетах экосистемы TanStack) подтверждает ценность задержки. Единственная крупная незакрытая тема безопасности — исполнение B6. Из рынка внедряется дёшево: нативная генерация SBOM в pnpm 12 (CycloneDX/SPDX), dependency-review action (закрывает «отчёт о новой зависимости» из B6 из коробки, умеет показывать OpenSSF Scorecard), токен-бюджеты в отчётах evals (вошло в E16), OSSF Scorecard — после B6, раньше счёт бессмысленно низкий. Не внедрять с обоснованием: Turborepo Boundaries (experimental, dependency-cruiser с protected-paths даёт больше), OTel GenAI-телеметрия evals (конвенции в статусе Development), мутационное для UI (сначала B11 и B2.2). Ждать стабильных: TS 7.1 (потом проверка packageExtensions), Drizzle 1.0, oRPC 2, Hono 5.
