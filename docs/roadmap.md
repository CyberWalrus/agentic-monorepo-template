# План развития обвязки

> Статус: действует · Дата аудита: 2026-11-12 · Проверенное состояние: ветка `feat/monorepo-foundation`, коммит `0c6fe45` · Развилки закрыты и очередь работ записана: 2026-11-15
> Для кого: агенты и люди, которые развивают сам шаблон.
> Правила, которым должно соответствовать любое изменение: [architecture.md](architecture.md). Номера вида З3 ссылаются на законы из её первого раздела.

## Где задачи

Задачи развития живут на доске `backlog/` — один файл на задачу (ADR 0007, перенесены задачей D6). Доска читается командой `pnpm backlog` (`next`, `start`, `resume`), протокол — в разделе «Начало сессии» в `AGENTS.md` и скиле `task-board`. Статус в файле не хранится, а вычисляется: ветка `task/<id>` — в работе; незакрытые `depends_on` или заполненное `needs_human` — заблокирована (вместо пометки 👤); путь из `touches` попадает под `deny` из `tools/protected-paths.json` — нужен режим обслуживания (вместо пометки 🔒). Порядок задают `priority` и `depends_on`.

Часть A — дыры в гарантиях, часть B — качество и масштаб (по мере роста команды и кода), часть C — недостающие возможности (по потребности), часть D — параллельная работа агентов и распространение шаблона. Демо-домен намеренно мал, но шаблон содержит образец для областей, где сгенерированный код ошибается чаще всего: данные, доступ, окружение, состояния интерфейса. Каждая возможность приходит вместе с гейтом, который удерживает образец.

## Кто что делает (с 2026-11-15)

2026-11-15 на доске не осталось свободных задач: 18 требовали режима обслуживания, 9 ждали выбора варианта. Решение — [ADR 0009](adr/0009-operator-delegation.md): развилки закрыты записанными решениями, действия человека переданы операторской сессии, человеку оставлена приёмка PR. Задачи больше не содержат вопросов: агент, которому не хватает решения, берёт вариант из раздела «Решение» своей задачи или запасной вариант оттуда же.

| Кто      | Как запускается                       | Что берёт                                                                                                                                                                           | Чего не делает                                                           |
| -------- | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Агент    | «продолжай по плану»                  | Свободные задачи: `pnpm backlog next` → `pnpm backlog start <id>`                                                                                                                   | Не трогает защищённые пути и не берёт задачи оператора                   |
| Оператор | «ты оператор» — сессия с computer use | Задачи со статусом «режим обслуживания» и с `needs_human: оператор: …`, по одной; сам включает и выключает режим обслуживания в worktree задачи; ставит пороги по правилам ADR 0009 | Не ставит label, не одобряет и не сливает PR, не вводит пароли и секреты |
| Человек  | —                                     | Запуск сессий; приёмка PR: approve, label `gate-change-approved` (последним, после финального push), merge; одобрение визуальных базлайнов; секреты и аккаунты                      | —                                                                        |

Поле `needs_human` теперь имеет три вида: `оператор: <действие>`, `отложено: <проверяемое условие>` и действие, которое остаётся человеку. Вопрос «какой вариант выбрать» в него не пишут: выбор записывается в задачу разделом «Решение» и ревьюится в PR.

### Очередь

Источник правды — `pnpm backlog list`: эта очередь — снимок порядка на 2026-11-15, статус по ней не ведётся. Правило порядка: приоритет, при равном — задача, которая открывает больше зависимых.

Агенты (параллельно, сразу после merge этих решений):

1. C1.2 → затем C1.4.
2. D8 (декомпозиция) → затем D9.
3. По мере работы оператора: C2.2 → C2.3 после C2.1; B3.4 после B3.1.

Оператор (по одной задаче, один гейт — один PR):

1. D13 — режим оператора в `pnpm backlog`: убирает ручной захват для всех следующих задач.
2. C3.1 → C3.2 → C3.3, C3.4 — самая длинная цепочка: окружение и production-сервер.
3. C2.1 — открывает агентам C2.2 и C2.3.
4. C10.1 → C10.3, C10.2 — контур L0 для основного клиента (ZCode).
5. B4.1 → B4.2.
6. B2.2 → B2.3 → B2.4.
7. C1.3 → C1.5 — как только агент закроет C1.2 и C1.4.
8. Остальные задачи высокого приоритета: C9.1 → C9.2, B3.1, A6, A7, B5, B6.
9. Средний приоритет: D2, C9.3 → C9.4, B7, B4.4, B3.3, C4, C6, D12. Низкий: B9, C11, C7.

Что может остановить очередь: непринятые PR. Доска читается из `main`, поэтому зависимые задачи открываются только после merge — узкое место по-прежнему приёмка человеком (ADR 0007).

## Итог аудита

Скорость уже отличная. Слабое место в другом: несколько гейтов можно обойти, а несколько не ловят то, ради чего созданы. Для системы, смысл которой в том, что агент не может ослабить проверку, это главный долг.

Что сделано хорошо и должно сохраниться:

- Один вход `pnpm verify` с режимом `--json`, шаги идут параллельно.
- Contract-first: один контракт для фронта, бэка и OpenAPI, дрейф ловится гейтом.
- Границы модулей заданы правилами dependency-cruiser, а не договорённостью.
- Сообщения гейтов говорят агенту, что делать и чего не делать.
- Supply-chain настройки pnpm: строгий каталог, задержка свежих релизов, запрет install-скриптов.
- Единый список защищённых путей для хука и CI.

Замеры (macOS, 16 ядер, демо-домен): `pnpm verify` с кэшем 0.8–1.0 с. Без кэша: typecheck 0.4 с, unit 1.4 с, сборка 0.7 с, E2E 2.5 с, перф 5.2 с, мутации API 2.3 с при счёте 100% (66 мутантов). CI на GitHub в рамках аудита не запускался.

Все утверждения проверены чтением кода или прогоном; доказательства задач теперь живут в файлах доски. Там, где вывод опирается на документацию или вторичный источник, это сказано явно.
