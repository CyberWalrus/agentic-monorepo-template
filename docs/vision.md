# Зачем нужна эта система

> Статус: принято как отправная точка · Дата: 2026-11-01
> Документ фиксирует **цель и принципы**. Конкретные инструменты описаны в [исследовании стека](research/2026-11-tech-stack.md), решения по ним будут оформляться в `docs/adr/`.

## Одной фразой

Шаблон монорепозитория (frontend + backend), в котором фичи могут писать AI-агенты («вайбкодинг»), а инфраструктура **объективно и быстро** не пускает в `main` код, который недостаточно хорош. Так в одном репозитории параллельно могут работать от 5 до 50 человек и любое количество агентов.

Продукт внутри намеренно абстрактный. Это минимальный демо-домен, на котором проверяется сама обвязка. Ценность репозитория в обвязке, а не в продукте.

## Проблема

1. **Агенты пишут код быстрее, чем люди успевают его читать.** При 5–50 разработчиках, у каждого из которых несколько агентов, поток изменений вырастает на порядок. Если ревью делает только человек, оно становится узким горлом, и приходится либо тормозить поток, либо пропускать код без проверки.
2. **Агент оптимизирует «зелёный CI», а не корректность.** Типичные способы «сделать зелёным»: ослабить или удалить тест, обновить скриншот-базлайн, поднять порог, добавить `skip`/`any`/`eslint-disable`, «залечить» упавший E2E так, что тест перестанет ловить баг.
3. **Деградации не видны в диффе.** Скорость загрузки, время ключевых сценариев, размер бандла, визуальные регрессии, рост связности между модулями, мёртвый код. Ничего из этого не заметно при чтении PR глазами.
4. **Медленные проверки ломают цикл агента.** Агент делает десятки итераций. Если обратная связь приходит через 20 минут, агент либо простаивает, либо уходит дальше на непроверенном фундаменте.
5. **LLM-ревью ненадёжно как единственный судья.** Модели пропускают мелкие визуальные изменения (лучшие VLM находят меньше половины изменений на бенчмарке DiffSpot), агентные E2E-прогоны дорогие ($15–30) и недетерминированные (данные Slack Engineering, 2026). Подробности в [исследовании](research/2026-11-tech-stack.md#сверка-с-исходным-анализом).

## Цели

| #   | Цель                                                           | Как поймём, что достигнута                                                                                               |
| --- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| G1  | Агент может довести фичу от постановки до PR без ручной помощи | Есть инструкции (AGENTS.md), скилы, хуки и одна команда локальной проверки с машиночитаемым выводом                      |
| G2  | Плохой код не попадает в `main`                                | Все обязательные проверки (gates) детерминированы, агент не может их ослабить, merge только через merge queue            |
| G3  | Проверки быстрые                                               | Соблюдаются бюджеты времени (см. ниже), проверяется только затронутое (affected) плюс кэш                                |
| G4  | Проверки надёжные                                              | Flaky rate < 1%, у каждого падения есть артефакт (trace, diff, отчёт), по которому причина понятна без перезапуска       |
| G5  | Продукт не деградирует                                         | Перф-бюджеты, визуальные базлайны и критические пользовательские сценарии защищены всегда, а не только в затронутой фиче |
| G6  | Ревью масштабируется                                           | Специализированные агенты-ревьюеры снимают с человека рутину, человек принимает решения, а не ищет опечатки              |

## Принципы

1. **Детерминированные проверки — ядро, LLM — советник.** Merge блокируют тесты, типы, линтеры, пиксельный дифф, перф-бюджеты. Агенты-ревьюеры комментируют, триажируют и предлагают, но не заменяют пиксельное сравнение и тесты.
2. **Агент не может ослабить gate.** Скриншот-базлайны, перф-пороги, конфиги линтеров и CI, CODEOWNERS и правила хуков являются защищёнными путями. Их меняет только человек отдельным осознанным действием. Защита работает на трёх уровнях: хук агента (`PreToolUse` deny), CI-проверка изменений в защищённых путях, CODEOWNERS.
3. **Shift-left: то же, что в CI, доступно локально.** Одна команда (`verify`) запускает те же проверки, что и CI, только для затронутых пакетов. Вывод компактный, есть режим `--json`. Хуки агента ловят проблемы ещё на этапе редактирования.
4. **Скорость — это требование, а не пожелание.** Предпочитаем Rust/Go-инструменты, кэш задач, affected-графы, шардирование. Каждый уровень проверок имеет бюджет времени, и превышение бюджета считается дефектом инфраструктуры.
5. **Фича проверяет себя, продукт защищён целиком.** Каждая фича приносит свои тесты (unit/integration/E2E/visual) и свои перф-бюджеты. Сверху лежит общий тонкий слой «продуктовых инвариантов»: критические сценарии, которые прогоняются всегда.
6. **Прозрачность вместо магии.** Self-healing тестов допустим только как явный патч в PR (так работает встроенный Playwright Healer), без тихого «залечивания» в CI. Агентный PR прикладывает доказательства: trace, видео прогона, отчёты.
7. **Двухэтапный контроль агентами.** Специализированные ревьюеры (архитектура, здравый смысл, качество и полнота тестов, безопасность, продуктовая логика) работают дважды: на этапе плана/дизайна, до написания кода, и на этапе приёма PR.
8. **Без vendor lock-in в ядре.** Облачные сервисы (визуальное ревью, бенчмарки, remote cache) подключаются опционально. Базовый контур работает на GitHub Actions и open source.

## Контуры проверки

Каждый следующий контур медленнее и полнее предыдущего. Задача каждого контура — поймать максимум того, что дешево поймать именно на нём.

| Контур                       | Где                               | Что проверяет                                                                                                                                  | Бюджет               | Блокирует                    |
| ---------------------------- | --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- | ---------------------------- |
| **L0. Агент**                | Хуки Claude Code / другого агента | Формат и линт изменённого файла после каждой правки; запрет записи в защищённые пути; перед завершением задачи прогон `verify` для затронутого | < 3 с на правку      | Действие агента              |
| **L1. pre-commit**           | Git hook                          | Формат, линт                                                                                                                                   | < 10 с               | Коммит                       |
| **L2. pre-push**             | Git hook                          | Typecheck, unit-тесты затронутых пакетов, границы модулей                                                                                      | < 60 с               | Push                         |
| **L3. PR CI**                | GitHub Actions                    | Полная статика, affected unit/integration, E2E затронутых фич, визуальные тесты, перф-бюджеты, мёртвый код, агентное ревью                     | p50 < 10 мин         | Merge                        |
| **L4. Merge queue**          | GitHub merge queue                | Повтор обязательных проверок на смёрженном состоянии, продуктовые инварианты (smoke критических сценариев), перф                               | p50 < 15 мин         | Попадание в `main`           |
| **L5. Nightly / post-merge** | По расписанию                     | Полный E2E, mutation testing, агентное исследовательское тестирование (Playwright MCP), тренды перфа                                           | Без жёсткого бюджета | Создаёт задачи, не блокирует |

Бюджеты — стартовые цели, их уточним после первых замеров.

## Что значит «код достаточно хорош»

PR (от агента или человека) может попасть в `main`, только если выполнены все условия:

- [ ] Формат, линт, типы без ошибок, без новых подавлений (`any`, `@ts-ignore`, `eslint-disable`, `.skip`) без обоснования
- [ ] Границы модулей и пакетов не нарушены, нет циклов, нет мёртвого кода и неиспользуемых зависимостей
- [ ] Новые и изменённые модули покрыты тестами, и эти тесты действительно ловят ошибки (mutation score на изменённом коде не ниже порога)
- [ ] E2E затронутых фич и продуктовые инварианты зелёные
- [ ] Визуальных изменений нет, либо каждое изменение явно одобрено человеком
- [ ] Перф-бюджеты (загрузка страниц, время сценариев, размер бандла, p95 API) не нарушены
- [ ] Защищённые пути не изменены, либо изменения одобрены CODEOWNERS
- [ ] Агентное ревью не нашло блокирующих проблем (или они разобраны человеком)
- [ ] Контракты API согласованы между фронтендом и бэкендом

## Роли

| Роль                  | Отвечает за                                                                                                                                                           |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Человек**           | Постановку задачи, ADR и архитектурные решения, одобрение визуальных изменений и изменений порогов, финальное решение о merge в спорных случаях                       |
| **Агент-исполнитель** | План, код, тесты, доказательства работы (trace/video)                                                                                                                 |
| **Агенты-ревьюеры**   | Ревью плана (архитектура, здравый смысл) и ревью PR (тесты, безопасность, продуктовая логика); только комментарии, без права merge и без права менять защищённые пути |
| **CI**                | Детерминированные gates, артефакты, единый итоговый статус                                                                                                            |

## Не-цели

- **Не строим реальный продукт.** Демо-домен минимален и нужен только для проверки обвязки.
- **Не заменяем человека в решениях**, которые нельзя проверить объективно: одобрение визуальных изменений, смена порогов, архитектурные развороты.
- **Не гонимся за 100% coverage.** Важнее, чтобы тесты ловили ошибки (mutation score), чем процент строк.
- **Не гоняем агентный E2E в каждом PR.** Это дорого и недетерминированно. Агенты нужны для исследования, отладки флаков и воспроизведения багов (L5 и по запросу).
- **Не привязываемся к одному агенту.** Основной сценарий — Claude Code, но инструкции лежат в открытом формате `AGENTS.md`, а проверки в CI не зависят от того, кто писал код.

## Метрики системы

Метрики самой инфраструктуры, не продукта:

- Время PR CI и merge queue (p50/p95) против бюджетов
- Flaky rate обязательных проверок
- Доля агентных PR, принятых без ручных правок
- Escaped defects: баги, прошедшие все gates (каждый такой случай рассматриваем как пробел в проверках)
- Mutation score изменённого кода
- Количество попыток ослабить gate, перехваченных хуками и CI
