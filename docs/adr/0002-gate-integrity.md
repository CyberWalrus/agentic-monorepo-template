# ADR 0002: Целостность гейтов в CI

- Статус: принято (внедрено 2026-11-12: PR#1 — workflow и инструменты, PR#2 — удаление исполнявшегося из PR job `protected-paths`; политика Actions id 13436, ruleset id 27137353)
- Дата: 2026-11-12
- Контекст: [architecture.md](../architecture.md) (З2, раздел 3.4–3.5), [roadmap.md](../roadmap.md) (задача A1 аудита 2026-11-12)

## Проблема

Для события `pull_request` GitHub берёт определение workflow из ветки PR. Job `protected-paths` в `ci.yml` делал checkout PR и запускал `tools/check-protected-paths.ts` и `tools/protected-paths.json` из самого PR: PR, удаливший строку из списка или переписавший скрипт или workflow, проходил собственную проверку. Оставался только ревью CODEOWNERS — детерминированного барьера не было. Дополнительно: `git diff --name-only` без `--no-renames` не показывал старое имя переименованного файла, а label `gate-change-approved` не был привязан ни к последнему push, ни к автору (поставить его мог любой участник с правом triage, включая job `agent-review`, читающий недоверенный текст PR).

## Внедрение (два PR, без окна без защиты)

1. **PR#1 (аддитивный)**: `gate-integrity.yml`, скрипты, снимок ruleset в репозитории. Старый job `protected-paths` в `ci.yml` остаётся.
2. Человек: проверяет `gate-integrity` на реальном PR (раздел «Проверка»), затем применяет ruleset в UI GitHub — два обязательных контекста: `gate` и `gate-integrity`.
3. **PR#2**: удаляет старый job `protected-paths` и триггеры `labeled`/`unlabeled` из `ci.yml`.

Если применить ruleset до мержа PR#1 — PR повиснет на несуществующем required check; если удалить старый job до применения ruleset — останется окно без детерминированной проверки. Порядок обязателен.

## Риски и их закрытие

- **`pull_request_target`** — источник известных атак «pwned pipeline». В `gate-integrity.yml`: никакого checkout кода PR (только `base.sha`), никакого исполнения кода PR, секреты не используются; права корня `contents: read`, право `pull-requests: write` — только у job снятия label. Workflow обязан оставаться минимальным: любое расширение — предмет отдельного ADR.
- **GitHub блокирует `pull_request_target` в публичных репозиториях без явной политики с 2026-12-02** (workflow execution protections, GA с 2026-09-17; режим evaluate идёт до этой даты). Владелец репозитория явно разрешает событие для файла `gate-integrity.yml` в политике исполнения workflow — действие человека при внедрении. Для приватного репозитория блок не применяется, политика всё равно рекомендуется.
- **События `labeled` хранятся в API ограниченно** (лента событий issues). Если событие не найдено, одобрение не засчитывается — безопасный отказ; мейнтейнер перепоставляет label.
- **API `pulls/{n}/files` отдаёт максимум 3000 файлов**. Порог проверяется скриптом: на границе проверка падает, а не пропускает.

## Проверка (человек, при внедрении)

Локальные канарейки (прогнаны 2026-11-12, см. PR): переименование через `previous_filename` и через `git --no-renames` во временном worktree; 3000 файлов — падение; одобрение — мейнтейнер после push / не-мейнтейнер / до push / без события / без label; запись `approved` в `$GITHUB_OUTPUT`.

В GitHub (на реальном PR после PR#1):

1. PR, меняющий `tools/protected-paths.json`, `ci.yml` или сам `gate-integrity.yml` в свою пользу, красный без одобрения.
2. `git mv .oxlintrc.json somewhere` в PR ловится.
3. Label, поставленный до нового push, снимается автоматически; label от не-мейнтейнера не одобряет.
4. Merge queue не виснет: `gate-integrity` приходит в очередь зелёным (имя check совпадает со снимком ruleset).

## Откат

Если появятся доступные required workflows (уровень организации) — перенести проверку туда и удалить событие `pull_request_target`; скрипты `tools/check-protected-paths.ts` и `tools/check-gate-approval.ts` переиспользуются как есть.
