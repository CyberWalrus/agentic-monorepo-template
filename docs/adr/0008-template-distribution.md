# ADR 0008: Распространение и обновление шаблона — одна ветка, теги и Copier

- Статус: предложено (принимается merge этого PR человеком). Выбор между одной веткой и генерируемым чистым `main` сделан человеком 2026-11-14 в пользу одной ветки.
- Дата: 2026-11-14
- Контекст: репозиторий — шаблон, из которого создаются реальные проекты. Нужно: проект получает настроенную обвязку (библиотеки, пайплайны, скилы, инструкции агентов) без файлов, относящихся к разработке самого шаблона; уже идущий проект может забрать новую версию шаблона без ручного переноса. Сейчас способа нет: кнопка GitHub «Use this template» копирует всё содержимое ветки и не оставляет связи с шаблоном. План прошёл ревью `architecture-reviewer` и `sanity-reviewer` до кода.

Copier в этом репозитории не запускался: всё, что сказано о его поведении, взято из документации и чужих проб. Первая задача внедрения — проба на этом репозитории.

## Решения

Постоянной ветки разработки с другим набором файлов нет                                                                                                                    | Гейты исполняются из `main` как доверенной базы (З2); вторая постоянная ветка с отличающимся содержимым требует вечного слияния с фильтрацией и перенастройки ruleset                          | Генерируемый чистый `main` из ветки `dev` — если понадобится, чтобы чистую копию давала именно кнопка GitHub |
| Версии                   | Версия шаблона — тег `vX.Y.Z` на `main`. Мажорная версия меняется, когда обновление требует ручных действий в проекте. Теги `v*` защищаются отдельным ruleset: запрет изменения и удаления                                                                                                               | Тег — доверенная база для проектов (З2): по нему инструмент находит старую и новую версии. | Создание проекта         | `copier copy` из тега шаблона. Ответы (имя проекта, владелец репозитория) сохраняются в `.copier-answers.yml` проекта. ## Что отвергнуто

- **Генерируемый чистый `main` из ветки `dev`.** Даёт буквально чистую основную ветку и работающую кнопку GitHub, обновление через `git merge`. Цена: `main` пишет бот, ruleset и `gate-integrity` переезжают на `dev`, а готовых примеров такой схемы нет. Отклонён решением человека.
- **Fork и `git merge` из upstream.** Приносит в проект файлы разработки шаблона и не работает, если проект — приватный репозиторий другого владельца.
- **actions-template-sync.** По умолчанию решает конфликты в пользу шаблона и затирает правки проекта (вторичный источник, issue 27 выше).
- **Плагин Claude Code** (задача C10). Переносит только `.claude/`, не гейты и не CI. Дополняет это решение, а не заменяет.

## Последствия

- В стеке появляется инструмент на Python. Он не входит в `package.json` и каталог версий, поэтому на него не действует задержка свежих релизов pnpm: версия закрепляется вручную в одном файле.
- Канарейка копии — исключение из З5: локально из песочницы агента она не запускается (PyPI нет в разрешённых доменах), её гоняет CI и человек. Исключение записывается в З5 тем же PR, который добавляет канарейку.
- В самом `main` файлы разработки шаблона остаются. Чистым будет проект, а не ветка.
- Документы, которые едут в проект, не могут ссылаться на документы, которые не едут. Поэтому в ADR и в `architecture.md` задачи называются номером, а не ссылкой на файл; существующие ссылки разводит задача D6.
- Проект, созданный до появления `copier.yml`, обновляться не сможет: у него нет `.copier-answers.yml`. Реальные проекты стоит создавать после задачи D8.
- Условие пересмотра: если обновление первого же проекта потребует ручного разбора конфликтов в большинстве смешанных файлов, вернуться к выбору между `_subdirectory`, генерируемой веткой и отказом от автоматического обновления.
