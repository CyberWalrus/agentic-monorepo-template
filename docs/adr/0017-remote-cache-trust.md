# ADR 0017: Доверие к remote cache Turborepo

Дата: 2026-11-20 · Задача: A7 · Статус: действует (бэкенд не подключён — контур фейл-клосед)

## Решение

Remote cache подключается по трём правилам доверия (подробная механика — `docs/architecture.md` §3.3):

1. **Пишет** в remote только доверенный код: job на `push` в `main` (`--cache=local:rw,remote:rw`), и только с токеном из environment `cache-write`, ограниченного deployment branch policy на protected-ветки.
2. **Читает** remote только job в PR и ручных прогонах PR (`--cache=local:rw,remote:r`, токен из environment `cache-read`). Merge queue remote **не читает вовсе**: `merge_group` гоняет задачи принудительно (`--cache=local:rw`) — кэшу `main` она не доверяет.
3. Замеры, зависящие от машины (задача `perf`), вне кэша полностью (`cache: false` в `turbo.json`).

Граница секретов — физическая: `TURBO_TOKEN` выдаётся job'у только через environment (repo-level turbo-секреты запрещены), поэтому job, исполняющий код PR, не может получить токен записи ни при каком содержимом PR, включая переписанный им самим `ci.yml`: на всех событиях, кроме `push` в protected `main`, deployment branch policy environment `cache-write` секрет не выдаёт.

## Почему

Код PR — недоверенный вход: с write-токеном PR-код мог бы записать артефакт «проверки пройдены» для нужного хеша, и последующие гейты засчитали бы кэш-попадание как реальный прогон. Подпись артефактов Turborepo проверяет целостность, но не является границей безопасности: ключ лежит в том же окружении, что и код PR.

## Альтернативы

- **Подпись артефактов вместо разделения токенов** — отклонено: ключ подписи в том же окружении, защита не закрывает модель угрозы (см. §3.3 п. 4).
- **Доверять merge queue кэшу `main`** — отклонено человеком (пакет A6/A7 от 2026-11-13): очередь — последняя инстанция перед `main`, для неё скорость дешевле полноты; компенсация — PR-джобы читают remote и `actions/cache` `.turbo` с ключом по номеру PR, поэтому очередь обычно догоняет быстро.
- **Полный запрет remote для PR** — отклонено: без чтения PR теряет ускорение зависимостей, а угроза определяется записью, не чтением (read-токен ограничен сервером; эксфильтрация read-кэша same-repo PR — принятый остаточный риск уровня доверия соавтора с write).

## Условие возврата

- Сервер кэша не умеет выдавать read-only токены — пересмотреть схему (или выбрать другой бэкенд): проверяется до подключения, до него контур остаётся фейл-клосед (секреты пусты).
- Появилась merge queue на тарифе — пересмотреть правило 2: очередь может читать remote, если её runner'ы перейдут в доверенный контур.
- Критерий приёмки «job из PR не может записать» проверяется попыткой после подключения по всем PR-job'ам (`static`, `unit`, `e2e`, `visual`, `perf`, `mutation`, `bundle-delta`).
