# ADR 0010: Облачные агенты — статус гарантий и облачный контур

- Статус: предложено (принимается merge этого PR человеком)
- Дата: 2026-11-15
- Контекст: аудит трендов 2026-11-14 назвал облачных агентов гэпом P1, задача D15. Облачный контур — агенты, работающие в чистом checkout на инфраструктуре вендора (Codex Cloud, Copilot coding agent и подобные): без интерфейса хоста, секретов человека и локальных инструментов клиента. Локальные клиенты и оператор описаны в [ADR 0007](0007-task-board.md) и [ADR 0009](0009-operator-delegation.md). План прошёл ревью `architecture-reviewer` и `sanity-reviewer` до написания; их находки учтены в этой редакции.

## Гарантия × контур запуска

Статусы: **держится** (гарантия действует в контуре), **не определено** (зависит от факта, которого нет: среды вендора или живого прогона), **не применимо** (механизм по построению отсутствует в контуре или осознанно выключен — причина указана). Границей закоммиченного результата во всех контурах остаётся L3: `gate-integrity` из доверенной базы и ревью CODEOWNERS.

## Решение

**Минимальный облачный контур** — то, что шаблон обещает облачному агенту: чистый checkout → `pnpm install --frozen-lockfile` → `pnpm verify --full` в среде, которая предоставляет:

- Node из `.nvmrc`;
- pnpm из `packageManager`;
- сеть до npm registry;
- Chromium для e2e и browser-тестов (`playwright install --with-deps chromium`);
- Docker для интеграционных тестов на Postgres.

Эталонная реализация требований — составной экшн `.github/actions/setup`. Обязательство самоподдерживающееся: тот же набор скриптов из чистого checkout на вендорной машине GitHub исполняет `gate` каждого PR — если минимальный контур ломается, ломается `gate`, и это видно громко. Формулировка списком требований, а не «эквивалентность ubuntu-latest»: облачные рантаймы — не образы GitHub-раннеров, сверять их с образом нельзя, сверять можно требования.

**Что шаблон не обещает облачному агенту:**

- контур L0 и песочницу `denyWrite` — их в рантайме вендора нет; границей закоммиченного остаётся CI (`gate-integrity`);
- бюджеты времени `verify` — они рассчитаны на машину разработчика и CI; холодный прогон в облаке дольше и дефектом гейтов не считается;
- захват задач доски — механика одного клона (см. таблицу);
- режим обслуживания и операторские действия — отдельный контур, облачным агентом не исполняется;
- исполнение инструкций `AGENTS.md` — клиенты обязаны их читать по документации вендоров, прогоном не проверено; проверяет прогон D16.

**Условия пересмотра:**

- первый живой прогон облачного клиента (задача D16) противоречит какому-либо статусу таблицы → ADR правится тем же PR, что приносит результаты прогона;
- появляется потребность «облачный агент работает с доской» → отдельный ADR о захвате через remote (условие возврата записано в ADR 0007);
- GitHub меняет политику `pull_request_target` или становятся доступны required workflows → пересмотреть строку gate-integrity (откат записан в [ADR 0002](0002-gate-integrity.md));
- облачные рантаймы получают исполнение политик хуков или их эквивалент → пересмотреть строки L0 и песочницы.

## Задачи из решения

- **D16 «Прогон облачного клиента»** (research): живой прогон одного облачного клиента по методу задачи D2 (прогоны трёх локальных клиентов). Ячейки прогона: checkout и `pnpm install` в рантайме вендора, сеть до реестра, Chromium, Docker, исполнение `AGENTS.md`, Lefthook (ставится ли `prepare` и срабатывает ли на коммите вендора — или вендор коммитит через API, минуя git-хуки), захват задачи, прохождение `gate` и `gate-integrity` PR облачного агента. Активация облачного агента — аккаунт или платный ресурс: не делегируется, поле `needs_human` вида `человек: …` ([ADR 0009](0009-operator-delegation.md), «Что остаётся человеку»).
- **Других задач не нужно.** Канарейка облачного контура отвергнута: минимальный контур исполняется CI на каждом PR из чистого checkout на вендорной машине — отдельная канарейка повторяла бы CI без новой информации; З6 требует канарейку у гейта, а новый гейт этим ADR не вводится. Специфику вендора (сеть, браузеры, Docker, инструкции, песочница) из CI не потрогать — её проверяет живой прогон D16. Остальные строки таблицы меняются только через уже существующие задачи (C10 — контур L0 локальных клиентов, D2 — локальные прогоны, D13 — команды доски) или через условия пересмотра.

## Что отвергнуто

- **Канарейка облачного контура** (см. «Задачи из решения»): повтор CI без новой информации; обязательство контура наблюдается существующим `gate`, который падает громко, а не тихо.
- **Отдельный CI-job «облачной среды»**: исполнял бы тот же набор, что существующий `gate`; единственное, что CI не проверяет, — рантаймы вендоров, до которых из CI не добраться.
- **Обещать облаку L0 и песочницу «документом»**: гарантия, которую некому исполнять, притворялась бы защитой; честный статус «не применимо» с сохранением границы L3 соответствует З4 (запрет встроен в инструмент) — инструмента в облаке нет, значит и обещания нет.

## Последствия

- Статусы «не определено» — проверяемые неизвестные со способом закрыть (живой прогон D16), а не молчаливые допущения.
- Обычные сессии и оператор этим ADR не затронуты: таблица констатирует уже принятые статусы, ни один гейт, порог или список не меняется.
- Документы, которые едут в проект, получают явный ответ, что шаблон гарантирует облачному агенту: минимальный контур — обещание, остальное — непромисы с условиями пересмотра.
