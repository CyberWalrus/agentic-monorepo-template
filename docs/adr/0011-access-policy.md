# ADR 0011: Метаданные политик доступа в контракте

- Статус: предложено (принимается merge этого PR человеком)
- Дата: 2026-11-15
- Контекст: задача C2.0 (аудит 2026-11-15). Ошибки доступа — чтение чужого ресурса по id — типичны для сгенерированного кода, а ревьюер-LLM гарантии не даёт: политика доступа должна объявляться в контракте и проверяться детерминированным тестом, а не договорённостью. План прошёл ревью `architecture-reviewer` и `sanity-reviewer` до написания; их находки учтены в этой редакции.

## Что проверено перед решением

## Решение

**Политика доступа объявляется метаданными самой процедуры контракта** — `.meta({ access })` на строителье с типом:

```ts
// packages/contracts/src/access-policy.ts
export const ocAccess = oc.$meta<{ access?: AccessPolicy }>({});
```

Набор типов политик — дискриминированное объединение на Zod, три варианта, без параметров:

- `public` — процедура доступна любому, включая неаутентифицированного;
- `owner` — доступ только владельцу ресурса процедуры (мидлварь сверяет актора с владельцем);
- `admin` — доступ только администратору.

Все процедуры сегодня объявляют `public`: акторов в системе ещё нет, они появятся в C2.2. Ценность декларации сейчас — явно записанное намерение и работающий механизм перебора: в день появления актора каждая процедура уже отвечает на вопрос «кто должен иметь доступ», и смена `public` → `owner` становится осознанной правкой контракта, а не побочным эффектом кода.

**Параметры политик отложены.** Добавление поля в вариант объединения — аддитивное, не ломающее изменение контракта; первый параметр появится с реальной потребностью (вторая доменная область, шаринг, роли администратора).

**Присутствие политики проверяет тест перебора** в `packages/contracts` — обычный шаг `test` в `pnpm verify`, без правок `tools/`: тест рекурсивно обходит контракт, находит процедуры guard-ом `isContractProcedure` и падает со списком процедур без `access` или с политикой, не проходящей `AccessPolicySchema`. Схемы вариантов строгие (`z.strictObject`): лишний ключ в политике отклоняется, а не стирается, — параметр нельзя добавить в meta незаметно от схемы.

## Что отвергнуто

- **Реестр-карта рядом с контрактом** (`Record<'tasks.list' | …, AccessPolicy>`): присутствие и форма проверялись бы уже типом, но политика живёт отдельно от процедуры — читатель контракта её не видит, а мидлвари C2.2 нужен поиск по пути вместо нативного чтения meta. Условие возврата: если мидлварь C2.2 упрётся в meta (например, политика не доедет до места исполнения) — реестр остаётся запасным вариантом, и смена снова ограничена пакетом контрактов.
- **Матрица RBAC (роль × действие)**: при одной доменной области и нуле ролей это спекулятивная конфигурируемость. Вернуться при второй области с собственными ролями.
- **Требовать политику типом строителя**: невозможно для объединения (см. факты) и опасно стартовым значением-сентинелом; тест даёт ту же гарантию дешевле.
- **Класть политику в `openapi.json`** (`x-access-policy`): генератор meta игнорирует, а потребителю REST-описания внутренняя политика авторизации не нужна.

## Последствия

- `packages/contracts/src/tasks.ts` строится на `ocAccess`; у каждой процедуры — `.meta({ access })`.
- Тест перебора выполняется обычным шагом `test`: красная ветка блокирует `pnpm verify` сразу. Постоянная канарейка шага — задача C2.1 (оператор); между merge этой задачи и C2.1 канарейка отстаёт на один PR — осознанный компромисс из журнала задачи.
- Мидлварь C2.2 читает политику как `procedure['~orpc'].meta.access`; два её обязательных свойства: процедура без `meta.access` отвергается по умолчанию (иначе расхождение «контракт объявил — роутер построил мимо контракта» уходит от перебора), и для исполняемых в схеме политик появляется мутационное покрытие (StrykerJS сейчас мутирует только `apps/api/src/**`). Из пакета наружу экспортируется только то, у чего уже есть импортёр: `AccessPolicySchema` (тест) и `ocAccess` (процедуры). Тип `AccessPolicy` остаётся приватным в модуле до появления импортёра (C2.2), иначе Knip пометит экспорт мёртвым.
- Миграция на oRPC 2 (после стабилизации): DSL и схемы не меняются, `.meta({ access })` заменяется на MetaPlugin — правка ограничена пакетом контрактов, как и требует задача.

## Задачи из решения

Новых задач не нужно: C2.1 (канарейка шага, оператор) и C2.2 (мидлварь авторизации) уже на доске и зависят от этой.
