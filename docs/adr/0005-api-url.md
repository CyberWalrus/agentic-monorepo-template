# ADR 0005: Адрес API и порты — один origin и порты из worktree

- Статус: принято
- Дата: 2026-11-13
- Контекст: [roadmap A5](../roadmap.md) — параллельные агенты в нескольких worktree. Запечённый в сборку `VITE_API_URL` давал: разные порты → разные сборки → промахи кэша turbo между worktree; фиксированные 3000/3001 сталкивали два параллельных `pnpm verify --full`.

## Решения: адрес API

| Область                | Решение                                                                                                                                                                                 | Почему                                                                                                                                                                                                                                      | Альтернатива и когда к ней вернуться                                                                                                                  |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Адрес API для браузера | Относительный `<origin>/rpc`: браузер ходит на тот же origin, что и страница                                                                                                            | Один origin: сборка web не зависит от адреса и порта API — `dist` идентичен во всех worktree, кэш сборки общий; CORS браузеру не нужен                                                                                                      | Передача адреса через SSR-payload — если API переедет на отдельный домен или появятся сторонние клиенты (не браузер)                                  |
| Адрес API для сервера  | `process.env.API_URL`, читается при старте процесса (SSR-рендер и прокси), не при сборке                                                                                                | Runtime-значение не попадает в бандл: серверная ветка `import.meta.env.SSR` выбрасывается минификатором                                                                                                                                     | `import.meta.env` на клиенте (запечывается) — никогда для адреса API                                                                                  |
| Механизм прокси        | `server.proxy` + `preview.proxy` для `/rpc` в `apps/web/vite.config.ts`, цель из env при старте процесса dev/preview                                                                    | Конфиг запуска, не код приложения; проверено эмпирически: и в `vite preview`, и в `vite dev` прокси перехватывает `/rpc` раньше SSR-обработчика TanStack Start (`POST /rpc/tasks/list` через origin web вернул ответ API, `/` остался HTML) | Server route `/rpc/$` в web (запасной вариант из обсуждения) — не потребовался; вернуть, если обновление Start начнёт перехватывать проксируемые пути |
| Что проксируется       | Только `/rpc`. `/health` и `/__test__/*` через web недоступны: фикстуры e2e, global setup и k6 ходят в API напрямую                                                                     | Тестовый API и внутренний эндпоинт не должны торчать из web-origin наружу; e2e-тест закрепляет «`/__test__/reset` через web → не 204»                                                                                                       | Расширение списка — только с ревью: каждый путь из прокси становится доступным из браузер                                                             |
| CORS                   | Удалён: `cors()` и `WEB_ORIGIN` убраны из API, браузерные запросы same-origin                                                                                                           | Прямые клиенты API (k6, фикстуры, OpenAPI-консьюмеры) не браузерные — им CORS не нужен; dead middleware не должен жить                                                                                                                      | Вернуть `cors()` с явным списком origin, если появится браузерный клиент вне web-origin                                                               |
| Production-топология   | Same-origin: `/rpc` маршрутизирует web-сервер (сейчас `vite preview`, после C3 — его production-сервер) или edge-прокси перед ним. API при этом может жить на любом порту той же машины | Топология не меняется при переезде с preview на production-сервер: прокси/маршрутизация `/rpc` остаётся свойством web-сервера                                                                                                               | Разделение доменов (api.example.com) — тогда возврат к передаче адреса через SSR и пересмотр CORS                                                     |

## Решения: порты

| Область               | Решение                                                                                                                                                                                                                   | Почему                                                                                                                                        | Альтернатива и когда к ней вернуться                                                                                             |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Вывод портов          | `tools/ports.ts`: база — детерминированный хеш абсолютного пути корня (чётная, 3300–3898), web = base, api = base+1; занятые порты сдвигают базу на +2, выбор — в `<root>/reports/ports.json`                             | Два worktree получают разные порты без координации; выбор диагностичен; канарейка «порты сведены к одному» красит e2e, если вывод сломан (З6) | Одна машина — один worktree; сервис-регистри портов — при реальном масштабе (C9), сейчас не нужен                                |
| Escape hatch          | `PORT_BASE` — точная база без сдвига; задана на уровне `ci.yml` (3300) — детерминизм портов в CI между раннерами                                                                                                          | turbo strict env передаёт её в задачи `e2e`/`perf`; человек может зафиксировать порты для отладки                                             | Ручной подбор свободного порта человеком                                                                                         |
| `pnpm dev`            | `node tools/dev.ts` — оркестратор: порты, env обеим задачам, токен instance-id (переиспользует существующий); turbo-задача `dev` удалена                                                                                  | turbo env не задаёт значений и не умеет вычислять; apps не импортируют tools — окружение собирает оркестратор                                 | Микро-пакет `packages/dev-ports` — e2e-black-box запрещает e2e импортировать packages, а playwright.config — главный потребитель |
| Reuse ручного сервера | Гейты (`verify --full`, CI) всегда стартуют свои серверы (`reuseExistingServer: false`). Ручной reuse — только `REUSE_SERVER=1` и токен этого worktree (его пишет оркестратор), иначе прогон не увидит занятый порт вовсе | Тихий reuse чужого кода — главный риск A5; токен-сверка PR-1 закрывает его с двух сторон                                                      | Долгоживущий общий dev-сервер на машину — если появится профиль параллельной отладки                                             |
| Перф под нагрузкой    | `tools/perf-lock.ts`: lock-файл в tmpdir (O_EXCL, pid + время), второй perf-прогон ждёт с логом; мёртвый pid или файл старше 15 минут — мусор упавшего прогона, забирается с предупреждением                              | Параллельные `verify --full` шумят под замерами; stale-детект не даёт одному краху навсегда заблокировать перф на машине                      | Ждать без stale-детекта — один крах = вечный lock                                                                                |

## Последствия

- Сборка web не зависит от адреса API: инвариант enforced сканом шага `bundle` (loopback-формы `localhost|127.0.0.1|0.0.0.0|[::1]` с портом в `dist/client/assets`) и канарейкой «адрес API запечён в бандл». Ограничение: не-loopback хост (например `https://api.internal`) скан не поймает — полное равенство двух `dist` не проверяется; расширяется, если появится потребность. «`/__test__` и `/health` не доступны через web-origin» — e2e-тест + канарейка «`/__test__` добавлен в прокси»; удаление прокси `/rpc` и сведение портов к одному роняют канарейками шаг `e2e` (З6).
- Каждый запрос браузера к API идёт через лишний локальный хоп (web → API). Замер после прокси лучше аудиторной линии (TTFB 5.5ms, LCP 28ms, сценарии 87.6/43.1ms против 6/32/95/49). Если сценарии покраснеют — сначала разбор, не поднятие порогов (З7).
- `pnpm dev` собирает окружение сам (порты из worktree, `reports/ports.json` для диагностики); продуктовый код читает только env и `--port` — apps tools не импортируют.
- Ручной `pnpm --filter @repo/api start` / `vite dev` внутри пакета требует env (`PORT`/`API_URL` из `node tools/ports.ts --env`) и падает с понятным сообщением без него (fail-closed, З4).
- Локальный кэш turbo общий для всех worktree одного репозитория — сборка web теперь не зависит от портов, поэтому кэш стабилен между параллельными агентами.
