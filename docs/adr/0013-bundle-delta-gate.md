# ADR 0013: Дельта-гейт бандла и доверенное одобрение роста

- Статус: принято (внедрено: PR-2 задачи A6 — merge #63, 2026-11-19: шаг `bundle-delta` в verify, job `bundle-delta` в `ci.yml`, доверенный workflow `bundle-approval`, label `bundle-growth-approved`; создание label и включение required check в ruleset — действия человека по github-setup.md п. 1–2)
- Дата: 2026-11-18
- Контекст: задача A6, PR-2 (план в файле задачи и [ADR 0006](0006-perf-strategy.md)). Абсолютный бюджет бандла стоит вплотную к факту (149.9/160 КБ total, 125.8/130 КБ крупнейший чанк): первая же фича с заметной зависимостью упирается в потолок, поднять который агент не может, — человек снова становится узким местом. При этом десятикратный рост прошёл бы потолок — абсолют ловит только катастрофу, а не нормальный рост. Решения человека 2026-11-14 ([ADR 0006](0006-perf-strategy.md)): рост бандла за один PR больше 5 КБ gzip одобряет человек label-ом, не через правку бюджета. Этот ADR фиксирует, как одобрение устроено механически.

## Что отвергнуто

- **Bundle-delta как required check напрямую.** Определение `pull_request`-workflow берётся из merge-ref: PR правит `ci.yml` и оставляет чек с тем же именем, но no-op-логикой. Одобрение роста нельзя доверять замеру, который контролирует сам автор.
- **Одобрение через тот же label `gate-change-approved`.** Рост бандла — не изменение гейта: он не трогает защищённые пути, и смешение двух одобрений в одном label сделало бы «одобренный рост» побочным эффектом гейт-правок (решение человека 2026-11-14).
- **Бюджет на маршрут вместо total.** Перекрыто решением человека в ADR 0006: дельта считается по total JS gzip; маршрутов в шаблоне один, грейд до маршрутных бюджетов — при втором маршруте.

## Последствия

- Рост бандла >5 КБ за PR требует одного человеческого действия (label) вместо PR в защищённый `perf-budgets.json`; агент по-прежнему не может ни поднять порог, ни сам себе одобрить рост.
- Пороги `maxJsWireKb` (155→160) и `maxLargestJsChunkGzipKb` (130→135) подняты тем же PR ради инварианта порядка срабатывания; абсолютные линии остаются потолками опыта, их дальнейший подъём — только человек.
- Окно без блокировки: между merge этого PR и включением человеком required check `bundle-approval` в ruleset рост бандла не блокирует merge — `bundle-delta` при этом уже красный и виден в PR. Человек создаёт label `bundle-growth-approved` до merge, required check включает после.
- Рост можно разбить на два PR по +4 КБ, минуя одобрение; это принято: вторая линия — абсолютный потолок 160 КБ, а храповик фактов — предмет PR-3.
- Тест инварианта порогов читает факты из отчётов `reports/bundle.json` и `e2e/reports/perf.json`: там, где их ещё нет (CI-джоба до сборки, свежий клон), он завершается пропуском — осознанный fail-open теста при fail-closed чекерах; фактически инвариант проверяется на прогоне verify --full.
- Доверенная база base-сборки: сейчас remote cache не включён; при подключении (A7) base-сборка в `bundle-delta` должна читать кэш только записей push-контурa main — иначе PR мог бы подсунуть отравленную запись кэша.
- PR-3 (ночное сравнение времени) — следующий PR задачи A6; 200-миллисекундный разрыв остаётся до него.
