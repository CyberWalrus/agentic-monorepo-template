# ADR 0006: Перф-стратегия — два уровня вместо абсолютных потолков

- Статус: принято (решения человека 2026-11-14, реализация PR-1..PR-3 A6)
- Дата: 2026-11-14
- Контекст: задача A6 — десятикратная регрессия времени проходит абсолютные потолки (LCP 64 мс CI при потолке 1500), а бюджет бандла стоит вплотную (149.8/160 КБ total, 125.6/130 КБ крупнейший чанк). Пороги времени калиброваны под машину разработчика и шумят на общих раннерах. Решения приняты человеком по пакету вариантов с последствиями (2026-11-14); реализация — три PR: детерминированные метрики, дельта-гейт бандла (свой ADR в своём PR), nightly-сравнение.

## Политика запаса порогов размера (C13, 2026-11-21)

Пороги размера делятся на два класса. **Фиксаторы поведения — без запаса**: `web.pages./.maxApiRequests = 0` (SSR отдаёт данные в HTML — `/rpc` на холодной загрузке значит регрессию гидратации) и сценарные `maxApiRequests` на уровне факта (10 и 10) — любое их изменение это событие для ревью контракта, а не для label `bundle-growth-approved`. **Охранители запаса — формула `ceil(факт + 15 КБ)`**: 15 КБ ≈ 3 × 5 КБ (три типовые зависимости; типовая ~5 КБ gzip — постановка C13); округление вверх гарантирует запас не меньше заявленного (floor дал бы 14.3–14.6 КБ). Дельта-гейт (ADR 0013, 5 КБ/PR) остаётся единственным механизмом одобрения пошагового роста; абсолюты существуют, чтобы запас не кончился незамеченным: инвариант «запас каждого JS-абсолюта > дельта-порога» (`tools/test/gates-canary.test.ts`) обязан оставаться зелёным.

Факты — замер в worktree `task/c13` (2026-11-21; совпадает с прогоном основного checkout тем же днём; «151.2» из постановки C13 — прогон аудита 2026-11-20, отчёты детерминированы):

| Порог                                | Факт  | Значение для `perf-budgets.json` | Эффективный запас |
| ------------------------------------ | ----- | -------------------------------- | ----------------- |
| `web.bundle.maxTotalJsGzipKb`        | 151.6 | 167                              | 15.4              |
| `web.bundle.maxLargestJsChunkGzipKb` | 126.7 | 142                              | 15.3              |
| `web.pages./.maxJsWireKb`            | 152.4 | 168                              | 15.6              |

Инвариант ADR 0013 выполнен по всем трём (15.3–15.6 > 5). `maxJsWireKb` поднимается вместе с total: perf-шаг сверяет wire-байты с ним (`e2e/perf/tasks.perf.ts:297`), без зеркального подъёма +10 КБ зависимости красят perf раньше нового запаса — обход политики через соседний шаг. **Поднятие — ослабление порога: числа в `perf-budgets.json` вносит человек своим коммитом в ветку задачи (З7; ADR 0009 «Пороги»)**. Симуляция C13: на текущих числах +10 КБ красят и `bundle` (161.6 > 160), и дельту (Δ ≈ +10 > 5); после коммита человека та же сборка зелёная по `bundle` (161.6 ≤ 167) и красная по дельте — одобрение роста остаётся за label.

Дублирование largest-чанка и total: 83.6 % JS — один entry-чанк (126.7 из 151.6), поэтому `maxLargestJsChunkGzipKb` фактически дублирует total. При route-сплиттинге (вторая страница) формулу для largest пересматривают отдельно.

Ночной канал после одобренного роста >5 КБ: байтовый допуск ночи равен `maxPrGrowthKb` (проводка `tools/check-perf-trend.main.ts:427`) — сверён, без изменений (тренд-допуски C13 «пересчитаны» = сверены). Следствие: одобренный рост >5 КБ первый ночной прогон после merge покажет как regression `jsWireKb`, и база не сдвинется сама — артефакт базы пишется только с зелёного сравнения (nightly.yml). Путь снятия — мейнтейнер удаляет артефакты `perf-baseline` прошлых зелёных прогонов (`gh api`): ближайший ночной прогон входит в режим «первый запуск» (fetch-baseline → none), сравнение пропускается и пишет свежую базу с одобренным размером. Закрытие issue путь не лечит: dedup создаст новое.

Условие возврата (раздел «Решение» C13): если после поднятия ночной тренд перестанет ловить реальные регрессии размера — вернуть нулевые запасы.

## Последствия

- perf-шаг в PR ловит структурные регрессии (новый файл на критическом пути, лишний запрос, вес чанка); временнúе — nightly. Разрыв по 200 мс в обработчике — осознанный, закрыт job `perf-canary` в nightly.
- Пороги детерминированных метрик стартуют с локальных фактов с запасом (страница: запросы ≤ 6 при факте 5, `/rpc` ≤ 0 — SSR отдаёт данные в HTML, и клиентский fetch = регрессия гидратации; сценарии: `/rpc` ≤ 10 при факте 10, long tasks ≤ 10 при локальном факте 0 — CI-раннер медленнее, порог затянется храповиком после фактов).
- Дельта-гейт бандла (5 КБ gzip от merge-base) и его доверенное одобрение — предмет отдельного ADR в PR-2 (заголовок gate-integrity.yml требует отдельного ADR на расширение доверенного workflow); `perf` выходит из канареечного вайтлиста З6 (канарейка «лишний `/rpc`-запрос»).
- Замеры детерминированных метрик идут по холодной загрузке в свежем контексте: тёплый кэш отдаёт пустые `encodedDataLength` и ломает детерминизм.
- Общий модуль `tools/perf-metrics.ts` — единственный источник ключей/схемы отчёта для perf-теста и тренд-чекера.
- Политика запаса (C13): абсолютные пороги размера держат запас ≈15 КБ (`ceil(факт + 15)`), фиксаторы поведения (`apiRequests`) — ноль; числа порогов двигает человек своим коммитом, инвариант «запас > дельта-порога» канареечится в `tools/test/gates-canary.test.ts`.
