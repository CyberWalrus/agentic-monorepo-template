# ADR 0020: Изоляция E2E по рабочему пространству — workspace-заголовок и «ничей» fallback

- Статус: принято (2026-11-22, merge #136)
- Дата: 2026-11-22
- Контекст: серия C1 «хранилище и изоляция тестов» ([architecture.md](../architecture.md) §5), задача c1.5 (зависимости c1.3 — гейт «схема совпадает с миграциями», [ADR 0018](0018-migrations-schema-sync-gate.md); c1.4 — база на воркер для integration). Прецеденты: ownerId — серверное поле строки вне публичного контракта (`apps/api/src/tasks/schema.ts`, комментарий «В контракте Task поля нет»); политика «owner» — C2.3. До этого PR E2E-проекты (functional, visual, perf) бьют в один InMemory-сторе одного API-процесса и сериализуются именованным локом `SHARED_DATA_LOCK`, потому что visual/perf перезаписывают общий список через `POST /__test__/reset`.

## Проблема

E2E-изоляция держится на общем сбросе данных и локах: визуальные и перф-сценарии вынуждены идти последовательно (`SHARED_DATA_LOCK`, `mode: 'serial'`), а сидирование перезаписывает данные соседних параллельных сценариев. Критерий приёмки c1.5 — «E2E, visual и perf идут параллельно на одном прогоне без взаимного влияния; общий сброс остаётся только в `/__test__/reset` для точечных сценариев» — требует изоляции данных на уровне сценария без изменения продукта для человека: страницы задач, публичный контракт и openapi не меняются (как было на момент решения; что с e58 меняется в openapi — см. «Поправка 2026-11-25»).

## Решение

1. **Домен: внутренний `workspaceId` у строки хранилища.** `TaskRepository` получает параметр `workspaceId?` в `list/create/toggle/remove/reset`; обе реализации (InMemory, Postgres — `apps/api/src/tasks/`) обновляются вместе, контрактный набор C1.1 гоняется против обеих. `workspaceId === undefined` означает «ничей» scope: `list()` без workspace видит только ничейные строки — это текущее поведение ручных клиентов и k6; `reset()` без workspace остаётся глобальным сбросом (легаси-семантика эндпоинта). `ownerOf` остаётся сквозным: политика «owner» — отдельная область доступа (C2.3), не изоляция E2E.
2. **Носитель — заголовок `x-workspace-id`, не вход процедуры.** Парсер (`parseWorkspaceId`, общий в `packages/contracts`, валидная форма `[\w-]{1,64}`) читает заголовок в `app.ts` для RPC-контекста и для `/__test__/*`; отсутствующий или невалидный заголовок — «ничей». Заголовок не входит в схему входа процедур и в `TaskSchema`: его читает мидлварь, а не валидация входа. Но в спеке он описан — с 2026-11-25 (e58) как необязательный параметр операции у каждой процедуры, которая его читает (см. «Поправка 2026-11-25»). Компромисс: носитель существует ради тестовой инфраструктуры, «ничей» режим без заголовка остаётся задокументированным поведением (см. «Отвергнутые варианты», вариант C).
3. **SSR тоже скопирован.** Лоадер `/` префетчит список на сервере напрямую в API (RPCLink, `apps/web/src/lib/api-client.ts`), и без заголовка SSR рендерил бы «ничей» (пустой) список при `staleTime: 10_000`. Кастомный server entry TanStack Start (`apps/web/src/server.ts`, точка `src/server.ts` поддерживается плагином) кладёт workspace документа-запроса в AsyncLocalStorage; SSR-fetch RPCLink добавляет заголовок оттуда. Клиентский бандл не получает серверную ветку (`import.meta.env.SSR`-branching, как zod в `env.ts` — проверяется шагом `bundle`). Браузерные запросы несут заголовок из `extraHTTPHeaders` контекста Playwright; прокси `/rpc` форвардит кастомные заголовки (`apps/web/src/server-app.ts`, `forwardHeaders`).
4. **Seed идёт в свой workspace, id сидированных задач уникальны на workspace.** Фикстура E2E выдаёт каждому тесту уникальный workspace и: ставит его в `extraHTTPHeaders` контекста (страница и её RPC-запросы), передаёт заголовком в `seedTasks` (request-фикстура не наследует рантайм-изменения контекста надёжно — заголовок идёт явно). `makeTasks(count, workspace)` строит детерминированные id из хэша `workspace:index` (uuid-форма), title остаётся `Seeded task #N` — пиксельные базлайны не меняются. Без уникальных id параллельные seed-ы разных workspace перетирали бы строки друг друга (Map по `task.id`, PRIMARY KEY на Postgres).
5. **Снятие сериализации.** Удаляются `SHARED_DATA_LOCK` (`e2e/fixtures.ts`), `mode: 'serial'` и `lock` у visual, `lock` у perf. Внутрисериализация perf-файла (`mode: 'serial'`, машинный лок `acquirePerfLock`) и Docker-обёртка visual — не `SHARED_DATA_LOCK`, остаются: это чистота замеров и контур базлайнов, не изоляция данных. `coldLoad` perf получает тот же workspace-заголовок, иначе детерминированные замеры молча меряли бы пустую страницу.

Тесты-носители решения: workspace-чеки в контрактном наборе репозитория (против обеих реализаций, в том числе «одинаковые id в разных workspace не влияют друг на друга»), тесты `app.ts` на заголовок `/rpc` и `/__test__/reset`, тесты SSR-fetch web, комбинированный прогон `--project=visual --project=perf` против одного API в Docker-контуре visual как доказательство критерия приёмки.

## Почему так

- Минимальный дифф продукта: страницы и фичи web не меняются; публичный контракт меняется только описанием в спеке (e58: параметр операции `x-workspace-id`, описание `createdAt`), схемы валидации и коды ответов прежние — изоляция существует только для тестов.
- Доменный паттерн тиражируем фичами (как схема изоляции c1.4): «workspace из контекста запроса, строки с внутренним scope, скопированный SSR» — один образец.
- Критерий доказуем на одном API-процессе: параллельные проекты не сериализуются данными.

## Отвергнутые варианты

- **API-инстанс (порт) на проект/воркер Playwright.** Изолирует надёжно, но правит защищённый `e2e/playwright.config.ts` (deny), требует перераспределения портов и не даёт фичам доменного образца изоляции. Вернуться, если workspace-заголовок перестанет доезжать по какому-то транспорту (сейчас: браузер через прокси — проверено `forwardHeaders`; SSR напрямую — проверяется тестом; request-фикстура — явный заголовок).
- **Workspace в явных параметрах контракта** (`list({ workspace })`, поле в `TaskSchema`). Меняет UI, openapi и публичную форму ради тестовой инфраструктуры; вернуться, когда появятся настоящие арендаторы — тогда workspace переезжает в актёра аутентификации и контракт по ADR про аутентификацию. Описание заголовка в openapi (поправка 2026-11-25) — не этот вариант: заголовок остаётся вне входа процедуры, схема входа и `TaskSchema` его не знают.
- **Изоляция только фикстурами без домена** (например, перезапись списков в клиенте). Не изоляция: сервер остаётся общим, любое состояние гонки между проектами сохраняется.

## Условие возврата

- Появляется реальная аутентификация или арендаторы: workspace переезжает в актёра/контракт, тестовый заголовок остаётся только в `/__test__/*`-подготовке; этот ADR закрывается ADR про аутентификацию.
- Заголовок оказался недостижим в новом транспорте (мобильный клиент, сторонний потребитель): переход к варианту «инстанс на проект» или включение workspace в контракт по тогдашней задаче.
- Скопированный SSR усложняет апгрейд TanStack Start (кастомный server entry): точка одна (`apps/web/src/server.ts`), откат — к «ничей» SSR с пустым префетчем и принудительным refetch (`staleTime: 0` для списка) — хуже по замерам, но работоспособно.

## Поправка 2026-11-25: заголовок описан в openapi.json

Основание — задача e58 (аудит владельца от 2026-11-23, «Низкие → Контракты»; строка реестра от 2026-11-25 в [escaped-defects.md](../escaped-defects.md)). Строка «Схемы процедур и `TaskSchema` не меняются → `openapi.json` не меняется» решения №2 перестала соответствовать коду. Журнал — в файле задачи (`backlog/done/e58.md`; каталог `backlog/` исключён из копии шаблона, поэтому не ссылкой).

### Решение

Заголовок `x-workspace-id` остаётся вне схем входа процедур, но описан в `openapi.json`: необязательный параметр операции (`in: header`, `required: false`, шаблон значения — форма парсера `[\w-]{1,64}`) у каждой процедуры, которая его читает. Процедура-читатель помечается при определении обёрткой `readsWorkspace` (`packages/contracts/src/workspace.ts`); шаг сборки спеки `documentWorkspaceHeader` (`packages/contracts/scripts/openapi-spec.ts`) навешивает параметр на каждую операцию реестра читателей. Fail-closed: читатель без полного `route` или операция реестра, которой нет в спеке, — ошибка сборки спеки, а не операция без описанного заголовка. Имя, шаблон и описание семантики отсутствующего заголовка живут в `workspace.ts` — один источник для парсера и спеки. Там же к `TaskSchema.createdAt` добавлено описание канонической формы (UTC с `Z`): `z.iso.datetime()` прежний, обе реализации хранилища отвечают формой `Date#toISOString()`.

### Почему так

- Параметр, который сервер читает на проводе, обязан быть в спеке: клиент, сгенерированный из `openapi.json`, иначе о нём не узнаёт, а опечатка в имени или отсутствие заголовка молча даёт «ничей» список — без ошибки. Гейты контракта (`openapi:check`, `openapi-compat`) видят только спеку: заголовок вне её был для них невидим.
- Компромисс решения №2 сужен, а не снят: носитель по-прежнему существует ради тестовой инфраструктуры, «ничей» режим без заголовка сохранён и описан в спеке как семантика отсутствующего параметра. Отказ 400 не вводился — это breaking change, которого никто не просил.

### Альтернативы

- **Оставить заголовок вне спеки и описать его только здесь.** Отклонено: сгенерированный клиент и гейты контракта параметр не видят — дефект остаётся, а ADR закреплял бы ложное правило «заголовок вне спеки by design».
- **Сделать заголовок частью валидируемого входа процедуры.** Отклонено: отсутствующий заголовок становился бы ошибкой валидации — breaking change; для настоящих арендаторов остаётся вариант «Workspace в явных параметрах контракта» выше.

### Условие возврата

- Наступило «Условие возврата» основного решения (аутентификация или арендаторы): workspace переезжает в актёра/контракт — обёртка `readsWorkspace`, шаг `documentWorkspaceHeader` и параметр операции удаляются вместе с заголовком.
- Процедура перестала читать заголовок: обёртка снимается с неё, а тест спеки («documents the header exactly on the operations workspace.ts names as readers», `packages/contracts/scripts/openapi-spec.test.ts`) требует убрать параметр из её операции.
