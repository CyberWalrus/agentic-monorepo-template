# ADR 0007: Параллельная работа агентов — доска задач в файлах и захват через ветку

- Статус: принято (2026-11-14, merge #20). Пополнение 2026-11-14: строки «Замыкание задачи» и «Планы и пакеты решений» — после первого задним числом закрытия задач (C5, C8)
- Дата: 2026-11-14
- Контекст: один человек запускает несколько сессий агентов в одном клоне репозитория и говорит каждой «продолжай по плану». До доски план был одним файлом `docs/roadmap.md`: в нём нет признака «задача занята», а статусы, записанные в общий файл, сами дают конфликты (З9). Основной клиент — ZCode, система обязана работать также в Claude Code и Codex. План прошёл ревью `architecture-reviewer` и `sanity-reviewer` до кода; их находки учтены в этой редакции.

## Прогон D2: три клиента (2026-11-14)

Одинаковый сценарий в клоне шаблона на `d4f861a`, вне основного репозитория: ветка → `git worktree add` вне репо → правка в `apps/api/src` → `pnpm install` → `pnpm verify` → коммит. ZCode — рабочая сессия агента; Claude Code 2.1.267 (`claude -p`, skip-permissions) и Codex 0.39.0 (`codex exec`) — headless.

| Шаг                     | ZCode                                                 | Claude Code                                                                                    | Codex                                                                      |
| ----------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Авторизация             | ✅                                                    | ✅ (ключ; проектный `.claude/settings.json` игнорируется без trust workspace)                  | ❌ 401 при refresh токена, нужен ручной `codex login`                      |

| Правка в `apps/api/src` | ✅                                                    | ✅                                                                                             | не дошёл                                                                   |
| `pnpm install`          | ✅ 0,6 с (общий store)                                | ❌ pnpm выбрал store в соседнем каталоге, песочница запретила операцию блокировки              | не дошёл                                                                   |
| `pnpm verify`           | ✅ PASS 13 с                                          | ❌ каскадно: без `node_modules`                                                                | не дошёл                                                                   |
| Коммит (Lefthook)       | ✅ с находкой: хуки не ставятся из worktree (см. D11) | ✅ хук сработал и отклонил коммит без инструментов; `--no-verify` агент не применял            | не дошёл                                                                   |

Выводы.

- Решение «Рабочее место» подтверждено для основного клиента: ZCode-агент создаёт ветку, worktree вне workspace и проходит гейты сам.
- Оба клиента, дошедшие до шагов, не пытались обходить ограничения и вели отчёт по шагам; Lefthook в Claude Code отклонил коммит fail-closed.
- Найден пробел защиты: `prepare` ставит хуки только при `[ -d .git ]`, а в worktree `.git` — файл. Захвачено задачей D11.
- Для Claude Code полный сценарий требует двух настроек рабочего места: allowlist записи на каталог worktrees и предсказуемый store-dir pnpm; для Codex — ручного `codex login`. До этого таблица «клиент × шаг» неполна по этим двум клиентам.

## Решения

| Область                       | Решение                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Почему                                                                                                                                                                                                                                                                                                                              | Альтернатива и когда к ней вернуться                                                                                                                      |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Единица                       | Одна задача → одна ветка `task/<id>` → один worktree → один агент → один PR                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Два агента в одной задаче правят одни файлы; задача больше одного PR плохо ревьюится (architecture.md, раздел 4)                                                                                                                                                                                                                    | Несколько агентов на одну задачу — только через оркестратор конкретного клиента, поверх этой схемы                                                        |
| Где лежат задачи              | Каталог `backlog/`, один файл на задачу: `backlog/<id>.md`. Закрытые — в `backlog/done/`. Имя `tasks` не используется: так называется демо-домен                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Общий файл со всеми задачами правит каждый PR — это «горячий» файл (З9). Файлы читает любой клиент без сети и без SaaS (З12)                                                                                                                                                                                                        | GitHub Issues — если появится команда, которой нужны обсуждения и уведомления; файлы тогда остаются источником для агентов                                |
| Идентификатор                 | `id` — имя файла. Дочерние задачи получают id от родителя (`d12.1`). Общего счётчика нет                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Два PR с одним id дают конфликт добавления одного файла — его ловит сам git, а не гейт после merge                                                                                                                                                                                                                                  | —                                                                                                                                                         |
| Поля задачи                   | Front matter: `title`, `type` (`research`, `decompose`, `change`), `priority`, `depends_on` (список id), `touches` (литеральные пути и `каталог/**`; для `research` и `decompose` может быть пустым), `needs_human` (что должен решить человек). Тело: проблема с доказательством, что сделать, критерии приёмки, журнал                                                                                                                                                                                                                                                                                                      | Минимум, по которому задачу можно выбрать детерминированно. Произвольные glob-ы не разрешены: их пересечение нельзя посчитать точно                                                                                                                                                                                                 | —                                                                                                                                                         |
| Откуда читается доска         | Из ссылки `main`, а не из рабочего дерева. Блокирующие поля (`depends_on`, `needs_human`, `touches`) тоже берутся из `main`. Если remote доступен, команда сначала обновляет `main`; если нет — печатает возраст данных. Задача, добавленная в ветке, появляется на доске только после merge                                                                                                                                                                                                                                                                                                                                  | У каждого worktree своё рабочее дерево: иначе у каждого агента была бы своя доска, а ветка могла бы сама снять с себя блокировку или захватить задачу из чужого непроверенного PR (З2)                                                                                                                                              | —                                                                                                                                                         |
| Статус                        | В файле не хранится, вычисляется: файл в `backlog/done/` — закрыта; есть ветка `task/<id>` — в работе; есть незакрытые `depends_on` или `needs_human` — заблокирована; путь из `touches` попадает под `deny` из `tools/protected-paths.json` — нужен режим обслуживания; иначе свободна                                                                                                                                                                                                                                                                                                                                       | Хранимый статус расходится с действительностью и требует записи в `main` (З10). Пометка 🔒 вычисляется из того же списка, что и защита путей                                                                                                                                                                                        | Поле `status` в файле — никогда: это второй источник правды                                                                                               |
| Захват                        | Создание локальной ветки `task/<id>` от `main` в общем хранилище ссылок клона: второй агент на той же машине получает отказ git. В remote ветка попадает обычным push, когда появляются коммиты                                                                                                                                                                                                                                                                                                                                                                                                                               | Атомарность даёт блокировка ссылки в git. Не нужен демон, сервер очереди и сеть                                                                                                                                                                                                                                                     | Захват через push новой ветки с уникальным коммитом — когда агенты появятся на второй машине или в облаке; тогда же решать, как он уживается с `pre-push` |
| Задачи с режимом обслуживания | `next` их не выдаёт, а перечисляет человеку. Начинает такую задачу только человек: включает режим обслуживания и называет id                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Агент не может менять защищённые пути и не должен искать обход; в ZCode его остановил бы только CI                                                                                                                                                                                                                                  | —                                                                                                                                                         |
| Брошенный захват              | Автоматического перехвата нет. `list` показывает возраст последнего коммита ветки, есть ли у неё worktree, и отдельно — закрытые задачи, от которых остались ветка или worktree. Освобождает задачу человек: `release` требует интерактивного терминала и переименовывает ветку в `abandoned/<id>`, а не удаляет                                                                                                                                                                                                                                                                                                              | Нельзя отличить упавшую сессию от медленной без демона; ошибочный перехват даёт двух агентов в одной задаче. Переименование обратимо                                                                                                                                                                                                | Перехват по порогу времени — если брошенных задач станет больше, чем человек успевает разбирать                                                           |
| Что можно параллельно         | Последовательность задаёт `depends_on`. Пересечение `touches` с задачами в работе не запрещает захват: `next` ставит такие задачи в конец и предупреждает                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Пока общие реестры правит каждая фича (задача B7), жёсткий запрет остановил бы почти всё или приучил бы занижать `touches`. Предупреждение не требует атомарной проверки «пути свободны»                                                                                                                                            | Запрет при пересечении и проверка «дифф внутри объявленных путей» (задача D7) — после B7, если конфликты слияния станут частыми                           |
| Тип `research`                | Берётся, когда нельзя написать проверяемые критерии приёмки или выбор зависит от факта вне репозитория. Результат — ADR, файл в `docs/research/` или новые задачи; журнал результатом не считается                                                                                                                                                                                                                                                                                                                                                                                                                            | Исследование, спрятанное внутри задачи с кодом, не видно другим агентам и не ревьюится до кода                                                                                                                                                                                                                                      | —                                                                                                                                                         |
| Тип `decompose`               | Берётся, когда задача не помещается в один PR или для неё нельзя назвать `touches`. Результат — файлы задач с `depends_on` и `touches`. Изменение контракта API всегда отдельная задача, от которой зависят остальные                                                                                                                                                                                                                                                                                                                                                                                                         | Декомпозиция — единственное место, где решается, что пойдёт параллельно. `packages/contracts` — общий файл для фронта и бэка (contract-first)                                                                                                                                                                                       | —                                                                                                                                                         |
| Передача между сессиями       | Состояние задачи — её ветка: `next` и `resume` печатают коммиты и статистику диффа относительно `main`. В разделе «Журнал» файла задачи остаётся то, чего нет в диффе: что решено и что дальше. Закрывающий PR переносит файл в `backlog/done/`                                                                                                                                                                                                                                                                                                                                                                               | Журнал держится на инструкции, и агент его забудет; дифф ветки не врёт. Перенос вместо удаления сохраняет журнал и позволяет проверять `depends_on` без истории git                                                                                                                                                                 | Память клиента (ZCode Memory, память Claude Code) — не переносится между клиентами и не лежит в git                                                       |
| Замыкание задачи              | Работа над задачей с доски завершается переносом `backlog/<id>.md` в `backlog/done/` тем же PR, что и работа — на ветке задачи это её собственный файл. Перенос делается сразу после захвата (`pnpm backlog close <id>`): гейт `docs` красит ветку `task/<id>`, пока файл задачи открыт в её дереве, поэтому «забыл перенести» — невозможное состояние, а не дисциплина. Для работы вне доски по задаче с доски перенос делает PR, в теле которого назван `<id>`. Расхождение «ветка `task/<id>` смержена, файл ещё открыт» ловит `pnpm backlog doctor` (локально и в nightly): красит и перечисляет расхождения, а не молчит | Правило «Закрывающий PR переносит файл» держалось на инструкции и уже дважды не сработало на работе вне доски (C5, C8, 2026-11-14): доска продолжала показывать закрытые задачи открытыми. Гонец расхождений нужен потому, что статус вычисляется из нескольких фактов (файл, ветка, merge), каждый из которых меняется своим путём | Бот, автоматически переносящий файл после merge, — если расхождения станут появляться чаще, чем человек успевает разбирать doctor                         |
| Планы и пакеты решений        | План задачи и пакеты решений человека живут в «Журнале» файла задачи или в ADR. `/tmp` и память клиента источником не являются: `/tmp` эфемерен, память клиента не переносится между машинами и клиентами; память агента хранит указатель на задачу, а не её состояние — статус вычисляет доска                                                                                                                                                                                                                                                                                                                               | Материал, по которому другая сессия продолжает работу, должен лежать рядом с задачей (З12: без SaaS и без конкретного клиента). План A6 в `/tmp` пережил сессии случайно, а не по построению                                                                                                                                        | —                                                                                                                                                         |
| Команды                       | `pnpm backlog list` — доска со статусами; `pnpm backlog next` — в worktree с веткой `task/<id>` показывает её состояние, иначе первую свободную задачу; `pnpm backlog start <id>` — захват и рабочее место; `pnpm backlog close <id>` — закрыть задачу: перенос файла в `done/` тем же PR; `pnpm backlog resume <id>` — продолжить брошенную по поручению человека; `pnpm backlog release <id>` — только человек; `pnpm backlog doctor` — расхождения «смержена — доска не знает», красит nightly                                                                                                                             | Один вход для любого клиента (З5). Git вызывает сама команда, а не агент: текст команды не зависит от клиента                                                                                                                                                                                                                       | Команды клиента (`/next-task`) — тонкая обёртка над `pnpm backlog`, не замена                                                                             |
| Рабочее место                 | Основной checkout всегда остаётся на `main`: `start` в нём ветку не переключает, а создаёт worktree рядом с репозиторием и печатает путь. В уже созданном worktree `start` переключает ветку. Если worktree создать нельзя (песочница), команда объясняет, как открыть его средствами клиента (З11)                                                                                                                                                                                                                                                                                                                           | Человек не выбирает ветку и worktree руками. Клиенты создают worktree по-разному, команда подстраивается под то, где её запустили                                                                                                                                                                                                   | Worktree всегда создаёт клиент (галочка в ZCode), а `start` только создаёт ветку — если задача D2 покажет, что агент плохо работает вне своего workspace  |
| Работа вне доски              | По прямому поручению человека агент работает без задачи, в ветке с любым именем, кроме `task/*`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Доска — способ выбрать работу самому, а не обязательная бюрократия для каждой правки                                                                                                                                                                                                                                                | —                                                                                                                                                         |
| Проверка доски                | Часть существующего шага `docs:check`: схема front matter, ссылки `depends_on` на существующие или закрытые задачи, отсутствие циклов, грамматика `touches`; на ветке `task/<id>` среди существующих файлов доски меняется только свой. Front matter — подмножество «ключ: значение или список в строку», без новой зависимости. Канарейки: испорченная доска красит шаг; из двух одновременных `start` одной задачи проходит один                                                                                                                                                                                            | Доска — инструкция, которой доверяет агент, ровно то, что уже проверяет `docs:check` (architecture.md 3.10). Отдельный гейт потребовал бы шага, job, записи в `deny` и бюджета ради одной проверки                                                                                                                                  | Отдельный шаг `verify` — если проверка доски выйдет за бюджет времени `docs:check`                                                                        |
| Защита доски                  | `backlog/**` добавляется в класс `review` защищённых путей                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Изменение чужой задачи или её блокирующих полей должен увидеть человек                                                                                                                                                                                                                                                              | —                                                                                                                                                         |
| Инструкции                    | `AGENTS.md` получает короткий раздел «Начало сессии» (выполни `pnpm backlog next`, дальше по типу задачи) и таблицу скилов с путями. Подробности — в скиле. ## Что отвергнуто

- **Оркестратор как основа** (ведущая сессия раздаёт задачи субагентам или сессиям). Механизм у каждого клиента свой, перенести его между ZCode, Claude Code и Codex нельзя. Доска не мешает оркестратору: он может вызывать те же команды.
- **Готовые инструменты.** Спецификация [tasks.md](https://github.com/tasksmd/tasks.md) и форк [Backlog.md с захватами](https://github.com/lunetics/Backlog.md) решают ту же задачу, но на 2026-11-14 это проекты одного автора без подтверждённого применения. Условие возврата: один из форматов поддержат сами клиенты.
- **Сервер очереди с арендой.** Противоречит З12 и не нужен, пока агенты работают в одном клоне.
- **Закрытие задачи удалением файла** (как сейчас в roadmap). Вместе с файлом пропадает журнал, опечатка в `depends_on` неотличима от закрытой задачи без истории git, а случайное удаление чужой задачи молча её закрывает.

## Последствия

- Захват виден только внутри одного клона. Агент на другой машине или в облаке чужих захватов не видит — этот случай не поддерживается до появления второго слоя.
- Доска обновляется с опозданием на merge: задачи из декомпозиции нельзя взять, пока человек не слил её PR. Это намеренно — декомпозицию сначала ревьюят.
- Настоящую параллельность ограничивают общие файлы. Для продуктовых фич это реестры (`router.ts`, barrel-файлы, `openapi.json`) — задача B7. Для задач самой обвязки это `docs/architecture.md` (статусы законов), `AGENTS.md`, `tools/verify-steps.ts`, `ci.yml`, `tools/protected-paths.json`, `CODEOWNERS`, `.claude/settings.json`: такие задачи идут по очереди, что совпадает с правилом «один гейт на один PR».
- В ZCode нет контура L0: формат после правки и `verify` перед завершением агент запускает сам, по инструкции. Гарантией остаются Lefthook и CI. Адаптер хуков для ZCode — задача C10; как новый контур он потребует своего ADR.
- Хук `Stop` Claude Code считает `*.md` документацией и `verify` не запускает: сломанную доску после декомпозиции покажет только CI, пока `backlog/**` не причислен к коду (входит в D3).
- Команды и проверка лежат в `tools/` — защищённый путь, внедрение требует режима обслуживания.
