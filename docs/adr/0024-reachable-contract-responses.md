# ADR 0024: Контракт описывает только достижимое — ошибка объявлена там, где её бросают

- Статус: принято (одобрил владелец в чате 2026-11-24 — ответ на запрос согласия на несовместимые изменения контракта этой задачи, дословно: «да окей»; merge — по поручению владельца от 24.11, конвейером, запись согласия — в PR)
- Дата: 2026-11-24
- Контекст: [ADR 0011](0011-access-policy.md) (политика доступа в контракте), [architecture.md](../architecture.md) §2.2, [реестр пропущенных дефектов](../escaped-defects.md) за 2026-11-24, задача e57 (`backlog/done/e57.md`).

## Проблема

Строитель `ocAccess` прикреплял всем процедурам контракта tasks общий каталог ошибок — `FORBIDDEN` и `INTERNAL_SERVER_ERROR` (с PR #57, `69de7bba`, 2026-11-17). У public-процедур `list`, `create`, `toggle` проверку доступа мидлварь не выполняет — политика `public` сразу пропускает (ADR 0011), — бросать `FORBIDDEN` некому. Тем не менее `openapi.json` описывал для них 403: спека обещала ответ, которого сервер не даёт.

С той же стороны принципа — вход: `CreateTaskInputSchema` на `z.object` молча отбрасывал лишние ключи. Контракт принимал то, чего не описывал: `{ "title": "x", "extra": 1 }` создавал задачу, поле исчезало без ошибки.

Оба дефекта прошли все гейты: `openapi:check` сверяет спеку с контрактом, но ни один контур не сверяет контракт с рантаймом — достижим ли объявленный ответ.

## Решение

**Контракт описывает только достижимое и отказывает явно.**

1. **Строитель — по политике процедуры** (`packages/contracts/src/access-policy.ts`). `ocPublic` — для политик `public`: из общих ошибок только `INTERNAL_SERVER_ERROR`. `ocAccess` — для процедур с проверкой доступа (`owner`, `admin`): общие ошибки и `FORBIDDEN`. Конструкторы `errors` обработчика строятся из ошибок, объявленных процедуре, поэтому обработчик public-процедуры не бросит `FORBIDDEN`.
2. **Вход — строгий объект.** `CreateTaskInputSchema` — `z.strictObject`: лишний ключ — ошибка валидации `BAD_REQUEST`, одна и та же на клиенте и на сервере (одна схема).
3. **Отказ мидлвари авторизации — своя ошибка мидлвари** (`apps/api/src/authorization.ts`), а не конструктор процедуры: конструктор `FORBIDDEN` теперь есть не у каждой процедуры, а отказать мидлварь обязана любую — в том числе без политики (deny-by-default). Код, статус и текст каталога те же, что давал `errors.FORBIDDEN()`; `defined` по-прежнему говорит, объявлен ли код процедуре.
4. **Правило держат тесты перебора**, по одному на каждом уровне:
   - контракт — `FORBIDDEN is declared exactly by procedures that check access` (`packages/contracts/src/errors.test.ts`);
   - спека — `documents 403 only for the procedure that checks access` (`packages/contracts/scripts/openapi-spec.test.ts`);
   - рантайм — `public procedures never answer FORBIDDEN` (`apps/api/src/router-divergence.test.ts`): в роутере `FORBIDDEN` объявлен ровно у `remove`, анонимный актор получает ответ от `list`, `create`, `toggle`;
   - мидлварь — `denies a procedure without an access policy` (`apps/api/src/authorization.test.ts`): двойник без политики стоит на строителе без `FORBIDDEN` и всё равно получает отказ.

**Несовместимые изменения оформлены по правилу гейта C6** (`packages/contracts/scripts/openapi-compat.ts`), а не отключением. Гейт сигнализирует четыре изменения, все — намеренные:

- `[response-status-removed]` — `GET /tasks`, `POST /tasks`, `POST /tasks/{id}/toggle`: ответ 403 удалён;
- `[additional-properties-narrowed]` — `POST /tasks.requestBody.application/json`: появился `additionalProperties: false`.

Совет гейта «делай аддитивно» здесь не исполняется: 403 сервер никогда не отдавал, переносить нечего, а старый вариант существует только в спеке. Этот ADR и ревью PR — явное согласие человека (скил `api-contract-change`, раздел «Breaking changes»).

**Миграция для проектов-потребителей.** Обработка 403 у `GET /tasks`, `POST /tasks`, `POST /tasks/{id}/toggle` становится мёртвым кодом — её нужно убрать; при кодогенерации по `openapi.json` вариант ошибки исчезает из типов. `POST /tasks` с лишним полем отвечает 400 вместо молчаливой отбраски — отправлять только описанные поля. 403 сервер и раньше не отдавал; строгость входа — намеренное изменение поведения.

**Что не меняется.** Роутер (`apps/api/src/router.ts`) прежний: `tasks.remove` бросает объявленный `errors.FORBIDDEN()`. Ответы сервера для всех процедур с корректным контрактом — прежние: public-процедуры мидлварь и раньше пропускала, процедуры с проверкой доступа объявляли `FORBIDDEN`. Путь «процедура на `ocPublic` без политики» достижим только при расхождении контракта, которое красят тесты политики доступа.

## Отвергнутый вариант: снимать FORBIDDEN обходом после сборки контракта

Можно было оставить один строитель и удалять `FORBIDDEN` из public-процедур обходом контракта. Спека стала бы верной, а типы обработчиков — нет: у обработчика public-процедуры оставался бы конструктор `errors.FORBIDDEN()`, и контракт снова разрешал бросить то, чего не описывает. Правило держалось бы обходом, а не типами строителя.

Второй отвергнутый вариант — оставить `FORBIDDEN` у всех процедур и описать неточность в документации: спека остаётся обещанием, которого сервер не выполняет.

## Условие возврата

Если в шаблоне появится общесерверная проверка, которая отвечает 403 public-процедурам до входа в политику доступа (лимит по ключу, запрет записи из «ничьего» scope), 403 снова станет достижимым. Тогда затронутые процедуры получают `.errors({ FORBIDDEN: forbiddenError })` явной строкой вместе с рантайм-тестом; возвращать `FORBIDDEN` всем процедурам «на всякий случай» нельзя.

Для строгого входа условие то же, что в задаче: если strict-режим ломает сценарий шаблона (отправитель шлёт лишние поля) — править отправителя, не возвращая молчаливую отбраску.
