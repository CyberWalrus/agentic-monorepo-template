# Архитектурные и инфраструктурные подходы

> Статус: действует · Дата: 2026-11-12
> Для кого: агенты и люди, которые развивают сам шаблон. Правила работы над фичами продукта остаются в [AGENTS.md](../AGENTS.md).
> Что делать дальше и в каком порядке: доска задач `backlog/` (`pnpm backlog next`, ADR 0007). Почему выбран стек: [ADR 0001](adr/0001-initial-stack.md). Зачем система существует: [vision.md](vision.md).

## Как читать этот документ

У каждого правила есть статус:

- **действует**: правило уже обеспечено кодом или гейтом. Нарушать его нельзя.
- **целевое**: направление принято, реализации ещё нет. Рядом стоит номер задачи — id файла в `backlog/`. Новый код не должен отдалять репозиторий от целевого состояния.

Если документ расходится с кодом, для правил «действует» это ошибка документа: исправь его в том же PR. Для правил «целевое» прав документ.

Термины:

- **Гейт**: детерминированная проверка, которая может заблокировать merge.
- **Канарейка гейта**: тест, который подаёт гейту заведомо плохой вход и проверяет, что гейт упал.
- **Доверенная база**: код из целевой ветки (`main`), а не из проверяемого изменения.
- **Режим обслуживания**: сессия, в которой осознанно изменяют гейт (см. [AGENTS.md, раздел «Claude Code»](../AGENTS.md#claude-code)). Включает человек или оператор. Две формы (b9): локальная — файл `.claude/maintenance.json` открывает Edit/Write перечисленных путей, песочница и остальные хуки работают; полная — `.claude/settings.local.json` выключает все хуки и песочницу.
- **Оператор**: сессия агента с computer use, которой человек в чате поручил действия, раньше требовавшие его самого: включить режим обслуживания, вести задачу, меняющую гейт, поставить порог по правилу. Приёмка PR остаётся человеку ([ADR 0009](adr/0009-operator-delegation.md)).

## 1. Законы обвязки

Эти правила важнее любого конкретного инструмента. Инструменты меняются, законы остаются.

**З1. Merge блокирует только детерминированная проверка.** Ревьюеры-LLM комментируют и предлагают. Находка ревьюера становится блокером, только когда её подтвердил гейт или человек. _Действует: `agent-review.yml` не входит в `gate`._

**З2. Гейт исполняется из доверенной базы.** Скрипт проверки, список защищённых путей и workflow, которые решают судьбу PR, берутся из `main`, а не из самого PR. Иначе PR переписывает собственного судью. _Действует для защищённых путей: `gate-integrity.yml` на `pull_request_target` исполняется из базовой ветки, список файлов берёт из GitHub API ([ADR 0002](adr/0002-gate-integrity.md)). Остальные job CI (`gate`) по-прежнему исполняются из PR — их удерживает требование одобрения любых правок `.github/**`._

**З3. Проверяй результат, а не способ.** Чёрный список команд или синтаксиса всегда неполон. Надёжная проверка смотрит на итог: какие файлы изменились, сколько тестов пропущено в отчёте раннера, сколько весит собранный бандл. Разбор команд допустим только как быстрая подсказка агенту. _Частично: защищённые пути проверяются по результату — снимок сессии ([ADR 0003](adr/0003-result-based-protection.md), 2026-11-13); пропуск тестов — по отчёту раннера, гейт `test-report` (2026-11-13); невидимое отчёту (`it.fails`, комментарии подавления) — синтаксический слой гейта `test-integrity` (2026-11-13), ранний `return` перед `expect` — задача B2._

**З4. Запрет встроен в инструмент и закрыт при сбое.** Если действие запрещено, отказать должен сам инструмент: конфиг бросает ошибку, ОС не даёт записать файл. Защитный хук, который упал или не успел ответить, блокирует действие, а не пропускает его. _Действует: хуки агента падают закрытыми (неожиданная ошибка → exit 2, без зависимости от `node_modules`, 2026-11-13); запись в защищённые пути запрещена на уровне ОС — песочница Bash ([ADR 0004](adr/0004-sandbox.md), 2026-11-13); отказ вне Linux встроен в оба конфига визуальных тестов — Vitest UI инлайн, Playwright через `tools/visual-guard.ts` до побочных эффектов конфига, запись базлайнов только при `VISUAL_UPDATE=1` (A8, 2026-11-13). Осталось: поле `onFailure: "block"` добавится после обновления CLI (нужен ≥ 2.1.295)._

**З5. Один вход для всех проверок: `pnpm verify`.** CI вызывает те же скрипты, что и локальная команда. Новый гейт добавляется сразу в три места: шаг в `tools/verify.ts`, job в `ci.yml`, список `needs` у job `gate`. Гейт, который есть только в CI, считается недоделанным. _Действует. Исключения: скриншот-тесты (нужен Docker), k6 и `gate-integrity` (нужен контекст GitHub API: файлы PR, label, события); канарейки гейтов (`pnpm canaries`) — по замыслу B1 не в каждом PR, а при изменении гейтов, на push в `main` (e79 — 3.4) и в nightly; `--only` в verify — подмножество для человека и канареек, хуки и CI его не передают. Объём E2E в PR — файловый выбор по фичам (`E2E_FEATURES`, B4.1, 2026-11-17, по образцу `--affected`): `testIgnore` проекта functional отсекает только незаданные фичи с app-каталогом; сквозные e2e-фичи (без app-каталога) и `@critical`-файлы гоняются всегда, на push/merge queue/nightly — весь проект. Дельта-гейт бандла — шаг `bundle-delta` в verify есть, но блокирует merge не через `needs` у `gate`: job исполняет код PR (сборку), а определение `pull_request` берётся из merge-ref; решение живёт в доверенном `bundle-approval` ([ADR 0013](adr/0013-bundle-delta-gate.md)). Канарейка копии шаблона в `pnpm canaries` (d8.3, 2026-11-19): copier ставится из PyPI — вне allowlist доменов песочницы ([ADR 0004](adr/0004-sandbox.md)), её гоняют CI и человек; без copier локально — громкий skip, в CI отсутствие copier красит прогон. Эталонные агентные прогоны (evals) — не в каждом PR (минуты агента и токены): push обвязки на `main` и раз в неделю ([ADR 0016](adr/0016-agent-evals.md), 2026-11-19)._

**З6. У каждого гейта есть канарейка и бюджет времени.** Гейт без канарейки может тихо перестать ловить после смены конфига или обновления инструмента. Гейт без бюджета незаметно замедляет цикл агента. _Действует (B1, 2026-11-13): каждый блокирующий шаг verify покрыт worktree-канарейкой (`pnpm canaries`, гоняются при изменении гейтов, на push в `main` (e79, 3.4) и в nightly); бюджеты времени — verify-budgets.json, превышение — предупреждение локально и в PR, enforce в nightly. Исключения: test-count (warning-only, exit 0 по контракту), e2e-report (тяжёлый, время покрыто бюджетом) и tool-class (образец B4.1: удаление шага делает `verify --only` красным без JSON-отчёта — шаг сам себе канарейка на удаление; логику чекера канареечат фикстуры tools/test/check-tool-class, проводку — wiring-канарейка на `test:hooks`; [ADR 0014](adr/0014-tools-protection-classes.md)); шаг e2e канареечится с ADR 0005 (удаление прокси `/rpc` — детерминированный bad-change), perf — с A6 PR-1 (лишний `/rpc`-запрос в сценарии), build — с b14 (битый ассет-импорт в клиентском модуле import-графа: до неё build жил только в union соседей «build,bundle», и красный сам шаг не детектировал никто); срыв привязки файлового выбора E2E (`E2E_FEATURES` → `testIgnore`, B4.1) ловит wiring-канарейка на `test:hooks`; привязка канарейки копии шаблона (d8.3) к скрипту canaries ловит wiring-канарейка на `test:hooks`; якоря канареек держит тест живости на `test:hooks` (`tools/test/gates-canary.test.ts`), поимённо: (1) применение — каждая канарейка, кроме двух, которым нужен настоящий git, применяется к копии дерева в каждом PR; исчезший якорь, который читает `apply` (например, регистрация `/rpc` в `server-app.ts`), даёт «canary anchor not found» (2026-11-24: PR e55 переписал регистрацию, канарейки не запустились из-за фильтра путей и краснели на всех следующих PR); (2) с e77 (2026-11-25) — тексты вне `tools/**`, на которые опирается `expect`: заголовки тестов и шаблоны сообщений (`expects` у канарейки — файл на месте, литерал в нём, expect матчит литерал или начинается с его приставки; переименование текста или файла замечается — контроль с обеих сторон в том же тесте); (3) цели зондов границ (`probe`: файл-цель существует, и зонд импортирует её относительным путём — иначе шаг падает `not-to-unresolvable`, а не своим правилом); (4) якорь карантина — вставка в существующий массив, пустой и с настоящей записью; (5) постпроверка канарейки удаления `/rpc` — лишняя регистрация `/rpc`, `/rpc/*` или `/rpc*` любым `….all(` даёт «якорь не найден»; шаг `test` идёт с `turbo --continue` — упавший прогон доводится до конца, отчёты пишут все пакеты, и канарейка с диагностикой падений читает сообщение любого пакета, а не только первого упавшего (2026-11-25: два останова поезда за двое суток — канарейка owner-процедуры слепла за упавшим тестом соседнего пакета), проводку держит канарейка «шаг test останавливается на первом падении» на `test:hooks`. Только `pnpm canaries` держит: что шаг падает по своей причине и текст `expect` остаётся в хвосте вывода; заголовки wiring-тестов и сообщения чекеров в `tools/**`, кроме названных в (2) (эти пути — в фильтре `canaries.yml`: переименование запускает канарейки в том же PR); шаги-вайтлист меняет только человек. Логика чекеров канареечна отдельно в tools/test/._

**З7. Пороги работают как храповик.** Автоматически порог может только ужесточаться. Ослабляет его человек отдельным PR. Порог стоит рядом с фактическим значением, иначе он ничего не ловит. _Частично: защита от ослабления действует; число тестов — храповик с базлайном у фактических значений, warning-only (2026-11-13); мутационные пороги break web и контрактов стоят у фактических значений (старт по правилу ADR 0009) и поднимаются ночным храповиком b2.4; остальные пороги далеки от фактических значений, задача A6. На деревья гейт-инфраструктуры — чекеры `tools/`, хуки, `packages/preflight`, e2e-инфраструктуру — мутационный гейт сознательно не распространяется; свод всех зон вне мутаций и условие возврата — [ADR 0022](adr/0022-mutation-gate-scope.md)._

**З8. Шумную метрику сравнивай с базой, детерминированную с абсолютом.** Время (LCP, длительность сценария, p95) на общих раннерах шумит, поэтому регрессию ловит сравнение с базовой веткой в том же прогоне. Байты, число запросов и число тестов детерминированы, для них хватает предела и дельты. _Целевое, задача A6._

**З9. Всё рассчитано на параллельную работу.** Несколько агентов одновременно работают в разных worktree на одной машине и в разных PR. Следствия: нет фиксированных портов и общих серверов, тест не опирается на общие данные и порядок, файл, который правит каждая фича, считается дефектом структуры. _Действует: данные E2E изолированы через `uniqueTitle()`, порты выводятся из worktree — `tools/ports.ts` (ADR 0005), чужой API-сервер ловится сверкой instance-id в global setup Playwright (2026-11-13); «горячие» файлы ждут задачи B7._

**З10. У производного файла один источник.** `openapi.json`, `routeTree.gen.ts`, определения Playwright Test Agents создаются командой. Руками их не правят, конфликты слияния в них решают перегенерацией, расхождение с источником ловит гейт. _Действует для `openapi.json` (`openapi:check`), для `routeTree.gen.ts` (`routetree`, b7.1: генерация без сборки — `@tanstack/router-cli` плюс футер Start, `pnpm regen` без `vite build`) и для `denyWrite` песочницы (`sandbox`, [ADR 0004](adr/0004-sandbox.md)); определения Test Agents — пока без гейта._

**З11. Падение объясняет себя.** У красного гейта есть артефакт (trace, diff, отчёт). Сообщение об ошибке говорит, что делать и чего не делать («уменьши бандл, не поднимай бюджет»). Вывод для агента компактный и машиночитаемый. _Действует._

**З12. Ядро работает без SaaS.** Облачные сервисы подключаются как необязательный слой сверху. _Действует._

**З13. Код детерминирован по построению.** Время, случайность, идентификаторы и сеть приходят через параметры. Образец: `InMemoryTaskRepository` принимает `now` и `generateId`. Тест, которому нужен `sleep` или реальные часы, указывает на дефект кода. _Действует как соглашение, гейта нет._

## 2. Архитектура кода

### 2.1 Слои и направление зависимостей

```
            packages/contracts      Zod-схемы и oRPC-контракт; зависит только от zod и @orpc/contract
              ▲            ▲
              │            │
         apps/api       apps/web ──► packages/ui      презентационные компоненты без домена

  e2e/     чёрный ящик: видит систему только через HTTP и браузер
  tools/   гейты; код продукта их не импортирует
```

| Правило                                                              | Чем обеспечено (`.dependency-cruiser.cjs`)       |
| -------------------------------------------------------------------- | ------------------------------------------------ |
| Пакеты не импортируют приложения                                     | `packages-not-to-apps`                           |
| Приложения не импортируют друг друга, общаются через контракт        | `no-app-to-app`                                  |
| E2E не импортирует код приложений и пакетов                          | `e2e-black-box`                                  |
| `@repo/ui` не знает о контрактах, oRPC, TanStack и Hono              | `ui-is-presentational`                           |
| Контракты зависят только от `zod` и `@orpc/contract`                 | `contracts-are-pure`                             |
| Фичи web не импортируют друг друга                                   | `no-cross-feature-imports`                       |
| Доменные модули API не зависят от `app.ts`, `router.ts`, `server.ts` | `api-domain-independent-of-transport`            |
| Пакет импортируется только через `exports`                           | `no-deep-package-imports`                        |
| Циклов нет                                                           | `no-circular` и правило Oxlint `import/no-cycle` |
| Production-код не зависит от devDependencies                         | `not-to-dev-dep`                                 |
| Продуктовый код не импортирует обвязку (`tools/`)                    | `product-not-to-tools` (ADR 0005)                |
| E2e импортирует из `tools/` только модули из списка                  | `e2e-tools-allow-list` (e63)                     |

Список модулей для `e2e` — `E2E_ALLOWED_TOOLS` в самом конфиге: разрешение именем файла, а не каталогом (`e2e` целиком вне правила — та же дыра классом ниже). Новый импорт из `e2e` в `tools/` начинается со строки в списке и ревьюится вместе с правилом.

Новое правило границ добавляется вместе с канарейкой: плохой импорт в фикстуре, гейт обязан упасть.

### 2.2 Контракт: единственный источник правды API

_Действует._

- Порядок изменения API всегда один: `packages/contracts` → `openapi.json` → `apps/api` → `apps/web`.
- Вход валидирует одна Zod-схема на клиенте и на сервере. Образец: `CreateTaskForm` и сервер используют `CreateTaskInputSchema`.
- Ошибки объявлены в контракте (`.errors({ NOT_FOUND })`). Обработчик бросает `errors.NOT_FOUND()`, клиент получает типизированный код.
- Оба транспорта (RPC на `/rpc`, REST на `/api`) строятся из одного роутера, и оба покрыты тестами.
- Политика доступа процедуры объявляется в контракте метаданными (ADR 0011), тест перебора в пакете контрактов красит ветку с процедурой без политики. Мидлварь авторизации исполняет объявленные политики: актор приходит через контекст, отказ — типизированный `FORBIDDEN` (C2.2). Контракт описывает только достижимое: ошибка объявлена ровно там, где её бросают — `FORBIDDEN` у процедур с проверкой доступа (строитель `ocAccess`), у public-процедур его нет (`ocPublic`); лишний ключ входа — ошибка валидации, а не молчаливая отбраска ([ADR 0024](adr/0024-reachable-contract-responses.md)). Несовместимое изменение контракта ловит гейт — _Целевое:_ (задача C6).

### 2.3 API

_Действует._

- `src/<module>/` содержит домен: интерфейс репозитория и реализацию. О Hono и oRPC домен не знает.
- `router.ts` тонкий: вызывает домен и превращает «не найдено» в типизированную ошибку.
- `app.ts` экспортирует фабрику `createApp(options)` без глобального состояния. Зависимости приходят параметрами, поэтому тесты идут внутри процесса (`app.request()`, oRPC-клиент с `fetch: app.fetch`) и не открывают порт.
- Окружение читает ровно один модуль на приложение (C3.0): в `apps/api` — `server-config.ts` (при старте; Zod-схема, невалидное окружение — отказ со списком «переменная: причина»), в `apps/web` — `src/lib/env.ts` (SSR-клиент читает `API_URL` лениво на запрос, цель прокси — при старте из `vite.config.ts`, [ADR 0005](adr/0005-api-url.md), §2.4). `server.ts` исключён из покрытия и мутаций, поэтому логики в нём быть не должно: только проводка.
- `/health` отдаёт `{ status: 'ok' }`; идентификатор экземпляра (`INSTANCE_ID`) — внутренние данные, публичный ответ (сервер без тестового API) его не содержит (e68). Потребность в идентификаторе закрыта логом — штамп `instanceId` в каждой записи при заданном `INSTANCE_ID` — и тестовым контуром: при включённом тестовом API `/health` дополняется полем `instance`, global setup Playwright сверяет его с токеном прогона, поэтому тест не может незаметно пройти против чужого процесса на порту (З9). Тестовый API в production не поднимается (двойной guard), поэтому там идентификатор не отдаёт ни один эндпоинт. Гейты всегда стартуют свой сервер; ручной сервер переиспользуется только явно (`REUSE_SERVER=1`, токен этого worktree — его пишет `pnpm dev`, и `ENABLE_TEST_API=1` с явным `NODE_ENV=development`: без тестового API `/health` не отдаёт идентификатор, и гейт красит прогон до первого теста).
- Тестовые эндпоинты `/__test__/*` включаются только флагом, по умолчанию выключены, запрещены в production. Открываются явной парой `ENABLE_TEST_API=1` + `NODE_ENV=development|test` (e69, default-fail-closed): незаданный или написанный иначе `NODE_ENV` — не «не production», а отказ при старте с названной причиной. Оба рубежа — `superRefine` схемы окружения (`server-config.ts`) и проверка в `createApp` для входов мимо неё — держат одну и ту же матрицу, у каждого запрета один текст в обоих рубежах. Прод-образ `apps/api/Dockerfile` задаёт `NODE_ENV=production` в ENV и перечисляет переменные явно: `NODE_ENV` — обязательная прод-переменная, её не снимают через `docker run -e`. Каждый новый такой эндпоинт приходит с тестом «выключено по умолчанию».
- Сброс `/__test__/reset` требует явной сферы (e68): валидный `x-workspace-id` заменяет содержимое одного рабочего пространства (ADR 0020), `"scope": "global"` в теле — всего хранилища для точечных сценариев. Запрос без заголовка и без `scope` отвечает 400 с названием причины и не трогает данные — молчаливого глобального сброса больше нет (одна забытая шапка в параллельном прогоне стирала чужие данные); мусорный заголовок и заголовок вместе с `scope` — тоже 400.
- Node запускает TypeScript напрямую, без сборки. Отсюда `erasableSyntaxOnly` и импорты с расширением `.ts`: никаких `enum`, `namespace` и parameter properties.

### 2.4 Web

_Действует, кроме отмеченного._

- `routes/` только связывает: loader и подключение хуков фичи к компоненту страницы.
- Компонент страницы в `features/<feature>/` получает данные и колбэки через props (образец: `TasksPage`). Поэтому он тестируется в браузерном режиме Vitest без сети и роутера.
- Серверное состояние живёт только в кэше TanStack Query. Оптимистичное обновление пишется в кэш, инвалидация идёт после последней мутации (`refetchAfterLastMutation`). `router.invalidate()` для этого не используется, причина записана в ADR 0001.
- `QueryClient` создаётся на каждый SSR-запрос, чтобы кэш не утекал между пользователями.
- Один origin (ADR 0005): браузер ходит в `/rpc` своего web-сервера, цель прокси читается при старте из `API_URL`; сборка от адреса API не зависит. До гидратации контролы `disabled` (`useHydrated`), иначе клик по серверной разметке теряется.
- Контур запросов production-сервера (`server-app.ts`, e55): каждый не-GET/HEAD мимо статики (server functions, POST-маршруты) идёт в SSR-обработчик под ограждениями `src/lib/request-guards.ts` — лимит тела и таймаут на всех не-GET/HEAD мимо статики (GET/HEAD с телом — вне контура задачи): потолок 1 МиБ, срок 30 с, тела 413 и 504 те же, что у API (c1.7, `apps/api/src/app.ts`). Ограждение стоит на классе запросов (catch-all), а не на маршруте. Порядок — «форма → срок → потолок»: проверка формы не верит `request.body` (`TRACE` → 405, объявленное тело без потока → 400; та же проверка стоит перед прокси `/rpc`), срок стоит раньше потолка и накрывает чтение тела, а не только обработчик. Прокси `/rpc` читает тело сам — потоково, с потолком 1 МиБ и сроком 30 с: сверх потолка → 413, тело не дочитано вовремя → 408, отказ API → 502. `cache-control: immutable` решается по разрешённому файлу внутри каталога ассетов сборки, а не по префиксу URL.
- Стили: CSS Modules и токены из `@repo/ui/tokens.css`.
- _Целевое, задача B2:_ логика фичи лежит в модулях `*.ts` без React (образец: `summarize.ts`), компоненты и хуки тонкие. Причина: StrykerJS не поддерживает browser mode Vitest (подключение мутаций к web и контрактам — задача b2.2), и мутациями проверяется только то, что тестируется в node-проекте; слепая зона `.tsx` — одна из строк свода зон вне мутаций в [ADR 0022](adr/0022-mutation-gate-scope.md).

### 3.2 `verify` и Turborepo

_Действует._

- Инструменты, которые быстро обрабатывают весь репозиторий за один запуск (Oxfmt, Oxlint, dependency-cruiser, Knip, sherif), запускаются из корня, а не как задачи Turborepo. Раскладывать их по пакетам имеет смысл, только когда шаг превысит свой бюджет.
- То, что считается по пакетам (typecheck, test, build, e2e, perf, mutation), оформлено задачами Turborepo с кэшем. Задача `transit` заставляет зависимые пакеты пересчитаться при изменении исходников зависимости.
- Переменная окружения, которая влияет на задачу, обязана быть в `env` этой задачи в `turbo.json`. Иначе Turborepo в строгом режиме не передаст её процессу, а кэш вернёт результат прошлого запуска. Нарушение этого правила уже дало дефект: `VIDEO=on pnpm e2e` не писал видео ни при кэш-попадании, ни с `--force` (исправлено 2026-11-12, переменная объявлена в `env` задачи `e2e`).
- Правило двустороннее. Объявление, которое никто не читает (`API_URL` в задачах `e2e`/`perf` — адрес вычисляется в `tools/ports.ts`), лишь раздувает ключ кэша и маскирует дрейф. А необъявленная читаемая переменная — тот же класс дефекта, что `VIDEO=on`: `REUSE_SERVER=1` (задокументированный escape hatch ADR 0005) до e14 не доходил до конфига Playwright, и прогон против поднятого `pnpm dev` падал на занятых портах (исправлено 2026-11-21). Каждая переменная, которую конфиг задачи читает из `process.env`, должна стоять в `env` этой задачи.
- Быстрые шаги `verify` идут параллельно, медленные (`--full`) последовательно: perf перезаписывает отчёт `reports/e2e.json`, который читает шаг `e2e-report` (порядок — контракт A3). Порты с ADR 0005/З9 общие не бывают: они выводятся из worktree.
- Локальный кэш Turborepo общий для всех git worktree одного репозитория.

### 3.3 Кэш и доверие

_Действует (реализовано задачей A7, 2026-11-20; правила приняты человеком 2026-11-14 — журнал задачи A7). Remote cache пока не подключён: секрет `TURBO_TOKEN` и переменные `TURBO_TEAM`/`TURBO_API` пусты, turbo работает на локальном кэше `.turbo`._

1. В remote cache пишет только доверенный код: job на `push` в `main`. PR, merge queue, разработчики и агенты кэш читают, но не пишут.
2. Merge queue кэшу `main` не доверяет: задачи в `merge_group` гоняются принудительно, без remote-чтения (`--cache=local:rw`).
3. Результат задачи, зависящий от машины (перф-замеры), между машинами не переиспользуется: задача `perf` объявлена `cache: false` в `turbo.json` — вне кэша вовсе.
4. Подпись артефактов Turborepo проверяет целостность. Границей безопасности она не является.

Механика в `ci.yml`:

- Флаг каждой задачи turbo — из `TURBO_CACHE_ARGS`: `--cache=local:rw,remote:rw` на push в `main`, `--cache=local:rw` в merge queue, `--cache=local:rw,remote:r` в PR (и в ручных прогонах по ref PR). Скрипты, вызывающие turbo внутри job'а (`tools/visual-inner.sh`), наследуют ту же переменную.
- `TURBO_TOKEN`/`TURBO_TEAM`/`TURBO_API` выдаются job'у через environment: `cache-read` (без ограничений) или `cache-write` (deployment branch policy — только protected-ветки, то есть `main`). Секрет одного environment недоступен job'у другого: job из PR физически не может получить токен на запись. Инвариант контура: turbo-секретов на уровне репозитория не держат — repo-секрет наследуют все job, включая не имеющие environment, и механизм замолкает без красного гейта.
- Компенсация отсутствия remote-записи из PR: `actions/cache` каталога `.turbo` с ключом по номеру PR и суффиксом job'а (`turbo-pr-<номер>-static-<sha>`…) — локальный кэш PR изолирован от `main` и от других PR. Остаточный уровень доверия: код PR исполняется в этих job'ах и может подделать записи своего же локального кэша — радиус ровно один PR, то есть уровень доверия самого PR-кода; зелёный PR не значит «кэш проверен стороной».
- Решение о доверии оформлено [ADR 0017](adr/0017-remote-cache-trust.md).
- `nightly` и другие доверенные workflow (исполняют только код `main`) remote-кэш не используют; подключение к ним решается при выборе бэкенда.
- Условие подключения бэкенда: read-only токен — в секрет `TURBO_TOKEN` environment `cache-read`, токен на запись — в `cache-write`, `TURBO_API`/`TURBO_TEAM` — в переменные тех же environment; `cache-read` держать без required reviewers и wait timer — иначе зависнут job'ы PR; убедиться до выбора, что сервер умеет выдавать read-only токены; после подключения проверить попыткой запись из каждого job'а, исполняющего код PR (`static`, `unit`, `e2e`, `visual`, `perf`, `mutation`, `bundle-delta`) — критерий приёмки A7.

### 3.4 CI

_Действует, кроме отмеченного._

- В PR проверяется затронутое (`--affected` от базового SHA). В merge queue и на `main` проверяется всё.
- Обязательных check три: `gate` (агрегирует job `ci.yml`, исполняется из PR), `gate-integrity` ([ADR 0002](adr/0002-gate-integrity.md)) и `bundle-approval` ([ADR 0013](adr/0013-bundle-delta-gate.md)): оба доверенных workflow на `pull_request_target`, не читают и не исполняют код PR, факты берут из GitHub API. `bundle-approval` читает результат untrusted-замера `bundle-delta` (check-run head SHA) и решает: зелёный замер или label `bundle-growth-approved` от владельца CODEOWNERS. Оба слушают и `merge_group` (no-op с тем же именем check), иначе очередь ждёт вечно.
- CI перезапускается на новый head, а не на правку тела PR (e78): `ci.yml` слушает `[opened, synchronize, reopened]`. `edited` срабатывал и на правку тела — создавал второй прогон, а `concurrency` отменяла идущий прогон того же head (PR #239, 24.11.2026). Условие уровня job не годится: запуск всё равно создаётся, а `concurrency` отменяет предыдущий до вычисления условий. Смену base-ветки PR — она не порождает `synchronize`, а check привязан к head SHA — держит `ci-base-change.yml`: `pull_request: edited` при `changes.base` диспатчит `ci.yml` на head-ветку PR (по образцу `visual-approve`), с семантикой `workflow_dispatch` — всё дерево, без merge-ref и `bundle-delta`. На новой базе PR проверяют synchronize (Update branch) и merge queue — всё, кроме `bundle-delta`: в очереди и на push его нет, поэтому `bundle-approval` блокирует замер, чей run создан не позже последней смены base (время смены — таймлайн PR, время замера — check suite run'а), до следующего synchronize. Правка тела проходит мимо условия уровня job — без раннера и без отмены. Для PR из форка job падает с объяснением: диспатч по ref вне репозитория невозможен. Доверенный `gate-integrity.yml` (`gate-integrity`, `bundle-approval`) `edited` слушает по-прежнему. Проводку держат канарейки «ci.yml снова слушает edited», «смену base никто не перезапускает», «bundle-approval не видит смену base» и «bundle-approval доверяет замеру до смены base» (шаг `test:hooks`).
- Права по умолчанию `contents: read`. Устаревшие прогоны PR (новый head) отменяются через `concurrency`.
- Сводный check здоровья workflow (e26; контур — раздел 5): `.github/workflows/workflow-health.yml` запускает `tools/check-workflow-health.ts` на push в `main` и по расписанию (`40 4 * * *` UTC, позже nightly). Merge не блокирует; красный прогон заводит issue собственным job `report` (один открытый issue, дедуп по заголовку). Собственный хост — вне области сверки (`SELF_HOST_WORKFLOW`): живя внутри `nightly.yml`, чекер красил ночь за ночь сам себя (e39).
- Канарейки гейтов на `main` (e79): `canaries.yml` идёт по PR с путями фильтра, в nightly и — с 2026-11-25 — на push в `main` (пути: тот же фильтр плюс `apps/**`, `packages/**`, `e2e/**`). Необязательный check: вне `needs` у `gate` и required checks, merge не блокирует. Зачем: на PR с согласованными breaking changes шаг `openapi` красен по замыслу (гейт C6), negative control канареек красен, и отдельные канарейки не судятся — 24.11 мерж e57 (PR #239) оставил красной канарейку «owner-процедура без строки сценария таблицы», её увидели только на следующих PR ([реестр пропущенных дефектов](escaped-defects.md), 2026-11-25). На `main` negative control зелёный — шаг `openapi` сравнивает контракт с самим `HEAD`, — поэтому канарейки судятся: сломанная видна красным прогоном `Gate canaries` события `push` на SHA мержа, около 14 минут после мержа. Прогон `push` не отменяется следующим мержем (группа `concurrency` — на SHA): чекер здоровья считает отменённый последний push-прогон красным; он же заводит issue при следующем запуске. Действие по красному — как по красной джобе `canaries` на PR: поезд на паузу, причина — в строке канарейки. Проводку (область чекера, пути-суперсет, без отмены на push) держит `tools/test/check-workflow-health.test.ts`.
- Preview-окружение на PR — `preview.yml`, сознательно не гейт: вне `needs` у `gate` и required checks (иначе З5/З6 потребовали бы шаг в verify, канарейку и бюджет времени). Образы production-entry ([ADR 0012](adr/0012-production-server.md)) тегом `pr-<номер>` в GHCR, один комментарий в PR с командой запуска, удаление тега на merge/close; права и граница доверия — [ADR 0021](adr/0021-preview-images-trust.md).
- Ночной `ruleset drift (a11)` (`tools/check-ruleset-drift.ts`, реестр пар «id → снимок» — `docs/template-state.md`; файл исключён из копии шаблона (`copier.yml`, `_exclude`), поэтому здесь не ссылка — ссылка на него красит шаг `docs` в канарейке копии) сверяет живые rulesets с снимками `.github/rulesets/*.json` и различает три исхода (e35). **Дрейф** — ответ получен и расходится со снимком: красный, пути расхождений названы; массивы сверяются по живому — добавленные правило или обходчик краснят, убывание тоже. **Граница проверки** — ключ снимка отсутствует в ответе, потому что GitHub отдаёт его только при write-доступе (REST, «Get a repository ruleset»: `bypass_actors` «only returned if the user making the API request has write access to the ruleset»). **Отказ API** — сравнивать не с чем: красный с кодом и телом, в сообщении сказано, что это не дрейф. Права и граница: токен джобы — `contents: read`, `issues: write`; области `administration` у `GITHUB_TOKEN` нет (официальный список — workflow-syntax, `permissions`; её отсутствие во всех воркфлоу держит тест проводки `tools/test/ruleset-drift.test.ts`), поэтому список обходчиков ночью не проверяется — джоба зелёная с предупреждением, аннотацией и блоком в сводке прогона, где перечислено непроверенное, а в логе печатаются ключи живого ответа (по ним видно, что токен реально видит). Локальная проверка владельца — полная: `node tools/check-ruleset-drift.ts` токеном с write-доступом (`gh auth`): ключ возвращается и сверяется, `--dump-live <файл>` — дамп живого ответа. Скрытые ключи — `TOKEN_HIDDEN_KEYS` в чекере, пополняется только по документации REST.
- Числовые храповики поднимает автоматика: nightly после зелёного прогона обновляет `test-count-baseline.json` (пакетные отчёты и корневой `test:hooks`), коммитит поднятие в ветку `chore/test-count-ratchet`, а PR по ней открывает человек: настройка Actions «Allow GitHub Actions to create and approve pull requests» выключена (решение владельца), `github.token` PR не создаёт. Шаг публикации (`tools/check-test-count.ts --pr`, e40) либо выполнил действие, либо красный с причиной дословно и следующим действием человека: отказ create, кроме «PR уже открыт», красит джобу и заводит issue «Nightly failed»; при открытом PR ветка обновляется, шаг зелёный и называет, что CI на новый коммит не запустится: push делает `github.token`, события от него workflow не рождают (как в ADR 0015), обязательные checks появятся после synchronize человека (пустой push, Update branch) или reopen PR. Update понижать отказывается — дифф только вверх. Автор PR базлайн не поднимает: файл «горячий», параллельные PR с тестами конфликтовали бы в нём (З9, b7) — a10.
- Храповик мутационных порогов (b2.4): nightly после зелёного прогона мутаций готовит поднятие `thresholds.break` web и контрактов, когда счёт пакета выше порога в двух последних зелёных прогонах подряд (состояние — артефакт прошлого зелёного прогона, образец perf-baseline; вниз храповик не двигает). Публикация — шаг «PR with raised thresholds» (`nightly.yml`): коммит в ветку `chore/mutation-ratchet-web-contracts`, push и `gh pr create` с `github.token`; PR так не открывается — настройка Actions, разрешающая `github.token` создавать PR, выключена (решение владельца, строка выше), — а отказ create шаг пока маскирует текстом «PR храповика уже открыт — ветка обновлена» (`|| echo`): известен с e40, исправление — отдельной задачей; PR по ветке открывает человек. Стартовые пороги ставит оператор по правилу ADR 0009 («Пороги»: факт, округлённый вниз, минус 5 п.п.; замеры и итог — в PR). Канарейка инверсии подаёт завышенный порог прямо на вход чекера — полный прогон мутаций для неё не повторяется; артефакт `mutation-full` остаётся только api — телеметрия c9.4 читает его как «домен apps/api».

### 3.5 Защищённые пути

_Действует._

- Список один: `tools/protected-paths.json`. `deny`: агент менять не может, в CI нужен label мейнтейнера. `review`: менять можно, нужно ревью CODEOWNERS.
- Проводка плагина `agent-harness` — `.claude/.claude-plugin/**` (`hooks.json`, манифест) и маркетплейс-манифест `.claude-plugin/marketplace.json` (его `source` решает, какой каталог с манифестом и `hooks.json` получит потребитель) — в `deny` по роли: те же защитные хуки для репозиториев-потребителей ([ADR 0008](adr/0008-template-distribution.md)), класс как у `.claude/settings.json`. Равенство `hooks.json` и `hooks` из `settings.json` (события, matcher, команды с CLI потребителя, таймауты, `|| exit 2` у защитных хуков) держит тест шага `test:hooks` (`tools/test/check-tool-class.test.ts`) на каждом verify — fail-closed: ключ вне сверяемого набора (`if`, `async` и любой другой) в любом из двух файлов краснит тест, а не игнорируется; `source` плагина в маркетплейсе и имя плагина сверенены с корнем защищённого манифеста. `pnpm probe:plugin` остаётся полным пробником в чистом потребителе (e49).
- Уровней три: хук агента, `gate-integrity` из доверенной базы ([ADR 0002](adr/0002-gate-integrity.md)), CODEOWNERS.
- Чёрные списки команд — только подсказка агенту (З3); границей является проверка по результату: снимок защищённых файлов на старте сессии, изменение отменяется хуком с объяснением ([ADR 0003](adr/0003-result-based-protection.md)). Контур L0 действует только в агентах, исполняющих хуки проекта (Claude Code); в остальных детерминированным барьером остаётся `gate-integrity`.
- Локальный режим обслуживания по областям (b9): файл `.claude/maintenance.json` (сам под `deny` и `denyWrite`, создаёт человек/оператор) открывает только слой хуков Edit/Write и исключает пути из сверки по результату; `denyWrite` песочницы и guard-bash не поднимаются — режим Edit/Write-only, битый файл игнорируется (защита полная). Полное выключение — прежний `.claude/settings.local.json` ([ADR 0009](adr/0009-operator-delegation.md)).
- Label `gate-change-approved` действителен, только если его поставил человек из глобальных владельцев CODEOWNERS (строка `*`) после последнего push PR: job снимает label на `synchronize`, а `check-gate-approval.ts` независимо сверяет актёра и время события с датой head-коммита. Переименование защищённого файла ловится (`--no-renames`, `previous_filename`). Тот же механизм (тот же job снятия, то же ядро проверки) действует для `bundle-growth-approved` — одобрения роста бандла сверх 5 КБ за PR ([ADR 0013](adr/0013-bundle-delta-gate.md)); чекер параметризован по имени label.
- Новый гейт, порог или конфиг гейта попадает в `deny` и в CODEOWNERS тем же PR, которым он создан.
- `denyWrite` песочницы Bash — производный от того же списка: расхождение ловит гейт `sandbox` ([ADR 0004](adr/0004-sandbox.md)).
- `pnpm install` из песочечного Bash не поддерживается (граница — [ADR 0004](adr/0004-sandbox.md), раздел «`pnpm install` из песочницы»; e70): pnpm 12.21.0 держит блокировки хранилища в `/tmp/pnpm-store-operation-locks-<uid>` — вне `allowWrite`; с открытым каталогом блокировок установка падает на записи файлов пакетов (`denyWrite`-глобы `**/.gitignore` и пути, защищённые самим Claude Code) и оставляет проектный `.pnpm-store`. Зависимости ставит старт сессии агента или человек вне песочницы. В песочнице `pnpm preflight` остаётся красным на `node_modules` (сверить не удалось), но называет причину и выход, а не «дрейф lockfile» (`packages/preflight/src/checks.ts`, канарейка — `packages/preflight/src/checks.test.ts`).
- Классы защиты `tools/` следуют за ролью файла в контуре merge, а не за каталогом ([ADR 0014](adr/0014-tools-protection-classes.md)): замыкание гейтов вычисляет гейт `check-tool-class` (шаг `tool-class` verify) и держит равенство с `deny` в обе стороны — файл замыкания вне `deny` и лишняя `deny`-запись красят verify; инструменты разработчика — `review`. Правило «новый гейт попадает в `deny` тем же PR» проверяемо: новый гейт-файл попадает в замыкание, и незакрытая запись красит verify в том же PR.
- Обычная сессия: агенту, которому мешает гейт, чинить код; оператор в задаче режима обслуживания ведёт её по [ADR 0009](adr/0009-operator-delegation.md). Если агент считает, что неправ сам гейт, он останавливается и объясняет это человеку.
- Гейт меняет оператор или человек ([ADR 0009](adr/0009-operator-delegation.md)); границы оператора — строка «Что остаётся человеку» там же, канон правил не дублируется.

### 3.6 Визуальные тесты

_Действует, кроме отмеченного._

- Снимки делаются и сравниваются только в одном Docker-образе Playwright на `linux/amd64`. Версия образа равна версии Playwright из каталога, поэтому она закреплена точно, без `^`; совпадение закрепляет шаг `visual-image` verify (A8).
- Запуск visual-проекта вне Linux запрещён в самих конфигах (З4, A8): Playwright бросает до любых побочных эффектов, запись базлайнов включена только `VISUAL_UPDATE=1`. `ALLOW_HOST_SCREENSHOTS` — лаз для триажа, одинаковый в обоих конфигах. Проверка по платформе, а не по принадлежности образу; строгую гарантию «только образ» принесёт задача B3 — базлайны создаёт только CI.
- Базлайны без суффикса платформы, допуск нулевой.
- Владение базлайнами: локально — человек после просмотра диффа (`pnpm visual:update`, [ADR 0004](adr/0004-sandbox.md)); в CI — базлайны создаёт job `visual` (артефакт `visual-actuals`), а одобряет человек командой `/approve-visual <sha>` в PR — доверенный workflow `visual-approve` коммитит их в ветку PR и перезапускает CI ([ADR 0015](adr/0015-visual-baselines-approval.md), b3.1).
- Когда переходим на Argos — измеримые триггеры (≥ 50 дифф-событий в неделю двумя замерами подряд или медиана одобрения дольше суток), цена перехода и судьба базлайнов: [ADR 0019](adr/0019-argos-adoption-trigger.md) (b3.4).

### 3.7 Производительность

- _Действует:_ пороги лежат в `perf-budgets.json` и проверяются Zod-схемой (опечатка в ключе роняет проверку, а не отключает её). Замер: медиана пяти прогонов при замедлении CPU в 4 раза. Бандл считается в gzip.
- _Действует, e60:_ бюджет API (`api` в `perf-budgets.json`) меряет продуктовый путь — `/rpc` через прокси production-entry web (CI, шаг «API smoke (k6)» job `perf`, сценарий `e2e/perf/k6/api-smoke.js`): p95 и доля ошибок для `list` и `toggle`, каждый запрос под порогом отдельно. Набор фиксирован: сценарий сам доводит список до `DATASET_SIZE` задач перед замером и роняет прогон (`rpc_dataset_mismatch`), если в замере список другого размера. Прямой `/api/tasks` — диагностический тренд без бюджета: разница с ним — цена слоя «прокси + oRPC». k6 — отдельный шаг CI, в `pnpm perf` (Playwright-перф web) не входит.
- _Действует, A6:_ детерминированные метрики в PR-гейте (байты, запросы, long tasks, LCP под Fast 3G) и дельта-гейт бандла: рост total JS gzip от merge-base больше 5 КБ одобряет человек label-ом `bundle-growth-approved` ([ADR 0006](adr/0006-perf-strategy.md), [ADR 0013](adr/0013-bundle-delta-gate.md)). Инвариант порогов: запас каждого JS-абсолюта, который дельта опережает (total, крупнейший чанк, wire), над фактом больше дельта-порога — иначе абсолют краснеет раньше дельты, и label не разблокирует рост; CSS-потолки — жёсткая линия вне этого пути ([ADR 0013](adr/0013-bundle-delta-gate.md)).
- _Целевое, задача A6 (PR-3):_ ночное медианное сравнение времени с последним зелёным nightly; 200-миллисекундную задержку в обработчике в PR не ловит ни одна метрика — это осознанный разрыв до merge PR-3.

### 3.8 Зависимости

_Действует._

- Версии внешних зависимостей объявлены только в `catalog:` (`catalogMode: strict`).
- Свежий релиз ставится не раньше чем через сутки (`minimumReleaseAge`), Renovate ждёт три дня. Install-скрипты запрещены, пока не разрешены в `allowBuilds`.
- TypeScript 6 подложен только dependency-cruiser и StrykerJS через `packageExtensions`. Проект компилируется TypeScript 7.
- Renovate обновляет группами. Playwright идёт одной группой с Docker-образом, после обновления нужны `tools/playwright-agents.sh` и `pnpm visual`.
- Действия GitHub закреплены по SHA, и комментарий после пина называет неизменяемый тег релиза (`# v7.0.1`), а не подвижный тег мажорной версии: шаг verify `action-pins` (`tools/check-action-pins.ts`, e76) красит `# vN` сразу — zizmor замечает несоответствие только после того, как тег уехал на новый релиз (24.11.2026 — поезд стоял около двух часов). Тем же шагом зафиксирована версия сканера zizmor: вход `version` в `security.yml` — точная, обновление отдельным PR (Renovate — regex-правило в `.github/renovate.json`; путь обновления — [github-setup.md, раздел 5](github-setup.md)).

### 3.9 Агентный слой

_Действует._

- Что должно выполняться всегда, живёт в хуке или гейте. Что агент должен знать, записано в `AGENTS.md`. Как сделать типовую работу, описано в скиле. Инструкция гарантией не является.
- `AGENTS.md` остаётся каноном и коротким. `CLAUDE.md` содержит только импорт `@AGENTS.md`: прямое чтение `AGENTS.md` в Claude Code (v2.1.277+) отключается любым `CLAUDE.md` или `CLAUDE.local.md` и недоступно в старых версиях, а импорт работает всегда. Специфика Claude Code — раздел «Claude Code» в `AGENTS.md`.
- Ревьюеры только читают и возвращают находки с серьёзностью `blocker`, `major`, `minor`.
- Определения Playwright Test Agents генерируются скриптом и дополняются политикой репозитория. Healer не помечает тест `fixme`.
- MCP-серверы (Playwright, Chrome DevTools) служат для исследования и отладки. Найденную регрессию закрепляет детерминированный тест.
- Всё, что блокирует merge, живёт в Lefthook и CI, а не в хуках Claude Code. Хуки ускоряют обратную связь, но не являются единственной линией защиты: у других агентов их нет.
- Облачный контур — агенты в чистом checkout на инфраструктуре вендора: какие гарантии в нём держатся, какие не определены и какой минимальный контур шаблон обещает, записано в [ADR 0010](adr/0010-cloud-agents.md).
- Качество агентных фич меряет контур evals ([ADR 0016](adr/0016-agent-evals.md)): эталонные фичи в чистом worktree, `pass` — по факту зелёного `verify --full` руками раннера, а не по самоотчёту агента.

### 3.10 Целостность документации

_Действует._

- Гейт `docs:check` ([tools/check-docs.ts](../tools/check-docs.ts)) входит в `pnpm verify` и CI (job `static`). Он проверяет инструкции, которым доверяет агент: команды `pnpm …` из README.md, AGENTS.md, CLAUDE.md и скилов существуют (скрипт в `package.json` с учётом `--filter`, встроенная команда pnpm или бинарь из `node_modules/.bin`), относительные markdown-ссылки ведут на существующие файлы, а якоря — на существующие заголовки или `id`.
- Дрейф документации — дефект так же, как красный тест: чини документ, а не проверку. Если гейт ошибся на встроенной команде pnpm или ссылке-примере, исключение дополняют в `tools/check-docs.ts` тем же PR с ревью CODEOWNERS.

### 3.11 Параллельная работа агентов

_Целевое, задачи D1–D6; решение — [ADR 0007](adr/0007-task-board.md)._

- Одна задача → одна ветка `task/<id>` → один worktree → один агент → один PR.
- Задача — файл в `backlog/`. Доска читается из ссылки `main`, а не из рабочего дерева. Статус не хранится, а вычисляется: файл в `backlog/done/` — закрыта, есть ветка — в работе. Задача закрывается переносом файла тем же PR — гейт `docs` красит ветку задачи, пока файл открыт; расхождения «смержена, но открыта» перечисляет `pnpm backlog doctor` (ADR 0007, «Замыкание задачи»).
- Планы задач и пакеты решений живут в «Журнале» файла задачи или в ADR — не в `/tmp` и не в памяти клиента: память агента хранит указатель на задачу, а не её состояние (ADR 0007, «Планы и пакеты решений»).
- Захват — создание локальной ветки: атомарно внутри клона. Чужую задачу в работе агент не берёт; брошенную освобождает человек.
- Задачу, которая трогает защищённые пути, обычная сессия не начинает: её ведёт оператор; одновременно несколько, если `touches` не пересекаются, кроме мягких путей (D7, [ADR 0023](adr/0023-d7-shared-document-paths.md)) ([ADR 0009](adr/0009-operator-delegation.md)).
- Развилка в задаче закрывается записанным решением (что выбрано, почему, альтернатива, условие возврата), а не вопросом человеку. В `needs_human` остаётся только `оператор: …`, `отложено: <проверяемое условие>` или действие, которое нельзя делегировать.
- Задача объявляет пути, которые меняет. Порядок задаёт `depends_on`; пересечение путей с задачами в работе — запрет (D7, #149): `next` такую задачу не выдаёт, `start` отказывает под замком и откатывает ветку. Общий путь — файл, который по правилу правит каждая задача одного класса (сейчас `docs/escaped-defects.md`: строку реестра несёт каждое исправление) — пересечением не считается и разрешён любой задаче гейтом `branch-scope` (`SHARED_PATHS`, `tools/backlog-board.ts`): реестр append-only, а сам файл — дефект структуры по З9, а не повод становиться в очередь (ADR 0007, «Поправка 2026-11-23»). Мягкий путь — общий документ, который по записанному правилу обязана объявить в `touches` каждая задача некоторого класса (сейчас `docs/architecture.md`: законы обвязки, раздел 4), — пересечением не считается только с такой же мягкой записью, а `branch-scope` по-прежнему красит правку без объявления (`SOFT_OVERLAP_PATHS`, [ADR 0023](adr/0023-d7-shared-document-paths.md)).
- Исследование и декомпозиция — отдельные типы задач. Их результат — ADR, файл исследования или новые задачи, а не код.
- Всё, что должен знать агент любого клиента, записано в `AGENTS.md` — единственный файл инструкций, который читают все клиенты; ZCode не исполняет хуки проекта.

### 3.12 Шаблон и проекты

_Целевое, задачи D8–D10; решение — [ADR 0008](adr/0008-template-distribution.md)._

- Постоянная ветка одна, `main`. Версия шаблона — защищённый тег.
- Проект создаётся и обновляется из тега инструментом Copier. Обновление запускает человек: оно меняет защищённые пути.
- Файлы разработки шаблона остаются в `main`, но не попадают в проект. Корень репозитория остаётся рабочим монорепо: шаблон проверяет сам себя.
- У каждого файла есть класс: шаблон, проект или смешанный. Смешанных должно быть как можно меньше: файл, который правят обе стороны, считается дефектом структуры так же, как «горячий» файл (З9).

### 3.13 Ночная телеметрия обвязки

_Действует с c9.4 (2026-11-22)._

- Единый отчёт трендов (`reports/trends.json`, артефакт `trends-<run_id>` + GITHUB_STEP_SUMMARY) собирает job `telemetry` в nightly из уже существующих источников: время CI из GitHub API; flaky rate — число из артефакта `flaky-rate`, которое считает гейт `check-flaky-rate.ts` (`--rate-out`); бюджет verify — артефакт `verify-durations-<run_id>`; перф — `perf-trend-<run_id>`; mutation — `mutation-full`; отказы гейтов — `gate-denials` прогонов gate-integrity; evals — `evals-<run_id>`; доля агентных PR — чекбокс «PR создан агентом» в описании PR; конфликты задач доски — `git merge-tree` по парам `task/*`; escaped defects — реестр `docs/escaped-defects.md`. Отчёт — L5: не блокирует merge; при красном сборе issue создаёт job `report` (telemetry в его `needs`).
- У каждой метрики поле `coverage`: что измеряется и что честно «не собирается, чем закрыть» (критерий приёмки c9.4). Метрики без источника не зануляются: скипнутый evals без секрета, отсутствующий perf-артефакт и «0 прогонов merge queue» — «нет данных», не ноль; отсутствие у свежайшего ночного прогона артефакта, который пишется всегда (flaky-rate, verify-durations, mutation-full), — «источник сломан» и красный прогон (З11).
- Чекер — пара `tools/telemetry-report.ts` (чистое ядро, тестируется) / `tools/telemetry-report.main.ts` (CLI) по шву `check-perf-trend(.main).ts`; новые deny-файлы тем же PR попадают в `tools/protected-paths.json`, `KNOWN_GATES` и denyWrite песочницы ([ADR 0014](adr/0014-tools-protection-classes.md)). Локальный режим — `pnpm telemetry:report --local` (без gh: реестр, отказы локального журнала, конфликты task-веток). Гейты не переносятся: enforce бюджетов verify (B1) и сравнение перфа (A6) считаются как считали, телеметрия читает их сырые артефакты и становится местом трендов и калибровки порогов (З7); если ревью примут «гейты берут базу из тренд-отчёта» — это отдельное решение с ADR.

## 4. Как менять саму обвязку

1. Задача, чьи `touches` попадают в защищённые пути (доска показывает статус «режим обслуживания»), трогает защищённые пути. Обычная сессия не может их менять и не должна искать обход: такую задачу ведёт оператор, который сам включает режим обслуживания в worktree задачи и выключает его до открытия PR ([ADR 0009](adr/0009-operator-delegation.md)).
2. В режиме обслуживания выключены все хуки, включая линт после правки и `verify` перед завершением. Запускай `pnpm verify` вручную после каждого шага, `pnpm verify --full` и `pnpm canaries` в конце.
3. Сначала канарейка, потом гейт. Канарейка должна быть красной до изменения и зелёной после.
4. Измерь время затронутого контура до и после. Замедление считается дефектом.
5. Обнови документы тем же PR: этот файл (статус «целевое» меняется на «действует»), `AGENTS.md`, скилы, доску (файл задачи переносится в `backlog/done/`).
6. В PR заполни раздел «Изменения гейтов»: что изменено, замеры и находки ревьюеров `architecture-reviewer`, `sanity-reviewer`, `security-reviewer`. Label `gate-change-approved` ставит мейнтейнер-человек; оператор его не ставит.
7. Один гейт на один PR. Большие изменения обвязки трудно ревьюить, а ошибка в них стоит дороже ошибки в продукте.

### Решение без отдельного ADR: контур проверки здоровья workflow (e26, e39)

_Действует; раскладка — с e39 (2026-11-24)._

- **Что проверяет.** `tools/check-workflow-health.ts`: каждый workflow с ожидаемыми триггерами push на `main` или schedule (`loadScope`) стартовал и зелёный — push без paths-фильтра на head SHA `main`, push с paths — по последнему завершённому push-прогону, schedule — свежий (окно 8 дней) и зелёный. Класс дефекта — escaped-defect 2026-11-21: workflow существует, но не запускается, а вне required checks `main` остаётся зелёным. Отказ API — fail-loud (exit 2), а не «пройдено».
- **Где живёт.** `.github/workflows/workflow-health.yml`: push на `main` (сигнал о сломанном main в день поломки) и schedule (`40 4 * * *` UTC, позже nightly). Merge не блокирует — это не гейт в смысле З5; сигнал — красный прогон и issue (job `report`, один открытый issue на все красные прогоны).
- **Почему не в проверяемом файле.** Чекер судит о schedule-workflow по последнему завершённому schedule-прогону — о прошлой ночи. Джоба внутри `nightly.yml` красила ночь N, ночь N+1 видела красную ночь N и краснела снова: цикл не рвался и после фикса ([escaped-defect 2026-11-24](escaped-defects.md), e39). Поэтому собственный хост выведен из области сверки (`SELF_HOST_WORKFLOW`), а тест проводки держит: хост — ровно один workflow, и это `workflow-health.yml`.
- **Остаточная граница.** Если `workflow-health.yml` перестанет стартовать, пробел увидит только человек в списке Actions; файл намеренно минимальный (checkout и один run-шаг). Внешний контур — кандидат в задачи.
- **Альтернатива и условие возврата.** Альтернатива — оставить шаг в nightly и исключить в чекере собственную джобу (разбор джоб прошлого прогона): специальный случай «судить себя». Вернуться к ней — если прогон на push окажется шумным (лимит API, ложные красные на гонках push) или это решение будет отвергнуто в ревью.
