# Архитектурные и инфраструктурные подходы

> Статус: действует · Дата: 2026-11-12
> Для кого: агенты и люди, которые развивают сам шаблон. Правила работы над фичами продукта остаются в [AGENTS.md](../AGENTS.md).
> Что делать дальше и в каком порядке: [roadmap.md](roadmap.md). Почему выбран стек: [ADR 0001](adr/0001-initial-stack.md). Зачем система существует: [vision.md](vision.md).

## Как читать этот документ

У каждого правила есть статус:

- **действует**: правило уже обеспечено кодом или гейтом. Нарушать его нельзя.
- **целевое**: направление принято, реализации ещё нет. Рядом стоит номер задачи из [roadmap.md](roadmap.md). Новый код не должен отдалять репозиторий от целевого состояния.

Если документ расходится с кодом, для правил «действует» это ошибка документа: исправь его в том же PR. Для правил «целевое» прав документ.

Термины:

- **Гейт**: детерминированная проверка, которая может заблокировать merge.
- **Канарейка гейта**: тест, который подаёт гейту заведомо плохой вход и проверяет, что гейт упал.
- **Доверенная база**: код из целевой ветки (`main`), а не из проверяемого изменения.
- **Режим обслуживания**: сессия, в которой человек отключил хуки агента, чтобы осознанно изменить гейт (см. [CLAUDE.md](../CLAUDE.md)).

## 1. Законы обвязки

Эти правила важнее любого конкретного инструмента. Инструменты меняются, законы остаются.

**З1. Merge блокирует только детерминированная проверка.** Ревьюеры-LLM комментируют и предлагают. Находка ревьюера становится блокером, только когда её подтвердил гейт или человек. _Действует: `agent-review.yml` не входит в `gate`._

**З2. Гейт исполняется из доверенной базы.** Скрипт проверки, список защищённых путей и workflow, которые решают судьбу PR, берутся из `main`, а не из самого PR. Иначе PR переписывает собственного судью. _Действует для защищённых путей: `gate-integrity.yml` на `pull_request_target` исполняется из базовой ветки, список файлов берёт из GitHub API ([ADR 0002](adr/0002-gate-integrity.md)). Остальные job CI (`gate`) по-прежнему исполняются из PR — их удерживает требование одобрения любых правок `.github/**`._

**З3. Проверяй результат, а не способ.** Чёрный список команд или синтаксиса всегда неполон. Надёжная проверка смотрит на итог: какие файлы изменились, сколько тестов пропущено в отчёте раннера, сколько весит собранный бандл. Разбор команд допустим только как быстрая подсказка агенту. _Частично: защищённые пути проверяются по результату — снимок сессии ([ADR 0003](adr/0003-result-based-protection.md), 2026-11-13); пропуск тестов — [A3](roadmap.md#a3)._

**З4. Запрет встроен в инструмент и закрыт при сбое.** Если действие запрещено, отказать должен сам инструмент: конфиг бросает ошибку, ОС не даёт записать файл. Защитный хук, который упал или не успел ответить, блокирует действие, а не пропускает его. _Частично: хуки агента падают закрытыми (неожиданная ошибка → exit 2, без зависимости от `node_modules`, 2026-11-13); запись в защищённые пути запрещена на уровне ОС — песочница Bash ([ADR 0004](adr/0004-sandbox.md), 2026-11-13); поле `onFailure: "block"` добавится после обновления CLI (нужен ≥ 2.1.295); у Vitest-конфига UI отказ вне Linux есть, у Playwright — задача [A8](roadmap.md#a8)._

**З5. Один вход для всех проверок: `pnpm verify`.** CI вызывает те же скрипты, что и локальная команда. Новый гейт добавляется сразу в три места: шаг в `tools/verify.ts`, job в `ci.yml`, список `needs` у job `gate`. Гейт, который есть только в CI, считается недоделанным. _Действует. Исключения: скриншот-тесты (нужен Docker), k6 и `gate-integrity` (нужен контекст GitHub API: файлы PR, label, события)._

**З6. У каждого гейта есть канарейка и бюджет времени.** Гейт без канарейки может тихо перестать ловить после смены конфига или обновления инструмента. Гейт без бюджета незаметно замедляет цикл агента. _Целевое, [B1](roadmap.md#b1)._

**З7. Пороги работают как храповик.** Автоматически порог может только ужесточаться. Ослабляет его человек отдельным PR. Порог стоит рядом с фактическим значением, иначе он ничего не ловит. _Частично: защита от ослабления действует, но пороги далеки от фактических значений, [A6](roadmap.md#a6), [B2](roadmap.md#b2)._

**З8. Шумную метрику сравнивай с базой, детерминированную с абсолютом.** Время (LCP, длительность сценария, p95) на общих раннерах шумит, поэтому регрессию ловит сравнение с базовой веткой в том же прогоне. Байты, число запросов и число тестов детерминированы, для них хватает предела и дельты. _Целевое, [A6](roadmap.md#a6)._

**З9. Всё рассчитано на параллельную работу.** Несколько агентов одновременно работают в разных worktree на одной машине и в разных PR. Следствия: нет фиксированных портов и общих серверов, тест не опирается на общие данные и порядок, файл, который правит каждая фича, считается дефектом структуры. _Частично: данные E2E изолированы через `uniqueTitle()`, порты и «горячие» файлы ждут [A5](roadmap.md#a5) и [B7](roadmap.md#b7)._

**З10. У производного файла один источник.** `openapi.json`, `routeTree.gen.ts`, определения Playwright Test Agents создаются командой. Руками их не правят, конфликты слияния в них решают перегенерацией, расхождение с источником ловит гейт. _Действует для `openapi.json` (`openapi:check`) и для `denyWrite` песочницы (`sandbox`, [ADR 0004](adr/0004-sandbox.md)), для остальных [B7](roadmap.md#b7)._

**З11. Падение объясняет себя.** У красного гейта есть артефакт (trace, diff, отчёт). Сообщение об ошибке говорит, что делать и чего не делать («уменьши бандл, не поднимай бюджет»). Вывод для агента компактный и машиночитаемый. _Действует._

**З12. Ядро работает без SaaS.** Облачные сервисы подключаются как необязательный слой сверху. _Действует._

**З13. Код детерминирован по построению.** Время, случайность, идентификаторы и сеть приходят через параметры. Образец: `InMemoryTaskRepository` принимает `now` и `generateId`. Тест, которому нужен `sleep` или реальные часы, указывает на дефект кода. _Действует как соглашение, гейта нет._

## 2. Архитектура кода

### 2.1 Слои и направление зависимостей

```
            packages/contracts      Zod-схемы и oRPC-контракт; зависит только от zod и @orpc/contract
              ▲            ▲
              │            │
         apps/api       apps/web ──► packages/ui      презентационные компоненты без домена

  e2e/     чёрный ящик: видит систему только через HTTP и браузер
  tools/   гейты; код продукта их не импортирует
```

| Правило                                                              | Чем обеспечено (`.dependency-cruiser.cjs`)       |
| -------------------------------------------------------------------- | ------------------------------------------------ |
| Пакеты не импортируют приложения                                     | `packages-not-to-apps`                           |
| Приложения не импортируют друг друга, общаются через контракт        | `no-app-to-app`                                  |
| E2E не импортирует код приложений и пакетов                          | `e2e-black-box`                                  |
| `@repo/ui` не знает о контрактах, oRPC, TanStack и Hono              | `ui-is-presentational`                           |
| Контракты зависят только от `zod` и `@orpc/contract`                 | `contracts-are-pure`                             |
| Фичи web не импортируют друг друга                                   | `no-cross-feature-imports`                       |
| Доменные модули API не зависят от `app.ts`, `router.ts`, `server.ts` | `api-domain-independent-of-transport`            |
| Пакет импортируется только через `exports`                           | `no-deep-package-imports`                        |
| Циклов нет                                                           | `no-circular` и правило Oxlint `import/no-cycle` |
| Production-код не зависит от devDependencies                         | `not-to-dev-dep`                                 |

Новое правило границ добавляется вместе с канарейкой: плохой импорт в фикстуре, гейт обязан упасть.

### 2.2 Контракт: единственный источник правды API

_Действует._

- Порядок изменения API всегда один: `packages/contracts` → `openapi.json` → `apps/api` → `apps/web`.
- Вход валидирует одна Zod-схема на клиенте и на сервере. Образец: `CreateTaskForm` и сервер используют `CreateTaskInputSchema`.
- Ошибки объявлены в контракте (`.errors({ NOT_FOUND })`). Обработчик бросает `errors.NOT_FOUND()`, клиент получает типизированный код.
- Оба транспорта (RPC на `/rpc`, REST на `/api`) строятся из одного роутера, и оба покрыты тестами.
- _Целевое:_ политика доступа процедуры объявляется в контракте ([C2](roadmap.md#c2)), несовместимое изменение контракта ловит гейт ([C6](roadmap.md#c6)).

### 2.3 API

_Действует._

- `src/<module>/` содержит домен: интерфейс репозитория и реализацию. О Hono и oRPC домен не знает.
- `router.ts` тонкий: вызывает домен и превращает «не найдено» в типизированную ошибку.
- `app.ts` экспортирует фабрику `createApp(options)` без глобального состояния. Зависимости приходят параметрами, поэтому тесты идут внутри процесса (`app.request()`, oRPC-клиент с `fetch: app.fetch`) и не открывают порт.
- `server.ts` единственный читает окружение и открывает порт. Он исключён из покрытия и мутаций, поэтому логики в нём быть не должно.
- Тестовые эндпоинты `/__test__/*` включаются только флагом, по умолчанию выключены, запрещены в production. Каждый новый такой эндпоинт приходит с тестом «выключено по умолчанию».
- Node запускает TypeScript напрямую, без сборки. Отсюда `erasableSyntaxOnly` и импорты с расширением `.ts`: никаких `enum`, `namespace` и parameter properties.

### 2.4 Web

_Действует, кроме отмеченного._

- `routes/` только связывает: loader и подключение хуков фичи к компоненту страницы.
- Компонент страницы в `features/<feature>/` получает данные и колбэки через props (образец: `TasksPage`). Поэтому он тестируется в браузерном режиме Vitest без сети и роутера.
- Серверное состояние живёт только в кэше TanStack Query. Оптимистичное обновление пишется в кэш, инвалидация идёт после последней мутации (`refetchAfterLastMutation`). `router.invalidate()` для этого не используется, причина записана в ADR 0001.
- `QueryClient` создаётся на каждый SSR-запрос, чтобы кэш не утекал между пользователями.
- До гидратации контролы `disabled` (`useHydrated`), иначе клик по серверной разметке теряется.
- Стили: CSS Modules и токены из `@repo/ui/tokens.css`.
- _Целевое, [B2](roadmap.md#b2):_ логика фичи лежит в модулях `*.ts` без React (образец: `summarize.ts`), компоненты и хуки тонкие. Причина: StrykerJS не поддерживает browser mode Vitest, и мутациями проверяется только то, что тестируется в node-проекте.

### 2.5 UI-пакет

_Действует._

- Только представление: данные входят через props, события выходят через колбэки. `TaskItemData` описан в самом пакете, а не импортирован из контрактов.
- Состав компонента: `Component.tsx`, `Component.module.css`, `Component.test.tsx` (поведение и доступность) и визуальный сценарий.

### 2.6 Тесты

Уровни и правила описаны в скиле `writing-tests`. Здесь только принцип: поведение проверяется на самом низком уровне, где оно наблюдаемо. E2E отвечает за то, что части соединены правильно, а не за перебор случаев.

### 2.7 Куда класть новое

| Что появляется                      | Куда                                                                              | Что обязательно вместе с этим                                           |
| ----------------------------------- | --------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Процедура API                       | `packages/contracts/src/<domain>.ts`, затем `apps/api/src/<domain>/`, `router.ts` | `openapi.json`, тесты обоих транспортов                                 |
| Доменная область                    | файл контракта, модуль API, фича web                                              | строка в `contract` (`contracts/src/index.ts`) и в `router`             |
| Переиспользуемый визуальный элемент | `packages/ui/src/<component>/`                                                    | поведенческий тест, визуальный сценарий                                 |
| Экран                               | `apps/web/src/features/<feature>/` и маршрут в `routes/`                          | компонентные тесты, E2E, перф-бюджет (добавляет человек)                |
| Код, нужный двум фичам              | `apps/web/src/lib/` или пакет                                                     | —                                                                       |
| Гейт                                | `tools/`, шаг в `verify.ts`, job в CI, `needs` у `gate`                           | канарейка, бюджет времени, строка в `protected-paths.json` и CODEOWNERS |
| Зависимость                         | `catalog:` в `pnpm-workspace.yaml`                                                | обоснование в PR                                                        |
| Архитектурное решение               | `docs/adr/NNNN-*.md`                                                              | ссылка из этого документа                                               |

## 3. Инфраструктура

### 3.1 Контуры проверки

Замеры сделаны 2026-11-12 на демо-домене (macOS, 16 ядер). Это нижняя граница: домен крошечный.

| Контур              | Что входит                                                                                                         | Замер                                                            |
| ------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| L0, хуки агента     | формат и линт файла после правки, запрет записи, снимок защищённых файлов и сверка по результату, `verify` в конце | не измерялось отдельно                                           |
| L1, pre-commit      | Oxfmt и Oxlint по staged-файлам                                                                                    | меньше 1 с                                                       |
| L2, pre-push        | typecheck, unit, границы                                                                                           | около 2 с                                                        |
| `pnpm verify`       | 10 шагов параллельно                                                                                               | 0.8–1.0 с с кэшем                                                |
| Те же шаги без кэша | —                                                                                                                  | typecheck 0.4 с, unit 1.4 с, сборка 0.7 с, E2E 2.5 с, перф 5.2 с |
| Мутации API         | StrykerJS, 66 мутантов                                                                                             | 2.3 с                                                            |
| L3, PR CI           | 7 job, итог в `gate`                                                                                               | в CI не измерялось                                               |
| L4, merge queue     | то же без `--affected`                                                                                             | в CI не измерялось                                               |
| L5, nightly         | E2E в случайном порядке с повторами, полные мутации, тренд перфа                                                   | в CI не измерялось                                               |

Бюджеты времени из vision пока ничем не проверяются, см. [B1](roadmap.md#b1).

### 3.2 `verify` и Turborepo

_Действует._

- Инструменты, которые быстро обрабатывают весь репозиторий за один запуск (Oxfmt, Oxlint, dependency-cruiser, Knip, sherif), запускаются из корня, а не как задачи Turborepo. Раскладывать их по пакетам имеет смысл, только когда шаг превысит свой бюджет.
- То, что считается по пакетам (typecheck, test, build, e2e, perf, mutation), оформлено задачами Turborepo с кэшем. Задача `transit` заставляет зависимые пакеты пересчитаться при изменении исходников зависимости.
- Переменная окружения, которая влияет на задачу, обязана быть в `env` этой задачи в `turbo.json`. Иначе Turborepo в строгом режиме не передаст её процессу, а кэш вернёт результат прошлого запуска. Нарушение этого правила уже дало дефект: `VIDEO=on pnpm e2e` не писал видео ни при кэш-попадании, ни с `--force` (исправлено 2026-11-12, переменная объявлена в `env` задачи `e2e`).
- Быстрые шаги `verify` идут параллельно, медленные (`--full`) последовательно, потому что E2E и перф делят порты.
- Локальный кэш Turborepo общий для всех git worktree одного репозитория.

### 3.3 Кэш и доверие

_Целевое, [A7](roadmap.md#a7). Remote cache сейчас не подключён, правила нужно принять до подключения._

1. В remote cache пишет только доверенный код: job на `push` в `main`. PR, разработчики и агенты кэш читают, но не пишут.
2. Результат задачи, зависящий от машины (перф-замеры), между машинами не переиспользуется.
3. Подпись артефактов Turborepo проверяет целостность. Границей безопасности она не является.

### 3.4 CI

_Действует, кроме отмеченного._

- В PR проверяется затронутое (`--affected` от базового SHA). В merge queue и на `main` проверяется всё.
- Обязательных check два: `gate` (агрегирует job `ci.yml`, исполняется из PR) и `gate-integrity` ([ADR 0002](adr/0002-gate-integrity.md)): доверенный workflow на `pull_request_target`, не читает и не исполняет код PR, список файлов берёт из GitHub API. `gate-integrity` слушает и `merge_group` (no-op с тем же именем check), иначе очередь ждёт вечно.
- Смена base-ветки PR не порождает `synchronize`, поэтому workflow слушают и `edited`.
- Права по умолчанию `contents: read`. Устаревшие прогоны PR отменяются через `concurrency`.

### 3.5 Защищённые пути

_Действует._

- Список один: `tools/protected-paths.json`. `deny`: агент менять не может, в CI нужен label мейнтейнера. `review`: менять можно, нужно ревью CODEOWNERS.
- Уровней три: хук агента, `gate-integrity` из доверенной базы ([ADR 0002](adr/0002-gate-integrity.md)), CODEOWNERS.
- Чёрные списки команд — только подсказка агенту (З3); границей является проверка по результату: снимок защищённых файлов на старте сессии, изменение отменяется хуком с объяснением ([ADR 0003](adr/0003-result-based-protection.md)). Контур L0 действует только в агентах, исполняющих хуки проекта (Claude Code); в остальных детерминированным барьером остаётся `gate-integrity`.
- Label `gate-change-approved` действителен, только если его поставил человек из глобальных владельцев CODEOWNERS (строка `*`) после последнего push PR: job снимает label на `synchronize`, а `check-gate-approval.ts` независимо сверяет актёра и время события с датой head-коммита. Переименование защищённого файла ловится (`--no-renames`, `previous_filename`).
- Новый гейт, порог или конфиг гейта попадает в `deny` и в CODEOWNERS тем же PR, которым он создан.
- `denyWrite` песочницы Bash — производный от того же списка: расхождение ловит гейт `sandbox` ([ADR 0004](adr/0004-sandbox.md)).
- Агент, которому мешает гейт, чинит код. Если он считает, что неправ сам гейт, он останавливается и объясняет это человеку.

### 3.6 Визуальные тесты

_Действует, кроме отмеченного._

- Снимки делаются и сравниваются только в одном Docker-образе Playwright на `linux/amd64`. Версия образа равна версии Playwright из каталога, поэтому она закреплена точно, без `^`.
- Базлайны без суффикса платформы, допуск нулевой.
- Базлайны обновляет человек после просмотра диффа.
- _Целевое, [B3](roadmap.md#b3):_ базлайны создаёт только CI, человек одобряет их в PR.

### 3.7 Производительность

- _Действует:_ пороги лежат в `perf-budgets.json` и проверяются Zod-схемой (опечатка в ключе роняет проверку, а не отключает её). Замер: медиана пяти прогонов при замедлении CPU в 4 раза. Бандл считается в gzip.
- _Целевое, [A6](roadmap.md#a6):_ два уровня. Абсолютный потолок описывает допустимый опыт пользователя. Регрессию ловит сравнение с базовой веткой в том же прогоне и детерминированные метрики (байты, число запросов).

### 3.8 Зависимости

_Действует._

- Версии внешних зависимостей объявлены только в `catalog:` (`catalogMode: strict`).
- Свежий релиз ставится не раньше чем через сутки (`minimumReleaseAge`), Renovate ждёт три дня. Install-скрипты запрещены, пока не разрешены в `allowBuilds`.
- TypeScript 6 подложен только dependency-cruiser и StrykerJS через `packageExtensions`. Проект компилируется TypeScript 7.
- Renovate обновляет группами. Playwright идёт одной группой с Docker-образом, после обновления нужны `tools/playwright-agents.sh` и `pnpm visual`.

### 3.9 Агентный слой

_Действует._

- Что должно выполняться всегда, живёт в хуке или гейте. Что агент должен знать, записано в `AGENTS.md`. Как сделать типовую работу, описано в скиле. Инструкция гарантией не является.
- `AGENTS.md` остаётся каноном и коротким. `CLAUDE.md` импортирует его и добавляет специфику Claude Code.
- Ревьюеры только читают и возвращают находки с серьёзностью `blocker`, `major`, `minor`.
- Определения Playwright Test Agents генерируются скриптом и дополняются политикой репозитория. Healer не помечает тест `fixme`.
- MCP-серверы (Playwright, Chrome DevTools) служат для исследования и отладки. Найденную регрессию закрепляет детерминированный тест.
- Всё, что блокирует merge, живёт в Lefthook и CI, а не в хуках Claude Code. Хуки ускоряют обратную связь, но не являются единственной линией защиты: у других агентов их нет.

### 3.10 Целостность документации

_Действует._

- Гейт `docs:check` ([tools/check-docs.ts](../tools/check-docs.ts)) входит в `pnpm verify` и CI (job `static`). Он проверяет инструкции, которым доверяет агент: команды `pnpm …` из README.md, AGENTS.md, CLAUDE.md и скилов существуют (скрипт в `package.json` с учётом `--filter`, встроенная команда pnpm или бинарь из `node_modules/.bin`), относительные markdown-ссылки ведут на существующие файлы, а якоря — на существующие заголовки или `id`.
- Дрейф документации — дефект так же, как красный тест: чини документ, а не проверку. Если гейт ошибся на встроенной команде pnpm или ссылке-примере, исключение дополняют в `tools/check-docs.ts` тем же PR с ревью CODEOWNERS.

## 4. Как менять саму обвязку

1. Задача из roadmap с пометкой 🔒 трогает защищённые пути. Агент не может их менять и не должен искать обход. Подготовь план и попроси человека включить режим обслуживания.
2. В режиме обслуживания выключены все хуки, включая линт после правки и `verify` перед завершением. Запускай `pnpm verify` вручную после каждого шага и `pnpm verify --full` в конце.
3. Сначала канарейка, потом гейт. Канарейка должна быть красной до изменения и зелёной после.
4. Измерь время затронутого контура до и после. Замедление считается дефектом.
5. Обнови документы тем же PR: этот файл (статус «целевое» меняется на «действует»), `AGENTS.md`, скилы, roadmap (задача удаляется).
6. В PR заполни раздел «Изменения гейтов». Label `gate-change-approved` ставит мейнтейнер.
7. Один гейт на один PR. Большие изменения обвязки трудно ревьюить, а ошибка в них стоит дороже ошибки в продукте.

## 5. Когда нужен ADR

- Заменяется или добавляется инструмент стека.
- Меняется закон из раздела 1.
- Появляется новый обязательный check или контур проверки.
- Появляется новый тип пакета, слой или направление зависимостей.
- Принимается компромисс с известным риском.

Формат как в ADR 0001: решение, почему, альтернатива и условие возврата к ней. ADR, которые понадобятся для задач roadmap: двухуровневый перф (A6), доверие к remote cache (A7), адрес API и порты (A5), хранилище и изоляция тестов (C1), политика доступа в контракте (C2), production-сервер и деплой (C3). Написаны: [0002 — целостность гейтов](adr/0002-gate-integrity.md) (A1).
